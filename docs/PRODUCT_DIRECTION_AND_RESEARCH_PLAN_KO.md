# AgentFlow Studio 제품 방향과 다음 연구 계획

작성일: 2026-10-15 · 상태: 다른 세션의 검토를 위한 방향 정리안

## 1. 이번에 정리하는 범위

AgentFlow Studio는 사용자가 자신의 Codex·Claude 등에서 계획하고 개발하는 과정을 받아, 무엇을 만들고 있고 각 부분이 어떻게 구체화·변경·진행되는지 이해하기 쉽게 보여주며, 필요한 부분을 다른 세션에 이어 맡기도록 돕는 서비스다.

현재는 전체 틀과 연구 순서를 정리하는 단계다. 이 문서 작성은 구현·대규모 조사·자동 작업 재개의 지시가 아니다. 다른 세션의 검토를 받은 뒤 방향을 정돈하고, 새 총괄 세션과 작업 세션에서 다음 사이클을 시작할 예정이다.

사용자가 제시한 방향과 총괄이 제안하는 연구 방법을 구분한다. 노드 종류·층수·세분화 규칙·DB·모델·연동 기술은 이 문서로 확정하지 않는다. 기존 구현량보다 제품 목적에 맞는 최종 경험을 우선한다.

## 2. 최신 정정 사항과 설계 전제

### 최근 원본 기록에서 두 용도가 갈라진다

사용자가 effort 자동 조절 사례에서 참고하려는 것은 **최근 기록을 관측하고, 목적에 맞게 해석해 활용하는 메커니즘**이다. effort 조절의 출력이나 알고리즘을 그대로 구상도에 쓰자는 뜻이 아니다.

```text
사용자와 외부 AI의 접근 가능한 최근 원본 기록
  ├─ effort 조절용 해석 → 외부 AI의 추론 강도 조절
  └─ AgentFlow용 정리 → 사이트에 필요한 정보 전달
                           → 프로젝트 맥락에 연결
                           → 구상도·진행·변경·인계에 활용
```

두 갈래는 개념적으로 독립적이다. effort 조절 기능의 도입·구현·활성화가 AgentFlow 이용의 필수 조건은 아니다. 최근 기록을 볼 수 있는 연결 계층이나 하위모델의 역할을 AgentFlow 목적에 맞게 구성한다는 구상이다.

### 이번 설계는 정보를 전달받을 수 있다고 가정한다

현재의 초점은 전달받은 뒤의 제품 경험이다. 네트워크 전달 방식, 실시간 연결 구현, 도구별 설치·인증 등은 후속 구현 과제로 둔다. 연결 방식의 존재를 증명하는 작업을 UI·UX 연구의 선행 장벽으로 만들지 않는다. 이는 설계 전제이며 현재 제품에 연결이 구현됐다는 뜻은 아니다.

초기에 필요한 기술 파악은 **선택한 환경의 최근 원본 기록에서 어떤 정보를 얻을 수 있는지**의 범위와 대표 표본 정도다. 모든 도구와 환경을 전수 조사하거나 연결기를 먼저 완성할 필요는 없다. 한 환경에서 얻은 정보 범위를 다른 환경에도 같다고 확대하지 않는다.

그 범위 안에서 사이트가 어떤 정보를 필요로 하는지 구상도와 사용자 흐름을 설계하며 정한다. 이후 그 정보가 오도록 사용자 AI 옆 정리 담당의 역할·지시·전달 형식을 맞춘다. 지금부터 정리 모델의 상세 프롬프트나 고정된 입력 형식을 먼저 설계하지 않는다.

```text
원본에서 얻을 수 있는 정보 범위 파악
  → 사이트 경험과 필요한 정보 연구
  → 정리 담당에게 요구할 정보 결정
  → 정리·전달 구현을 맞춤
```

표현 연구에서 특정 정보가 필요해지면 초기 범위 파악으로 돌아가 확인할 수 있다. 후속 기술 문제는 해당 연결 범위의 문제로 다루며, 제품 전체를 수동 입력 중심으로 되돌리는 근거로 삼지 않는다.

## 3. 유지할 제품 방향

| 방향 | 제품에서 의미하는 것 |
|---|---|
| 사용자의 기존 개발 흐름 유지 | 사용자는 자신의 AI 도구에서 평소처럼 계획·설계·개발한다. 사이트에 같은 설명과 보고를 반복 입력하는 구조를 기본으로 삼지 않는다. |
| 자동 정리와 필요한 부분의 사용자 조정 | 구상·변경·진행이 자동 반영되고, 사용자는 맞지 않는 이름·묶음·관계·표현을 수정한다. 모든 갱신에 승인을 요구하지 않는다. |
| 프로그램 구성 중심의 다층 구상도 | 주로 사용자가 만들 프로그램의 구성부분을 보여준다. 작업·세션·파일·함수와 프로그램 구성부분을 무조건 같은 단위로 취급하지 않는다. |
| 전체 파악과 영역별 집중 | 전체 그림을 보다가 특정 부분을 선택해 설명·관계·진행·담당 세션·자료·인계를 살펴본다. |
| 코드가 생기기 전부터 사용 | 막연한 구상에서 시작해 일부만 상세해져도 자연스럽게 표현한다. 기존 저장소가 있는 프로젝트에도 적용할 수 있어야 한다. |
| 초보자와 숙련자 모두 고려 | 기본 정리는 자동으로 제공하고, 필요할 때 더 상세하게 이해하거나 조정할 수 있게 한다. 역할별 별도 제품을 미리 만들지는 않는다. |
| 외부 AI 작업을 이해하고 이어가기 | 사이트는 관찰 화면에 그치지 않고, 관련 정보 탐색·수정·부분 위임·세션 교체를 돕는다. 개발 도구의 모든 실행 기능을 다시 만드는 것이 현재 목적은 아니다. |

목표는 사용자가 긴 대화를 다시 읽거나 프로젝트 상태를 수동으로 관리하는 수고를 줄이는 것이다. 지도 자체를 관리하는 일이 새로운 부담이 되면 방향을 재검토해야 한다.

## 4. 전체 사용자 흐름

1. **프로젝트를 시작하거나 기존 프로젝트를 가져온다.** 계획용 또는 개발 중인 외부 AI 세션을 연결한다. 이미 대화를 시작했다면 처음부터 사이트의 설문을 다시 거치지 않는다.
2. **본인의 AI와 구상을 구체화한다.** 사이트는 전달받은 정보로 목적, 큰 구성, 관계, 결정과 미정 사항을 정리한다. 처음부터 빈 부분을 억지로 채우지 않는다.
3. **전체 구상도에서 관심 영역으로 들어간다.** 해당 부분의 의미, 관련 영역, 진행, 필요한 자료와 담당 세션을 확인한다. 선택 패널과 전용 상세 공간의 조합은 연구한다.
4. **필요하면 수정하거나 참고 자료를 활용한다.** 자동으로 정리된 부분을 조정하고, 후속 추천 모듈이 제공하는 기존 해결책을 검토할 수 있다.
5. **한 부분을 맡기거나 담당 세션을 바꾼다.** 전체 목적과 해당 범위의 맥락, 관련 결정·미정·자료 위치를 담은 시작문 또는 인계문을 만든다.
6. **외부에서 작업이 계속되면 같은 영역에 이어 반영된다.** 세션이 바뀌었다고 새 프로그램이나 새 구상도가 되는 것은 아니다. 일부는 계획 중이고 일부는 구현 중인 상태를 함께 다룬다.
7. **프로젝트 변화에 따라 구조도 발전한다.** 필요한 부분만 세분화하고, 목적이 나뉘면 별도 구상도 탭을 사용할 수 있다. 사용자가 전체를 잃지 않고 오갈 수 있어야 한다.

계획·설계·개발을 일괄적인 승인 단계로 강제하지 않는다. 수동 가져오기·복사·편집은 연결이 제한되거나 일부 정보만 다루려는 경우의 보조 경로로 검토한다.

## 5. 화면의 기본 틀과 열어둘 선택

기본 틀은 프로젝트 목록에서 프로젝트를 열고, 넓은 구상 공간에서 전체를 본 뒤 특정 부분으로 들어가는 흐름이다. Dify는 캔버스·선택·사이드 패널·탐색의 참고 사례다. Dify의 실행 노드 종류와 서비스 목적을 그대로 채택하지 않는다.

| 구역 | 방향 | 연구할 선택 |
|---|---|---|
| 프로젝트 입구 | 프로젝트를 구별하고 다시 찾기 쉬운 목록 또는 카드 | 새 프로젝트·기존 프로젝트·최근 작업의 진입 방식 |
| 중앙 구상 공간 | 큰 구성과 관계를 직관적으로 표현 | 배치, 묶음, 정보 밀도, 선택·펼침·이동 방식 |
| 선택한 부분의 상세 정보 | 설명·진행·자료·세션·인계·구조 조정을 맥락에 맞게 제공 | 사이드 패널·전용 화면·탭·접힘의 조합 |
| 상세 층 조절 | 큰 단위와 상세 단위를 선택하며 깊이가 다른 부분도 함께 표현 | 전역 상세 수준과 특정 영역 진입의 관계, 현재 위치와 복귀 방법 |
| 확대·축소·이동 | 화면 탐색을 위한 조작 | 상세 층 선택과 혼동되지 않는 표현 |
| 여러 구상도 | 같은 프로젝트 안의 별도 프로그램이나 목적을 구별 | 나누는 기준, 이름, 서로 공유하는 부분의 표현 |

겹친 지도처럼 보이는 레이어 조절기, 우측 아래 위치, 구체적인 아이콘은 시안 후보다. **확대·축소와 상세 층 선택은 별도 조작**이라는 사용자 의도를 유지한다.

노드의 성격이 다르면 표현도 다를 수 있다. 어떤 성격을 구분해야 유용한지부터 연구하고, 구분마다 색이나 모양을 추가하는 식으로 화면을 복잡하게 만들지 않는다.

## 6. 핵심 연구 영역

아래는 지금 답을 확정할 항목이 아니라, 새 사이클에서 집중할 질문이다.

### 6.1 무엇을 한 부분으로 볼 것인가

- 사용자가 독립적으로 이해하거나 맡길 수 있는 단위는 무엇인가?
- 목적·사용자 흐름·기능·기술 구성 등 서로 다른 관점이 있을 때 무엇을 기본으로 보여줄 것인가?
- 프로그램 구성부분과 그 부분에서 진행하는 작업, 담당 세션을 어떻게 구분하면서 함께 보여줄 것인가?
- 새 아이디어·설명 보강·실제 영역 분할을 어떻게 다르게 반영할 것인가?
- 처음 구상하는 프로젝트와 이미 개발 중인 프로젝트에서 같은 표현이 어디까지 유효한가?

### 6.2 깊이와 관계를 어떻게 표현할 것인가

깊이는 부분마다 다를 수 있다. 전체 상세 수준을 바꿀 때 세분화할 정보가 있는 부분만 펼쳐지고, 다른 부분은 기존 단위로 남는다. 깊이가 없다고 숨기거나 빈 자식을 만들지 않는다.

설명용 장면: A와 B가 연결되어 있고, A만 A1~A6으로 구체화된다. 실제로 B와 관계있는 부분이 A2·A4·A6이라면 그 부분만 B와 연결한다. 다시 큰 단위로 보면 A와 B의 관계로 묶어 보여준다. A의 선을 모든 자식에게 복제하지 않고, 펼쳤다는 이유로 관계를 잃지도 않는다.

- 부모와 자식의 포함 관계, 서로 다른 부분 사이의 관계를 어떻게 구별할 것인가?
- 상세 수준이 다른 대상의 관계를 어떻게 정돈할 것인가?
- 상위 관계는 알지만 하위 대상은 아직 모를 때 무엇을 보여줄 것인가?
- 방향이나 의미가 다른 관계를 접거나 펼칠 때 어떻게 보존할 것인가?
- 특정 영역에 집중해도 전체 위치와 관련 부분을 잃지 않게 하는 방법은 무엇인가?

예시의 여섯 자식이나 A·B 구조는 고정 요구가 아니다. 단일 트리·그래프·특정 라이브러리 채택도 아직 결정하지 않는다.

### 6.3 자동으로 변해도 이해하기 쉬운 상태를 어떻게 유지할 것인가

- 새로운 기록이 들어올 때 설명 갱신, 상태 갱신, 구성 변경, 화면 재배치를 어떻게 구분할 것인가?
- 사용자가 보고 있던 부분과 직접 조정한 구성을 어떻게 유지할 것인가?
- 무엇이 바뀌었는지 필요한 만큼 보여주고, 잘못된 변경을 어떻게 수정·되돌릴 것인가?
- 외부 세션에서의 사용자 변경과 사이트에서의 수정이 만날 때 어떻게 처리할 것인가?
- 제안·결정·보류·보고된 진행·확인 가능한 결과를 화면을 복잡하게 만들지 않으면서 어떻게 구별할 것인가?

자동 반영이 기본이다. 사용자가 모든 변경을 일괄 승인해야 하는 구조는 기본값으로 채택하지 않는다. 정보가 없다는 것을 미구현으로, AI의 완료 발언을 검증 완료로 바꾸어 표현하지 않는다. 이런 의미 차이를 다루는 UX는 연구하되, 현재 단계에서 정리 모델 구현을 먼저 완성하도록 범위를 바꾸지 않는다.

### 6.4 노드에서 다음 행동으로 어떻게 이어질 것인가

- 전체에서 관심 부분을 찾고, 필요한 자료를 확인하고, 다음 작업을 맡기는 흐름이 자연스러운가?
- 해당 부분을 처음 맡기는 문서와 기존 담당을 교체하는 인계문에 무엇이 달라야 하는가?
- 전체 목적과 관련 영역의 약속을 유지하면서 담당 범위에 필요한 내용만 전달할 수 있는가?
- 깊이 있는 자료가 필요할 때 정확한 위치와 읽는 이유를 알 수 있는가?

시작 질문·인계 템플릿은 상황에 맞는 내용을 생성하는 기능으로 본다. 긴 의무 양식을 사용자가 작성하게 하는 방향은 지양한다.

## 7. 타사이트와 다른 분야를 조사하는 방법

사용자는 철저한 비교 조사와 응용을 원한다. 비슷한 화면을 모으거나 기능 목록을 옮기는 데서 끝내지 않는다. 최근 사례와 실제 사용 경험을 우선하고, 반복되는 불편과 해결 방식을 찾아 우리 상황에 적용할 가설을 만든다.

| 연구 문제 | 참고 범위의 예시 | AgentFlow에서 확인할 것 |
|---|---|---|
| 전체와 상세 사이의 탐색 | 캔버스 도구, 지도, 설계·모델링 도구, 문서 탐색 | 혼합 깊이에서도 위치와 맥락을 이해하는가 |
| 다른 성격의 정보 표현 | 편집기, 분석 도구, 시각적 작업 공간 | 중요한 차이는 드러나고 장식은 과하지 않은가 |
| 관계가 많은 화면 정돈 | 의존성·네트워크·구조 시각화 | 선택·묶음·필터·단계별 공개가 관계 오해를 줄이는가 |
| 변화와 사용자 수정 | 협업 편집, 버전 비교, 변경 이력 | 자동 갱신 후 재탐색과 수정 부담이 줄어드는가 |
| 맥락에 맞는 행동 | 상세 패널, 검사기, 프로젝트 공간 | 조사·수정·인계로 이어지는 행동이 자연스러운가 |
| 첫 사용과 시각적 완성도 | Dify 및 유사 서비스, InstaLanding 등 화면 참고 자료 | 빈 상태·프로젝트 진입·정보 위계·밀도가 적절한가 |

Dify와 https://instalanding.ai/ 는 참고 후보이며 그대로 복제하거나 도입을 확정한 것이 아니다. 이번 정리에서 이들에 대한 상세 조사를 완료한 것은 아니다.

조사 결과의 기본 형식은 **원래 해결한 문제 → 작동 방식 → AgentFlow에 적용할 아이디어 → 맞지 않는 조건 → 비교 시안에서 볼 장면**으로 제안한다. 소스는 질문별로 작은 묶음으로 나누어 조사하고, 반복되는 결과는 통합한다. 참고 대상의 범위는 넓게 열되, 조사량 자체를 성과로 삼지 않는다.

## 8. 새 세션에서 시작할 순서 제안

다음 순서는 총괄의 제안이다. 외부 검토 후 조정할 수 있으며, 지금 실행을 시작하는 것은 아니다.

| 단계 | 수행할 일 | 산출물과 다음 단계의 판단 근거 |
|---|---|---|
| 1. 사용자 경험의 기준 정리 | 프로젝트 시작, 구체화, 부분 집중, 변경, 인계, 재개 장면을 정리 | 사용자가 각 장면에서 이해하고 할 수 있어야 할 것. 고정 화면 명세는 만들지 않음 |
| 2A. 원본 정보 범위 파악 | 접근 가능한 최근 기록의 정보 종류와 대표 표본을 제한된 범위에서 확인 | 무엇을 근거로 알 수 있고 무엇은 없는지. 연결기 제작·전 환경 조사로 확대하지 않음 |
| 2B. 표현과 조작 방식 조사 | 6절의 질문별로 유사 서비스·다른 분야·관련 오픈소스를 비교 | 적용 가능한 메커니즘과 대안. 2A와 병렬 진행하고 서로 필요한 정보를 확인 |
| 3. 작은 비교 시안 | 같은 프로젝트 기록으로 구성 단위를 비교하고, 내용을 맞춘 뒤 화면 대안을 비교 | 2~3개 안의 장단점과 조합할 부분. 한 가지 안을 일찍 정답으로 고정하지 않음 |
| 4. 변화가 들어오는 흐름 비교 | 일부 세분화, 결정 변경, 사용자 수정, 담당 세션 교체 등을 시안에 순서대로 반영 | 처음의 모양뿐 아니라 변화 뒤 이해·탐색·수정·인계가 쉬운지 확인 |
| 5. 방향 통합과 첫 구현 범위 선택 | 좋은 부분을 조합하고 필요한 정보·정리 역할·제품 동작을 정리 | 구현할 첫 흐름과 후속 범위. 기존 코드의 재사용·변경·제외를 이때 판단 |
| 6. 정리·전달 연결과 실제 흐름 구현 | 사이트가 필요로 하는 정보에 맞춰 외부 정리 담당과 전달 방식을 맞춤 | 선택한 환경에서 실제 흐름이 이어지는 제품. 지원 환경은 필요에 따라 확장 |

초기 시안에는 대표 기록을 재생하는 방식 등을 사용할 수 있다. 연구용 입력 전달 방식이 최종 사용자의 수동 보고 절차로 굳어지지 않게 한다.

사용자가 원하는 대략적 구상부터 시작하는 장면과, 중간에 돌아와 바뀐 내용을 이해하는 장면을 모두 포함한다. 후자는 좋은 비교 사례지만 제품 전체를 재개 요약 도구로 축소하는 기준은 아니다.

비교할 때는 모든 노드에 대한 유일한 정답 지도를 요구하기보다, 중요한 목적·관계·결정이 보존되고 사용자가 필요한 행동을 할 수 있는지를 본다. 사용자에게 정답 지도를 직접 만들도록 의무를 부과하지 않는다. AI 역할별 평가는 초기 정리에 활용할 수 있으나 실제 사람의 사용성과 동일하게 취급하지 않는다.

## 9. 후속 모듈로 보존할 재사용 탐색 아이디어

목적은 이미 있는 해결책을 늦게 발견하여 불필요하게 다시 만드는 일을 줄이는 것이다. 자료 수집·검색은 별도 모듈로 만들 수 있으며, 현재 핵심 UI·UX 연구의 선행 조건으로 두지 않는다.

사용자가 제시한 조합 예시는 다음과 같다. 현재 가용성·이용 조건·세부 제공 기능을 확인한 도입 명세가 아니다.

| 역할 | 검토 후보 예시 |
|---|---|
| 존재와 분야 발견 | ecosyste.ms, 분야별 목록·카탈로그 |
| 제공 기능 파악 | APIs.guru, Activepieces 등 명세·통합 정보 |
| 목적·조건에 맞는 검색 | PostgreSQL·pgvector 등 저장·검색 방식 |
| 선택 후보 보강 | deps.dev, 프로젝트 원문·공식 문서 등 |
| 제품 경험과 연결 | 해당 영역의 참고 자료, 채택·제외 판단, 인계·작업문 |

지금은 **어떤 상황에서 이 모듈을 열고 무엇을 판단하게 도울지**만 구상 흐름에 연결한다. 큰 구상에는 유사 해결 방식, 세부 영역에는 부품·서비스·API 후보를 보여주는 방향을 검토한다. 후보의 발견·채택·실제 사용 결과는 구별한다.

추천은 해당 부분의 상세 공간에서 접근하고, 전체 흐름을 방해하지 않는 위치를 연구한다. 정확한 탭·버튼·픽셀 위치는 아직 고정하지 않는다. 가능하면 비용이 들지 않는 기반을 우선하되, 모든 후보가 무료이거나 유지 비용이 없다고 가정하지 않는다. 지금 DB 설치나 수집 서비스 구축을 요청하지 않는다.

## 10. 현재 구현과 개편 방향의 관계

현재 구현은 새 방향의 재료다. 기존 구현에 맞춰 제품 방향을 축소하지 않고, 기존 코드 전체를 무조건 폐기하지도 않는다.

| 현재 부분 | 개편에서의 취급 |
|---|---|
| 목적·출처·원문·결정·변경 이력 | 의미와 보존 방식을 살필 재사용 후보 |
| 수동 수정 보호와 오래된 응답 처리 | 새 자동 반영 흐름에 맞춰 재사용 여부 확인 |
| 공간형 화면과 영역별 탐색 | 비교 시안의 참고·재사용 후보이며 최종 UI로 고정하지 않음 |
| 작업문·결과·인계 연결 | 구성부분·작업·세션의 관계에 맞춰 재검토 |
| 수동 목적 입력·결과 보고 중심 흐름 | 최종 제품의 중심으로 고정하지 않고 보조 경로로 검토 |
| 실제 AI 후보 | 기존 의미 품질 문제가 남아 있음. 새 입력 정리의 품질을 이미 검증한 것으로 취급하지 않음 |

현재 기준은 `checkpoint/2026-10-15`의 문서 작성 전 커밋 `3133323ef7615623b32dcf9728656c604b791ca3`이다. 공개 소스는 `618d9bd2b99ad433df35107d8902b15f45e30000`, 공개 배포는 `gh-pages`의 `63f5540d062861439f0932cd7311c6c5510e227c`이며 실제 AI 없는 정적 체험판이다.

현재 구현·검증·미해결의 기준: [PROJECT_STATUS](https://github.com/tlsee0813-cmd/agentflow-studio/blob/3133323ef7615623b32dcf9728656c604b791ca3/docs/PROJECT_STATUS.md).

## 12. 다른 세션에 요청할 검토

이 문서의 계획을 냉정하게 검토하되, 현재는 구현을 시작하지 않는다. 아래 질문을 중심으로 의견을 요청한다.

1. 최근 원본 기록의 두 갈래 활용과, 전달받을 수 있다는 설계 전제가 정확하게 반영되어 있는가? effort 기능 자체의 도입이나 연결기 선행 개발을 불필요하게 요구하고 있지는 않은가?
2. 사용자의 기존 AI 대화를 유지하면서 자동으로 구상을 이해·조정·인계하게 돕는 목적이 전체 흐름에 유지되는가?
3. 구성부분·작업·세션, 포함 관계·다른 부분과의 관계, 상세 수준·확대축소를 혼동하는 부분이 있는가?
4. 실제 필요한 정보와 표현 연구를 함께 발전시키는 순서가 적절한가? 빠진 핵심 사용 장면이나 더 나은 비교 방법이 있는가?
5. 고정된 노드 종류·층수·기술을 너무 일찍 정했거나, 반대로 다음 연구가 시작하기 어려울 만큼 모호한 부분은 무엇인가?
6. 추천 모듈을 후속으로 두면서도 자연스럽게 붙일 자리를 확보했는가?
7. 기존 구현에 얽매이지 않으면서 재사용할 가치가 있는 부분을 적절히 구분했는가?

검토 결과는 **유지할 방향 / 수정할 부분과 이유 / 빠진 질문 / 권장 시작 순서 / 나중으로 미룰 것**으로 정리하면 비교하기 쉽다. 사용자 의도를 바꾸는 제안은 별도 대안으로 명시한다. 구체적인 대안은 환영하되, 이전 문서나 현재 구현만을 근거로 수동 관리 중심 제품으로 되돌리지 않는다.

## 13. 정리 근거

- 사용자가 제공한 `AgentFlow_Studio_product_direction_handoff_ko.md`.
- 이후 사용자의 최신 정정: effort 조절과 AgentFlow 정리는 최근 원본 기록에서 갈라지는 별도 활용이며, 정리 담당의 역할은 사이트가 필요한 정보를 정한 뒤 맞춘다. 현재는 전달 가능을 전제로 수신 이후의 경험에 집중한다.
- 사용자가 제시한 재사용 탐색의 후속 모듈화와, 타사이트·다른 분야의 메커니즘을 비교하고 응용하자는 방향.
- 총괄의 검토 및 Claude·웹 Pro의 방향 자문 중 선택한 의견. 자문에서 제시된 전면 승인함, 저장소 기반의 고정 골격, 유일한 정답 지도, 정리 모델의 추출 전용 제한은 확정 요구로 채택하지 않았다.

이 문서는 외부 검토용 통합안이다. 검토에서 수정되는 내용은 사용자 방향과 구별해 반영하고, 이후 새 세션 인수인계의 기본 자료로 사용한다.
