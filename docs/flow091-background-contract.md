# FLOW091-C — 저장한 구상을 작업문에 배경 사본으로 연결 (후보 `flow090/spatial-workspace`, FLOW091-U 커밋 다음의 별도 커밋)

경고 문구를 늘리는 대신, 저장한 구상을 작업문에 안전하게 연결하는 최소 계약이다(Sol의 exact `f21114539` 분석 기반).
- 새 외부 호출, 키 요청, 실제 AI 실행은 없다. 공급자 경로는 가짜 fetch로만 검사했다.
- 완전한 이벤트 소싱으로 넓히지 않았다. 내보내기 기록(ExportRecord)이 과거 전문 전체를 보존하지 않는 기존 한계도 그대로다(아래 한계).

## 계약
| 구분 | 어디에 | 무엇 |
|---|---|---|
| 배경 사본 | `Task.background` `{version:'background.1', revision, brief, area:{id,name,note}\|null}` | 명시적인 새 사용자 요청(`request`)을 보낼 때만 고정한다. `revision`은 사본을 만든 기준 시점, `brief`는 `space.brief.text`, `area`는 submit이 정한 그 요청의 대상 영역이다(지도 선택 아님). 다른 영역, 관계, 좌표, 목적 이력은 넣지 않는다. 빈 값은 `null`이고 ‘미정’ 같은 표현을 내용으로 만들지 않는다 |
| 고정 | — | 이후 목적·영역 이름·구상 수정, 보관, 재배치, 작업 영역 옮기기, AI 재정리, 반복 내보내기, 탐색은 기존 사본을 바꾸지 않는다. 다음 명시 새 요청만 최신 구상을 캡처한다. 합성 시험답변(`test_answer`)은 사용자 요청이 아니므로 `null`이다 |
| 일반 보고 | 반환 작업의 `background` | 정확히 연결된 반환 대상 작업의 사본을 그대로 잇는다. 대상이 없으면 `null`이다 |
| 파일 반환 | 반환 작업의 `background` | 일치하는 `returnId`의 `ExportRecord.background`(실제로 함께 전달한 사본)를 쓴다. 옛 기록에 없으면 `null`이며, 최신 구상으로 메우지 않는다 |
| 내보내기 | `ExportRecord.background` | `markHandoff`가 그때 작업문에 실제로 넣은 사본(작업의 사본)을 기록과 함께 보존한다 |
| AI 입력 | `ContextRequest.background` (`idea022.context.7`) | `sources`·`bases`와 분리된 전용 필드다. 서버 검증기, 공급자 프롬프트, MOCK 서버 경로가 같은 형식을 받는다. 프롬프트에는 배경은 자료이고 실행 범위는 이번 요청이 정하며, 아이디어나 미정 사항을 확정하지 않고, `bases`만 인용한다고 적었다 |
| 작업문·미리보기·Markdown | `handoffText` | ‘## 프로젝트 배경·영역 구상 — 이번 요청 범위와 구분’ 블록을 둔다. 이번 요청이 실행 범위를 정하고, 배경 전체를 구현하거나 아이디어·아직 정하지 않은 점을 임의로 확정하지 말라고 명시한다. 사본이 없거나 둘 다 빈 값이면 블록을 넣지 않는다 |
| 승격 금지 | — | 배경은 `sources`, `bases`, 새 사용자 결정으로 자동 승격하지 않는다. `manual.scope/next/checks` 등 직접 수정 우선권은 그대로다 |
| 화면 | 작업 카드 ‘작업문에 넣을 프로젝트 배경… 보기’ | 전달되는 사본(목적 원문, 대상 영역, 구상 원문, 기준 시점)을 열어 볼 수 있다. 구상이 그 뒤 바뀌었으면 ‘이미 준비된 이 작업의 사본은 그대로이고 다음 새 요청부터 최신 구상’이라고 말한다. 자동 반영됐다고 표시하지 않는다 |

## 형식 이관과 한도
- **저장 형식** `idea015.project.5`.
  - project.1~4는 읽을 때 모든 작업과 내보내기에 `background:null`을 넣는다. 현재 구상을 소급해 넣지 않는다.
  - project.4 파일에 `background` 키가 있으면 거절한다. project.5에 키가 없으면 거절한다(엄격 형식).
  - 공개되지 않은 첫 project.4 후보의 정규화(draftTarget, layout)는 v4 이관 단계로 옮겼다.
- **한도.** 목적 12000자, 영역 이름 60자, 구상 2000자는 기존 상한 그대로다.
  - AI 요청은 배경까지 포함해 정확한 UTF-8 128 KiB로 검사한다. 넘으면 `CONTEXT_TOO_LARGE`로 요청 전체를 보내지 않고, 배경을 자르거나 빼지 않는다. 입력과 저장 내용은 그대로이고 화면 안내도 그렇게 말한다.
  - 프로젝트 8MB 저장·가져오기 한도도 모든 사본을 포함한다. 넘으면 기존 `FILE_TOO_LARGE` 경로가 저장을 거절한다(입력은 탭에 남음).
  - 로컬 작업문(복사·Markdown)은 AI 한도에 묶이지 않는다.

## 검사
- **노드** `flow091c.test.mjs`. U 커밋(`81fd2249`) 소스에서 6개 모두 실패하고 지금 통과한다.
  - a: 대상 영역의 사본이 AI 입력, 작업문, 미리보기·Markdown, 내보내기 기록에서 같다. 알림 영역 이름·구상·ID는 어디에도 없다. 저장된 대상, 후속 요청, 영역 없는 요청의 캡처도 확인한다.
  - b: A 뒤 목적·영역 수정, 보관, 재배치, 작업 옮기기, 재정리, 반복 내보내기, 새로고침을 거쳐도 A의 사본과 작업문은 같다. B만 최신이다.
  - c: A 내보내기(returnId) → B → 늦은 A 보고. 붙여넣기와 정확한 파일 반환 모두 A의 사본을 쓰고, B의 포커스·요청·사본은 그대로다. 보고를 다시 정리해도 A 사본이 간다. 다음 명시 요청은 최신 구상이다. project.4에서 이관한 옛 내보내기의 파일·붙여넣기 반환은 `null`이다.
  - d: 배경의 ‘추가 아이디어’와 ‘아직 못 정함’은 bases, sources, MOCK intent로 승격되지 않는다. 직접 수정한 next/scope는 목적이 바뀐 뒤에도 그대로다. 프롬프트 계약도 확인한다.
  - e: 옛 형식은 null이고 키 유무를 엄격히 따진다. 새로고침·백업 왕복이 같고, 빈 값은 null이며 ‘미정/미기재’ 문구를 만들지 않는다. 최대 길이 다중 바이트·이모지가 정확히 오간다. 위조·추가 키·누락 요청과 저장 길이 초과는 거절한다. 128 KiB 초과는 거절하고 저장 내용이 그대로이며, 8MB 초과는 저장 관문에서 거절한다.
  - server: MOCK HTTP와 가짜 fetch 공급자(키는 가짜, 실제 호출 없음) 모두 `background`를 전용 필드로 받는다. context.6 형식이나 키 누락 요청은 공급자 호출 전에 400으로 거절된다.
- **브라우저** `flow090_browser` test_16(실제 HTTP, MOCK).
  - 목적과 예약 구상 입력 → 예약 요청. 실제 POST 본문의 `background`가 저장된 사본과 같고 sources에는 목적이 없다.
  - 배경 보기, Markdown, 전체 작업문에 예약 구상만 있고 알림은 없다. 내보내기 기록에 사본이 남고 기준은 1개 그대로다.
  - 목적을 고치면 A는 그대로이고 ‘그 뒤 바뀌었어요’가 뜬다. A 보고는 A 사본을 쓰고, 알림 B 요청은 최신 목적과 구상 미기재(null)다.
  - 새로고침·백업 project.5에서 모든 사본이 같다.

## 한계 (숨기지 않음)
- 내보내기 기록은 여전히 작업문 전문을 저장하지 않는다(digest, 작업 값, 그리고 이제 배경 사본만 저장). 과거 전문 전체의 재현은 이번 범위가 아니다.
- 배경 사본은 작업마다, 내보내기마다 복사된다. 긴 목적(최대 12000자)으로 작업이 아주 많으면 8MB 한도에 더 빨리 닿는다. 넘으면 저장을 거절하며 자르지 않는다.
- 사본은 목적과 대상 영역 하나뿐이다. 영역 사이 관계나 다른 영역의 구상은 보내지 않는다(의도된 최소 범위).
- 실제 AI가 배경을 범위와 구분해 다루는지는 확인하지 않았다(실제 호출 없음). 프롬프트와 형식만 검사했다.
