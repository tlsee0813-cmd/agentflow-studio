# 기록 요청 v5 — 첫 구조 묶음, 출처 장부, 쪽 이어쓰기 (2026-11-05, 초안)

v4(.43) 지도는 OSS 8개 맹검에서 v3(.42)에 1승 7패했다(평균 21.9 대 26.5). 지도가 기록의 값을 잃은 것은 파이프라인 수정 .44의 몫이고, 이 문서는 **요청문이 만든 손실**만 다룬다. 가장 큰 것은 7/8 세션이 이월된 핵심 표(C-LINK·C-STEP·C-WITHDRAW)를 끝내 쓰지 않은 것이다(보충 표가 덩이 2를 먼저 차지함). 그다음은 분량(8/8이 12K에 닿음), 유형 낱말 부족(7/8), 좁은 이력 창, 빠진 점검이다.

v5의 결정은 다섯이다.
1. **한 줄짜리 차례**: 첫 구조(Q1) → 상세(Q2) → 보충(Q3). 쪽은 이 차례를 12,000자로 자른 것이고, 앞 표가 끝나기 전에는 뒤 표를 쓰지 않는다. 보충 표의 정의는 기본 요청에 없다.
2. **출처 장부**: 파일은 F, 근거 조각은 E. 행은 ID만 인용하고, 등급은 장부에만 둔다.
3. **C-PART 「표현군·역할」**: 닫힌 유형 목록을 버린다. 표현군 다섯과 미정, 구체 역할은 열린 낱말이다.
4. **쪽 규약**: 모든 행에 ID를 두고, ID는 다시 쓰지 않는다. 고침은 교체·삭제뿐이다. 같은 쪽을 다시 붙여도 결과가 같다. 완료는 두 단계다.
5. **점검 표 C-CHECK와 검색 기준 이력**. 종류별 첫 구조 줄은 기본 요청 안의 몇 줄로 둔다.

읽은 자료: `RECORD_ASKS_V4_KO.md`, `report-ask.ts`(v4.1), `record-table.ts`, `record-reading.ts`, `card-family.ts`·`claim-topic.ts`, scratchpad의 `research/{v4-record-frictions,astra-a4-asks-size,gpt-pro-projecttypes,oss-frictions}.md`, `runs/ab2-synthesis.md`. v4 기록 24개(`oss/*/*-v4-*.txt`)는 표마다 다시 쟀다(7절).

예시는 모두 가상의 프로젝트 **「물주기」**(화분 급수 알림 서비스: 사용자 앱, 매시 타이머, 일정 계산, 푸시 발송, 급수 기록 DB)에서 만들었다.

## 1. 쪽 구조

### 1.1 차례

| 단계 | 표(이 차례 그대로) | 쪽에 싣는 법 |
| --- | --- | --- |
| Q1 첫 구조 | C-HEAD · C-SUMMARY · C-PART · C-GROUP · C-LINK · C-LOOP · C-WITHDRAW · C-STATUS · C-CHECK | 기본 요청에 정의가 있다. C-PART는 쪽 1에 통째로 싣는다. Q1이 끝나면 그 쪽도 끝낸다. 그래서 첫 지도는 구조만으로 읽힌다 |
| Q2 상세 | C-STEP · C-DATA · C-COND · C-CHANGE · C-RULE · C-ENTRY · C-VARIANT · C-CONTRACT · C-ISSUE · C-GATE · C-UNKNOWN · C-DOUBT | 기본 요청에 정의가 있다. Q1 다음 쪽부터, 같은 답 안에서 이어 써도 된다 |
| Q3 보충 | P1-01…P6-04 가운데 행이 있는 표만 | **기본 요청에 없다.** 앱이 상세 완료(2단계)를 확인한 뒤에 만드는 「보충 쪽 요청」에만 목록이 실린다 |
| 쪽마다 끝 | C-SRC · C-EVID · C-DROP(삭제가 있을 때만) · C-END | 그 쪽에서 처음 쓴 F·E 행, 삭제, 꼬리 |

v4에서 빠지는 표가 넷이다. C-BASIS는 C-HEAD가 된다. C-FILES는 C-SRC F 장부가 된다. C-DONE은 C-END가 된다. C-DESIGN(평균 1,147자, C-DATA·C-STEP과 거의 겹침)은 없앤다. 받는·내는 것은 C-DATA의 만드는·읽는 부분에서 유도하고, 설정은 P6-01로 보낸다.

### 1.2 쪽 머리와 꼬리

**머리**(첫 줄, 글자 그대로):
`〔기록 AF5-3b7e0c19 · 쪽 1 · 기준 9f2c1ab · 앞 쪽 —〕 물주기 기록 v5 (쓴 세션, 2026-11-05 10:20)`
「앞 쪽」에는 쪽 1이면 —, 아니면 직전 쪽 번호를 쓴다. v4의 「경로 약속:」 줄은 없앤다. 경로는 C-SRC에 한 번만 적힌다.

**꼬리** C-END 쪽 끝 — 이 쪽이 손댄 표만 쓰고, 예약이 걸린 표와 건너뛴 표도 쓴다.
```
C-END 쪽 끝
| 표 ID | 상태 | 쓴 행 | 예약 | 남은 것 |
|---|---|---|---|---|
| C-LINK | 끝남 | LN01–LN09 | — | — |
| C-DATA | 아직 | — | D01 급수 일정 · D02 푸시 요청 | 표 전체 |
| C-LOOP | 이어짐 | B06:L01 | — | B07의 반복 |
완료 단계: 진행 중
다음: C-LOOP(B07부터)
```
- 상태는 다섯 값 가운데 하나다: 끝남 / 이어짐(분량 때문에 이 행에서 멈춤) / 아직(예약만 있음) / 해당 없음 / 확인 못함.
- 쓴 행은 ID 범위로 쓴다. 범위 안에 빠진 번호가 있으면 쉼표로 나눈다.
- 완료 단계는 세 값 가운데 하나다: 진행 중 / 첫 구조 완료 / 상세 완료. 앱은 이 값을 믿지 않고 스스로 계산한다(4.5). 둘이 다르면 진단을 남긴다.
- 「다음:」은 다음에 쓸 표와 시작 행이다.
- v4 C-DONE은 기록 하나에 평균 2,450자를 썼다. 모든 표를 매 덩이 적었기 때문이다. C-END는 손댄 표만 적어 쪽마다 약 500자로 줄인다.

### 1.3 핵심 표가 건너뛰어지지 않게 하는 장치

1. **차례 강제**: 쪽은 1.1의 차례대로만 쓴다. 표를 다 못 쓰면 그 행에서 쪽을 끝낸다(「이어짐」). 끝나지 않은 표 뒤의 표는 그 쪽에 나올 수 없다.
2. **보충 표는 정의가 없다**: 기본 요청과 상세 이어쓰기 요청에는 P 표의 열도 이름도 없다.
3. **파서가 거른다**: 2단계 전에 나온 P 표, 그리고 앞 표가 「끝남·해당 없음·확인 못함」이 아닌데 나온 뒤 표는 원형만 저장한다(`recordExtras`). 지도는 그 행을 쓰지 않고, 진단 `out-of-order`를 남긴다. 다음 요청은 빠진 앞 표부터 다시 청한다.
4. **C-END에도 표에도 없는 표**: 차례상 이미 지난 표가 C-END에도 없고 쪽 안에도 없으면 「C-END에 없음」으로 다시 청한다(v4.1의 규칙 그대로).
5. **해당 없음은 이유와 함께**: Q1·Q2 표의 「해당 없음」은 C-END의 남은 것 칸에 이유를 쓴다. 이유가 비면 「확인 못함」으로 읽는다.

### 1.4 앱이 다음 쪽 요청을 만드는 규칙

입력은 같은 기록 ID의 쪽 전부를 접은 결과(4.4)다. 요청에 싣는 「할 일」은 다음 차례를 따른다.
1. **고칠 것** — 앱 점검이 찾은 것이다. 표현군·역할이 없거나 고정 낱말 밖인 부분은 「C-PART 교체 B07」로 청한다. 그 밖에 칸 수가 맞지 않는 행, 표시 없이 겹친 ID, 장부에 없는 F·E 인용이 있다.
2. **예약 풀기** — 예약됐는데 아직 쓰지 않은 ID(D02, X01 …)와 그 이름.
3. **차례의 나머지** — 「다음:」의 표와 시작 행부터 Q2 끝까지. 각 표는 머리 줄과 설명을 기본 요청 그대로 싣는다.
4. **2단계가 끝났으면** 대신 「보충 쪽 요청」을 만든다. 6절의 첫 구조 줄에서 고른 P 묶음을 앞에 두고, P 목록 전체를 싣는다. 이 요청에서는 행이 있는 표만 쓰고, 묶음마다 C-END에 「썼음·해당 없음·미조사·후속 필요」 하나를 쓴다(표 ID 칸에 「P4」처럼).

요청 틀(고정 문구 약 2,300자 + 표 정의):
```
[AgentFlow 기록 쪽 요청 v5 · 기록 {ID} · 쪽 {n}]
앞서 쓴 기록 {ID}({이름}, 기준 {sha})를 쪽 {n}부터 이어 써 줘. 같은 기준 판본만 읽는다(다르면 머리 줄 다음에 「기준 바뀜: sha」만 쓰고 멈춤).
첫 줄: 〔기록 {ID} · 쪽 {n} · 기준 {sha} · 앞 쪽 {n-1}〕 {이름} 기록 v5 (쓴 세션, 시각). 쪽마다 12,000자 이하, 한 답에 여러 쪽 가능.
고칠 것: {목록} / 예약 풀기: {목록} / 쓸 차례: {표 ID(시작 행)…}
쓴 행(다시 쓰지 마): {표마다 ID 범위}
다음 ID: F{n} · E{n} · D{n} · X{n} · N{n} · K{n} · 단계·반복은 부분마다 · 표 행 ID는 접두마다 다음 번호 · 부분은 B01–B{m} 고정
{공통 규칙 요약 · 지어내기 방지 다섯 문장 · 표 정의}
기록 ID: {ID}
```

## 2. 출처 장부와 기본값

### 2.1 C-HEAD 기록 머리 (쪽 1에만, 고칠 때는 「교체 항목」)

`| 항목 | 값 | 근거 |`. 항목은 아래 아홉 가지이고, 값이 없는 항목도 줄은 쓴다.

| 항목 | 값의 형식 | 기본값으로서의 효과 |
| --- | --- | --- |
| 기준 커밋 | 브랜치 · sha · 매니페스트 판본 | C-STATUS 「기준」이 비면 이것 |
| 작성 시각 | 날짜 시각 시간대 | — |
| 읽은 범위 | 폴더·파일 묶음 | — |
| 못 읽은 범위 | 빠진 폴더, 실행 안 함, 대화 요약 여부 | 「없음」 주장을 이 범위에서는 막는다 |
| 클론 | 전체 / 얕은 클론(커밋 N개) / 태그 N개 | 이력 「없음」의 한계 |
| 실린 판본 | 확인됨(태그·릴리스 기록) / 미확인(태그 없음·얕은 클론) / 릴리스 없음(근거 필요) | 미확인이면 C-CHANGE 실린 판본 칸은 —이고, 행마다 「모름」을 쓰지 않는다 |
| 이력 검색 | 검색어 · 맞은 커밋 수 · 가장 오래된 날짜 | C-CHANGE·C-WITHDRAW의 범위(5.1) |
| 기본 행위자 | 「작성: 메인테이너(계정)」 같은 역할: 주체 | C-CHANGE 관련 주체 칸이 비면 이것(1인 유지 저장소의 반복 제거) |
| 첫 구조 줄 | 6절의 줄 이름 1~3개 / 이유 | 질문의 우선순위일 뿐이다. 지도에 「이 프로젝트는 …」으로 그리지 않는다(v4 K4 유지) |

예: `|실린 판본|미확인(태그 없음·얕은 클론)|E01|`

### 2.2 C-SRC 파일 장부 (F)

`| F ID | 경로 | 속한 부분 | 읽음 | 역할 |`
- F01부터 기록 전체에서 이어 매긴다. 각 쪽은 그 쪽에서 처음 인용한 F만 쓴다.
- 경로는 저장소 뿌리 기준이다. 폴더도 된다(끝에 /).
- 읽음은 셋 가운데 하나다: 읽음 / 일부(읽은 범위를 역할 칸 괄호에) / 안 읽음.
- 역할은 한 줄이거나 —다. 생성물·시험·문서는 폴더 한 줄로 묶는다. 실행 때 생기는 것은 「(실행 시)」로 표시한다.
- C-FILES를 대신하고, C-PART의 「담당 F」가 이 ID를 가리킨다.

예: `|F03|server/schedule/|B05|읽음|급수 일정 계산|`

### 2.3 C-EVID 근거 장부 (E)

`| E ID | 등급 | 출처 | 자리 | 짧은 인용 |`
- 등급은 셋 가운데 하나다: 파일 / 실행 / 보고.
  - 파일이면 출처는 F ID다.
  - 실행이면 출처는 이 대화에서 돌린 읽기 명령이다.
  - 보고면 출처는 「커밋 sha」, 「PR #n」, 「이슈 #n」, 「문서 이름 날짜」, 「세션 이름 시각」 가운데 하나다.
- 자리는 함수·줄 범위·절 이름이다.
- 짧은 인용은 60자 이하이거나 —다. 이슈 본문을 못 읽었으면 「이슈 본문 미확인(#n)」이라고 쓴다.
- E는 「이 파일」보다 좁은 근거가 필요할 때만 만든다. 예를 들면 특정 함수, 명령 결과, 커밋·PR·릴리스 기록이다.

예: `|E04|보고|PR #41|본문|「야간에는 푸시를 미룬다」|` · `|E05|실행|git tag -l|—|(빈 출력)|`

### 2.4 행이 근거를 인용하는 법

마지막 열 「근거」에는 아래 다섯 가지 가운데 하나를 쓴다. 여럿이면 「+」로 잇는다.

| 쓰는 값 | 뜻 | 등급 |
| --- | --- | --- |
| `F03` | 그 파일을 이번에 읽음 | 파일(F가 「안 읽음」이면 모름과 진단 `cite-unread`) |
| `E04` | 그 근거 조각 | E 행의 등급 |
| `=` | 그 행의 첫 「부분」 칸이 가리키는 부분의 담당 F 전부 | 파일 |
| `추정` 또는 `추정(F03)` | 네 판단. 괄호는 판단의 바탕 | 추정 |
| `모름` | — | 모름 |

C-SUMMARY는 문장 끝에 `(F02)`처럼 쓴다. 칸 안의 대괄호 꼬리표(`[파일: …]`)도 그대로 받는다(v4 호환).

### 2.5 등급 보존 규칙

1. 등급은 E 행의 「등급」과 F 행의 「읽음」에만 있다. 행은 등급을 다시 적지 않는다. 압축(ID 인용)이 등급을 바꿀 자리가 없다.
2. 「실행」 E의 출처는 명령이어야 한다. 명령이 아니면 「보고」로 읽고 진단 `grade-source`를 남긴다.
3. 인용이 여럿이면 등급을 합치지 않고 인용마다 둔다. 상태 주장은 그 주장이 요구하는 등급의 인용이 있을 때만 그 등급이다. 예를 들어 배포됨은 보고나 실행 인용이 있어야 한다. 「[보고]를 [실행]으로 올리지 마」(v4)가 장부에서도 같은 뜻으로 유지된다.
4. C-LINK의 「설계/관찰」 열은 없앤다. 관찰은 그 행에 「실행」 등급 E가 있을 때만이다. 등급이 곧 관찰 여부라서 둘이 어긋날 수 없다.
5. 프로그램이 기록을 읽을 때 인용을 풀어 `{ ref, grade, source, place, quote }`로 행에 단다. 정리 AI에 보내는 구간 앞에는 그 기록의 「열쇠 묶음」을 붙인다. 열쇠 묶음은 C-PART의 ID·이름·표현군, C-SRC, C-EVID다(8.3). 그래서 모델도 ID를 등급까지 풀어 읽는다.

## 3. C-PART 「표현군·역할」

### 3.1 열과 판정 기준

`| 행 ID | 이름 | 표현군·역할 | 하는 일 한 줄 | 담당 F | 구현 상태 | 근거 |`
- 칸 값은 「표현군 · 구체 역할」이다(예: `처리 · 실행 조정`). 표현군은 고정 낱말이고, 역할은 2~8자의 열린 낱말이다.
- **모든 행이 하나를 가진다.** 빈 칸이나 고정 낱말 밖의 값은 1.4의 「고칠 것」이 된다.

| 표현군 | 기준(이것을 실제로 하는가) | 아닌 것 | 역할 낱말 예 |
| --- | --- | --- | --- |
| 참여 | 이 코드의 통제 밖에서 일·요청·판단을 주고받는다 | 개발에 쓴 AI 세션(제품 밖) | 사람(소유자·기여자·방문자·사용자·운영자) · 봇 · 외부 시스템 · 사용자 코드 |

| 미정 | 지금 근거로 정할 수 없다 | — | 이유 셋 가운데 하나(3.2) |

판정 규칙(요청문에 그대로 넣는다):
- 이름이 아니라 하는 일로 고른다. 「기다린다」 같은 동사 하나로는 정하지 않는다. 사람도, 사건도, 타이머도 기다린다.
- 둘에 걸치면 막는 일이 있는 쪽이 관문, 스스로 깨어나는 쪽이 촉발이다. 남으면 미정 · 서로 다른 역할 혼재다.
- 진입점·어댑터·확장 지점·신호는 표현군이 아니다. C-ENTRY·C-VARIANT·P2-02에 쓴다(v4 K12 유지).

### 3.2 미정

- `미정 · 책임 설명 부족` / `미정 · 서로 다른 역할 혼재(처리·저장)` / `미정 · 대상 범위 불명확`. 괄호 안 후보는 쓰고 싶을 때만 쓴다.
- 중심 부분(C-LINK 행 3개 이상이거나 C-LOOP 소유)이 미정이면 쪽을 끝내기 전에 한 번 다시 읽는다. 그래도 미정이면 C-DOUBT에 그 부분을 쓴다. 그럴듯한 표현군을 억지로 붙이지 않는다.
- 카드는 중립 계열로 그리고 「미정: 이유」 칩을 단다. 모양은 기록된 내부 구조(단계·반복·묶음)로만 정한다.

### 3.5 루프는 표현군이 아니라 구조다 — 결정

**구조로 한다.** 「루프·엔진」 유형 낱말은 없앤다. 반복은 C-LOOP 행에서만 온다. 이유는 넷이다.
1. **유형 오판이 이 낱말로 몰렸다.** dispatch 함수, 웹 서버, 실행기가 「루프·엔진」이나 「집행」으로 적혔다(ab2 5절). 「반복이 있다」와 「하는 일」은 다른 물음이다.
2. **한 부분에 반복이 여럿 있을 수 있다.** 중첩 루프 손실이 5/8이었다. 유형은 하나라서 둘째 반복을 담지 못한다. C-LOOP는 부분마다 여러 행과 부모 반복을 가진다.
3. **반복은 어느 표현군에도 있다.** 촉발(매시 틱), 저장(압축 주기), 참여(사람의 재시도), 처리(학습 반복) 모두 반복을 가질 수 있다.
4. **card-family.ts가 이미 그렇게 말한다.** 「단계가 있는 루프도 처리 계열에 머문다」고 하고, 내부는 계열과 따로 붙는 능력(`innerOf`)이다.

따라 바뀌는 것:
- `LOOP_TYPES`로 반복을 거르는 규칙(map-reading.ts:626)은 v5 기록에 쓰지 않는다. C-LOOP 행이 있으면 반복이 있다.
- 몸통은 C-STEP의 「소속 반복」이 그 반복 ID인 단계들이다. 그런 단계가 없으면 「단계 미전개」로 두고, 카드는 반복 배지와 몸통 설명만 보인다. 앱은 임의의 단계를 넣지 않는다.

## 4. 이어쓰기(쪽) 규약

### 4.1 ID

| 대상 | ID | 정하는 표 |
| --- | --- | --- |
| 부분 | B01… | C-PART. **쪽 1에서 고정**한다. 뒤 쪽은 「추가 B31」처럼 다음 번호에 「추가」 표시를 붙여서만 더한다(진단 `part-added`, 측정 항목) |
| 단계 · 반복 | B03:S01, 갈래 B03:S04a·b · B03:L01 | C-STEP · C-LOOP |
| 산출물 · 변형 · 진입 · 외부 계약 | D01 · X01 · N01 · K01 | C-DATA · C-VARIANT · C-ENTRY · C-CONTRACT |
| 파일 · 근거 | F01 · E01 | C-SRC · C-EVID |
| 다른 표의 행 | GR(C-GROUP) · LN(C-LINK) · WD(C-WITHDRAW) · ST(C-STATUS) · CK(C-CHECK) · CD(C-COND) · CH(C-CHANGE) · RU(C-RULE) · IS(C-ISSUE) · GT(C-GATE) · UN(C-UNKNOWN) · DB(C-DOUBT) + 두 자리 | 각 표 |
| 보충 표 행 | P4-02.3 | 각 보충 표(v4 그대로) |

- C-HEAD(항목이 열쇠)를 빼고 모든 표가 첫 열에 「행 ID」를 갖는다. 행마다 약 5자, 30부분 저장소에서 약 1,000자가 든다. 대신 교체·삭제와 멱등 접기가 행 단위로 성립한다.
- ID는 표마다 번호를 늘리기만 하고, 한 번 쓴 ID는 삭제된 뒤에도 다시 쓰지 않는다.
- 「부분」으로 끝나는 열에는 B ID를 쓴다. 이름 안의 「·」와 부딪히던 문제(마찰 9)가 이것으로 사라진다. 목록 항목은 「B12: 항목」으로 쓴다.

### 4.2 예약

- 아직 쓰지 않은 행을 이 쪽의 행이 **가리킬 때만** 예약한다. 예를 들어 C-LINK가 D02를 가리키는데 C-DATA는 Q2에 있는 경우다.
- 예약은 C-END의 「예약」 칸에 「ID 이름」을 쓴다.
- 이 쪽에서 아무 행도 인용하지 않은 예약은 진단 `reserve-unused`를 받고 버려진다.
- 예약되지 않았고 쓰이지도 않은 ID를 인용하면 진단 `dangling-ref`다.
- 예약은 다음 요청의 「예약 풀기」에 들어간다(1.4의 2번). 풀릴 때까지 지도는 그 참조를 「미해결 참조」로 보인다. 이름은 C-END의 예약 글을 쓴다.

### 4.3 교체와 삭제

- **교체**: 같은 표에 행 ID 칸을 「교체 B07」로 쓰고 행 전체를 다시 쓴다. 칸 일부만 고치는 방법은 없다. v4.1의 「정정 B03」은 교체의 다른 이름으로 받는다.
- **삭제**: C-DROP 표에 쓴다. 형식은 `| 행 ID | 이유 | 근거 |`, 예는 `|LN07|같은 호출을 LN03이 이미 적음|F03|`. 삭제된 ID를 가리키는 행은 진단 `ref-deleted`를 받는다.
- **표시 없는 겹침**: 이미 있는 ID가 「교체」 없이 다시 나오면 앞 행이 이긴다. 뒤 행은 원형만 남고 진단 `duplicate-id`를 받으며, 다음 요청의 「고칠 것」에 들어간다(교체할지, 새 ID로 쓸지).
- 고침은 프로젝트의 변화가 아니다. 프로젝트가 실제로 바뀐 것은 C-CHANGE에 쓴다.

### 4.4 접기와 멱등

- 쪽의 열쇠는 (기록 ID, 쪽 번호)다. 기록은 쪽들을 번호순으로 접은 결과다. 새 ID는 더하고, 교체는 바꾸고, 삭제는 지운다.
- 같은 글을 다시 붙이면 해시가 같아서 아무 일도 없다.
- 같은 열쇠에 다른 글이 오면 그 쪽을 통째로 바꾸고 다시 접는다(진단 `page-replaced`, 화면에 한 줄). 다시 접은 결과는 붙인 순서와 상관없다.
- 쪽 번호가 비면(쪽 3은 있는데 쪽 2가 없으면) 끊긴 곳까지만 접는다. 뒤 쪽은 보관만 하고, 다음 요청은 「쪽 2를 붙여 넣거나 쪽 2부터 다시」를 청한다.
- 머리의 기준 sha가 다르면 같은 기록으로 접지 않는다(v4 규칙 그대로).

### 4.5 완료 두 단계 (앱이 계산함)

- **1단계 첫 구조 완료**: 다음 셋을 모두 만족할 때다.
  - Q1의 모든 표가 끝남·해당 없음(이유 있음)·확인 못함이다.
  - 모든 B 행이 고정 낱말의 표현군을 가진다.
  - Q1 행의 칸 수 오류가 0이다.
  - 이때부터 지도는 「첫 구조」로 그려지고, 정리 칸에 「상세 남음: 표 N개」가 보인다.
- **2단계 상세 완료**: 1단계에 더해 Q2의 모든 표가 같은 상태이고, 예약 0, `duplicate-id` 0일 때다. 이때 「보충 쪽 요청」이 열린다. 보충 쪽이 묶음마다 상태를 적으면 기록은 「보충 판단 끝」이다(3단계가 아니라 표시만).

### 4.6 꼬리가 쓴 것을 말한다

C-END의 「쓴 행」은 그 쪽에 실제로 있는 ID와 맞춰 본다. 다르면 진단 `end-mismatch`이고, 기준은 쪽 안의 행이다. 다음 요청의 「쓴 행(다시 쓰지 마)」은 앱이 접은 결과로 만들고, 세션의 말은 쓰지 않는다.

## 5. 점검 추가

### 5.1 이력은 날짜 창이 아니라 검색으로

C-WITHDRAW(Q1)와 C-CHANGE(Q2)는 같은 검색 결과에서 고른다.
1. `git log -i -E --grep='revert|remove|deprecat|breaking|drop|rollback' --format='%h %ad %s' --date=short` 전부를 본다. CHANGELOG·릴리스 노트의 Removed·Deprecated·Breaking 절도 본다.
2. 맞은 것은 부분마다 묶어 C-WITHDRAW로 보낸다. 방식에 「문서로만 폐기」를 더한다(실행 경고가 없는 폐기). 나머지 큰 변화는 C-CHANGE로 보낸다.
3. C-CHANGE에 최근 변화 6줄을 더한다.
4. C-CHANGE에 「찾은 길」 열을 둔다(검색 / 최근 / 변경 기록).
5. 검색어·맞은 수·가장 오래된 날짜는 C-HEAD 「이력 검색」에 쓴다. 얕은 클론이면 「클론」 항목이 「없음」 주장을 막는다.

### 5.2 C-CHECK 점검 (Q1 끝, 다섯 행 고정)

`| 행 ID | 점검 | 결과 | 찾은 것 | 찾은 방법 | 근거 |`
- 결과는 셋 가운데 하나다: 있음 / 없음 / 확인 못함. 「없음」에는 찾은 방법이 반드시 있어야 한다.
- 찾은 것은 그 결과를 담은 ID들이다(B·L·LN …). 찾은 것이 표에 없으면 그 표에 행을 더하는 것이 이 점검의 일이다.

| 행 ID | 점검 | 무엇을 찾나 |
| --- | --- | --- |
| CK1 | 시간·배경 실행 전부 | 타이머·주기 작업·cron·고루틴·스레드·워커·백그라운드 작업. 시작하는 곳을 모두 찾아, 하나도 빠짐없이 C-PART 부분(촉발)이나 C-LOOP 행에 둔다 |
| CK2 | 정지·취소 경로 | 신호 처리, 취소 토큰·컨텍스트 취소, 종료 훅, 강제 종료, 취소 요청 상태. 각각 C-LINK·C-LOOP 종료 칸에 둔다 |
| CK3 | 사람 관문 | 사람이 승인하거나 손으로 해야 흐름이 이어지는 곳. 관문 · 사람 승인 부분이나 C-RULE 장치 「사람」에 둔다 |
| CK4 | 사람 역할 분리 | 권한이나 경로가 다른 사람 역할(방문자·로그인 사용자·관리자, 소유자·기여자). 역할마다 참여 부분 하나 |
| CK5 | 이력 검색 | 5.1의 검색을 했나, 맞은 수 |

예: `|CK1|시간·배경 실행 전부|있음|B06·B06:L01|rg -n "setInterval&#124;cron" server/|E07|`

## 6. 종류별 첫 구조 줄 (기본 요청 안의 줄, 따로 묻지 않음)

요청문에는 「이런 것이 있으면 첫 구조에서 먼저 볼 것」으로 넣는다. 세션은 맞는 줄 1~3개를 C-HEAD 「첫 구조 줄」에 쓴다. 섞인 프로젝트는 여럿을 쓰고, 맞는 줄이 없으면 「그 밖」이다. 줄의 낱말은 ASK-12의 금지 낱말 시험(검증 저장소 값)을 통과해야 한다.

| 줄 | 먼저 | 피할 것 | 보충 쪽에서 앞에 둘 묶음 |
| --- | --- | --- | --- |

### 8.1 record-table.ts

- `TableDef`: `chunk: 0|1|2` → `queue: 0|1|2|3`(0 = 쪽마다 끝), `rowId`(접두, 예: 'LN')와 `dialect: 'v5'|'v4'`를 더한다.
- `COMMON_TABLES`는 v5 목록이 된다. 지금 목록은 `V4_TABLES`로 얼려 v4 기록에만 쓴다. `PROFILE_TABLES`는 그대로다.
- 머리 줄 정규식 `PAGE_HEAD = /^〔\s*기록\s+(\S+?)\s*·\s*쪽\s+(\d{1,2})\s*·\s*기준\s+([^〕\s]+)\s*·\s*앞\s*쪽\s+(\d{1,2}|—)\s*〕\s*(.*)$/`를 더한다.
- `recordVersion`이 'v5'를 돌려준다. 쪽 머리나 「기록 v5」가 있을 때다.
- `CHUNK_HEAD`는 v4용으로 그대로 둔다. `TITLE_LINE`은 C-HEAD·C-SRC·C-EVID·C-CHECK·C-DROP·C-END를 이미 받는다.
- 새 낱말 표:
  - `FAMILY_WORDS`(참여·처리·저장·촉발·관문·미정), `UNDECIDED_WORDS`(이유 셋), `ROLE_TYPES`(아는 역할 낱말 → PartType, 호환용)
  - `V4_TYPE_FAMILY`(3.3 표)
  - `END_WORDS`(끝남·이어짐·아직·해당 없음·확인 못함), `CHECK_WORDS`(있음·없음·확인 못함), `GRADE_WORDS`(파일·실행·보고), `READ_WORDS`(읽음·일부·안 읽음), `FOUND_WORDS`(검색·최근·변경 기록)
  - `WITHDRAW_WORDS`에 「문서로만 폐기」를 더한다
- 새 함수:
  - `readCites(cell, ledger)` → `{ ref, grade, source, place, quote }[]`
  - `foldPages(pages)` → 표마다 현재 행. 교체·삭제·겹침·예약·`out-of-order`·`page-gap` 진단을 함께 낸다.
  - `pageKey`·`pageHash`
  - `recordLevel(folded)` → 0|1|2
- `rowsOf`는 v5 기록에 대해 접은 행을 돌려준다. 패스들은 바뀌지 않는다.

### 8.2 v4·v3 대체 읽기

- **v4**는 `V4_TABLES`로 읽고, 지금(.43)과 같은 필드를 낸다. 더해지는 것은 둘이다. 첫째, 유형 낱말에서 `family`·`role`을 3.3 표로 채운다. 둘째, C-DONE을 `coverage`로 읽는다(지금 그대로). `level`은 null이고, 이어쓰기는 v4.1의 `continuationAsk` 그대로다.
- **v3·v1**은 제목 대응표 그대로 읽고, `family`는 v4와 같은 표에서 채운다.
- 이미 저장된 map-reading.18 이하의 읽기는 다시 읽지 않는다.

### 8.3 record-reading.ts와 파이프라인

- **v5 부분은 프로그램이 C-PART에서 만든다.** B ID가 열쇠이고, 모델이 쓴 부분과는 ID로 잇는다. 지금은 모델의 부분과 이름이 맞을 때만 유형을 단다(record-reading.ts:105의 `byName`). 그래서 유형이 null로 빠지는 일(8/8)이 이 경로에서는 생기지 않는다. 이름 맞춤은 v4·v3에만 남긴다.
- 「부분」 칸의 B ID, 산출물 칸의 D ID는 프로그램이 풀어서 관계를 만든다.
- 정리 AI에 보내는 구간마다 「열쇠 묶음」을 앞에 붙인다(2.5의 5번). 30부분 기준 약 3,500자이고, `MAP_RECORD_CHARS`(12,000)에 더해지는 몫이다. 바이트 상한에 맞는지는 측정 항목이다(9.2).
- C-LINK의 `mode`는 인용 등급에서 유도한다(observed ⇔ 실행 등급 E).
- C-LOOP의 `body`는 C-STEP의 `loopIds`로 모은다. 비면 `bodyState: 'unexpanded'`다. `LOOP_TYPES`로 거르는 규칙은 v5에 쓰지 않는다.
- C-SRC는 `fileRoles`가 된다(`runtime`, `read`). C-HEAD는 `basisScope`, `reading.defaults`, `reading.firstLines`가 된다.

## 11. 열린 질문

1. **보충 목록을 언제 싣나.** 이 초안은 2단계 뒤에만 싣는다. 파일로 쓰는 세션이 한 답에 상세까지 마치는 경우, 왕복 2의 요청에 목록을 붙이면 붙여 넣기가 2번 준다. 그 대신 1.3의 2번 장치가 약해진다. 측정 뒤에 정한다.
2. **C-DESIGN을 없애도 되나.** 측정에서는 겹쳤지만, 부분별 「설정 키=값」이 P6-01로 밀리면 첫 지도에서 설정이 사라진다. C-PART에 「설정」 열을 둘지 정하지 못했다.
3. **관문을 계열로 따로 둘지.** 지금은 촉발·관문 한 계열 안에서 글리프만 나눈다. 카드 설계 v3(촉발·관문 한 계열)를 바꿀지는 화면 쪽 결정이다.
4. **F·E 머리 글자.** 검토자의 제안대로 F·E를 썼지만, v4 K23은 시나리오 대장·응답과 머리 글자가 겹치지 않게 골랐었다. 실제 충돌 경로는 찾지 못했다. 그래도 하나를 고쳐야 한다면 어느 쪽인지 소유자가 정해야 한다.
5. **열쇠 묶음의 크기.** 구간마다 약 3.5K를 더하면 `MAP_BYTES`(65,536) 안에 쪽이 몇 개 드는지 재지 않았다. 넘치면 프로그램이 B ID를 이름으로 풀어 주는 방법(원문 위치 보존이 어려움)과 견줘야 한다.
6. **C-STEP 부분당 상한 24.** 마찰에서 20·18단계가 필요했던 두 사례만 근거다. 상한을 없애고 쪽 상한에만 맡길지 정하지 못했다.
7. **.44를 v5보다 먼저 낼지.** 8.6의 순서는 측정을 깨끗하게 하지만 한 주기가 늘어난다.

## 12. 검토 반영 (Astra 2차 검토, 2026-11-05) — 위 절보다 이 절이 우선

검토 요지: Q3를 떼어 낸 것은 보충 표가 새어 나오는 문제를 크게 줄인다. 그러나 세션이 앞 표를 「끝남·해당 없음」으로 닫아 버리면 앱이 그것을 가려낼 수 없어서 핵심 표 누락은 남는다. 더 큰 위험은 근거 압축이 주장의 뜻까지 바꾸는 규칙(`=`, 실행 E가 있으면 관찰)과, 요청문 효과와 파이프라인 효과가 섞인 측정 설계였다. 아래와 같이 고친다.

1. **엄격한 순서 대신 「남은 의무」** (1.3·4.5 수정)
   - Q3는 계속 떼어 둔다(기본 요청에 정의 없음).
   - Q1·Q2 안의 표 순서는 **권장**이다. 차례를 어긴 행도 유효하면 받아서 쓴다. 다시 쓰게 하지 않는다. 진단 `out-of-order`는 기록만 하고 행은 버리지 않는다.
   - 완료는 둘로 나눈다. 하나는 **작성자 선언**(C-END)이고, 다른 하나는 **앱 검사**다. 앱 검사는 남은 의무를 센다. 남은 의무는 다음과 같다.
     - 「단계 미전개」인 핵심 반복
     - 진입점·시나리오는 있는데 대응 연결이 없는 부분
     - 풀리지 않은 예약
     - 건너뛴 필수 표
     - 처리하지 않은 고침
   - 연결이 없다고 바로 오류로 보지 않는다. 앱은 「누락 후보」와 「확정 오류」를 나눠 보인다.
   - 다음 쪽 요청에는 남은 의무 목록만 싣는다. 보충 목록은 싣지 않는다.
2. **`=` 삭제, 관찰 자동 승격 삭제** (2.4·2.5 수정)
   - 근거 칸에는 `F03+F08`처럼 명시한 ID만 쓴다.
   - C-LINK의 「설계/관찰」은 **주장 성격** 열로 남긴다. 값은 정의된 관계 / 실행 보고 / 실행 관측 / 추정 넷이다.
   - 「실행 관측」은 인용한 E가 바로 그 연결이 일어났음을 보일 때만 쓴다. 근거 종류(파일·실행·보고)와 주장 성격은 따로 둔다.
   - E 인용은 「짧고 연속된 정확 인용」이다. 부정어와 조건을 잘라내지 않고, 60자 고정은 없앤다.
   - C-SRC·C-EVID 행은 처음 인용하기 전에 같은 쪽 안에 둔다. 쪽 머리 바로 뒤에 둔다.
3. **표현군 기준은 「주된 계약」으로** (3.1 수정)
   - 판단 물음은 「이 부분을 지금 지도에서 어떤 책임의 단위로 다루는가」다. 기준 문장은 검토의 표를 쓴다.
     - 평가기는 처리다. 그 결과로 막는 부분이 관문이다.
     - 시간 신호만 내는 스케줄러는 촉발이고, 작업 배정을 조정하면 처리다.
     - 내부 변수가 있다는 것만으로 저장이 아니다.
     - 반복하거나 기다린다는 것만으로 촉발이 아니다.
   - 주된 계약이 분명하면 역할이 섞여 있어도 그 표현군을 쓴다. 미정은 주된 계약을 정할 수 없을 때만 쓴다. 유형을 붙이려고 부분을 쪼개지 않는다.

   - 이력 검색 결과는 「접근 가능한 이력에서 이 검색으로 찾지 못함. 전체 이력에 없다는 뜻이 아님」으로 쓴다. 검색 대상(메시지/변경 내용)과 얕은 이력 여부를 함께 쓴다. 검색어·맞은 수·날짜는 C-HEAD가 아니라 C-CHECK CK5에 둔다.
   - 기본 행위자는 C-CHANGE의 관련 주체에만 적용한다.
   - 「첫 구조 줄」은 종류 할당이 아니다. **실제로 중요한 책임·흐름 1~3개**를 쓴다. 종류별 줄(6절)은 요청문 안의 참고 문장으로만 남긴다.
7. **분량·붙여 넣기** (7절 수정)
   - 산술을 바로잡는다. 쪽당 12K이고 기록 전체가 50~55K이면 **최소 5쪽**이다.
   - 첫 구조는 두 쪽에 걸칠 수 있다고 전제한다. 여유 140자는 실용적인 여유가 아니다.
   - 목표를 나눈다.
     - 첫 쓸 만한 지도: 기록이 돌아오는 횟수 1~2번.
     - 상세 보강: 사용자가 이어 가기로 고를 때.
     - 보충: 공백에 맞춰 골라서.
   - 「붙여 넣기」는 사용자 왕복 수와 전달 조작 수로 따로 센다.
   - 이어쓰기 요청은 기본 요청 전체가 아니다. 진행 위치, 남은 의무, 필요한 규칙만 싣는다.
8. **측정 설계** (9.2 수정)
   - 파이프라인 효과는 같은 v4 기록을 .43과 .44로 처리해 비교한다.
   - 요청문 효과는 v3·v4·v5 기록을 **같은 파이프라인(.45, 호환 읽기)**으로 처리해 비교한다.
   - 첫 사용 경험은 첫 구조까지의 품질과 왕복 비용이다.
   - 전체 기록의 가치는 상세 완료까지의 품질과 총비용이다.
   - 실패 조건을 따로 둔다. 핵심 반복이나 조건을 지어낸 지도는 다른 항목 점수로 만회해도 실패다.
   - v5의 직접 목표:
     - 보충 표를 먼저 써서 핵심이 미완료로 남는 사례 0
     - 완료 표시를 했는데 남은 의무가 있는 사례 0
     - 출처 압축으로 생긴 잘못된 인용·관찰 승격 0
     - 첫 구조까지의 사용자 왕복이 늘지 않음
