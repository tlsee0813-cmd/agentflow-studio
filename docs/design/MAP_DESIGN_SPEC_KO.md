# 지도 설계서 — 요구와 설계를 한 지도에 (2026-11-03)

이 문서는 "어떻게 설계해야 하는가"만 적는다. 구현 순서는 마지막 절에 있다. 생각의 경로와 버린 안은 [MAP_FUSION_KO.md](MAP_FUSION_KO.md)에, 읽기면은 [PART_READING_KO.md](PART_READING_KO.md)에 있다. GPT-6(Pro) 두 대화 — 융합 모형 비판과 2025–2026 사례 조사 — 와 오케스트레이터 세션의 실제 기록(현황 v3·설계 v1)을 바탕으로 썼다. 시험 자료는 KORU지만 문법은 모든 프로젝트에 같다.

## 0. 판단 기준 (이 설계가 맞는지 보는 질문)

화면 자체가 아래 다섯 질문에 답하면 설계서이고, 옆 글상자에서만 답하면 요구 명세서다.

1. 이 부분은 어떤 형식의 입력을 받는가?
2. 입력을 받으면 어떤 순서와 조건으로 처리하는가?
3. 처리 중 무슨 상태를 보관하고 바꾸는가?
4. 무엇을 내놓으며, 다음 부분은 언제 그것을 소비하는가?
5. 결과를 바꾸는 설정과 규칙은 어디에 걸려 있는가?

유형 아이콘과 번호 경로를 더하는 것만으로는 이 질문들이 글상자에 남는다. **카드 내부의 구조가 달라져야 한다.**

## 1. 모형: 공통 접점 위에 네 가지 내용

요구와 설계는 단위가 다르므로 둘을 직접 붙이지 않는다. 둘이 모두 가리킬 수 있는 **접점**을 두고, 그 접점 위에 네 가지 내용을 얹는다.

**접점** (지도의 고정 대상, 안정된 ID):
- 요소의 **경계** (부분)
- 경계의 **포트** (이름 있는 입력·출력)
- 경계 안의 **행동** (단계)
- 행동이 다루는 **데이터** (산출물과 그 형식)
- 요소 사이의 **연결** (전달·제어)

**네 가지 내용**:
| 내용 | 무엇을 말하나 | 접점에 어떻게 얹히나 |
| --- | --- | --- |
| 구성·동작 (설계) | 무엇이 있고 어떻게 움직이나 | 접점 자체. 카드의 몸통과 선 |
| 시나리오 (요구의 행위 쪽) | 촉발에서 결과까지 어느 접점을 어떤 순서로 지나나 | 접점의 **방문** 목록 |
| 규칙·결정·철회 (요구의 조건 쪽) | 어느 접점에 어떤 조건이 걸리고, 무엇이 무엇으로 바뀌었나 | 접점에 붙는 **표지**와 같은 자리의 **이전→현재** |
| 상태·시각·출처 | 어느 주장이 언제 어떤 근거로 성립했나 | 각 주장 옆의 **칩**. 선 모양을 쓰지 않음 |

요구는 세 자리를 가진다: ① 시나리오 머리의 **바라는 결과**, ② 단계·포트·구간에 붙는 **조건**, ③ 아직 연결할 접점이 없는 **설계 미정**(지도 밖 목록에 남고, 억지로 노드에 붙이지 않는다). 셋째를 지우면 해결되지 않은 설계가 해결된 것처럼 보인다.

"안"은 두 종류다. **구성**(엔진 안의 하위 부품: ARM, 집행자)과 **동작**(엔진이 수행하는 10단계)은 다르다. 열리는 면에 구성 / 동작을 명시한다.

## 2. 지형: 노드·경계·선·산출물의 문법

### 2.1 노드의 공통 골격과 유형별 몸통

폭 220–280px, 제목 15–16px, 계약·설정 12–13px. 픽셀보다 **자리의 반복성**이 중요하다.

| 자리 | 내용 |
| --- | --- |
| 머리 왼쪽 | 작은 유형명(11px, 추적 자간) + 요소 이름 |
| 머리 오른쪽 | 상태 단어(색 점) + 바로 아래 기준 시각·출처 칩 |
| 왼쪽 경계 | 이름 있는 입력 포트 (받는 산출물 이름) |
| 오른쪽 경계 | 이름 있는 출력 포트 (내는 산출물 이름) |
| 몸통 | 유형별 핵심 구조 (아래) |
| 아래 한 줄 | 동작을 바꾸는 설정 1–2개(모노스페이스) + "더" |
| 각 문장 옆 | 근거 꼬리표 칩 (파일/실행/보고/추정/모름) |

유형과 몸통:
| 유형 | 접힌 몸통 | 열린 면 |
| --- | --- | --- |
| 수집기 | 받는 스트림·주기 | 원천 목록, 저장 위치 |
| 계산 | 입력 → 변환 → 출력의 짧은 처리판 | 단계, 분기, 실패 처리 |
| AI 판단 | 쓰는 맥락 · 판단 기준 · 반환 형식 (셋을 구별) | 팔(모델)별 단계, 검증(valid), 상한 |
| 루프·엔진 | 안쪽 공간이 있는 **프레임**: 머리에 반복 단위와 종료·재개 조건, 안에 행동, 유지 상태는 프레임 안 별도 작은 영역 | 행동과 분기 전부, 되돌아가는 선은 프레임 안쪽 한 변을 따라 |
| 타이머·일정 | 시각·주기 한 줄 | 켜는 대상, 실패 시 |
| 집행·외부 호출 | 밖으로 만드는 효과를 **출구 쪽에** 명시 (주문·HARD 스탑) | 호출 계약, 되돌림 |
| 행 파일·보관소 | **장부 모양**(행 구분선). 쓰기 접점과 읽기 접점 구별 | 행 형식, 쓰는 주체·읽는 주체, 보존·교체·만료 |
| 사람 / 세션 / 외부 시스템 | 시스템 경계 밖의 작은 **참여자 카드** | 어떤 입력·판단·효과로 참여하나 |

같은 사각 계열을 유지해도 몸통의 밀도와 리듬이 유형을 말한다. 아이콘만 바꾼 동일 카드보다 설계의 성질이 직접 보인다. "엔진"이라는 이름만으로 반복 프레임을 주지 않는다 — 반복 범위가 **기록되어** 있을 때만 프레임이다. 반복의 세 가지(각 행마다 / 상태를 이어 반복 / 타이머가 매번 다시 기동)를 같은 둥근 아이콘으로 뭉개지 않고 프레임 머리에 단위를 쓴다.

색: 큰 영역은 중성 두 톤, 선택 경로에 강조색 하나, 실패·충돌에 제한된 표시. **형태와 내부 구조가 종류를 말하고, 색은 지금 읽는 대상을 말한다.**

### 2.2 경계(묶음)의 세 가지 뜻

| 경계 | 모양 | 뜻 |
| --- | --- | --- |
| 구성 묶음 (정보 층 등) | 옅은 바탕 영역, 이름은 왼쪽 윗변 | 포함. 입출력 의미를 자동으로 부여하지 않음 |
| 반복·실행 범위 | 안쪽 공간을 가진 프레임, 머리에 단위·종료·재개 조건 | 안의 행동이 그 단위로 반복됨 |
| 화면에서 잠시 묶은 영역 | 점선, 저장 안 함 | 읽기 편의 |

n8n처럼 **묶음의 이름·설명은 프로젝트에, 펼침 상태는 사용자 브라우저에** 저장한다.

### 2.3 선: 뜻마다 다른 모양, 뜻은 하나

| 선 | 모양 | 라벨 자리 |
| --- | --- | --- |
| 데이터 전달 | 1–1.5px 중성 실선 + 화살표 | 긴 구간 중앙에 **타입 칩**(산출물 이름), 그 아래 한 줄에 박자 |
| 기동·제어 (사람 지시, 타이머 켜기, 깨우기) | 가는 점선 + 화살표 | 발동 사건을 짧게 |
| 사용·의존 | 아주 옅은 실선, 화살표 없음 | 없음 |
| 모르는 이어짐 | 선을 잇지 않고 끝단에 "다음 연결 ?" | |

점선은 **제어**에만 쓴다. 추정·이전·설계만에는 쓰지 않는다(선 모양 충돌 금지). 교차와 접속을 구별한다: 실제 합류에는 점, 단순 교차에는 한 선의 작은 끊김. 라벨은 교차점에 두지 않는다.

**비동기 저장을 건너뛰는 화살표를 그리지 않는다.** A가 파일에 쓰고 B가 제 주기에 읽으면, A→파일(쓰기)과 B의 별도 촉발(타이머·루프)→파일(읽기)로 그린다. 매끈한 A→B 실행 화살표는 거짓이다.

### 2.4 산출물: 노드인가 칩인가

| 대상 | 표현 | 열면 |
| --- | --- | --- |
| 파일·큐·보관소 (독립 생애) | 장부 모양 노드 | 보관·쓰기·읽기·교체·수명 |
| 행·메시지의 형식 | 선 위 타입 칩 | 필드·타입·단위·필수·뜻 |
| 실제 한 행·한 메시지 | 실행 근거의 표본 | 실제 값·시각·그 실행 |

노드가 되는 조건: 생산자가 끝나도 내용이 남는다 / 생산과 소비의 시각이 다르다 / 재처리·누적·교체를 설명해야 한다 / 여러 주체가 공유한다 / 거기서 기다리거나 다시 시작한다. 하나만 읽어도 비동기 저장소면 노드다. 여러 소비자가 같은 형식을 받는다고 형식이 노드가 되지는 않는다. review.jsonl: 노드(보관 대상) + 쓰기·읽기 선의 칩 "review 행"(데이터 계약) — 같은 것을 두 번 그린 게 아니다. 파일 지도 25줄을 전부 노드로 만들지 않는다: 실행에서 독립 역할을 하는 파일만 지형, 구현 위치를 알려주는 파일은 요소·단계의 **위치 참조**다. 개요에서 저장소를 작게 접어도 저장 후 읽기라는 뜻과 장부 표식은 남긴다.

### 2.5 사람과 세션의 자리

운영 중 판단 데이터를 생산하는 세션(감독자·ops·design)은 **참여 요소**다. 개발 기록을 작성한 세션(검토 세션, Claude Code)은 지형이 아니라 **작성 근거·담당 맥락**에 놓인다. 같은 "세션"이라도 프로그램 안의 역할이 다르다.

## 3. 시나리오(길)의 문법

### 3.1 방문과 단계의 분리
- **고정 대상**: 엔진의 "review 읽기" 단계 (단계 ID S04).
- **방문**: 이번 시나리오가 그 단계를 지나는 사건 (방문 ID V03). 같은 단계를 한 시나리오가 두 번 지나면 방문이 둘(V03, V07)이지 단계가 둘이 아니다. 엔진을 복제하지 않고 같은 접점에 방문표 03, 07을 놓는다.

### 3.2 그리는 방식
- 시나리오를 위한 **새 선망을 깔지 않는다.** 선택한 시나리오가 **쓰는 기존 연결**을 약 3px 강조색으로 밝힌다(실선·점선 구분 유지). 지나는 노드 전체를 색칠하지 않는다 — 유형·계약·상태는 그대로 읽혀야 한다. 연결·포트·방문표·내부 통과 구간만 밝힌다.
- 방문 번호는 **실제 진입 포트 또는 내부 행동의 왼쪽**에 작은 원형 배지로. 카드 제목에 붙이면 "부품의 고정 번호"로 읽힌다.
- 전경 시나리오는 **하나**. 다른 시나리오는 선택한 요소에 "다른 시나리오에서 사용 N" 작은 입구로.
- 선택 직후 짧게 시선을 유도하되(경로를 먼저 보이고 나머지가 뒤따름), 멈춘 뒤에도 강조가 남아 있어야 한다(Ephemeral Paths 연구: 일시 효과만 쓰면 오류 증가).
- 시작과 끝을 함께 둔다: 위에 촉발과 **바라는 결과**, 지도에 방문과 경로, 끝에 **설계가 내놓는 결과**와 **아직 남은 차이**. 세 가지(요구가 기대하는 결과 / 현재 설계가 만드는 결과 / 둘 사이에 정하지 못한 것)를 구별한다.

### 3.3 분기·병렬·반복·대기
| | 문법 |
| --- | --- |
| 분기 | 실제 판정 단계에 작은 마름모. 출구 바로 뒤에 조건. 선택하지 않은 갈래도 짧은 입구와 결과 이름(NONE_SIDE 쉼, STOP_NOT_RESIDENT)을 남긴다 |
| 병렬 | 짧은 분기 막대, 04-A/04-B, "동시". 합류에는 기록된 뜻(모두 기다림 / 먼저 완료 / 기다리지 않음)만. 선이 다시 만난다고 합류 뜻을 추정하지 않는다 |
| 반복 | 프레임 머리에 단위(각 행마다 / 조건 충족까지 / 분마다). 되돌아가는 선은 프레임 안쪽 한 변을 따라. 지도를 크게 감는 고리 금지. 회차는 실제 한 번의 실행을 볼 때만 |
| 대기 | 기다리는 대상과 재개시키는 사건을 점선 제어로 |

### 3.4 경로의 세 성격을 명시
| 종류 | 뜻 |
| --- | --- |
| 설계된 시나리오 | 이런 조건에서 이렇게 동작하도록 되어 있다 |
| 관측된 실행 | 이 판본·이 입력·이 실행에서 이렇게 지나갔다 (같은 실행에 속한 사건들의 연결이 확인될 때만) |
| 설명용 투어 | 이해를 위해 이 순서로 본다 — 프로그램 연결을 추가하지 않는다 |

[실행] 꼬리표가 여기저기 있다고 전체 경로를 한 번의 실행으로 표시하지 않는다. 행동 A와 B가 각각 기록되었다는 사실은 A 다음 B가 일어났다는 근거가 아니다.

## 4. 열기: 깊이의 세 종류와 두 규모

깊이는 셋이다. 열었을 때 나와야 하는 것이 다르다.
| 깊이 | 묻는 것 | 열면 |
| --- | --- | --- |
| 구성 | 무엇으로 이루어졌나 | 하위 요소, 책임, 경계, 공유 대상 |
| 동작 | 안에서 어떻게 처리되나 | 단계, 분기, 반복, 병렬, 실패·재시도 |
| 근거 | 왜 이렇게 그렸나 | 요구 원문, 결정 기록, 코드 위치, 특정 실행·검사 자료 |

닫힌 요소에는 이름 있는 입구·출구와 작은 **통과 영역**이 있다. 열면 통과 영역이 내부 단계로 펼쳐진다. 바깥의 방문 03은 안에서 03.1, 03.2, 03.3이 되고 바깥의 04는 바뀌지 않는다. 내부 단계의 고정 ID는 따로 유지한다(같은 단계가 다른 방문에서는 07.1). 이를 위해 **외부 포트 ↔ 내부 단계의 대응**이 필요하다(외부 관계 R07 → 엔진 입력 포트 → 내부 단계 S04; 내부 S09 → 출력 포트 → 외부 R12). 대응이 없으면 경계 포트에서 "진입 단계 미상"으로 끝내고 억지로 잇지 않는다.

열기의 두 규모:
- **짧은 펼침**: 몇 개의 단계나 설정을 제자리에서. 주변 배치는 가능한 범위에서 유지.
- **내부 상세**: 선택 요소의 경계를 중심 작업면으로, 바깥 입력·출력 대상은 경계 밖의 작은 참조 카드로. 10단계 엔진과 12단계 러너를 읽을 크기로 펼치면서 전체 좌표를 유지하는 것은 불가능하므로 여기로 간다. 단계 수만으로 강제하지 않는다(짧아도 분기가 복잡하면 내부 상세).

내부 상세에서도 들어온 포트, 현재 방문, 나갈 포트, 바깥 대상이 보인다. 상위로 돌아오면 **카메라·선택·시나리오·갈래** 네 가지를 복원한다 — 같은 길을 더 깊게 읽었다는 연속성은 이 넷이 만든다. 의미 확대 연구는 선호를 지지하지만 생산성 향상을 입증하지 못했으므로, 자동 펼침·자동 카메라 이동보다 **명시적 열기**를 우선하고 대상의 정체성과 기억한 위치를 지킨다.

## 5. 표지: 규칙·관문·철회

### 5.1 규칙 — 적용 자리와 보장 장치를 구별
작은 사각 탭 R7을 그 규칙이 작용하는 자리에 둔다:
- 특정 필드의 조건 → 필드 줄 오른쪽
- 한 행동의 조건 → 행동 상자 윗변
- 한 전달의 조건 → 포트 옆
- 연속 단계의 조건 → 구간 아래 얇은 괄호
- 떨어진 여러 자리 → 같은 R7을 각 자리에 반복 (큰 테두리로 둘러싸면 새 구성 묶음처럼 보이므로 금지; 동일 표지의 동시 강조로)

규칙의 **적용 위치**와 실제 **검사·보장 위치**는 다른 참조다. "만료된 판단은 집행하지 않는다"를 집행 입구에 붙일 수 있지만, 검사 마름모가 자동으로 생기지 않는다. valid_until 필드가 있다는 것만으로 검사 구현을 만들어 내면 안 된다. 선택했을 때 같은 자리에서 두 줄이 이어 보이면 융합이다:
> 요구: 만료된 판단은 집행하지 않음 / 설계 대응: 이 단계(S04 review 읽기 · LINE_STALE)에서 확인함 — 또는 — 적용 방식 미정

SysML의 구별을 가져온다: **satisfy**(이 설계가 이 요구를 충족하도록 되어 있음), **verify**(이 검사가 이 요구를 확인함), 그리고 검사 연결의 존재와 실제 통과는 다르다.

### 5.2 관문 — 실행 관문과 개발 관문
- **실행 관문**: 경로 위. 판정 단계와 실제 출구(통과·거절·대기·중단)를 가진다. 예: "allowed_side ≠ NONE이고 CALM이면 진입".
- **개발·검증 관문**: 시나리오 결과 옆 또는 범위 머리의 사각 깃발. "운영 시작 전 확인", "다음 개발 조건"처럼 목적을 적고 필요한 증거를 연다. 실행 경로를 통과하는 화살표를 연결하지 않는다. 예: "11-04 02:15Z 하루 장이 나오면 design이 읽기 한 쪽".
- 사람의 실제 승인이 운영 절차에 포함되면 사람 참여자에 연결된 명시적 행동으로. 단순한 개발 승인 문장을 그 행동으로 바꾸지 않는다.

### 5.3 철회 — 같은 자리의 이전→현재
기본 화면에는 선택한 판본의 내용이 보이고, 바뀐 자리에 작은 변경 표지만. 표지를 고르면 **그 자리에서** 비교한다.
| 바뀐 대상 | 비교 |
| --- | --- |
| 설정 | 같은 설정 줄에서 이전 값과 현재 값 위아래 |
| 규칙 | 같은 규칙 탭에서 이전 문장과 현재 문장 |
| 연결 | 같은 접점 기준으로 이전 경로와 현재 경로를 가까이 |
| 부분 | 현재 대상과 대응되는 이전 윤곽 |
| 요구·보고·해석 | 문장과 기준 시각 비교. 구조 변경은 별도 |

옛 선도 원래 선 모양(실선/점선)을 유지하고 "이전" 글자와 낮은 강조도로만 구별한다. **철회됨**과 **실제로 제거됨**을 분리한다 — 옛 방식을 폐기하기로 결정했어도 구현·운영에 남아 있을 수 있다. 비교 머리에 "설계 변경 / 구현 변화 / 보고 정정" 중 무엇인지 쓴다. Structurizr의 ADR처럼 결정 전문을 펼치지 않고 작용 대상에 접근점을 남긴다(D12 · 채택 / D8 · D12로 대체).

## 6. 상태·시각·출처: 각자의 자리

"날씨" 은유는 버린다. 돌고 있음=실선, 추정=점선, 파일=진하게를 함께 쓰면 선의 뜻이 충돌하고, 파일에서 본 설정과 특정 실행에서 본 동작은 같은 종류의 근거가 아니며, 돌면서 개선 작업 중일 수도 있다.

| 화면 요소 | 맡는 뜻 |
| --- | --- |
| 노드의 형태·작은 유형명 | 무엇인가 |
| 경계의 제목·윤곽 | 어떤 범위인가 |
| 경로의 강조와 번호 | 지금 어떤 시나리오를 읽나 |
| 머리의 상태 단어 + 색 점 | 돌고 있음/작업 중/미구현/멈춤/폐기/모름 (기록의 단어) |
| 상태 아래 기준 시각 | 언제의 말인가 |
| 각 주장 옆 출처 칩 | 파일/실행/보고/추정/모름 — 열면 정확한 원문 위치·코드 판본·실행 식별자 |
| 짧은 상태 칩(결정·요구) | 제안·채택·대체·철회 |

[파일]은 출처의 종류, [추정]은 해석의 성격, [모름]은 빈칸이다 — 하나의 신뢰도 순위로 바꾸지 않는다. 모르는 것은 안개로 가리지 않고 **"기동 주체 ?", "종료 조건 ?", "다음 연결 ?"처럼 모르는 내용이 있는 자리**를 드러낸다. 자료가 서로 충돌하면 충돌을 남긴다. 사용자가 가져온 검사 기록은 사용자가 제공한 자료이지 앱이 확인한 사실이 아니다. 불확실성 표현(흔들림·둘레·흐림·채도)은 연구에서 우열이 없었고 범주형(미정·보고·철회)에 수량적 기법을 쓰면 안 되므로, 임의의 신뢰도 퍼센트를 만들지 않는다.

지도 위에 기준을 한 번 고정한다: **"대상: 설계 판본 618df374 · 현황: 11-03 08:49Z 보고 기준"**. 완성 설계를 보고 있으면 그 사실을 명시하고, 현재 구현과 다른 곳에만 국소 차이를 표시한다 — 정교하게 그려진 설계가 곧 현재 구현으로 읽히는 것을 여기서 막는다.

## 7. 기본 화면과 상호작용

기본 화면이 이름과 상태만 보이면 지금 문제를 벗어나지 못한다. 접힌 상태에서도 반드시: 요소의 유형과 이름 / 대표 입출력 계약(포트 이름) / 동작을 좌우하는 핵심 설정 또는 반복 단위 / 상태와 기준 / 연결에서 오가는 것과 박자. 시나리오 전문과 규칙 전문은 선택할 때. 작동 구조는 지도 안에, 긴 원문과 이유는 읽기면에 — 입력·설정·분기·행 형식까지 읽기면에만 있으면 지도는 다시 제목과 선만 남는다.

| 조작 | 결과 |
| --- | --- |
| 요소 클릭 | 요소와 접점 선택. 카메라 유지. 읽기면에 긴 내용 |
| 선 클릭 | 전달·제어의 뜻과 박자 |
| 타입 칩 클릭 | 데이터 계약의 필드 펼침 |
| 시나리오 선택 | 방문표와 경로 강조, 구조 유지, 위에 촉발·바라는 결과, 끝에 결과·남은 차이 |
| 방문 번호 클릭 | 같은 요소의 특정 방문 선택 |
| 조건 선택 | 그 조건일 때의 설계 경로 (관측 결과와 구별) |
| 동작 열기 | 경계 포트를 유지하며 내부 행동으로 |
| 구성 열기 | 실제 하위 구성 요소로 |
| 규칙 표지 클릭 | 적용 위치와 설계 대응을 함께 강조 |
| 변경 표지 클릭 | 그 대상의 이전·현재 비교 |
| 근거 칩 클릭 | 정확한 원문. 지도·방문 선택 보존 |
| 상위로 | 이전 카메라·선택·시나리오·갈래 복원 |

시나리오는 **지속되는 읽기 맥락**이고 요소·규칙·방문은 그 안의 초점이다. 요소를 눌렀다고 시나리오가 해제되지 않는다. 모든 것을 항상 펼치지 않는다(Eraser Maps도 거대한 한 그림 대신 연결된 뷰를 쓴다; Dagster는 보일 정보를 고르게 한다). 보존할 것은 같은 대상의 정체성, 현재 질문, 출발 맥락, 돌아갈 위치다.

## 8. 기록과 계약

### 8.1 세 기록
| 기록 | 요청 | 지도에 주는 것 | 상태 |
| --- | --- | --- | --- |
| 현황 보고 (v3 표) | 부분·상태 단어·기준 시각, 묶음, 연결(넘기는 것·박자·설계/관찰), 요청, 철회, 규칙, 오류, 관문, 모름 | 상태·시각·표지의 재료, 지형의 뼈대 | 받음 |
| 설계 기록 (v1 표) | 부분 유형, 산출물과 필드, 받는 것→단계→내는 것→설정, 안의 단계, 조건·분기, 파일 지도 | 지형(요소 몸통, 포트, 장부, 프레임, 단계, 분기) | 받음 |
| 시나리오 기록 | 아래 | 길(방문), 외부 포트↔내부 단계 대응, 바라는 결과와 설계 결과의 차이 | 요청문 확정, 미발송 |

### 8.2 시나리오 기록 요청 (최소 여섯 묶음)
안정된 ID(부분 P, 단계 S, 관계 R, 산출물 A, 규칙 Q)를 전제한다. 기존 두 기록을 재요약하지 않고 그 ID를 참조한다.
| 묶음 | 최소 내용 |
| --- | --- |
| 기준과 목적 | 시나리오 ID·이름, 관련 소유자 요청, 설계 판본, 현황 기준 시각, 설계 경로인지 실행 사례인지 |
| 시작 | 촉발 사건, 시작 조건, 필요한 이전 상태 |
| 방문 | 방문 ID, 참조하는 부분·단계·포트, 필요한 입력·출력 산출물 |
| 이어짐 | 다음 방문, 쓰는 기존 연결, 분기·반복·병렬·대기의 뜻(있을 때만) |
| 끝 | 만들어지는 결과, 바라는 결과, 이탈 결과 또는 확인 가능한 마지막 지점, 둘 사이 차이 |
| 근거와 빈칸 | 각 행동·이어짐의 기록 참조(설계 설명/보고/관측/추론 구별), 모르는 대응, 충돌하는 설명 |

요청문 요지: "먼저 전체 동작을 이해하는 데 가장 중요한 경로 하나를 고르고, 그 결과를 바꾸는 주요 갈래·반복·대기를 포함하라. 별도 촉발로 시작하는 동작은 경계를 밝혀라. 같은 단계를 다시 방문하면 방문 ID만 새로. 외부 입력·출력이 내부 어느 단계로 이어지는지 — 확인할 수 없으면 미상. 보기 좋은 완결 경로를 위해 빠진 연결을 추측하지 말고, 동작의 정의와 실제 한 번의 실행 사례를 구별하며, 읽는 순서만으로 프로그램 연결을 추가하지 마라." 조건식은 원문과 기존 조건 ID 참조로 충분하다 — 앱에 워크플로 실행기를 만들지 않는다.

### 8.3 계약에 더해지는 것 (map-reading.7 위에)
- 요소: `type`(10 유형), `ports{in[],out[]}`(이름 = 산출물 참조), `steps[]`(id, name, does, uses, branch), `config[]`, `loop{unit, stop, resume}|null`, `files[]`
- 산출물: `artifacts[]`(id, name, fields[], producer, readers[], where, kind: store|format)
- 연결: `payload`(artifact ref)·`cadence`·`mode`에 더해 `kind: data|control|uses`, `via: store|direct`
- 시나리오: `scenarios[]`(id, name, request ref, version, asOf, kind: designed|observed|tour, trigger, visits[{id, part, step|null, port|null, in[], out[]}], links[{from, to, relation, kind: next|branch|parallel|loop|wait, condition}], end{produced, desired, exits[], gap}, evidence[])
- 표지 앵커: 규칙·관문·철회 claim에 `anchors[]`(part/step/port/field/relation ref)와 `enforcedBy`(step ref | null | 'unknown'), 철회에 `kind: design|implementation|report`
- 외부↔내부 대응: `portMap[]`(relation → port → step)
- 모두 선택 칸, 틀린 값은 그 항목만 제외하고 진단(지금 규칙 그대로).

## 9. 배치 엔진이 해야 할 일
1. 유형별 카드 크기(몸통 높이가 내용에 따라 다름)와 포트 위치(왼/오른 경계에 이름 순)를 계산하고, 선을 포트에서 포트로 긋는다(지금은 카드 중심/변).
2. 장부 노드(산출물)를 쓰는 쪽과 읽는 쪽 사이에 놓고, 쓰기·읽기 선을 구별해 긋는다.
3. 프레임(반복)의 안쪽 공간을 실제로 잡고, 안의 행동을 배치하며, 되돌아가는 선을 안쪽 변을 따라 긋는다.
4. 시나리오 선택 시 기존 선의 강조와 방문 배지 배치(포트·행동 왼쪽), 겹침 없이.
5. 내부 상세 화면: 선택 요소를 작업면 중심에, 바깥 대상을 참조 카드로, 포트는 경계에 유지.
6. 복귀 상태(카메라·선택·시나리오·갈래)의 저장과 복원.
7. 레이아웃은 결정적(같은 자료에 같은 배치; Langfuse가 그래프 개편에서 한 선택) — 읽는 중에 노드가 움직이면 안 된다(Helveg 평가의 남은 문제).

## 10. 함정 (하지 않을 것)
1. **모든 것을 항상 펼치기.** 전경 시나리오 하나, 요소는 명시적으로 열기, 내부 상세는 별도 작업면.
2. **비슷한 선과 경계를 같은 뜻으로.** Dify의 실행 연결, Langflow의 타입 포트, Airflow의 의존, 서비스 맵의 관측 호출은 다른 관계다. AI 세션의 도구 호출 그래프를 제품의 구조·실행 지도에 넣으면 개발 활동이 제품 구조로 둔갑한다.
3. **AI가 그린 구체성을 확정 설계나 검증 결과로.** 원문에 없는 재시도 횟수·동기/비동기·타입을 채우면 그림은 풍부해지고 근거는 약해진다. 알려진 설계 / AI가 제안한 보완 / 모르는 내부를 화면에서 구별한다. 제안 채택·구현 보고·검사 통과·실제 배포 동작은 각각 다른 상태이며 하나의 초록 "완료"로 합치지 않는다.

## 11. 구현 순서 (한 주기에 하나)
1. **지형 1차**: 유형별 카드 몸통(접힌 모습), 이름 있는 포트, 선 위 타입 칩+박자, 장부 노드(산출물 노드/칩 기준 적용), 제어 선 점선, 기준 고정 줄. 자료: 설계 기록 v1 + 현황 v3. 계약: type·ports·artifacts·connection kind/via.
2. **깊이**: 동작 열기(짧은 펼침)와 내부 상세 작업면, 외부↔내부 대응, 복귀 네 가지. 계약: steps·portMap·loop.
3. **시나리오**: 시나리오 기록 요청 발송·계약·방문표·경로 강조·시작/끝 머리. 분기·병렬·반복 문법.
4. **표지와 비교**: 규칙 탭(적용 자리 + 설계 대응), 실행/개발 관문 구별, 변경 표지와 같은 자리의 이전→현재, satisfy/verify 구별. 계약: anchors·enforcedBy·withdrawal kind.
5. **읽기면 재정렬**: 작동 구조가 지도로 간 뒤, 읽기면은 원문·이유·이력만.

각 주기는 지금처럼: 계약 변경 → 레시피 판본 → 시험 → 같은 KORU 기록으로 실제 실행 → 블라인드 심사(심사표에 "0절의 다섯 질문에 화면이 답하는가" 추가) → 문서·커밋.
