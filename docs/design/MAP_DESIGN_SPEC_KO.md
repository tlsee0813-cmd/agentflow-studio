# 지도 설계서 — 요구와 설계를 한 지도에 (v2, 2026-11-03)

이 문서만 구현 규범이다. 생각의 경로와 버린 안은 [MAP_FUSION_KO.md](MAP_FUSION_KO.md)(비규범, 충돌하는 문장은 적용하지 않음)에, 읽기면은 [PART_READING_KO.md](PART_READING_KO.md)에 있다. v1(커밋 21a729eb)은 GPT-6 Pro 두 대화와 오케스트레이터의 실제 기록(현황 v3·설계 v1)으로 썼고, v2는 GPT-6 Astra High 네 관점(구현자·명세 검토 / 처음 보는 개발자와 소유자 / 정보 디자인·시각화 연구 / LLM 추출 설계)과 두 라운드씩 토론해 고쳤다. 토론 요지는 12절. 시험 자료는 KORU지만 문법은 모든 프로젝트에 같다.

앱의 전제: 코드를 실행하지도 검증하지도 않는다. 기록에 있는 것만 그린다. 모델 답을 고쳐 통과시키지 않고, 틀린 항목만 제외하고 진단을 남긴다. 사용자도 지도를 편집하지 않는다(기록을 고쳐 다시 읽게 한다).

## 0. 판단 기준

다섯 질문은 "설계서인가 요구 명세인가"를 판정하는 기준이 아니라, **기록에 있는 동작 구조가 지도에서 읽히는가**를 평가하는 기준이다.

1. 이 부분은 어떤 형식의 입력을 받는가?
2. 입력을 받으면 어떤 순서와 조건으로 처리하는가?
3. 처리 중 무슨 상태를 보관하고 바꾸는가?
4. 무엇을 내놓으며, 다음 부분은 어떤 조건에서 그것을 소비하는가?
5. 결과를 바꾸는 설정과 규칙은 어디에 걸려 있는가?

여기에 넷을 더한다: 어느 판본·환경의 이야기인가 / 실패하면 어디서 멈추고 생긴 외부 효과는 어떻게 되는가 / 내가 바꿀 단계의 구현 위치는 어디인가 / 기록이 답하지 못하는 범위는 무엇인가.

규칙: 기록에 답이 없으면 그 접점에 **무엇이 미정인지 드러낸다**. 미정을 그럴듯한 설계로 채우는 것은 실패다. 모든 답을 개요에 상시 노출하는 것도 합격 기준이 아니다 — 현재 확대 단계에서 구조를 읽고, 필요한 계약·내부·근거로 이어지는가를 본다. 작동 구조는 지도에, 긴 원문과 이유는 읽기면에.

## 1. 모형: 공통 접점 위에 네 가지 내용

요구와 설계는 단위가 다르므로 둘을 직접 붙이지 않는다. 둘이 모두 가리킬 수 있는 **접점**을 두고 그 위에 네 내용을 얹는다.

**접점** (안정된 ID를 가진 지도의 고정 대상):
- 요소의 **경계** — 부분 P (보관소도 P)
- 경계의 **포트** — O (이름 있는 입력·출력; 역할이며 산출물이 아님)
- 경계 안의 **행동** — 단계 S
- 행동이 다루는 **데이터** — 산출물 A (저장 대상 store와 형식 format을 구별), 필드 F
- 요소 사이와 단계 사이의 **연결** — R (양 끝은 부분·포트·단계 중 하나를 가리키는 유형 있는 참조)
- 규칙·관문·결정 — Q

**네 가지 내용**:
| 내용 | 무엇을 말하나 | 접점에 어떻게 얹히나 |
| --- | --- | --- |
| 구성·동작 (설계) | 무엇이 있고 어떻게 움직이나 | 접점 자체. 카드의 몸통과 선 |
| 시나리오 (요구의 행위 쪽) | 촉발에서 결과까지 어느 접점을 어떤 순서로 지나나 | 접점의 **방문** V와 방문 사이의 **이어짐** L |
| 규칙·결정·철회 (요구의 조건 쪽) | 어느 접점에 어떤 조건이 걸리고 무엇이 무엇으로 바뀌었나 | 접점에 붙는 **표지**와 같은 자리의 **이전→현재** |
| 상태·시각·출처 | 어느 주장이 언제 어떤 근거로 성립했나 | 각 주장의 **속성**. 선 모양을 쓰지 않음 |

요구는 세 자리를 가진다: ① 시나리오 머리의 **바라는 결과**, ② 단계·포트·구간에 붙는 **조건**, ③ 아직 연결할 접점이 없는 **설계 미정**. 셋째는 지도 안의 고정된 입구("배치 미정 N")로 존재를 보이고, 억지로 노드에 붙이지 않는다.

"안"은 두 종류다. **구성**(엔진 안의 하위 부품)과 **동작**(엔진이 수행하는 단계)은 다른 계층이다. **근거**는 계층이 아니라 대상에 붙는 출처 보기다.

### 1.1 불변식
- 대상 ID와 화면 표시 ID를 분리한다. 하나의 대상은 여러 화면(내부 상세의 참조 카드 등)에 나타날 수 있지만 데이터는 하나다.
- 구성 포함, 실행(반복) 범위, 임시 표시 묶음은 서로 다른 관계다. 구성 포함은 순환할 수 없다. 공유 대상은 여러 부모에 복제하지 않고 참조로 나타낸다.
- 이름·배열 순서·화면 번호는 ID가 아니다. steps[]의 배열 순서는 표시 순서이지 실행 순서가 아니다.
- 사용·의존(uses)은 실행 전이가 아니다. 의존의 방향은 데이터에 보존하고 선택 시 표시한다.
- 제거된 항목의 앞뒤를 자동으로 잇지 않는다(어디서든).

## 2. 지형: 카드·경계·선·산출물의 문법

### 2.1 카드

기준 폭 240px(220–280 허용), 좌우 여백 16px, 접힌 높이는 144/176px 두 규격. 글자 12/14/16px, 행간 16/20/22px, 굵기 400/600만. 한글 유형명에 추적 자간을 쓰지 않는다. 고정폭은 코드·시각에만.

접힌 카드의 **네 단위**(이 넷 외에는 선택 시):
| 자리 | 내용 |
| --- | --- |
| 머리 1줄 | 작은 유형명 + 이름 (이름이 2줄이면 몸통 1줄을 줄임) |
| 머리 아래 1줄 | **운영 기록 한 줄**: `가동 보고 · 08:49Z · 현재 미확인` 형식(기준 날짜와 같으면 날짜 생략). 운영 주장이 없으면 `운영 기록 없음`(미구현·설계만으로 바꾸지 않음). 보관소는 쓰기 보고, 사람은 승인 보고처럼 실제 기록된 동작. 상충하면 `운영 기록 충돌`. 색 없음 |
| 좌·우 경계 | 이름 있는 입력·출력 포트(한쪽 최대 3, 넘으면 실제 2 + `그 밖의 N개`). 입출력 이름은 몸통의 입력·출력 자리와 공유하고 경계 밖에 다시 쓰지 않음 |
| 몸통 ≤3줄 | **유형별 핵심 구조 하나를 담은 영역** (한 문장이 아니라 구조) |
| 아래 1줄 | 핵심 설정 하나 또는 내부 입구(`구성 4 · 기록된 단계 7`) |

텍스트 예산은 총 6줄. 시각·출처 칩·추가 설정·개발 상태·결정 상태는 선택 시. 국소 충돌이나 판본 불일치가 있으면 몸통 셋째 줄을 그 표식으로 대체한다. 기록에 없는 항목은 그 자리에 `반환 형식 미상`처럼 **빈 자리를 드러내고**, 카드 형식을 완성하기 위해 값을 만들지 않는다.

**형태군 5개**(멀리서 구별하는 큰 실루엣): 처리 / 저장 / 반복 범위 / 일정 / 참여자. 10 유형은 닫힌 분류가 아니라 몸통 표현 방식이고, 유형명이 세부를 맡는다. 유형 불명이면 **중립 카드**가 기본값이다.

유형별 최소 형태 신호(이름을 가려도 보관·변환·반복·외부 효과가 구별돼야 한다; AI와 계산의 차이는 유형명이 맡는다):
| 유형 | 접힌 상태의 최소 형태 신호 | 몸통이 말해야 하는 것 |
| --- | --- | --- |
| 수집기 | 왼쪽 입력 자리에서 처리칸으로 들어가는 짧은 수신 경로 | 무엇을 받아 무엇으로 내는가. 복수 원천 표식은 복수가 기록된 경우만 |
| 계산 | 입력 자리 – 중앙 변환칸 – 출력 자리 | 변환 동사는 중앙. 알려진 단계만 연결 |
| AI 판단 | 맥락·기준 두 구획 + 별도 반환 구획 | 맥락과 기준은 순서가 아님. 반환 형식을 결과 자리에 |
| 루프·엔진 | 안쪽 공간과 한쪽 귀환 경로가 있는 프레임 | 반복 단위·종료·재개를 머리에, 유지 상태는 행동과 분리된 작은 구획. 귀환 대응이 미상이면 닫힌 고리를 그리지 않음 |
| 타이머·일정 | 작은 시계 표식 + 정렬된 일정 행 | 시각인지 간격인지, 시간대 |
| 집행·외부 호출 | 오른쪽 경계를 넘는 출력 + 외부 효과 이름 | 외부에서 달라지는 것. 요청과 성공을 구별 |
| 보관소 | 상단 이중선 + 의미 있는 행 구분(행 수를 흉내 내지 않음) | 쓰기·읽기·보존을 구별 |
| 사람 / 운영 세션 / 외부 시스템 | 공통 참여자 골격 + 유형명 | 제공하는 판단·입력·효과. 외부는 경계 밖 위치로 표현, 전용 장식 없음 |

**합성 규칙**(중립 카드에 기록된 특성을 붙인다, 우선순위 범위 → 내부 행동 → 출구 효과): 반복 범위가 기록되면 외피를 반복 프레임으로, 안에 알려진 행동을, 외부 효과는 실제 출구에. "반복하는 집행기"는 반복 프레임 안의 집행 행동 + 효과 출구이며 둘 중 하나를 버리지 않는다. 저장 표식은 저장 책임을 가진 대상에만(상태를 유지한다고 엔진을 장부로 바꾸지 않음). 서로 다른 하위 대상의 특성이면 한 카드에 합성하지 않고 내부 구성으로. 처리 순서가 없으면 입력과 출력을 내부 화살표로 잇지 않고, 역할도 없으면 `내부 동작 미상`.

"엔진"이라는 이름만으로 반복 프레임을 주지 않는다 — 반복 범위가 **기록되어** 있을 때만. 반복의 세 가지(각 행마다 / 상태를 이어 반복 / 타이머가 매번 다시 기동)를 같은 아이콘으로 뭉개지 않고 프레임 머리에 단위를 쓴다.

포트 표시: 4–6px 경계 표시. 드래그 손잡이·연결 호버 효과 없음(편집기가 아님). 포트 이름은 역할, 선의 타입은 자료 형식. 실제 선언 이름이 없으면 `declaredName=null`이고 화면 이름은 산출물 이름+방향으로 만든다(표시명을 실제 인터페이스 이름으로 오인시키지 않음). 대표 포트와 순서는 저장된 표시 순서, 이름순 재정렬 금지. 묶음을 누르면 실제 포트 선택. 시나리오가 숨은 포트를 쓰면 묶음 옆에 실제 이름. 서로 다른 포트의 선이 같은 묶음에 닿아도 합류점을 찍지 않는다.

색: 중성 두 톤 + **강조색 1개**(지금 읽는 대상) + **문제색 1개**. 상태별 색 점은 없다. 문제색의 적용 범위: 예상 밖 중단·고장이 발생했다는 기록, 요구 위반이 발생했다는 기록, 같은 대상·판본·시점에 대한 양립 불가능한 주장. 계획된 정지·정상 종료·안전 정지·정상 거절·미구현·정보 미상에는 쓰지 않는다. 설계상의 실패·거절 출구도 기본은 중성, 선택하면 강조색, 그 출구와 관련된 실제 문제 기록을 볼 때만 출구 옆 표식에 문제색. 경로 전체를 붉게 만들거나 과거 고장 기록을 현재 고장처럼 계속 표시하지 않는다. 카드마다 외곽선·그림자·색 바탕을 동시에 쓰지 않는다.

**형태와 내부 구조가 종류를 말하고, 색은 지금 읽는 대상과 문제를 말한다.** 아이콘은 작은 배율에서의 보조 식별에만 쓴다: 아이콘을 가려도 처리 성질이 구별되어야 하고, 몸통을 가리면 동작 설명이 사라져야 한다.

### 2.2 경계(묶음)의 두 가지 뜻
| 경계 | 모양 | 뜻 |
| --- | --- | --- |
| 구성 묶음 (정보 층 등) | 옅은 바탕 영역, 이름은 왼쪽 윗변 | 포함. 입출력 의미를 자동으로 부여하지 않음 |
| 반복·실행 범위 | 안쪽 공간을 가진 프레임, 머리에 단위·종료·재개 | 안의 행동이 그 단위로 반복됨 |

사용자가 화면에서 잠시 묶는 임시 묶음은 1차 범위에서 뺀다(들어온다면 점선 폐곡선이 아니라 모서리 선택 표시). 묶음의 이름·설명은 프로젝트에, 펼침 상태는 사용자 브라우저에 저장한다. 같은 묶음 안의 간격보다 다른 묶음 사이 간격이 좁아지는 배치를 금지한다.

### 2.3 선: 관계 의미 셋, 선 패턴 둘, 화살촉 둘
| 관계 | 모양 | 라벨 |
| --- | --- | --- |
| 데이터 전달 | 실선 1–1.5px + **채운 삼각 화살촉** | 명사: `review 행` (타입 칩 = 산출물 이름) |
| 기동·제어 (사람 지시, 일정 도래, 깨우기) | 실선 + **밑변 없는 열린 V 화살촉** | 동사구: `기동: 일정 도래` |
| 참조·의존 | 점선 + 열린 V 화살촉 (방향은 참조자→대상) | `참조: 설정` |
| 모르는 이어짐 | 선을 잇지 않고 끝단에 `다음 연결 ?` | |

화살촉은 확대율과 무관하게 화면 기준 약 10px, 3px 강조에서도 V 안이 메워지지 않게. 속 빈 삼각(UML 일반화)과 출발점 원은 쓰지 않는다. 점선은 제어가 아니라 정적 참조다(BPMN 메시지 흐름과의 충돌을 피한다). 실제 사용 중인 세 관계의 **작은 범례**를 상시 제공하고 UML·BPMN 호환 문법이라고 주장하지 않는다.

라벨: 연결 하나에 기본 라벨 1개, 1줄. 타입 아래 박자 줄은 없다. 라벨은 실제 글자 폭 + 좌우 8px의 직선 구간에만; 공간이 없으면 접점 가까이, 그래도 겹치면 선택 시 표시. 글자를 축소하지 않는다. 같은 타입 반복 제거는 실제 공통 출력 포트에서 갈라지는 분기에만(줄기에 한 번). 선택한 연결의 타입·조건·미상 표시는 라벨 충돌 때문에 숨기지 않는다. 포트에서 최소 16px 직진 후 꺾는다. 교차와 접속을 구별한다: 실제 합류에는 점, 단순 교차에는 끊김. 라벨은 교차점에 두지 않는다.

**박자는 모든 선의 필수 정보가 아니라 촉발·소비 조건의 한 종류**다. 뜻을 붙여 소유자에게 둔다:
| 기록의 뜻 | 표기 | 자리 |
| --- | --- | --- |
| 반복 간격 | `반복 간격 ≈0.2 s` | 루프 머리 |
| 매일 정해진 시각 | `매일 00:15Z` | 해당 일정 |
| 유효 기간 | `유효 24 h` | 판단·자료의 유효 조건 |
| 상주 운영 시간 | `24 h 상주` | 운영 주장 |
| 사건에 따른 소비 | `새 행 도착 시` / `기동 후 읽기` | 소비 조건 |
| 요청·사용자 행동·준비 완료·수동 호출 | 그대로 | 촉발 |
| 뜻 불명 | `24 h의 뜻 미상` | 해당 주장 |

≈0.2 s를 처리 지연으로, 24 h를 주기로 변환하지 않는다. 시간대 없는 일정은 `시간대 미상`.

**비동기 저장소는 세 관계로 그린다**(화살표는 데이터가 이동하는 방향):
- 생산자 → 보관소: 쓰는 데이터
- 보관소 → 소비자: 읽어 오는 데이터
- 타이머·사건 → 소비자의 읽기 행동: 기동(제어)
- 읽기 요청 자체가 기록되어 있고 설명에 필요할 때만 소비자 → 보관소 `읽기 요청`

A→B의 매끈한 실행 화살표도, 옅은 "실효 흐름" 선도 그리지 않는다. 개요에서는 작은 보관소 노드를 두 데이터 선 사이에 유지(장부 표식·이름·쓰기/읽기 접점만). 선택하면 "A가 기록 → 보관 → B가 자기 촉발에 따라 소비"의 기존 경로를 함께 강조한다. 같은 행의 인계라는 근거가 없으면 `같은 보관소 사용 · 인계 여부 미상`. 쓰기 직후 소비된 것처럼 움직이지 않는다.

### 2.4 산출물: 노드인가 칩인가
| 대상 | 표현 | 열면 |
| --- | --- | --- |
| 파일·큐·보관소 (store, 독립 생애) | 장부 모양 노드 (P) | 보관·쓰기·읽기·교체·수명, 동시 쓰기·중복 소비·중단 후 재개의 자리(기록 없으면 빈칸) |
| 행·메시지의 형식 (format) | 선 위 타입 칩 (A) | 필드·타입·단위·필수·뜻 — 존재·선언 타입·관측값·필수를 구별 |
| 실제 한 행·한 메시지 | 실행 근거의 표본 | 실제 값·시각·그 실행 |

노드가 되는 조건: 생산자가 끝나도 내용이 남는다 / 생산과 소비의 시각이 다르다 / 재처리·누적·교체를 설명해야 한다 / 여러 주체가 공유한다 / 거기서 기다리거나 다시 시작한다. 하나만 읽어도 비동기 저장소면 노드다. 여러 소비자가 같은 형식을 받는다고 형식이 노드가 되지는 않는다. review.jsonl: 노드(보관 대상) + 쓰기·읽기 선의 칩 "review 행"(데이터 계약). 생산자·소비자 목록은 저장하지 않고 채택된 쓰기·읽기 관계에서 **계산**한다. 공유 저장소는 복제하지 않는다(모든 생산자·소비자 사이에 두는 것은 다대다에서 불가능). 파일 지도의 모든 파일을 노드로 만들지 않는다: 실행에서 독립 역할을 하는 파일만 지형, 구현 위치를 알려주는 파일은 요소·단계의 **위치 참조**(경로·판본·대응 근거).

### 2.5 사람과 세션의 자리
운영 중 판단 데이터를 생산하는 세션(감독자·ops·design)은 **참여 요소**다. 개발 기록을 작성한 세션(검토 세션, Claude Code)은 지형이 아니라 **작성 근거·담당 맥락**에 놓인다. "세션"이라는 유형만으로 시스템 밖에 배치하지 않는다. AI 세션의 도구 호출 그래프를 제품의 구조·실행 지도에 넣지 않는다.

## 3. 시나리오(길)의 문법

### 3.1 방문과 단계의 분리
- **고정 대상**: 엔진의 "review 읽기" 단계 S04.
- **방문**: 이번 시나리오가 그 단계를 지나는 사건 V03. 같은 단계를 두 번 지나면 방문이 둘(V03, V07)이지 단계가 둘이 아니다. 요소를 복제하지 않는다.
- **이어짐** L: 두 방문 사이의 전이. 실행 순서는 방문 배열이 아니라 **명시적 이어짐**으로만 정의한다. 각 이어짐은 기존 연결 R을 참조한다. 병렬 방문에는 전체 순서를 부여하지 않는다.

### 3.2 그리는 방식
- 새 선망을 깔지 않는다. 선택한 시나리오가 **쓰는 기존 연결**을 강조색 3px로 밝힌다(화살촉 유지). 주변 연결은 중성 1.25px. 글자 4.5:1·필수 그래픽 3:1 이상(WCAG), 경로 라벨 7:1 목표. 선택되지 않았다는 이유로 읽을 수 없는 회색을 쓰지 않는다.
- 비전경 카드는 이름·형태·문제 표식을 유지하고 설정·출처·중복 타입 라벨을 접는다. 노드 전체를 색칠하지 않는다.
- **방문 배지는 선 위에 두지 않는다.** 포트·단계 옆의 고정된 방문 자리에 지름 20px, 접점에서 8px. 같은 접점에 여러 방문이면 `[03 · 07]`, 둘을 넘으면 `[03 · 07 · +N]`(범위 `03–07`로 합치지 않음). 누르면 방문 선택, 그 방문의 들어오고 나가는 이어짐을 강조.
- 전경 시나리오는 **하나**. 다른 시나리오는 선택한 요소에 "다른 시나리오에서 사용 N" 입구.
- 시나리오가 켜진 채 경로 밖 요소를 누르면 `현재 시나리오 밖의 요소`로 표시하고 경로를 연장하지 않는다. "이 시나리오로 돌아가기"는 마지막 방문을 복원. 같은 요소를 두 번 방문하는 경우 요소 클릭으로 방문을 임의 선택하지 않는다(현재 방문 맥락 유지, 없으면 둘을 구별해 보임).
- 선택 직후 200ms 정도 경로가 먼저 보이고 나머지가 뒤따르는 효과는 허용하되, 정지 상태의 강조가 유지돼야 한다(Ephemeral Paths: 일시 효과만 쓰면 오류 증가). 움직임 줄이기 설정에서는 즉시 전환.
- 시작과 끝을 함께 둔다: 위에 촉발과 **바라는 결과**, 끝에 **설계가 내놓는 결과**·이탈 결과·**아직 남은 차이**. 셋을 서로 복사하지 않는다. 경로가 중간에서 끊겼으면 결과에 도달했다고 표시하지 않는다(`pathStatus=partial`은 앱이 계산).

닫힌 카드의 **통과 영역**:
| 근거 상태 | 표시 |
| --- | --- |
| 입구·내부 경로·출구가 확인됨 | `03 입력명 → 출력명 · 내부 4단계` |
| 입구만 확인됨 | `03 입력명 · 내부 연결 미상` |
| 여러 방문이 같은 카드를 통과 | 방문별 짧은 행, 초과분은 접음 |

"확인됨"은 기록에 대응이 있다는 뜻이지 실행 검증이 아니다. 열기 동작은 방문을 생성하거나 번호를 다시 매기지 않는다. `03.1` 같은 번호는 저장된 부모 방문 관계가 있을 때만 쓰는 표시 번호다.

### 3.3 분기·병렬·반복·대기
| | 문법 |
| --- | --- |
| 분기 | 실제 판정 단계에 마름모. 조건은 출구에서 8–16px 떨어진 곳. 선택하지 않은 갈래도 짧은 출구와 결과 이름(NONE_SIDE 쉼, STOP_NOT_RESIDENT). 마름모만으로 XOR를 선언하지 않는다 — 배타성이 기록에 없으면 `선택 방식 미상` |
| 병렬 | 짧은 분기 막대, 04-A/04-B, "동시". A가 B보다 먼저라는 뜻 없음. 동기화 막대는 **모두 기다림**에만. 먼저 완료·대기 없음은 각각 명시된 합류 행동 또는 독립 종료로. 단순 접속점은 절대 "모두 완료"를 뜻하지 않음 |
| 반복 | 프레임 머리에 단위(각 행마다 / 조건 충족까지 / 분마다). 되돌아가는 선은 프레임 안쪽 한 변을 따라. 지도를 크게 감는 고리 금지. 회차는 실제 한 번의 실행을 볼 때만, 기록된 사건만 펼침 |
| 대기 | 기다리는 대상과 재개시키는 사건을 제어 선으로. 재개 사건이 명시되지 않으면 `재개 조건 미상` |
| 저장소 경유 | 읽기 쪽의 별도 촉발을 유지. 색칠된 연속선이 즉시 연속 실행을 뜻하지 않게 |

### 3.4 경로의 세 성격과 금지된 추론
| 종류 | 뜻 |
| --- | --- |
| 설계된 시나리오 | 이런 조건에서 이렇게 동작하도록 되어 있다 |
| 관측된 실행 | 이 판본·이 입력·이 실행에서 이렇게 지나갔다 — 같은 실행에 속한다는 식별 근거가 있을 때만. 시간상 가깝다는 이유로 합치지 않음 |
| 설명용 투어 | 이해를 위해 이 순서로 본다 — 방문 번호만 쓰고 프로그램 경로를 강조하지 않음 (첫 구현에서 미룸) |

[실행] 꼬리표가 여기저기 있다고 전체 경로를 한 번의 실행으로 표시하지 않는다. 행동 A와 B가 각각 기록되었다는 사실은 A 다음 B의 근거가 아니다. 미상 분기·미상 합류·미상 다음 단계는 그 위치에서 끝낸다.

## 4. 열기: 두 계층, 근거 보기, 세 확대 단계

구성과 동작은 각각 **계층**을 가진다. 근거는 계층이 아니라 대상에 붙는 **출처 보기**다(근거를 열었다고 구조 안으로 한 단계 들어간 것이 아니다).
| | 묻는 것 | 열면 |
| --- | --- | --- |
| 구성 | 무엇으로 이루어졌나 | 실제 하위 요소, 책임, 경계, 공유 대상 |
| 동작 | 안에서 어떻게 처리되나 | 단계, 분기, 반복, 병렬, 실패·재시도·대기 |
| 근거 | 왜 이렇게 그렸나 | 요구 원문, 결정 기록, 코드 위치, 특정 실행·검사 자료 |

닫힌 카드 아래에는 실제 기록에 따라 `구성 4 · 기록된 단계 7` 입구를 둔다. 내부 정보가 없으면 `내부 미상`; 빈 카드와 내부가 없는 카드를 구별한다. 장식용 격자·가짜 작은 상자·겹친 그림자로 "안에 더 있다"를 암시하지 않는다. 하위 미리보기에는 실제 하위 요소만.

**외부 포트 ↔ 내부 단계의 대응**(portMap)이 있을 때만 통과 영역이 내부 단계로 펼쳐진다(외부 관계 R07 → 입력 포트 O → 내부 단계 S04; 내부 S09 → 출력 포트 → 외부 R12). 대응이 없으면 경계 포트에서 `진입 단계 미상`으로 끝내고 억지로 잇지 않는다. 바깥의 방문 03은 안에서 03.1, 03.2가 되고 바깥의 04는 바뀌지 않는다.

열기는 "동작 열기" 하나로 시작한다(사용자가 펼침 규모를 고르지 않는다). 규모는 앱이 판정한다:
- **짧은 펼침**: 한 단계 깊이의 내용(분기 출구·반복 표시·실패·대기 출구·필요한 라벨 포함)을 기본 글자 크기로 사전 배치했을 때 **420×280 CSS px 안에 들어가고**, 선택 카드의 기존 자리와 인접 빈 공간만 쓰며, 다른 노드·라벨·의미 있는 연결선·경계를 가리지 않을 때만. **기존 노드 좌표와 카메라는 바꾸지 않는다.** 맞추기 위한 축소·생략·주변 이동·선 우회는 하지 않는다. 설정만 여는 경우도 같은 판정. 420×280은 이 제품의 상한이지 연구값이 아니다. 전환 180–240ms.
- **내부 상세**: 위 조건을 하나라도 못 맞추면 즉시. 선택 요소의 경계가 작업면 중심, 바깥 입력·출력 대상은 경계 밖의 작은 참조 카드(같은 대상의 표현이지 새 대상이 아님). 들어온 포트·현재 방문·나갈 포트·바깥 대상이 보인다.

**의미 확대 3단계**(화면에 표시된 카드 폭 기준, 글자는 화면 기준 최소 12px, 전환에 ±10% 여유):
| 단계 | 카드 폭 | 보이는 것 | 숨기는 것 |
| --- | --- | --- | --- |
| 전체 | <180px | 이름, 형태군, 저장소·반복 표식, 내부 존재, 문제 유무, 선택 경로의 조건·미상 | 포트명, 설정, 출처, 박자 |
| 읽기 | 180–319px | 6줄 카드, 대표 계약, 핵심 동작·설정, 국소 상태 차이 | 전체 필드·단계, 출처 원문 |
| 접점 상세 | ≥320px | 선택 대상과 직접 연결의 전체 포트명·타입·조건 | 선택하지 않은 카드의 자동 상세화 |

휠 확대는 표현량만 바꾸고 내부 계층 진입이나 전역 재배치를 일으키지 않는다. 1280×720에서 상세 읽기 카드 6–9개가 초기 화면 목표; 15–40개를 다 넣을 때는 전체 단계로 내려간다. 폰트를 줄여 우겨 넣지 않는다.

**복귀**: 카메라·선택·시나리오·갈래에 **보기 종류(구성/동작)·특정 방문·내부 초점·펼침 상태**를 더해 복원한다. 세 이동을 구별한다: **닫기**는 마지막에 연 근거·비교 면을 닫고, **이전 읽기 위치**는 탐색 전 상태로, **상위 구성**은 실제 포함 관계의 부모로. 서로 다른 이동을 "상위로" 하나에 맡기지 않는다. 자동 펼침·자동 카메라 이동보다 명시적 열기를 우선한다.

**개발자 경로**: 선택한 단계에서 그 판본의 구현 위치(파일·판본·대응 근거), 소비자(관계에서 계산), 실패·재개 조건, 관련 검사와 미확인 범위로 이어지는 조작을 둔다. 방향 없는 참조 선만으로 영향 방향을 읽게 하지 않는다.

## 5. 표지: 규칙·관문·철회

### 5.1 규칙 — 범위, 적용 자리, 보장 장치를 따로
규칙 Q에는 `scopeRef`(적용 범위)와 `anchors[]`(정확한 접점)와 `enforcedBy`(보장 장치)를 따로 둔다. 범위가 알려졌다고 접점이 알려진 것이 아니고, 접점이 있다고 보장 장치가 있는 것이 아니다.
| 기록에서 알 수 있는 것 | 표시 위치 |
| --- | --- |
| 정확한 단계·필드·포트가 명시됨 | 해당 접점의 작은 사각 탭 `Q7` (필드 줄 오른쪽 / 행동 윗변 / 포트 옆 / 구간 아래 괄호). 떨어진 여러 자리는 같은 Q7을 반복(큰 테두리 금지) |
| 특정 부분 전체에 적용 | 해당 부분의 범위 머리: `범위 규칙 · 세부 접점 미정` |
| 프로젝트 전체 원칙 | 지도 안 프로젝트 머리의 `전체 규칙 N` |
| 범위조차 정할 수 없음 | 지도 안 고정된 `배치 미정 N` 입구 |

"돈 안전"이라는 문구만으로 전체 원칙으로 추정하지 않는다. 앵커 미정을 이유로 규칙을 숨기지 않는다. 기본 화면에는 규칙의 짧은 이름이 먼저, 식별자는 선택 시.

`enforcedBy`는 검사·보장 장치(단계 S)의 참조 목록이고 **비어 있음 / 장치 미상 / 기록상 미설계**를 구별한다. valid_until 필드가 있다는 이유로 검사 마름모를 만들지 않는다. 선택하면 같은 자리에서 두 줄이 이어 보인다:
> 요구: 만료된 판단은 집행하지 않음 / 설계 대응: S04 review 읽기 · LINE_STALE에서 확인함 — 또는 — 적용 방식 미정

SysML의 satisfy/verify 구별을 가져오되 화면 용어는 **설계 대응 / 확인 검사**로 쓴다. 검사 연결의 존재와 실제 통과는 다르다(검사 대상·판본·결과·미확인 범위를 함께 읽는다).

### 5.2 관문 — 실행 관문과 개발 관문
- **실행 관문**: 경로 위. 판정 단계와 실제 출구(통과·거절·대기·중단). 예: "allowed_side ≠ NONE이고 CALM이면 진입". 정상 거절 갈래를 장애로 칠하지 않는다.
- **개발·검증 관문**: 시나리오 결과 옆 또는 범위 머리의 사각 깃발(경로 밖 텍스트 접근점). "운영 시작 전 확인", "다음 개발 조건". 실행 경로를 통과하는 화살표를 연결하지 않는다.
- 사람의 실제 승인이 운영 절차에 포함되면 사람 참여자에 연결된 명시적 행동으로. 개발 승인 문장을 그 행동으로 바꾸지 않는다.

### 5.3 철회·변경 — 같은 자리의 이전→현재
기본 화면에는 선택한 판본의 내용과 바뀐 자리의 작은 변경 접근점만. 이전 윤곽은 비교 중에만.
| 바뀐 대상 | 비교 |
| --- | --- |
| 설정 | 같은 설정 줄에서 이전 값과 현재 값 위아래 |
| 규칙 | 같은 규칙 탭에서 이전 문장과 현재 문장 |
| 연결 | 같은 접점 기준으로 이전 경로와 현재 경로 — 각각 끝까지 추적 가능, 둘을 섞은 시나리오 강조 금지. 과거 경로 자료가 없으면 `이전 경로 자료 없음` |
| 부분 | 현재 대상과 대응되는 이전 윤곽 |
| 요구·보고·해석 | 문장과 기준 시각 비교 |

비교 머리에 "설계 변경 / 구현 변화 / 보고 정정 / 새로 알려진 과거 사실" 중 무엇인지와 판본을 계속 남긴다. **철회됨**과 **실제로 제거됨**을 분리한다. "현재"는 선택한 판본의 현재이지 실제 운영의 현재가 아니다. 현재 시나리오를 과거 판본에 자동 적용하지 않는다. 결정 전문을 펼치지 않고 작용 대상에 접근점을 남긴다(D12 · 채택 / D8 · D12로 대체).

"어제와 뭐가 달라졌나"의 1차형은 두 스냅샷 비교가 아니라 **기준 시각 이후 작성된 기록** 필터다(프로그램 변화가 아니라 작성 시각 조건임을 이름에 드러냄). 조건에 맞는 주장·변경 표지와 위치만 강조하고, 선택 시 작성 시각과 대상 사건·적용 시각을 구별한다. 작성 시각이 없으면 `작성 시각 미상`으로 따로(가져온 시각으로 대체하지 않음). 결과가 없으면 `조건에 맞는 기록 없음`이지 "변경 없음"이 아니다.

## 6. 상태·시각·출처: 각자의 축

한 enum에 넣지 않는 여섯 축:
| 축 | 값 | 표현 |
| --- | --- | --- |
| 출처 종류 | 파일 내용 / 실행 자료 / 작성자 보고 | 원문 접근점(참조). 보고만 받았으면 [보고]를 유지하고, 파일 발췌·판본·위치가 함께 왔을 때 그 발췌만 [파일] — **출처 세탁 금지** |
| AI 해석 여부 | 원문에 명시 / AI가 연결해 해석 | 해석이 개입한 주장에 `추론`을 직접 붙임 |
| 공백 | **미상**(기록에 없음) / **없음**(없다는 기록이 있음) / **해당 없음** / **숨김 +3**(있지만 표시 안 함) | 그 자리의 명시적 질문 `종료 조건 미상`. 아무 표식 없는 빈칸을 모름으로 쓰지 않음 |
| 충돌 | 같은 대상·판본·시점에서 양립 불가능한 주장 | `충돌 2건`; 선택하면 같은 자리에 같은 크기·대비로 병치(한쪽을 흐리게 하지 않음) |
| 결정 상태 | 제안 / 채택 / 철회 / 대체 | 짧은 상태 칩(선택 시) |
| 운영·구현·개발 상태 | 운영 주장(가동 보고·멈춤 보고·운영 기록 없음), 구현 주장, 작업 진행 | 운영 주장은 카드 머리 한 줄(2.1), 나머지는 선택 시. "작업 중"은 "가동 중"을 덮어쓰지 않음 |

"돌고 있음" 같은 현재형 단독 표시는 금지한다. 구현 완료·설계 채택을 근거로 가동 중을 만들지 않는다. 사용자가 가져온 검사·실행 기록은 "제공된 실행 기록"이지 앱이 확인한 사실이 아니다. 불확실성에 수량 기법(흔들림·둘레·흐림·채도·퍼센트)을 쓰지 않는다 — 범주형 불확실성에서 투명도의 우위는 확인되지 않았고(Potter, VIS 2025), Wiggle 등은 정도의 불확실성에 대한 연구다.

**주장마다 넷을 구별한다**: 대상 판본(어느 설계·코드·배포) / 대상 시각(언제의 상태·사건) / 작성 시각(기록이 언제 작성됐나) / 원문 참조. 작성 시각은 대상 판본의 대체물이 아니다. 대상 판본은 기록이 특정 커밋·태그를 설명한다고 **명시**할 때만(해시가 등장한다는 이유로 연결하지 않음; 날짜도 기록이 판본 식별자로 직접 쓴 경우만). 앱 내부에서는 보고 자체에 고유 ID를 붙여 같은 시각의 기록도 구별한다.

지도 머리의 **기준 줄**: `설계 근거: 11-03 08:49Z 작성 보고 · 대상 판본 미상 · 운영: 보고된 상태(복수 시점)`, 필요할 때 `판본 불일치 2 · 시각 미상 3`. 기준 줄에 "기록 없음은 제공된 자료 기준"임을 밝힌다. 대조할 구현 자료가 없는 곳도 표시한다 — 표지 없음이 "설계=구현"으로 읽혀서는 안 된다.

시각 처리:
| 상황 | 처리 |
| --- | --- |
| 같은 대상·판본·상태 축에서 같은 시점을 다르게 설명 | 충돌로 병기 |
| 서로 다른 시점을 설명 | 상태 이력으로 보존 |
| 명시적으로 이전 보고를 정정 | 정정 관계를 저장하고 새 주장을 현재 읽기에 |
| 다른 판본의 현황 보고 | `다른 판본`으로 표시, 현재 설계에 자동 적용하지 않음 |
| 대상 판본을 모름 | `기준 대응 미상` |
| 시나리오가 이전 설계를 참조 | 이전 판본에서 열거나, 현재 지도에서 대응 가능한 구간과 끊긴 지점을 구별 |

**출처 묶음**: 문장마다 칩을 반복하지 않는다. 동일한 정확 원문 참조 집합·판본·환경·적용 시각·해석 성격이 **연속**되면 그 문장들 왼쪽의 짧은 세로 줄 + 묶음 첫머리의 칩 한 번. 하나라도 다르거나 중간에 근거 없는 문장이 끼면 줄을 끊는다. 카드 제목·상태 줄·설정 줄처럼 떨어진 자리는 같은 출처여도 합치지 않는다. 같은 파일이라는 이유만으로 묶지 않는다(카드 전체에 [파일] 하나 금지 — 반복 주기는 기록에 있고 종료 조건은 없고 내부 연결은 해석일 수 있다). 이것은 모델이 반환한 참조의 동일성을 이용한 표시 규칙일 뿐, 빠진 출처를 이웃에서 물려주지 않는다.

근거 면에서 사용자가 "이 해석이 틀림"을 표시할 수 있다: 원문은 보존하고 그 해석과 의존하는 표현을 재검토 대상으로 둔다(지도 편집이 아니라 제외+진단).

## 7. 기본 화면과 상호작용

첫 화면은 이 순서로 고정한다(전 카드의 동등한 정보 밀도를 없앤다):
1. 프로젝트 목적과 **외부 효과** 한 문장
2. 기준 줄(설계 근거·대상 판본·운영 기준·환경 또는 미상)
3. 주요 입구 → 처리 → 저장·재개 → 외부 효과의 **골격**, 주요 독립 촉발이 개요에서 식별되게
4. 외부 효과 주변의 구현·운영 정보와 **중요한 빈칸**
5. "대표 동작 따라가기" 입구 하나

접힌 상태에서 보이는 것은 **기록으로 확인된** 유형·이름 / 대표 입출력 / 핵심 구조 또는 반복 단위 / 운영 기록 한 줄 / 연결의 자료·촉발 조건이다. 없는 내용은 그 자리에서 미기재를 드러낸다. 시나리오 전문·규칙 전문은 선택 시. 입력·설정·분기·행 형식까지 읽기면에만 있으면 지도는 다시 제목과 선만 남는다.

실패·복구 빈칸은 **외부 효과 출구**와 **보관소 쓰기·갱신 접점**, 그리고 기록이 실패·복구 요구를 명시적으로 연결한 단계에만 둔다(모든 단계에 붙이지 않음). 같은 동작의 출구와 쓰기 접점이 중복되면 실제 효과가 생기는 한 곳에만. 제공되지 않으면 `실패 대응 미제공` / `복구 설명 미제공`(없다고 단정하지 않음). 선택하면 응답에 빠진 것인지 제외된 것인지 진단을 구별한다. 제외된 항목이 영향을 주는 접점에는 `연결 자료를 읽지 못함`을 남기고 정상 종료로 취급하지 않는다.

| 조작 | 결과 |
| --- | --- |
| 요소 클릭 | 요소와 접점 선택. 카메라 유지. 읽기면에 긴 내용. 시나리오는 유지 |
| 선 클릭 | 관계 의미·자료·촉발 조건. 참조 선이면 누가 무엇에 의존하는지 |
| 타입 칩 클릭 | 데이터 계약의 필드(존재·선언 타입·관측값·필수 구별) |
| 포트 묶음 클릭 | 실제 포트 선택 |
| 시나리오 선택 | 방문 배지와 경로 강조, 구조 유지, 위에 촉발·바라는 결과, 끝에 결과·남은 차이·끊긴 지점 |
| 방문 배지 클릭 | 그 방문과 들어오고 나가는 이어짐 |
| 조건 선택 | 그 조건일 때의 설계 경로(관측 결과와 구별) |
| 동작 열기 | 앱이 짧은 펼침/내부 상세를 판정. 경계 포트 유지 |
| 구성 열기 | 실제 하위 구성 요소 |
| 규칙 탭 클릭 | 범위·적용 위치·설계 대응·확인 검사를 함께 |
| 변경 접근점 클릭 | 그 대상의 이전·현재 비교(머리에 변경 성격·판본) |
| 기준 시각 이후 필터 | 그 시각 이후 작성된 주장·변경 표지만 강조 |
| 근거 칩·세로 줄 클릭 | 해당 문장들 강조와 정확한 원문. 지도·방문 선택 보존 |
| 단계에서 구현 위치 | 파일·판본·대응 근거, 소비자, 실패·재개, 관련 검사 |
| 닫기 / 이전 읽기 위치 / 상위 구성 | 4절의 세 이동 |

키보드로 포트 묶음·방문 배지·규칙 탭·변경 접근점을 선택하고 닫을 수 있어야 한다. 색과 작은 마우스 표적만으로 필수 정보에 접근하게 하지 않는다.

1차 범위에서 **미루는 것**: 임시 묶음, 설명용 투어, 상시 식별자 표시(R7·D12·03.2), 두 스냅샷 비교, 사용자가 고르는 펼침 규모. **남기는 것**: 장부 노드, 포트↔단계 대응, 효과 출구, 빈 자리 표시.

### 8.2 시나리오 기록 요청 v2 (오케스트레이터 세션에 보내는 문안)

> 목적은 현재 자료로 설명할 수 있는 동작 경로를 소프트웨어 지도에 연결하는 것이다. 설계를 개선하거나 빠진 동작을 완성하는 요청이 아니다. 아래 여섯 묶음을 표로 작성하라.
>
> 입력: 현황 보고 v3 / 설계 기록 v1 / 이번 요청에 첨부된 ID 대장과 대장 판본 / 현재 세션에서 실제로 확인 가능한 기존 기록·파일 발췌·실행 자료.
>
> 공통 규칙:
> 1. P=부분, O=포트, S=단계, R=연결, A=산출물, F=필드, Q=규칙이다. 첨부 대장의 ID를 그대로 참조하라. 이름으로 ID를 추정하거나 기존 ID의 뜻을 바꾸지 마라.
> 2. 이번 응답에서 새로 발급할 수 있는 ID는 시나리오 C01, 방문 V01…, 이어짐 L01…, 근거 E01…, 빈칸 G01…뿐이다. 모두 이번 보고 안에서만 유효하다.
> 3. 기존 두 기록을 재요약하지 마라. 경로를 설명하는 데 필요한 참조와 새로 확인한 근거만 적어라.
> 4. 핵심 시나리오 하나를 선택하라. 명시된 소유자 요청이 있으면 그것을 기준으로 고른다. 없으면 요청 참조는 '모름', 선택 이유는 '설명 목적'으로 적어라.
> 5. 종류는 '설계 경로 / 관측 실행 / 설명용 투어' 중 하나다. 관측 실행은 같은 실행에 속한다는 식별 근거가 있을 때만 사용한다. 시간상 가깝다는 이유만으로 서로 다른 로그를 하나의 실행으로 합치지 마라.
> 6. 모르면 '모름'이라고 적어라. '없음'은 실제로 없다는 근거가 있을 때만 사용한다. 표에서 생략한 것을 없다고 주장하지 마라.
> 7. 한 행에는 하나의 방문 또는 하나의 이어짐만 적어라. 같은 단계를 다시 방문하면 S는 유지하고 V만 새로 발급한다.
> 8. 보기 좋은 완결 경로를 위해 빠진 연결·포트·단계·조건·종료·재개를 만들지 마라. A와 B가 각각 기록되어 있다는 사실만으로 A 다음 B라고 쓰지 마라.
> 9. 파일·큐에 쓰는 동작과 나중에 읽는 동작을 직접 호출로 합치지 마라. 별도 촉발이면 그 경계를 표시하라.
> 10. 분기 조건·반복·병렬·합류·대기는 기록에 명시된 의미만 적어라. '모두 기다림', '먼저 끝난 것', '즉시 재개' 등을 상식으로 보충하지 마라.
> 11. 새 P/O/S/R/A/F/Q가 필요하지만 대장에 없으면, 해당 연결을 작성하지 말고 여섯째 묶음의 빈칸 표에 원문과 함께 보고하라.
> 12. 파일을 확인했다는 보고와 실제 파일 발췌, 실행했다고 한 보고와 실제 실행 자료를 구별하라. 이번 보고를 만들기 위해 새 코드 변경·새 실행·새 검사를 하지 마라.
> 13. 각 사실 행에 E 근거 ID를 붙여라. 기존 자료를 찾을 수 없는 기억이나 보고자 판단은 '보고' 또는 '추정'으로 표시한다. 원문 인용을 만들어 내지 마라.
> 14. 방문·연결·결과의 사실과 바라는 결과를 구별하라. 결과를 알 수 없으면 마지막으로 확인 가능한 지점에서 멈춰라.
>
> 분량 상한: 시나리오 1개, 방문 최대 16개, 이어짐 최대 20개. 전체 표 데이터 행은 최대 80개, 전체 응답은 12,000자 이내. 상한 때문에 빠지는 갈래·범위는 빈칸 표에 기록한다. 두 단계를 합치거나 중간 저장소를 없애서 상한을 맞추지 마라. 설명 셀은 가급적 100자 이내. 정확 인용은 240자 이내의 연속 발췌로 적는다. 짧게 자르면 뜻이 달라지는 인용은 요약으로 바꾸지 말고 자료 위치와 누락 사유를 남긴다.
>
> **① 기준과 목적** — 시나리오 ID | 이름 | 관련 요청 ID 또는 원문 위치 | ID 대장 판본 | 설계 판본 | 현황 기준 시각 | 종류 | 실행 ID·실행 범위 또는 모름 | 선택 이유 | 근거 E
>
> **② 시작** — 시작 ID | 촉발 사건 | 시작 대상 P/O/S | 시작 조건 원문·Q 참조 | 필요한 이전 상태 | 이 촉발이 다른 동작과 독립적인지 | 근거 E
>
> **③ 방문** — 방문 V | 부분 P | 단계 S 또는 모름 | 포트 O 또는 모름 | 필요한 입력 A | 이 방문이 내놓는 출력 A | 관측 실행일 때 사건 식별자 | 근거 E
> 행 순서는 보기 위한 순서다. 실행 순서는 다음 표에 근거가 있는 이어짐으로만 표현한다. 부분만 확인되면 단계·포트를 추정하지 마라.
>
> **④ 이어짐** — 이어짐 L | 출발 V | 도착 V | 기존 연결 R | 뜻: next/branch/parallel/loop/wait | 조건 원문·Q 참조 | 반복 단위·합류 정책·재개 사건 중 해당 내용 | 근거 E
> 기존 연결 R이 없거나 이어짐의 근거가 없으면 이 표에 쓰지 말고 빈칸 표에 적어라. 설명용 투어의 읽기 순서는 '투어 읽기 순서'라고 따로 표시하며 실행 연결 R을 요구하거나 새로 만들지 않는다.
>
> **⑤ 끝** — 끝 ID | 도달 방문 V 또는 모름 | 설계가 내놓는 결과 | 바라는 결과·요청 참조 | 이탈·거절·중단 결과 | 마지막 확인 지점 | 두 결과의 차이·미정 | 근거 E
> 설계가 내놓는 결과, 바라는 결과, 실제 관측 결과를 서로 복사하지 마라. 경로가 중간에서 끊겼으면 끝까지 도달했다고 쓰지 마라.
>
> **⑥ 근거와 빈칸**
> 근거: E | 뒷받침하는 행·열 | 제공된 자료 종류: 파일/실행/보고 | 원문 자료·위치 | 판본·실행 ID | 정확 인용 또는 원문 미제공 | 명시적 내용/보고자 추정
> 외부↔내부 대응(확인된 것만): 대응 ID | 외부 연결 R | 경계 포트 O | 내부 단계 S | 들어감/나감 | 근거 E
> 빈칸·충돌·상한으로 생략한 범위: G | 관련 P/O/S/R/V/Q | 모르는 내용 또는 충돌 | 관련 원문·E | 이유: 미언급/자료없음/대장없음/충돌/분량상한 | 확인하려면 필요한 자료
>
> ID 대장 자체가 없으면 P/O/S/R/A/F/Q를 새로 만들지 마라. 첫째 표에 대장 미제공을 적고 여섯째 표에 필요한 대응을 남겨라. 완결 경로 대신 정확한 부분 경로를 반환하라.

### 8.3 계약 (map-reading.7 위에)

**영속 ID 대장.** 영속 ID는 앱이 발급·보관하고, AI는 기존 ID 참조 또는 신규 대상 후보(+기존 대상과의 대응 근거)만 반환한다. 대장에는 ID / 대상 종류 / 소속 ID / 이름 이력 / 최초 근거 / 명시적 원천 ID / 변경·분할 이력만 둔다. 과거 역할 설명과 추정 경로를 현재 사실처럼 프롬프트에 다시 넣지 않는다. 정규화(공백·유니코드)는 후보 검색용일 뿐이며 정규화 이름의 해시를 ID로 쓰지 않는다.
| 상황 | 처리 |
| --- | --- |
| 같은 입력·같은 추출 작업 재실행 | 저장된 원천 대응으로 기존 ID 재사용 |
| 보고서에 기존 ID가 명시됨 | 프로젝트·대장 판본·종류·소속 검사 후 재사용 |
| '기존 X를 Y로 개명'이 명시됨 | ID 유지, 이름 이력 추가 |
| 이름만 같거나 유사함 | 동일성 후보일 뿐, 자동 병합 금지 |
| 후보가 둘 이상 | 상위 범위·종류·원문 식별자 비교; 여전히 모호하면 `대응 미정`, 기존 ID 배정 안 함 |
| 기존 ID 하나가 두 대상에 배정됨 | 충돌한 대응 모두 보류(먼저 나온 것을 채택하지 않음) |
| 이번 기록에 옛 대상이 안 나옴 | 삭제·폐기·철회로 해석하지 않음(이번 자료에서 미언급) |
| 같은 단계의 내부를 상세화 | 책임이 유지되면 기존 ID 아래 하위 단계 ID |
| 한 대상을 실제로 둘로 분할 | 새 ID 둘 + `splitFrom`; 옛 ID는 역사에 보존 |
| 둘이 하나로 합쳐짐 | 새 ID + `mergedFrom`; 과거 참조 일괄 치환 금지 |
| 같은 대상의 값·설명 변경 | ID 유지, 주장 판본과 근거 변경 |
| 관계의 끝점이나 의미가 달라짐 | 새 관계 ID; 명시된 경우 대체 이력 |

S04가 S17·S18로 분할되면: 이전 판본의 S04와 그것을 참조하는 시나리오는 보존, 현재 판본에는 `S04 → S17·S18 분할 · 방문 대응 미해결`. 분할 사실만으로 V03을 둘로 늘리거나 S17→S18 순서를 만들지 않는다. 새 기록이 대응과 순서를 명시할 때만 새 시나리오 판본.

**추가 칸.**
- 요소 P: `type`(10 유형 + `unknown`; 이름으로 추정하지 않음), `ports[]`(O: id, declaredName|null, displayName, direction, artifact ref), `steps[]`(S: id, name, does, uses[] — 단계별 근거), `config[]`(값·단위·적용 범위·판본·설계/보고 성격 분리), `loop{unit, stop, resume}|null`(각각 독립 주장; 없으면 미상), `state[]`(유지 상태: 이름·소유 범위·읽는 단계·바꾸는 단계, 기록된 것만), `files[]`(경로·판본·대응 근거)
- 산출물 A: `kind: store|format`, `fields[]`(F: 존재·선언 타입·관측값·필수 구별), `where`. producer/readers는 저장하지 않고 관계에서 계산
- 연결 R: 양 끝 `{part|port|step}` 참조, `kind: data|control|uses`(불명확하면 보류), `payload`(A ref), `trigger`(촉발·소비 조건), `cadence`, `mode`. 내부 단계 간 선후·분기·반복도 R. `via`는 없다(경유 저장소는 실제 P 보관소로; 미상이면 미상)
- 시나리오 C: `kind: designed|observed|tour`, `request`, `version`, `asOf`, `trigger`, `visits[]`(V: part, step|null, port|null, in[], out[], event), `links[]`(L: from, to, relation R, kind: next|branch|parallel|loop|wait, condition, policy), `end{produced, desired, exits[], lastConfirmed, gap}`, 근거는 방문·이어짐·조건·결과마다
- 규칙 Q: `scopeRef`, `anchors[]`(명시 vs 근거 있는 해석), `enforcedBy[]`(비어 있음/장치 미상/기록상 미설계), 철회에 `kind: design|implementation|report`
- 외부↔내부 대응: `portMap[]`(R → O → S, 명시 대응만)
- 주장 공통: 대상 판본·대상 시각·작성 시각·원문 참조·해석 여부

"모두 선택 칸"은 다음으로 바꾼다: 확장 기능 자체는 생략할 수 있다. 그러나 객체가 존재하면 그 객체의 ID·종류별 필수 참조는 유효해야 한다. **생략 / 명시적 미상 / 알려진 빈 목록**을 구별한다.

**인용 앵커.** LLM에 문자 오프셋을 요구하지 않는다. 출력은 `sourceId + quote(짧은 축자 앵커, 권장 40–120자, 짧은 셀은 더 짧아도 됨; 떨어진 문장을 이어 붙이지 않음) + 선택적 위치 단서(표 이름·행의 첫 셀·열 이름·인접 문구)`. 앱이 현재 정규화 규칙으로 검색해 정확히 한 구간이 남을 때만 구간 ID를 부여한다. 복수 일치면 첫 번째를 고르지 않고 `ambiguousEvidence` 진단을 남기고 그 근거 연결을 제외한다(다른 유효 근거가 있으면 주장 유지, 없으면 주장도 제외). 위치 단서는 주장 근거를 대신하는 인용이 아니다.

**제외 단위**(모델 답은 보존, 채택 목록에서만 제외):
| 오류 | 제외 단위 | 남는 결과 |
| --- | --- | --- |
| 설정값·필드 타입 등 독립 주장 오류 | 해당 주장 | 나머지 정보 유지 |
| 단계의 정체성·소속 오류 | 해당 단계 | 그 단계를 참조하는 관계·대응·방문도 후속 제외 |
| 관계의 끝점·방향·필수 조건 오류 | 해당 관계 | 양 끝 대상 유지 |
| 방문의 part/step/port 참조 불일치 | 해당 방문과 그 방문에 붙은 이어짐 | 나머지 방문 유지, 끊긴 자리 표시 |
| 이어짐이 없는 R을 참조 | 해당 이어짐 | 두 방문 유지, 이어 그리지 않음 |
| 방문의 입력 주장 하나 오류 | 해당 입력 주장 | 방문 유지 |
| 앵커 하나 오류 | 해당 앵커 | 규칙은 `적용 위치 미해결` |
| enforcedBy 오류 | 해당 보장 관계 | 규칙·앵커 유지, 보장 위치 미확인 |
| portMap 한 대응 오류 | 대응 행 전체 | 경계에서 `내부 대응 미상` |
| 시나리오 식별 정보 오류 또는 유효 방문 0 | 시나리오 경로 전체 | 독립적으로 유효한 요구·결과 문장은 별도 주장으로 보존 |
| JSON 구문 자체가 깨짐 | 그 호출의 응답 전체 | 다른 호출 결과 유지; 잘린 JSON 복구 금지 |

핵심: V1→V2→V3에서 V2를 제외해도 V1→V3를 만들지 않고 번호를 당기지 않는다. plan이 놓친 대상을 뒤 단계가 발견하면 `unplannedEntity` 진단과 원문 위치를 남기고, 대장에 없는 대상을 몰래 추가하거나 다른 부분으로 대체하지 않는다.

### 8.4 파이프라인 단계와 예산
| 단계 | 누가 | 만드는 것 / 검사 |
| --- | --- | --- |
| 전처리 | 프로그램 | 자료 ID·구간 ID, 표 행 경계, 이전 ID 대장. 원문을 수정하지 않음. 기록 안의 지시문은 자료 |
| plan | AI | 부분·외부 접점·공유 데이터·외부 관계·규칙의 후보 + 원문 근거 + focus. 아직 채택 아님. 입력: 전체 원문 한 번 + 이전 지도의 P(ID·이름·상위 P·책임 한 줄·원문 식별 키; 알려진 옛 이름은 관련 후보에만) |
| render (부분별 한 호출, 유지) | AI | 그 부분의 유형·포트·단계·설정·반복·파일·유지 상태, 산출물·필드, 주장(≤6)·관계(≤16), **규칙의 지역 앵커**. 입력: 그 부분의 관련 원문 구간(연결 상대가 언급된 관계 행, 적용 규칙, 변경·철회·충돌 문구, 표는 헤더·행 제목 포함) + 압축 대장(그 부분의 S·O·Q·관련 A의 ID·이름·한 줄·원문 식별 키, 실제 연결 상대의 경계 포트만). 다른 부분의 내부 단계·과거 원문 전체는 넣지 않음. 단계·필드 같은 상세 배열은 별도 상세 출력 예산으로(주장 상한 우회 금지) |
| combine | 프로그램 (AI 없음) | 지역 ID → 영속 ID, 전역 참조·포함·소유 검사, 생산자·소비자 계산, 설계 스냅샷 확정. 유사 매칭으로 참조를 고치거나 빠진 연결을 추가하지 않음 |
| 시나리오 추출 | AI (별도 단계, 오케스트레이터 표가 있을 때) | 확정된 ID를 참조하는 방문·이어짐·portMap·여러 부분에 걸친 규칙 앵커의 통합. 존재·종류·판본·포트 대응·연결 방향 검사 |
| 게시 | 프로그램 | 유효 내용과 진단을 원자적으로 저장. 새 해석이 불완전해도 이전 유효 스냅샷과 원문 보존 |

여러 부분에 걸친 규칙은 같은 Q ID에 앵커를 합치고, 타 부분의 접점을 확정하지 못하면 그 앵커만 미해결로 남긴다.

**예산**($1 전부를 생성 파이프라인에; 심사는 별도 세션): 호출 전 예약제 — 기지출 + 진행 중 호출의 최대 예약 + 이번 호출의 최대액(입력 + 추론 포함 과금 출력 상한). 정상 경로 $0.85 이하, $0.15는 국소 보정. 초기 호출 한도: 입력 누계 32,000 토큰, 출력 누계 8,000 토큰(이것만으로 $1을 보장하지는 않음; 설정된 단가로 사전 계산). plan 직후 모든 부분의 필수 render를 예약한다. 집행 순서는 뼈대·부분 간 관계·필수 근거 → 내부 단계 → 상세 필드 → portMap → 시나리오. 생략 순서는 그 역순(시나리오 → portMap → 필드 → 단계). 부족한 작업은 호출하지 않고 `notProcessed: budget`으로 남기며, 이미 생성한 결과를 사후에 잘라 맞추지 않는다. 필드 생략이 타입 칩의 산출물 정체성까지 지우지 않고, 단계 생략이 경로를 직통선으로 바꾸지 않는다. 뼈대와 관계조차 예약할 수 없으면 계획 단계에서 예산 부족을 알리고 완성본을 내지 않는다. 근거·판본·모름·충돌 표시는 절감 대상이 아니다. 자동 재시도·모델 대체 없음.

## 9. 배치 엔진

1주기(포트·장부 노드·선 라벨)는 **손으로 짠 층 배치를 확장**한다. 2주기(중첩 프레임·계층 간 연결)에서 고정 시험 집합(KORU + 웹앱 + 배치 예제)으로 판정한다: 포트 오접속·노드 및 라벨 겹침·허용되지 않은 경계 침범은 0, 단순 선 교차는 별도 상한. 기준 미달일 때만 elkjs(ELK Layered + 직교, 버전 고정, Web Worker, public에 벤더링)를 검토하되 ELK도 같은 집합을 통과하는지 확인한 뒤 들인다. "중첩이 생겼다" 자체는 도입 조건이 아니다. 손 배치로 절대 불가능한 것은 없다; 커지는 것은 구현·유지 비용이다.

책임: 카드·문자·포트·칩 크기 측정 = 앱 / 층·중첩·경로 = 배치 엔진 / 고정 카드의 포트 위치 = 앱 계산(엔진이면 FIXED_POS) / 프레임의 포트 측면·순서 = 명시 순서(FIXED_ORDER) / 반복선 안쪽 여백·방문 배지·규칙 탭 = 앱 후처리 / 선택·시나리오 변경 = 기존 좌표 위 강조만 / 복귀 위치·사용자 배치 = 앱 저장·복원.

엔진이 할 일:
1. 유형별 카드 크기(접힌 높이 두 규격)와 포트 위치를 계산하고 선을 포트에서 포트로 긋는다. 포트에서 16px 직진 후 꺾음.
2. 장부 노드를 데이터 방향이 읽기 좋게 놓되 공유 저장소를 복제하지 않는다. 쓰기·읽기·기동 선을 구별.
3. 프레임의 안쪽 공간을 잡고 안의 행동을 배치하며 되돌아가는 선을 안쪽 변을 따라.
4. 시나리오 선택 시 기존 선의 강조와 방문 배지(접점 옆 20px, 8px 간격) 배치, 겹침 없이.
5. 내부 상세: 선택 요소를 작업면 중심에, 바깥 대상을 참조 카드로, 포트는 경계에.
6. 복귀 상태의 저장과 복원.
7. 결정적 배치: 입력에 그래프·표시 판본·측정 크기·포트 순서·엔진 버전·옵션·시드를 포함하고 입력 순서를 영속 ID로 정규화. **읽는 중에는 재배치하지 않는다** — 기존 화면은 저장된 좌표, 구조가 바뀐 새 스냅샷의 배치는 별도 계산.
8. 간격 단위 4/8/16/24/48px: 카드 내부 8–16, 같은 묶음 형제 ≥24, 묶음 경계 여유 24, 다른 묶음 ≥48, 선 라벨 통로는 별도 확보. 큰 흐름의 좌우 방향 유지, 3열 강제 금지. 정렬을 위해 공유 요소를 복제하지 않음.

## 10. 함정과 수용 기준

하지 않을 것:
1. **모든 것을 항상 펼치기.** 전경 시나리오 하나, 명시적 열기, 내부 상세는 별도 작업면.
2. **비슷한 선과 경계를 같은 뜻으로.** Dify의 실행 연결, Langflow의 타입 포트, Airflow의 의존, 서비스 맵의 관측 호출은 다른 관계다.
3. **AI가 그린 구체성을 확정 설계나 검증 결과로.** 원문에 없는 재시도·동기/비동기·타입·순서·종료 조건을 채우면 그림은 풍부해지고 근거는 약해진다. 제안 채택·구현 보고·검사 통과·실제 배포 동작은 다른 상태이며 하나의 초록 "완료"로 합치지 않는다.
4. **보고를 파일·실행 확인으로 승격**(출처 세탁).
5. **표기법 모양을 빌리면서 뜻을 바꾸고 설명하지 않기.** 작은 범례로 실제 쓰는 선·경계·표식만 설명한다.

수용 사례: KORU 외에 **웹앱(요청 시·사용자 행동 시·응답 뒤 비동기, 화면·진입점) / CLI(호출 한 번의 생애, 출력·오류·종료 코드, 재실행 조건) / 야간 배치(처리 대상 기간, 실행 식별자, 산출물 완결 범위, 예약·시작·완료·사용 가능)**와, 변형 사례로 이름 변경·실제 분할·동명 충돌·끊긴 시나리오 참조·복수 시점 보고·포트 초과. 수용 여부는 "완성된 그림인가"보다 **"없는 연결·상태·동일성을 만들어 내지 않았는가"**를 먼저 검사한다.

심사: 기존 20점표(항목 1–5)와 추가 항목 6–8은 문구·배점을 고정해 .25→.27 비교의 연속성을 지킨다. 설계 지형이 들어오는 주기부터 **설계 추출 심사**(10항목 × 0–2, 적용 항목 수 함께 보고, 환산·합산하지 않음)를 병행한다: 주장과 근거 대응 / 자료 성격과 상태 / 핵심 내용 보존 / 포트·산출물 계약 / 내부 동작 / 전달과 비동기 경계 / 시나리오의 인과와 실행 동일성 / 표지의 적용·보장 구별 / 참조·판본·정체성 / 빈칸·충돌·제외의 정직성. 심사자는 지도 평가 전에 원문에서 핵심 사실·관계·명시적 미정을 먼저 작성한 뒤 대조하고, 각 감점에 원문 위치와 출력 경로를 남긴다. **중대 오류**는 점수와 무관하게 불합격: 원문에 없는 동작·조건을 확정 설계로 표시 / 비동기 저장소나 독립 촉발을 없애 실행 인과 변경 / 서로 다른 실행을 한 관측 경로로 합침 / 요구·보고를 구현 완료나 검증 통과로 승격 / 잘못된 정체성 대응으로 다른 대상의 규칙·동작을 붙임. 합격선은 보정 뒤 정한다. 심사 결과로 지도를 자동 수정하거나 재호출하지 않는다.

## 11. 구현 순서 (한 주기에 하나)
