# 지도 표현 재설계 — 배치·선·카드·읽기면

> 2026-11-03 · 브랜치 `claude/compassionate-ritchie-or1h11` · 구현과 함께 쓴 설계 기록. 사용자 평가("선이 겹치고, 끌면 선이 튀고, 구성이 무엇을 보여주려는지 모르겠고, 읽기면의 근거·주장이 무슨 말인지 모르겠다")에서 시작했다.

이 문서는 코드가 지금 하는 일을 적는다. 값은 실제 화면에서 조정한 것이며, 더 바꾸면 여기와 `app/continuity/README.md`를 같이 고친다. 참고한 자료는 끝에 있다.

## 1. 무엇을 보여주려는가

지도 한 장이 먼저 답해야 하는 것은 셋이다.

1. **흐름이 어디서 어디로 가는가.** 부분들 사이의 넘겨줌(flow)과 필요로 함(needs)이 왼쪽에서 오른쪽으로 읽히고, 그 가운데 가장 긴 사슬(척추)이 한 줄로 놓인다. 척추의 선은 더 진하고 굵다.
2. **각 부분의 기록이 어디까지 왔는가.** 요청 → 보고 → 확인의 사다리. 보고는 확인이 아니다(주황 다음에 초록).
3. **무엇이 비어 있고 무엇이 미정인가.** 제목 아래 "정리 근거 · 빈틈"에서 이번 정리가 읽은 것과 빈틈을 연다.

관계가 없는 부분은 흐름 블록 옆이나 아래에 따로 놓여 흐름과 섞이지 않는다. 서로 다른 흐름 덩어리(연결 요소)는 위아래로 나뉘어 놓인다.

## 2. 배치 (`src/client/map-layout.ts`, `layoutScope`)

| 단계 | 규칙 |
| --- | --- |
| 층(layer) | 방향 있는 관계(flow·needs)만 층을 정한다. 화살표가 읽히는 방향 그대로 a → b이면 b가 오른쪽. `shares`·`related`는 층을 정하지 않고, 그런 관계로만 이어진 부분은 상대의 층(중앙값)에 들어간다. 방향 있는 관계가 하나도 없는 블록은 기록된 순서대로 층을 정한다(그렇지 않으면 한 열에 선이 위아래로만 오간다). |
| 블록 | 관계로 이어진 부분들이 한 블록. 큰 블록부터 위에서 아래로 쌓는다. |
| 층 안 순서 | 이웃 층의 짝이 놓인 자리의 평균(barycentre)으로 정렬, 오른쪽·왼쪽으로 4회 왕복. 같은 값이면 들어온 순서. |
| 척추 | 블록 안에서 flow(가중치 2)·needs(1)를 따라 가장 무거운 사슬. 블록 세로 중앙의 한 줄에 놓이고, 그 선은 `Edge.spine`으로 표시된다. 범위의 척추는 `ScopeLayout.spine`. |
| 높이 맞추기(levelling) | 각 부분을 다른 열의 이웃 중앙값 높이로 당기고, 척추 부분은 척추 줄에 고정한 뒤 열 안 순서와 간격을 지킨다(척추 부분을 축으로 위·아래로 밀어냄). 6회 왕복. 사람이 끌어 둔 위치는 그대로. |
| 그 밖 | 긴 층은 접어 여러 열로(wrap), 그룹 안 단순 사슬은 위에서 아래로, 목록 그룹, 바깥 짝(ghost) 배치, 그룹 사이 통로(FRAME_GUTTER)는 이전과 같다. |

## 3. 선 (`map-layout.ts` `edgePath`, `src/client/map-route.ts` `routeEdges`)

- **모든 선은 둥근 모서리의 직교선**이다. 기본 모양은 "옆면에서 나와 → 사이 통로 가운데의 세로 → 상대 옆면으로". 높이가 같으면 직선. 중간에 다른 상자가 있으면 이전처럼 통로·차선 탐색으로 돌아간다(가로지르지 않는다는 규칙은 그대로). 곡선은 없앴다: 끌 때 곡선과 직교선 사이를 오가며 튀던 원인이었다.
- **포트.** 한 옆면에 닿는 선이 여럿이면 상대 끝의 높이 순서로 옆면을 따라 펼친다(간격 12px, 최소 7px, 면 중앙 기준). 한 선이면 중앙.
- **나란히 놓기(nudging).** 같은 통로에 겹치는 세로 선분(또는 같은 높이의 가로 선분)은 9px 간격의 차선에 놓는다. 순서는 두 선분의 이음 선이 서로를 가로지르는 횟수가 적은 쪽(쌍별 비교를 여러 번 훑음). 차선은 그 선이 자기 끝이 아닌 상자에 닿지 않는 자리에서만 잡고, 통로가 좁으면(목록의 18px 열) 3px까지 줄인 뒤 그래도 없으면 그대로 둔다. 포트에 붙은 첫·끝 선분은 움직이지 않는다.
- **끌 때.** `quick` 모드: 포트에서 나온 기본 모양만(장애물 탐색 없음) 그려 손을 따라 연속으로 움직인다. 놓으면 전체 경로를 다시 잡고, 각 선은 끌던 모양에서 새 경로로 200ms 동안 보간(morph)한다(48점 표본).
- **종류별 표현.** 기록이 계획이라고 적은 관계(note에 계획·예정)는 가는 점선 2 5(`.edge.planned`)이며 선 설명에 "계획된 연결 · 아직 돌지 않음"이 붙는다. flow 실선 1.5px, 척추 2px 진한 색, needs 점선 6 4, shares 점선 1.5 4.5, related 점선 1 6 + 양끝 점, 접힌 그룹의 요약선은 3px 옅은 띠. 화살촉은 뒤가 파인 삼각형. 선택하면 그 부분의 선만 파란색이고 나머지는 .22로 물러난다.

검사: `tests/map-route.test.mjs`(포트 순서·간격, 나란히 놓기, quick의 연속성, OSS 사례 전부에서 가로지르지 않음과 공유 선분 없음), 기존 배치·경로 검사(`workspace58`, `polish67`, `context75`, `fix68`, `boundary83`, `ui62`)는 새 규칙에 맞춰 유지.

## 4. 카드와 영역 (`styles.css`, `app.ts` `renderSpace`)

- **사다리.** 카드 상태 줄의 점 대신 요청·보고·확인 세 칸(11×3px). 그 부분과 안쪽의 기록(요청·보고/답변·확인 자료)과 읽은 주장(want·reported·checked)으로 켠다. 색: 요청 회청, 보고 주황, 확인 초록, 없음 연회색. 조작법 창(?)에 범례가 있다.
- **영역 색.** 범위의 직접 자식 그룹마다 고정 색상환(파랑·청록·호박·보라·장미·초록)의 옅은 바탕과 테두리. 이름은 글자 회색을 유지한다.
- **배경.** 24px 점 격자, 점은 더 작고 옅게.

## 6. 지도의 내용: AI 배치와 역할 (`.11`·`.12`)

표현을 바꿔도 내용이 평평하면 지도는 읽히지 않는다. 같은 KORU 보고서를 기준으로 역할을 다시 나눴다(`server/map-blueprint.mjs`, `server/map-pipeline.mjs`).

| 단계 | 모델 | 맡는 것(바뀐 점) |
| --- | --- | --- |
| 추출 | DeepSeek, 구간마다 | 단서 찾기(그대로) |
| 설계 | gpt-6.1-sol | 부분을 기록 자신의 단위(구성 목록·층 번호·「A → B」)로 5~12개 자르기, 화살표 양 끝을 다른 부분에, 「X의 입력」은 X 옆에, 부모는 기록이 「A(B·C)」로 열거할 때만, 흐름 뼈대(「from → to: 넘기는 것」)와 정정·모름의 담당 부분(「→ ref」) 제안 |
| 작성 | gpt-6.1-terra, 3부분씩 | role에 입출력 이름, 상태 보고를 일정보다 먼저, 「예정」은 want, 직접 하지 않은 통과는 reported, [모름]은 「확인하지 못했다」로만, 부정 보존, 같은 원문 줄은 한 부분에만 |
| 전역 | gpt-6.1-terra | 뼈대를 원문으로 확인해 관계로(보고·제어 흐름 포함), note는 넘기는 것의 이름과 박자, 요약·후보·빈틈(빈틈은 원문 어디를 보면 되는지) |

블라인드 심사(opus, 기준표 5항목 20점): `.10` 9점 → `.11` 14~15점 → `.12` 17점 → `.13` 13점(중간 산출을 부분으로 세움, 되돌림) → `.14` 18점 → `.15` 17점(표본 흔들림) → `.17`(focus 400·global 32; `.16`은 240자 상한에 거절). 실행마다 자름이 달라 17~18 사이에서 흔들리며, 관계 상한 12가 다음 한계다. 실행마다 자름이 달라지므로(화면 실행은 최상위 5·안쪽 13, 직접 실행은 최상위 9·안쪽 3) 한 번의 점수로 판단하지 않는다.

## 7. 들어오는 기록의 질: 현황 보고 요청 문구 (`src/shared/report-ask.ts`)

지도의 질은 들어오는 기록이 구조와 상태를 얼마나 분명히 적었는지에 달려 있다. 그래서 사람이 자기 프로젝트를 보고 있는 AI 대화에 붙여 넣을 요청 문구를 앱이 준다(아무것도 보내지 않고 사람이 나른다).

| 문구 | 언제 | 요구하는 것 |
| --- | --- | --- |
| 현황 보고 요청(파일 접근형) | 처음 넣을 때, 빈 지도 카드·붙여넣기 칸 | 기준(날짜·sha·파일 접근 여부·대화 요약 여부) → 한 줄 요약 → 부분 표(이름·하는 일·파일·상태·근거, 「A 안에 B·C」) → 연결 「A → B: 넘기는 것 (언제)」에 [설계]/[관찰] 구분과 사람에게 가는 화살표 → 소유자 요청과 실제 변화 표 → 철회 표(옛 결정 → 지금 → 근거) → 요구사항 → 미해결 → 다음 관문 → 모르는 것 → 자신 없는 3가지. 문장마다 [파일]/[보고]/[실행]/[추정]/[모름]; 「통과」는 [실행]이 아니면 인용. 상한만 12,000자(하한은 지어내게 한다). 예시 값 없음(베낀다). |
| 파일을 못 보는 대화용 | 대화로만 아는 프로젝트 | 같은 차례, [대화]/[붙임]만 쓰고 [파일]·[실행] 금지, 「됐다」는 누가 말했는지 |
| 변경 보고 요청 | 지도가 생긴 뒤(돌아와 읽기 › 지도 정리) | 지도의 부분 이름을 그대로 쓰게 하고 부분마다 「상태 전→후 / 바뀐 것 없음 / 확인 못 함」, 새 부분·연결, 철회, 지난 빈틈·미정은 「여전히 모름」을 답으로 허용(콕 집어 물으면 답을 지어낸다) |

참고한 틀: ADR의 superseded, I-PASS의 조건부 계획과 되짚어 확인, SBAR의 사실과 평가 분리, C4의 사람 요소, Structurizr의 「a -> b "설명"」, ICD 203의 바탕 정보·가정·판단 구분, Anthropic의 "모른다고 말해도 된다". 다음 후보: 붙여 넣기 전 점검(꼬리표 없는 문장·[실행] 없는 통과·비밀값 패턴), 사람에게 묻는 세 질문(다음에 원하는 것·믿지 못하는 보고·직접 뒤집은 결정), 지도가 만든 "이렇게 이해했다" 5줄을 AI에 되돌려 틀린 줄만 고치게 하기.

## 8. 남은 것

- [보고]가 붙은 관측 결과(「아직 한 번도 보지 못함」 같은 부정 관측 포함)를 그 결과를 낸 부분의 reported로 옮기기; 계획된 지시는 아직 flow로 그려짐.

- 관계 행을 문장으로 읽기("시장 사실 수집이 이 부분에 달력을 넘겨줌").
- 확대 단계별 표시(semantic zoom)의 재정리: 0.5 미만에서 영역·요약선만.
- AI 배치·프롬프트에서 구조 자체(영역·안쪽 부분·흐름의 수)를 더 풍부하게 읽게 하는 일은 별도 주기.
