# 기록 요청 v4 — 기본 기록 하나, 고른 보충 표, 이어쓰기 (2026-11-04, 확정)

현황 기록 요청 v3와 설계 기록 요청 v1은 KORU 한 프로젝트(AI 세션·타이머·사람 승인이 도는 자동화)에 맞춰 다듬었다. 오픈소스 8개(nanoGPT · hyperfine · axios · umami · pocketbase · dagu · gpt-researcher · shapez)에서 같은 요청문으로 기록을 받아 보니, 요청문이 막은 곳 대부분은 종류와 상관없는 공통 결함이었다. 나머지는 종류마다 다른 「이 종류는 이걸 물어야 한다」였다.

이 문서는 같은 날 쓴 초안을 확정한 것이다. 확정에는 세 자료를 썼다.
- **초안**: 공통 핵심 + 프로필 절, 상태 네 칸, 원한 이 ↔ 구현한 이, `\|`, 14,000자.
- **적대 검토**: 고칠 것 12개. 그중 셋이 초안의 기둥을 흔들었다. 글자 한도 진단은 바이트로 센 값이었다. 「v3 호환」은 파서 정규식과 맞지 않았다. 프로필 덩이의 분량 계산이 틀렸다.
- **Astra 결정(GPT-6 Astra, A3)**: 요청 구조 (c), 상태 주장 표, 공통 표 넷과 안정 ID, 보충 표 목록 P1-01…P6-04, 지어내기 방지 문장 다섯, 틀린 것 세 가지.

결과는 이렇다. **요청은 하나다.** 현황과 설계가 공통 표를 함께 쓰고, 한 답에 두 덩이로 온다. 기록 세션은 보충 표를 모듈이 아니라 표 단위로 골라 쓴다. 넘친 것은 앱이 완료표를 읽고 이어쓰기 요청으로 만든다. 파서는 절 제목이 아니라 **고정 표 ID**로 표를 찾는다. 파이프라인은 하나로 유지한다.

## 1. 진단 — v3/v1이 종류를 넘어서 실패한 곳

표의 「보인 곳」에서 이름만 있는 것은 기록 세션의 마찰 메모이고, 「심사」가 붙은 것은 맹검 심사가 지도 손실로 확인한 것이다. umami·pocketbase·dagu는 r41 심사 파일이 없어서 마찰 메모만 근거로 삼았다.

### 1.1 말의 틀이 한 종류(상주 자동화)를 전제함

| 문제 | 무엇이 일어났나 | 보인 곳 |
| --- | --- | --- |
| **상태 단어 하나에 여러 축이 섞임** (돌고 있음/작업 중/미구현/멈춤/폐기/모름) | 라이브러리·CLI·스크립트는 부를 때만 돈다. 그래서 모듈 전부가 「돌고 있음 [추정]」이 됐고, 지도에서는 데몬처럼 읽혔다. 하고 싶던 말은 따로 있었다: 「1.21.0에 배포됨」, 「병합됐지만 미릴리스」, 「deprecated지만 동작」, 「옵션 뒤」, 「플랫폼 한정」, 「코드는 있으나 꺼짐」, 「폐기됐지만 보존용으로 쓸 수 있음」. 폐기를 「폐기」라고 쓰면 '쓰지 마'로 읽히고, 「멈춤」이라고 쓰면 '고장'으로 읽힌다 | 8개 모두. 심사 axios·gpt-researcher·hyperfine·shapez는 「코드 부분 전부 state=running, 데몬처럼 읽힘」을 정확성 감점으로 매김 |

| **「누가 정했나」가 지키는 장치로 읽힘** | 규칙 대부분이 코드 assert·bail!·검사인데, 결정자 칸에 사람 이름이 들어가자 .41의 사람 장치 패스(`programPerson`, map-reading.ts:978)가 「사람이 지킨다」로 저장했다 | nanoGPT, hyperfine, umami, shapez. 심사 hyperfine(s123·s125), nanoGPT(s184·s482·s483), axios(s361), gpt-researcher(s61) |

| **1절 요약에 모양이 없음** | 「한 줄 요약」이라서 무엇인지와 핵심 흐름 대신 계획이 섞였다. 지도 요약의 둘째 문장은 계획이나 추정을 골랐다 | 심사 5건 모두(멘탈 모델 3점 이하의 공통 감점) |

### 1.3 형식의 결함

| 문제 | 무엇이 일어났나 | 보인 곳 |
| --- | --- | --- |
| **칸 안의 `\|`** | 코드 조건의 `\|\|`, 꼬리표 안 명령(`git log --format='%h \| %s'`, `grep 'TODO\|FIXME'`)이 표를 깼다. 파이프라인은 `split('\|')`로 칸을 나누는데, 그 자리가 한 곳이 아니라 13곳이다(map-reading.ts 7곳, map-blueprint.mjs 5곳, pane-view.ts 1곳; 4.2). axios settle의 when이 「!response.status \」로 잘렸고, 4xx ERR_BAD_REQUEST 분기가 지도에서 사라졌다 | hyperfine, shapez. **심사 axios(규칙·조건 2점의 주된 원인)** |
| **12,000자 한도 — 사실은 바이트로 셈** | 세션들이 바이트를 글자로 알고 셌다. r41 기록 16개 중 10개(5개 저장소)가 **11,840~11,980바이트**에서 정확히 멈췄고, 실제 글자 수는 **8,686~9,694자**였다. 12,000자까지 2,300~3,300자가 남아 있었는데 「뒤 표부터 빼라」 규칙 때문에 신입에게 가장 쓸모 있는 파일 지도가 먼저 비었다(umami, shapez 6줄). 나머지 6개(pocketbase·dagu·shapez)는 11,277~11,961자로 실제로 한도에 닿았다. 초안의 「첫 판 15,000자(hyperfine, pocketbase), 22,600자(gpt-researcher)」도 바이트 값으로 보인다. hyperfine 15,000바이트는 약 11,100자라 12,000자 안이다. 줄마다 반복되는 경로 꼬리표만 약 1,500자였고(pocketbase), 현황 요청에는 경로 별칭이 없었다 | 8개 모두(검토 1의 재측정) |

### 1.5 진단의 결론

- 1.1과 1.3은 **어느 종류에서도 틀린 말의 틀**이다. 공통 핵심을 고친다. 상태는 구현 상태와 상태 주장으로 나누고, 변화의 사람은 역할로 쓰고, 정한 이와 지키는 장치를 나눈다. 관문은 0줄을 허용하고, 0절은 읽은 범위를 받는다. `|`는 한 형식으로 적게 하고 파서 한 곳에서 푼다. 글자 수는 앱이 센다. **한도는 올리지 않는다.** 바이트 착오를 고치면 기록당 실제 분량이 25~37% 는다.
- 1.2 가운데 **반복·조건·변형·진입점·조건부 연결·외부 계약·철회 방식·묶음 뜻·목록**은 모든 종류에 있다. 공통 표나 공통 열로 넣는다.
- **플래그·설정 우선순위·오류 코드 상세·공개 계약 상세·번들 배선·모양·프리셋·상태 기계·신호·작업 정책·재시도·자원 경계**는 종류에 따라 핵심이기도 하고 소음이기도 하다. 고를 수 있는 보충 표로 보낸다.

### 2.2 왜 한 요청에 두 덩이인가 (길이 근거)

- **한 덩이는 불가능하다.** r41에서 현황 + 설계가 18,065~23,908자였다(1.4). v4는 그보다 커진다. 덩이 1(지금 상태)은 현황 v3에 비해 늘고 준다. 유형 열 +~250, 행 ID +~150, C-STATUS +600~1,000, 연결의 조건·선택·경계 +~300, 변화의 역할·계약 변화·실린 판본 +~300, 철회 방식·규칙 장치 +~350, 완료표 +~300이 늘고, 기준 시각 열 −~500, 경로 별칭 −500~1,000이 준다. 그래서 약 10,200~14,100자다. 덩이 2(설계)는 설계 v1에서 1절 −1,077~1,666, C-LOOP·C-VARIANT·C-ENTRY·C-CONTRACT +~2,500, 소속 반복 열 +~250, 완료표 +~300이 바뀌어 보충 표 전에 약 11,000~13,800자다. 기본 덩이 하나(12,000)는 어느 저장소에서도 둘을 담지 못한다.
- **두 요청은 비싸다.** 사용자의 왕복이 둘이 된다(요청 붙여 넣기 2 + 답 붙여 넣기 2). 기준 줄·경로 약속·부분 이름 목록을 두 번 쓴다. 두 기록이 서로 다른 기준 sha를 읽을 위험도 생긴다.
- **한 요청 두 덩이면** 요청 붙여 넣기 1 + 답 붙여 넣기 1이다. 각 덩이가 `MAP_RECORD_CHARS`(12,000) 안이라 앱의 기존 기록 읽기가 덩이 하나를 자르지 않는다. 덩이 둘의 바이트는 2 × 12,000 × 1.20~1.39 = 28.8~33.4KB다. 조각(span) 오버헤드를 더해도 첫 지도의 `MAP_BYTES` 65,536 안에 들 것으로 본다. 확인은 검증의 측정 항목이다(5.3).
- **답 길이 한계**: 두 덩이는 한 답으로 약 18,000~24,000자다. 파일을 쓰는 세션은 문제가 없고, 대화 창은 잘릴 수 있다. 그래서 요청문은 「한 답에 다 못 쓰면 덩이 1 끝에서 멈추고 「이어서」를 받으면 덩이 2」라고 정한다. 사용자는 「이어서」 한 마디를 더 치고, 답 둘을 함께 붙여 넣으면 된다.
- **완성도**: 기본 덩이 둘만으로 첫 지도는 성립한다. 완료표가 남긴 범위는 이어쓰기로 채우는 선택이다. r41에서 바이트 착오와 「뒤 표부터 빼라」로 말없이 사라지던 것이 이제 완료표에 이름으로 남는다.

| C-STATUS 배포 | 배포됨 / 미배포 / 철회됨 / 모름 | 특정 환경에 특정 판본이 반영됐나. 판본 + 대상 환경 + 반영을 보여 주는 기록이나 명시적 보고가 필요하다. 배포 설정·스크립트가 있다는 것은 근거가 아니다. 보고만 있으면 [보고]이고 [실행]으로 올리지 않는다 |
| C-STATUS 활성 방식 | 항상 적용 / 조건부 / 비활성 / 모름 | 조건부·비활성이면 조건이나 꺼진 위치를 적용 범위에 글자 그대로 쓰고, 기본 설정에서 켜지는지도 쓴다 |
| C-STATUS 유지 방침 | 기능 개발 / 수정만 / 사용 중단 권고 / 유지 종료 / 모름 | 명시된 방침만 쓴다. 활동량으로 추정하지 않는다. 대체·후속은 값 뒤 「(후속: 이름)」 |
| C-STATUS 운영 상태 | 실행 중 / 유휴·대기 / 정지 / 실패 / 모름 | 특정 실행·서비스 인스턴스에 대한, 시점이 있는 주장이다. 보거나 보고받았을 때만 쓴다 |

- 미배포·미릴리스는 「확인 못함」이 아니다. 하지 않았다는 근거가 있을 때만 쓴다.
- 병합은 C-CHANGE에 쓰고, 미배포를 뜻하지 않는다.
- 기준 판본·작성 시각은 C-BASIS에 한 번 쓴다. C-STATUS의 「기준」 칸은 다른 판본·시각에 선 주장에만 쓰고, 같으면 —다.

ID는 그 기록 안에서만 뜻이 있다. 앱의 저장 ID나 시나리오 대장 ID가 아니다. 이어쓰기는 앞 덩이의 ID를 가리키고 새 번호를 이어 붙인다.

행 ID 열은 다른 표가 가리키는 공통 표(C-PART·C-STEP·C-LOOP·C-DATA·C-VARIANT·C-ENTRY·C-CONTRACT)와 모든 보충 표에만 둔다. 보충 표는 Astra대로 모두 「행 ID / 근거」로 끝난다. 아무도 가리키지 않는 공통 표(연결·변화·규칙 등)에도 붙이면 행마다 약 6자, 기록당 600~900자가 든다. 이어쓰기는 앞 행을 고치지 않고 덧붙이기만 하므로, 그 표들은 행 ID 없이도 겹치지 않는다.

## 3. 요청문 전문

### 3.1 기본 기록 요청 v4 (붙여 넣는 글 그대로)

앱이 복사할 때 `{기록 ID}` 두 곳을 새 ID(`AF4-` + 16진 8자)로 채운다. ID 없이 옮겨진 글이면 세션이 그 자리를 그대로 두고, 앱이 붙여 넣을 때 ID를 준다.

```text
[AgentFlow 기록 요청 v4]
이 프로젝트를 처음 보는 사람이 이어서 일할 수 있게, 지금 상태와 설계를 코드·문서·기록에서 읽어 아래 표로 써 줘. 표는 마크다운이다(머리 줄 다음에 |---| 줄). 표마다 제목 줄 「표 ID 제목」(예: 「C-PART 부분」)을 쓰고 바로 아래에 머리 줄을 글자 그대로 쓴다. 표 ID가 앱이 표를 찾는 열쇠다. 바꾸거나 새로 만들지 마.

덩이와 분량
- 기본 기록은 두 덩이다. 덩이 1은 C-BASIS부터 C-DOUBT까지, 덩이 2는 C-DATA부터 C-FILES까지와 고른 보충 표. 덩이마다 첫 줄은 「〔기록 {기록 ID} · 덩이 n · 기준 sha〕 프로젝트 이름 기록 v4 (쓴 세션, 날짜·시각)」, 둘째 줄은 「경로 약속:」 줄(두 덩이에 같게), 마지막은 C-DONE 완료표.
- 덩이 1과 2를 한 답에 차례로 써. 한 답에 다 못 쓰면 덩이 1 끝에서 멈추고 마지막 줄에 「덩이 2는 「이어서」에」라고 써. 「이어서」를 받으면 덩이 2를 쓴다.
- 덩이마다 약 9,000자를 목표로 하고 12,000자를 넘기지 마. 바이트가 아니라 글자 수다(셀 수 있으면 LC_ALL=C.UTF-8 wc -m 파일, 또는 PowerShell (Get-Content -Raw -Encoding UTF8 파일).Length. 바이트밖에 못 세면 바이트÷1.3). 정확한 수는 앱이 센다.
- 넘칠 것 같으면 덜 중요한 행부터 덜어 내되 말없이 빼지 마. 덜어 낸 표는 C-DONE에 「일부 작성」이나 「분량상 이월」로 적고 남은 범위를 쓴다. 앱이 그 범위로 이어쓰기 요청을 만든다. C-SUMMARY와 C-FILES는 끝까지 남겨.
- 짧아도 된다. 빈 칸이 꾸민 칸보다 낫다.

공통 규칙
- 근거: 표마다 마지막 열 「근거」에 하나, C-SUMMARY는 문장마다. [파일: 경로] 이번에 직접 읽은 파일 / [보고: 출처·날짜] 다른 세션·문서·사람·커밋·PR·이슈의 말 / [실행: 명령] 이 대화에서 직접 돌린 것과 결과 / [추정] 네 판단 / [모름]. ‘통과·OK·완료’는 [실행]이 아니면 인용이다. 여러 작업 세션을 감독하는 세션이면 각 세션의 말은 [보고: 세션 이름 문서 시각]. 이 기록을 쓰려고 코드를 고치거나 검사·프로그램을 새로 돌리지 마(읽기 명령만).
- 칸 값의 모름은 대괄호 없이 「모름」이고 [모름]은 근거 꼬리표다. 「없음」은 찾아봤더니 없다는 뜻이고, 「해당 없음」은 그 질문이 그 대상에 성립하지 않는다는 뜻이다.
- 행이 하나도 없는 표: 찾아봤더니 없으면 제목 아래 머리 줄 대신 「없음: 확인한 범위 [근거]」 한 줄. 질문이 이 프로젝트에 성립하지 않으면 표를 쓰지 말고 C-DONE에 「해당 없음」. 확인하지 못했으면 C-DONE에 「확인 못함」.
- 칸 안의 | 글자는 &#124;로 쓴다(||는 &#124;&#124;). 코드 식은 그렇게 적힌 그대로 두고, 말로 풀 때만 「또는」「그리고」. 칸 안에 줄바꿈이나 긴 코드 전문을 넣지 마.
- 이름: 열 이름이 「부분」으로 끝나는 칸에는 C-PART의 이름을 글자 그대로, 「ID」로 끝나는 칸에는 ID를 쓴다. 프로젝트 전체에 걸린 줄은 「전체」. 여러 값은 「·」로 잇는다(「+」로 잇게 한 칸만 「+」).
- ID: 부분 B01…(C-PART 행 ID), 단계 B03:S01…(그 부분 안에서 실행 순서대로. 둘 중 하나만 도는 갈래는 B03:S04a·B03:S04b), 반복 B03:L01…, 산출물 D01…, 변형 X01…, 진입 N01…, 외부 계약 K01…, 보충 표의 행은 「표 ID.번호」(P4-01.2). ID는 이 기록 안에서만 뜻이 있고, 한 번 쓴 ID를 다른 것에 다시 쓰지 마.
- 경로: 「경로 약속:」의 별칭으로 써도 된다([파일: 별칭], 별칭/하위 경로). 형식은 「경로 약속: @기준 sha · 별칭 = 경로 · 별칭 = 경로」, 별칭은 로마자 1~4자.
- 키·토큰·비밀번호·접속 주소의 비밀 부분·경로 속 사용자 이름은 [가림]. .env 같은 비밀 파일은 열지 마. 이 요청문은 옮기지 말고 기록 밖의 말은 쓰지 마.

지어내지 마
- 확인하지 못한 값은 모름으로 적어라. 없음, 미구현, 미배포는 부재를 확인한 범위와 근거가 있을 때만 사용하라.
- 파일·함수·변수 이름은 동작의 증거가 아니다. 연결·실행 순서·조건은 실제 호출, 등록, 분기 또는 이를 명시한 기록으로 확인하라. 확인되지 않은 관계를 그럴듯하게 연결하지 마라.
- 소스에 구현이 있음, 시험을 통과함, 릴리스됨, 특정 환경에 배포됨, 현재 실행 중임을 별개의 주장으로 작성하라. 한 주장의 근거를 다른 주장에 재사용하려면 그 사실도 실제로 증명하는지 확인하라.
- 기본값·우선순위·반복 횟수·배타성·재시도·보안 보장을 관례로 채우지 마라. 확인한 식과 조건을 그대로 기록하고, 미확정 부분을 표시하라.
- 표를 채우기 위해 예시·권고·계획을 구현 사실로 바꾸지 마라. 분량 때문에 생략한 내용은 완료표에 남겨라. 해당 없음은 빈칸을 없애기 위한 값이 아니다.

덩이 1 — 지금 상태

C-BASIS 기준
| 날짜·시각 | 브랜치·커밋 sha·판본 | 읽은 범위 |
한 줄, 칸마다 꼬리표. 읽은 범위는 무엇을 읽었고 무엇을 못 읽었나(클론 깊이, 빠진 폴더, 실행 여부. 대화가 요약된 세션이면 그것도).
표 아래 한 줄: 「이번 기록의 초점: P?, P? / 선택 이유 / 작성한 보충 표 ID」. 이 프로젝트를 이해하려면 아래 여섯 질문 묶음 가운데 무엇을 먼저 더 물어야 하는지다. 프로젝트의 분류가 아니다. 1~3개, 범위가 다르면 범위를 괄호로. 근거가 모자라면 「초점: 없음 / 이유」.

C-SUMMARY 요약
두 문장, 문장마다 꼬리표: 무엇이고 누가 어떻게 쓰나 / 핵심 흐름 한 줄. 계획·추정은 C-GATE·C-DOUBT에.

C-PART 부분
| 이름 | 유형 | 하는 일 한 줄 | 담당 파일·폴더 | 구현 상태 | 행 ID | 근거 |
이름은 프로젝트가 부르는 그대로. 파일 하나하나가 아니라 맡은 일 단위로 5~30개(목록 한 줄은 하나로 센다). 결정하거나 일하는 사람(소유자·메인테이너·기여자)·봇·CI·외부 시스템·설계만 있는 것·제거된 것도 넣어. 남의 코드가 부르는 라이브러리·SDK면 「사용자 코드」도 한 줄(구체 소비자를 확인 못했으면 하는 일에 「구체 대상 모름」).
유형 하나: 사람 / 세션 / 루프·엔진 / 행 파일·저장소 / AI 판단 / 타이머·일정 / 계산 / 수집기 / 집행·외부 호출 / 화면 / 빌드·배포 자동화 / 외부 시스템 / 모름. 이름이 아니라 하는 일로 고른다. 진입점·어댑터·확장 지점·계약·신호는 유형이 아니라 C-ENTRY·C-VARIANT·C-CONTRACT와 보충 표에 쓴다. 자료형·오류 객체·메시지는 부분이 아니라 C-DATA·C-CONTRACT에 둔다(따로 맡은 일이 있을 때만 부분).
구현 상태 하나: 구현됨(이 판본에 구현이 있음. 작동·시험 통과의 뜻은 없음) / 일부 구현 / 미구현 / 제거됨 / 모름 / 해당 없음(사람·봇·외부). 릴리스·배포·활성·유지·운영은 C-STATUS에.
같은 일을 하는 항목의 목록은 한 줄로 두고 하는 일 끝에 「항목 N · 순서 있음」 또는 「항목 N · 순서 없음」(정확히 셌을 때만 N, 아니면 「항목 여럿」). 항목 이름은 C-GROUP에 두고, 따로 연결을 가진 항목만 자기 행을 갖는다.

C-GROUP 묶음
| 부모 이름 | 자식 이름들 | 묶음 뜻 | 근거 |
자식은 「·」로 잇는다. 묶음 뜻 하나: 실행 위치(어디서 도나) / 구성(무엇의 일부) / 참여자(밖에서 판단·입력을 주는 사람·봇) / 외부 / 목록(목록 줄의 항목. 순서 있는 목록은 순서대로) / 모름. 실행 위치 묶음의 부모는 C-PART에 없는 이름이어도 된다. 한 부분의 부모는 하나(목록은 빼고 센다): 실행 위치를 바깥에, 구성을 안쪽에 둔다.

C-LINK 연결
| 보내는 부분 | 받는 부분 | 넘기는 것 | 박자 | 조건·선택 | 경계 | 설계/관찰 | 근거 |
한 줄에 화살표 하나. 목록의 항목이 보내거나 받으면 「목록 이름: 항목」. 넘기는 것은 C-DATA에 행이 있으면 앞에 그 ID(「D03 …」), 통로가 있으면 그다음에 「통로: …」. 박자 하나에 글자를 붙일 수 있다: 한 번 / 호출마다 / 항목마다 / 주기 / 사건 때 / 끝에 한 번(「주기: 간격 그대로」). 조건·선택: 늘 흐르면 —, 조건이 있을 때만 흐르면 그 조건을 글자 그대로, 고른 변형일 때만 흐르면 「변형 X02」. 경계 하나: 같은 프로세스 / 자식 프로세스 / 프로세스 사이 / 네트워크 / 사람 / 모름. 설계는 코드·문서상의 흐름, 관찰은 실제로 돈 것을 본 경우이고 둘이 다르면 두 줄. 사람·사용자 코드가 부르거나 지시하는 화살표와, 결과가 그쪽으로 돌아가는 화살표도 넣어.

C-CHANGE 최근 변화
| 날짜 | 관련 주체·역할 | 원한 것 | 바뀐 부분 | 실제로 바뀐 것 | 계약 변화 | 실린 판본 | 근거 |
새것부터 15줄까지. 봇의 의존성 갱신이나 같은 종류의 잔수정은 한 줄에 묶고 개수를 쓴다. 실은 기간은 C-DONE 수록 범위에. 날짜는 작성일과 병합일이 다르면 「작성 / 병합」.
관련 주체·역할: 「역할: 주체」를 「+」로 잇는다. 역할은 요청 / 제안 / 작성 / 검토·승인 / 병합, 주체는 소유자 / 메인테이너(계정) / 기여자(계정) / 봇(이름) / 이슈 #번호(작성자, 모르면 「작성자 모름」) / 모름. 「요청:」은 따로 적힌 요청(대화·이슈)이 있을 때만. PR 작성자가 스스로 낸 변화는 「작성: 그 사람」뿐이다.
원한 것: 요청 원문을 짧게 「」로. 따로 적힌 요청이 없으면 —(커밋·PR 제목을 옮기지 마).
계약 변화: —(외부 계약이 안 바뀜) / 깨짐: K ID 또는 무엇 / 호환: K ID 또는 무엇 / 모름. 깨짐은 깨짐 표시·BREAKING 문구·메이저 판본·제거된 인자·이주 안내 같은 근거가 있을 때만.
실린 판본: 그 변화가 실린 릴리스 / 미릴리스(마지막 릴리스 뒤라는 근거가 있을 때) / 모름.

C-WITHDRAW 철회·변경
| 부분 | 옛 결정 | 지금 | 방식 | 계약 변화 | 근거 |
철회·폐기·채택 안 함을 빠뜨리지 마. 방식 하나: 되돌림 / 제거 / 폐기 예정(경고 후 유지) / 옮김 / 기본값 바꿈 / 채택 안 함 / 다시 도입. 옛 동작을 지키는 장치(호환 스위치, 제거된 인자의 안내)가 있으면 지금 칸에. 계약 변화는 C-CHANGE와 같다.

C-RULE 지켜야 할 것과 하지 않기로 한 것
| 부분 | 규칙 한 줄 | 정한 이·언제 | 지키는 장치 | 장치 위치 | 근거 |
정한 이는 규칙을 정한 사람·문서(모르면 모름). 지키는 장치는 코드 / 검사(시험·CI) / 사람 / 없음 / 모름, 여럿이면 「+」로. 코드의 검사·assert가 막으면 정한 이가 사람이어도 장치는 코드다. 장치 위치는 파일·함수 또는 사람 이름(장치가 없음·모름이면 —). 믿지 않는 입력·권한·비밀을 지키는 규칙도 넣어.

C-STATUS 상태 주장
| 대상 | 상태 차원 | 값 | 적용 범위·조건 | 기준 | 근거 |
할 말이 있는 대상만, 8줄까지(넘치면 C-DONE에). 대상은 부분 이름·배포 단위(패키지·서비스)·「전체」. 차원마다 값 하나:
- 릴리스: 릴리스됨 / 미릴리스 / 회수됨 / 모름. 이용자에게 낸 판본·채널(적용 범위에 채널·판본).
- 배포: 배포됨 / 미배포 / 철회됨 / 모름. 특정 환경에 특정 판본이 반영됐나(적용 범위에 환경).
- 활성 방식: 항상 적용 / 조건부 / 비활성 / 모름. 조건부·비활성이면 켜지는 조건이나 꺼진 위치를 적용 범위에 글자 그대로(기본 설정에서 켜지는지도).
- 유지 방침: 기능 개발 / 수정만 / 사용 중단 권고 / 유지 종료 / 모름. 명시된 방침만(활동량으로 추정하지 마). 대체·후속이 있으면 값 뒤에 「(후속: 이름)」.
- 운영 상태: 실행 중 / 유휴·대기 / 정지 / 실패 / 모름. 특정 실행·서비스 인스턴스를 보거나 보고받았을 때만.
기준은 그 주장이 선 판본·sha·시각(C-BASIS와 같으면 —).
근거 규칙: 매니페스트의 판본은 선언된 판본만, Git 태그는 태그가 있다는 것만 증명한다. 릴리스 기록·배포된 패키지는 그 판본·채널의 릴리스 근거다. 배포됨에는 판본 + 대상 환경 + 반영을 보여 주는 기록이나 명시적 보고가 필요하다. 배포 설정·스크립트가 있다는 것은 배포 근거가 아니다. 보고만 있으면 [보고]로 두고 [실행]으로 올리지 마. 병합은 C-CHANGE에 쓰고, 미배포를 뜻하지 않는다.

덩이 2 — 설계

C-DATA 산출물
| 이름 | 종류 | 필드·모양 | 만드는 부분 | 읽는 부분 | 있는 곳·쓰기 방식 | 행 ID | 근거 |
부분 사이를 오가는 자료·파일·테이블·메시지마다 한 줄. 종류 하나: 외부 계약(명세는 C-CONTRACT에 쓰고 여기는 이름과 K ID) / 내부 자료 / 저장(파일·테이블) / 메시지·신호. 필드·모양은 코드의 이름 그대로. 필드 없는 배열은 형식·모양·크기, 넓은 테이블은 키 필드 몇 개와 「그 밖 N개」. 만드는·읽는 부분은 직접 만들고 직접 읽는 부분만(지나가게만 하는 부분은 빼). 있는 곳은 경로(파일이 아니면 메모리·DB 이름). 쓰기 방식은 확인했을 때만 괄호로: 덧붙임 / 통째 교체 / 원자 교체(어디까지가 한 번에 바뀌나).

C-DESIGN 부분별 설계

C-STEP 안의 단계
| 단계 이름 | 하는 일 한 줄 | 쓰는 파일·함수 | 소속 반복 ID | 조건·분기 | 행 ID | 근거 |
지도의 중심인 부분 3~8개를 골라 그 부분의 단계를 실행 순서대로 쓴다(부분당 16줄까지. 넘으면 하위 부분으로 나누거나 남은 단계를 C-DONE에). 한 줄에 한 단계. 코드에 없는 단계를 지어내거나 두 단계를 한 줄로 합치지 마.
- 소속 반복 ID는 그 단계가 도는 가장 안쪽 반복(C-LOOP)이고 반복 밖이면 —. 두 반복이 같은 단계를 부르면 그 단계는 한 번만 쓰고 두 반복 ID를 「+」로.
- 조건·분기: 갈리거나 멈추는 조건과 결과를 「→ S06」, 거부 사유 코드 그대로, 되돌아가면 「→ S02, 최대 3번」으로. 없으면 —.
- 쓰는 파일·함수에 AI 모델이나 학습 대상 모델이 있으면 그 이름 앞에 「모델:」.
- 순서 있는 목록이 20개를 넘으면 단계로 펼치지 말고 C-GROUP의 목록으로.

C-LOOP 반복
| 소유 부분 | 부모 반복 ID | 몸통 단계 ID | 반복 단위 | 횟수·계속 조건 | 종료·탈출 조건 | 행 ID | 근거 |
코드에 반복문·재귀·주기 실행이 있는 것만. 부모 반복 ID는 바로 바깥 반복(다른 부분의 반복이어도 된다), 없으면 —. 몸통 단계 ID는 반복마다 도는 단계(「B03:S04–S06」). 한 번만 도는 준비·마무리는 몸통에 넣지 마. 반복 단위는 무엇마다 도나. 횟수·계속 조건은 확인한 식 그대로(값을 읽지 않았으면 숫자로 계산해 넣지 마).

C-COND 조건·거부·분기
| 부분 | 조건 | 참이면 | 거짓이면 | 갈리는 때 | 근거 |
한 줄에 조건 하나. 조건은 코드의 식을 적힌 그대로(길면 뜻이 바뀌지 않게 줄여). 참이면·거짓이면은 결과·사유 코드·가는 곳이고, 다음 검사로 넘어가면 「다음」. 갈래가 셋 이상이면 갈래마다 한 줄. 갈리는 때 하나: 실행 시 / 설정 읽을 때 / 빌드·컴파일 시. 프로그램 전체를 바꾸는 모드 스위치도 여기에.

C-VARIANT 변형
| 공통 계약·접점 ID | 구현 부분 | 선택 주체·시점 | 선택 조건 | 함께 사용 가능 여부 | 행 ID | 근거 |
같은 계약·접점의 여러 구현(어댑터·드라이버·실행 전략·플랫폼 구현·저장 백엔드·실행 모드)마다 한 줄. 공통 계약·접점 ID는 K ID, 부분 안의 자리면 「B03: 자리 이름」(P2-02를 쓴 경우에만 그 행 ID). 사용자가 바꿔 끼우는 자리면 구현 부분이 「사용자 지정」인 줄. 선택 주체·시점은 누가(사용자 설정 / 코드 / 플랫폼·빌드), 어떻게(지정 / 우선순위로 첫 가능 항목 / 실패하면 다음), 언제(빌드 시 / 시작 시 / 호출마다). 함께 사용 가능 여부: 배타 / 병용 가능 / 모름, 범위를 괄호로(「배타(호출마다)」).

C-ENTRY 진입·소비
| 진입점 | 소유 부분 | 소비자·호출 주체 | 호출 방식 | 계약 ID | 행 ID | 근거 |
프로그램이 시작되거나 불리는 곳마다 한 줄(많으면 기능 묶음마다 한 줄에 정확히 센 개수). 소비자·호출 주체: 사람 / 사용자 코드 / 외부 시스템 / 일정 / 다른 부분 이름. 호출 방식 하나: 명령 / 함수·클래스 호출 / HTTP·WS 요청 / 메시지·사건 / 일정 / 상주(시작 후 계속 돎) / 손으로 돌리는 스크립트. 사람이 차례로 돌리는 스크립트면 진입점 앞에 순서(「1) 」). 계약 ID는 C-CONTRACT 행, 없으면 —.

C-CONTRACT 외부 계약
| 제공 부분 | 외부 소비자 | 접점·방향 | 자료·응답·종료·오류 명세 | 적용 판본 | 행 ID | 근거 |
그 부분·패키지 경계 바깥(사용자 코드·사람·다른 프로그램)이 의존하는 약속만: 공개 함수·명령의 입출력, 파일·응답 형식, 종료 코드·오류 코드, 프로토콜. 바뀌면 소비자가 깨지는 것이다. 내부 구조체를 공개 계약으로 올리지 마. 구체 소비자를 확인 못했으면 「사용자 코드—구체 대상 모름」. 적용 판본은 형식·스키마 판본이 있을 때만, 없으면 —.

C-FILES 파일 지도
| 경로 | 속한 부분 | 역할 한 줄 | 근거 |
폴더 단위로 써도 된다. 생성물·시험·문서·예제는 한 줄씩 묶는다. 실행 때 생기는 디스크 배치는 경로 끝에 「(실행 시)」. 읽지 않은 것은 역할 끝에 「(이번에 안 읽음)」과 [모름].

보충 표 — 고른 것만
공통 표만으로 설명이 모자란 곳의 표만 고른다. 초점 밖의 표도 고를 수 있고, 한 묶음의 표를 다 쓸 필요는 없다. 덩이 2의 C-FILES 다음에, 자리가 남는 만큼 중요한 표부터 쓰고 나머지는 C-DONE에 「분량상 이월」. 행 상한은 한 덩이에 싣는 상한이다. 머리 줄은 아래 열 목록 뒤에 「행 ID | 근거」를 붙인 것이다(「| 열 | … | 행 ID | 근거 |」). 첫 열이 그 표가 처음 정하는 것의 ID면 그 행의 행 ID를 그대로 쓰고, 다른 표의 것을 가리키면 그 ID를 쓴다(사슬 ID는 그 사슬 첫 행의 행 ID).
정확히 센 목록만 「총 N개」라고 쓴다. 「개수 + 처음·끝」은 같은 모양의 반복 자료에만 쓰고, 중간의 분기·권한 검사·오류 처리·우선순위 예외를 감추는 압축에는 쓰지 마. 싣지 못한 목록은 총수·고른 기준·나머지 위치를 남긴다.
흔히 놓치는 것도 해당 표에 쓴다: 앱 수명(전경·배경·복귀)·권한·오프라인, 실행 문맥 사이의 메시지, 인터럽트·시간 제한, 패키지 경계·릴리스 단위, 트랜잭션·격리·내구성 시점, 중간 표현·증분 무효화, 전달·순서 보장·역압력, 계획과 적용의 차이.
```

### 3.2 이어쓰기 요청 v4 (앱이 만드는 글의 틀)

앱은 덩이마다 C-DONE을 읽고, 「일부 작성」·「분량상 이월」인 표와 초점 줄의 「작성한 보충 표 ID」에 있는데 어느 덩이에도 없는 표를 모아 아래 틀을 채운다. `{표마다 …}` 자리에는 기본 요청에서 그 표의 머리 줄과 설명을 그대로 옮긴다. 덩이 2가 통째로 없으면 「쓸 표」는 기본 요청의 덩이 2 전체(보충 표 목록 포함)다.

### 3.4 앱이 이어쓰기를 만드는 규칙

1. 같은 기록 ID의 덩이를 모아 C-DONE을 합친다. 같은 표가 여러 덩이에 있으면 마지막 덩이의 작성 상태가 이긴다.
2. 쓸 표는 「일부 작성」·「분량상 이월」인 표, 그리고 초점 줄이 적었는데 어느 덩이에도 없는 보충 표다. 「해당 없음」·「확인 못함」·「작성 완료」는 다시 청하지 않는다. 기본 표가 C-DONE에도 표로도 없으면 「C-DONE에 없음」으로 다시 청한다(표가 없다는 것만으로 해당 없음이 되지 않는다).
3. 「다음 ID」는 앞 덩이들에서 쓴 가장 큰 번호 + 1이다.
4. 이어쓰기는 덩이 3~5까지만 권한다. 그 뒤로 남은 범위는 지도 정리 칸의 「기록이 다 싣지 못한 범위」 줄로만 보인다.
5. 이어쓰기 답의 기준 sha가 다르거나 「기준 바뀜:」 줄이 있으면 그 덩이를 같은 기록으로 합치지 않고 새 기록으로 받는다(경고 줄과 함께).

## 4. 파서·계약 계획

### 4.1 붙여 넣기와 덩이

- **덩이 나누기**: 붙여 넣은 글에서 `^〔기록 (\S+) · 덩이 (\d+) · 기준 (\S+)〕` 줄마다 새 덩이를 시작한다. 덩이 하나가 기록(record) 하나다. `pasteRecord`(src/shared/domain.ts)를 부르기 전에 나눈다(app.ts:4049의 `texts`). 덩이 머리 줄이 없는 v4 글은 한 덩이로 받고 진단을 남긴다.
- **기록 메타**: 덩이마다 `{ recordId, chunk, basis }`를 기록에 저장한다. 같은 recordId의 덩이는 지도 정리에서 한 기록의 여러 구간처럼 함께 보인다. 지금처럼 `MAP_RECORDS`(4)·`MAP_RECORD_CHARS`(12,000) 안에서 첫 정리에 다 싣지 못한 덩이는 다음 정리에서 읽는다(`first-map-divided`의 남은 구간 규칙).
- **판 가리기**: 첫 줄에 「기록 v4」가 있거나 덩이 머리 줄이 있으면 v4다. 「현황 보고서 (v3 표 형식」이면 v3 현황, 첫 줄의 「설계 기록」이면 v1 설계다. **「경로 약속:」 줄로는 가리지 않는다**(report-ask.ts:287 `isDesignRecord`의 고침. v4에서는 모든 덩이에 그 줄이 있다).

### 4.2 표 읽기 기반 (V0)

**새 공용 모듈 `src/shared/record-table.ts`**(서버는 `dist/public/shared/record-table.js`로 가져온다)에 셋을 둔다.

1. **`splitCells(line, from)`** — 칸 나누기 하나. 지금 같은 일을 하는 13곳을 모두 이것으로 바꾼다.
   - map-reading.ts: `tableRows`(274), `lineSenders`(304), `artifactFiles`(322), `factRowNames`(342), `rowsUnder`(366), `lineCells`(845), `connectionLines`(895)
   - map-blueprint.mjs: `sectionRows`(269), `connectionRows`(286), `connectionPayloadRows`(302), `tableRowsUnder`(386), 1284
   - pane-view.ts:492
   
   규칙은 이렇다.
   - 앞뒤 바깥 `|`를 떼고, 역슬래시가 앞에 없는 `|`에서만 나눈다(`(?<!\\)\|`).
   - 칸마다 원문 위치 `[from, to)`를 돌려준다. 인용 검사와 조각 정렬은 이 원문 위치를 쓴다.
   - 비교용 글(`text`)에서만 `&#124;`와 `\|`를 `|`로 되돌린다. 되돌리기는 나눈 뒤 한 번만 한다(Astra).
   - 백틱은 보호하지 않는다(Astra). `` `a|b` ``도 나뉜다.
   - **v3 되살리기**: 칸 수가 머리 줄보다 많으면, 빈 칸을 사이에 둔 두 이웃(`a || b` → 「a」, 「」, 「b」)을 왼쪽부터 `||`로 다시 붙인다. 칸 수가 맞을 때까지 반복한다. 그래도 많으면 그 행은 데이터로 쓰지 않는다. 진단 `{ rule: 'contract', category: 'row-cells' }`를 남기고 원문은 인용 가능한 글로만 둔다. 홑 `|`(`'%h | %s'`)는 되살리지 않는다(뜻을 알 수 없다).
2. **`readRecordTables(text)`** — 기록 하나의 표를 표 ID로 돌려준다: `{ version: 'v4' | 'v3-status' | 'v1-design', chunk, tables: Map<ID, { title, header, columns, rows, none, extra }>, focus, aliases, diagnostics }`.
   - **v4 제목 줄**: `^(?:#{1,4}\s*)?(C-[A-Z]+|P[1-6]-0[1-9])\s+(.+)$`(표 줄이 아닌 줄). 다음 표 줄이 머리 줄이다. 머리 줄 대신 「없음:」 줄이면 `none: { text, quote }`.
   - **열 이름**: 3.5의 고정 머리 줄과 정규화(NFC, 공백·가운뎃점 변형)해서 맞춘다. 순서는 달라도 된다. 모르는 열은 `extra`에 원문 그대로 두고 진단 `unknown-column`을 남긴다. 빠진 열은 null과 진단 `missing-column`이다.
   - **모르는 표 ID**(C-FOO, P7-01)는 원문 표 그대로 `tables`에 두고 진단 `unknown-table`을 남긴다. 버리지 않는다(Astra).
   - **줄 모양**: 「이번 기록의 초점:」, 「경로 약속:」, 덩이 머리 줄, 「덩이 2는 「이어서」에」는 각자 읽는다. 표가 끝난 뒤의 평문 줄은 그 표를 닫는다(지금의 `rowsUnder`와 같다).
   - **v3 대응표**(제목 → ID, 앵커 단 정규식): 0 기준 → C-BASIS, `^(한\s*줄\s*)?요약` → C-SUMMARY, `^부분(\s*\(표\))?$` → C-PART, `^부분\s*유형` → C-PARTTYPE(v1 설계에만, C-PART의 유형으로 합쳐 읽음), `^묶음` → C-GROUP, `^연결` → C-LINK, `실제\s*(로\s*)?(바뀐|변화)` → C-CHANGE, `^철회` → C-WITHDRAW, `^지켜야\s*할` → C-RULE, `^오류\s*·\s*미해결` → C-ISSUE(검토 4의 앵커), `^다음\s*관문` → C-GATE, `^모르는\s*것` → C-UNKNOWN, `^가장\s*자신\s*없는` → C-DOUBT, `^산출물` → C-DATA, `^부분별\s*설계` → C-DESIGN, `^안의\s*단계` → C-STEP, `^조건\s*·\s*거부` → C-COND, `^파일\s*지도` → C-FILES.
   - **v3 열 대응**(정규식은 `^`로 앵커): 상태 단어 → legacyState, 상태의 기준 시각 → legacyStateAt, 언제·얼마나 자주 → 박자(글만, 종류 null), 누가 정했나·언제 → 정한 이·언제, 바뀐 부분 이름 → 바뀐 부분, 부분 이름 → 부분, 순번 → 순서, 쓰는 파일·함수·모델 → 쓰는 파일·함수, 꼬리표·확인 방법·근거·날짜 → 근거.
3. **`rowsOf(texts, id)`** — 모든 패스가 쓰는 하나의 입구. `rowsUnder(texts, TITLE)`·`sectionRows(ask, TITLE)`·`tableRowsUnder(ask, TITLE)`를 대신한다. 표마다 `{ record, from, to, cells, byColumn, header }`를 돌려준다. 패스는 이제 제목 정규식이 아니라 표 ID와 열 열쇠로 읽는다.

### 4.4 정리 AI(레시피 .43)의 규칙 변화

- **요약**: C-SUMMARY 두 문장(v3는 「1. 한 줄 요약」)이 1순위 원문이다. C-GATE·C-DOUBT·[추정] 줄로 요약 문장을 만들지 않는다. 초점 줄은 요약에 쓰지 않는다.
- **상태**: v4 기록에서 모델은 `state`를 정하지 않는다. 프로그램이 4.6대로 유도한다. 구현됨·릴리스됨·배포됨을 `running`으로 옮기지 않는다. status 주장은 C-STATUS 행과 C-GATE·C-CHANGE의 진행 보고에서만 나온다.
- **변화의 글**: change 주장의 글은 `actors`를 따른다. 「소유자의 「…」 요청에 따라」는 「요청: 소유자」일 때만 쓴다. 요청이 없으면 「…가 작성함(PR #)」처럼 요청이 없었다고 쓴다.
- **규칙**: v4의 `enforcedBy`는 표에서 오고 모델은 바꾸지 않는다(anchors만 더할 수 있음). 장치를 추론해 만들지 않는다.
- **유형 어휘**: 프롬프트의 유형 낱말 목록에 화면(`screen`)·빌드·배포 자동화(`automation`)를 더한다. 진입점·어댑터·신호는 유형이 아니라고 적는다.
- **표 이름**: 프롬프트가 부르는 표 이름을 표 ID로 바꾼다(괄호에 v3 이름). 예: 「C-RULE(v3: 지켜야 할 것)」, 「C-DESIGN(v3: 부분별 설계)」. 판본 낱말 규칙(map-pipeline.mjs:48)은 C-DESIGN·C-PART 칸에 그대로 적용한다.
- **보충 표**는 .43에서 주장의 출처가 되지 않는다. 원형 저장만 한다(.44에서 옮김).

| 기록 | 정한 이 | 지키는 장치 |

### 4.6 `PartState` 유도 (화면·옛 코드 호환)

v4 부분의 `state`는 프로그램만 정한다. 순서대로 처음 맞는 것을 쓴다.
1. C-STATUS 운영 상태: 실행 중 → `running`, 정지·실패 → `stopped`, 모름 → `unknown`. 유휴·대기는 `statusClaims`에만 두고 state는 정하지 않는다.
2. 구현 상태: 미구현 → `unbuilt`, 제거됨 → `retired`, 모름 → `unknown`.
3. 그 밖(구현됨·일부 구현·해당 없음, 릴리스·배포·활성·유지 주장만 있음) → `null`.

**`running`은 운영 상태 「실행 중」 주장에서만 나온다.** 「작업 중」(`working`)은 v4에서 유도하지 않는다. v3 기록은 상태 단어 그대로다(`STATE_SAID`, map-reading.ts:1049).

- **덩이마다**: 글자 수(JS 문자열 길이. 한글과 대부분의 코드 글자는 1)를 센다. 기본 덩이 12,000, 이어쓰기 8,000을 넘으면 「N자 넘음 — 앱은 처음 12,000자만 첫 정리에서 읽어요」를 띄운다. `REPORT_FIRST_CHARS`는 12,000 그대로다.

  - 덩이 머리 줄 없음 / 기록 ID·기준 sha가 덩이마다 다름

  - 초점 줄 없음

## 5. 검증 계획

### 5.1 기록을 다시 만든다

1. **같은 사본**: r41에 쓴 8개 저장소 사본(같은 sha, 같은 클론 깊이와 sparse 제외)을 쓴다. 기록 차이가 코드 차이에서 오지 않게 하기 위해서다.
2. **기록 세션 = 하위 에이전트**(저장소마다 하나, opus 5.5, high).
   - 세션에 주는 것: 저장소 경로, 앱의 요청 상수에서 뽑은 **기본 기록 요청 v4 글**(기록 ID를 채운 것), 「읽기 명령만, 실행 금지, 비밀 가림」.

3. **이어쓰기**: 세션의 답을 앱의 빌드된 코드(`readRecordTables` + 이어쓰기 만들기)에 넣는다. 이어쓰기 글이 나오면 **같은 하위 에이전트에게** 보낸다(SendMessage). 덩이 5까지다. 사람이 하는 일을 그대로 흉내 내며, 사람이 덩이를 고르거나 고치지 않는다.
4. 각 세션은 r41과 같은 형식의 메모(요청문 마찰 · 표현 제안)를 따로 남긴다.

요청문 자체의 성공 기준도 둔다.
- 기본 덩이가 12,000자를, 이어쓰기 덩이가 8,000자를 넘긴 기록이 없다(앱의 셈).
- C-FILES가 5줄 이하인 기록이 없다.
- 칸 깨짐 줄은 8개 합쳐 0이다.
- 기록 세션 메모의 「요청문 마찰」에서 1.1·1.3 항목이 다시 나오지 않는다. 새 마찰은 저장소당 3개 이하다.
- 저장소당 사용자 일이 「요청 붙여 넣기 1 + 답 붙여 넣기 1」에 이어쓰기 2쌍 이하다(덩이 2를 위한 「이어서」 한 번은 따로 센다).
- ASK-12(검증 저장소 낱말)가 통과한다.

이 기준을 넘지 못하는 항목은 문안을 다시 고친다. 한 번에 한 표만 고쳐 다시 잰다.
