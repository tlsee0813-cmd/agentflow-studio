# 기록 요청 v4 — 공통 핵심 + 프로필 절 (2026-11-04, 초안)

현황 기록 요청 v3와 설계 기록 요청 v1은 KORU 한 프로젝트(AI 세션·타이머·사람 승인이 도는 자동화)에 맞춰 다듬었다. 오픈소스 8개(nanoGPT · hyperfine · axios · umami · pocketbase · dagu · gpt-researcher · shapez)에서 같은 요청문으로 기록을 받아 보니, 요청문이 막은 곳 대부분은 종류와 상관없는 공통 결함이었다. 나머지는 종류마다 다른 "이 종류는 이걸 물어야 한다"였다. 이 문서는 둘을 나눈다. **공통 핵심은 고치고, 종류별 질문은 짧은 프로필 절로 붙인다.** 파이프라인은 하나로 유지한다.

읽은 자료:

- 맹검 심사 5건의 「기록 요청 보충 질문」과 점수 `scratchpad/runs/judge-{hyperfine,nanogpt,axios,gpt-researcher,shapez}-r41.md`
- 분류 연구 `scratchpad/research/gpt-pro-projecttypes.md` §3–§6
- 지도 설계 v3 §10(프로필), §2.3(묶음 축), §4.4(중첩 루프), §6.2(선 덧표식), §11 S10·S11

## 1. 진단 — v3/v1이 종류를 넘어서 실패한 곳

표의 「보인 곳」에서 이름만 있는 것은 기록 세션의 마찰 메모이고, 「심사」가 붙은 것은 맹검 심사가 지도 손실로 확인한 것이다.

### 1.1 말의 틀이 한 종류(상주 자동화)를 전제함

| 문제 | 무엇이 일어났나 | 보인 곳 |
| --- | --- | --- |
| **상태 단어 하나에 여러 축이 섞임** (돌고 있음/작업 중/미구현/멈춤/폐기/모름) | 라이브러리·CLI·스크립트는 부를 때만 돈다. 그래서 모듈 전부가 「돌고 있음 [추정]」이 됐고, 지도에서는 데몬처럼 읽혔다. 하고 싶던 말은 따로 있었다: 「1.21.0에 배포됨」, 「병합됐지만 미릴리스」, 「deprecated지만 동작」, 「옵션 뒤」, 「플랫폼 한정」, 「코드는 있으나 꺼짐(`&& false`)」, 「폐기됐지만 보존용으로 쓸 수 있음」. 폐기를 「폐기」라고 쓰면 '쓰지 마'로 읽히고, 「멈춤」이라고 쓰면 '고장'으로 읽힌다 | 8개 모두. 심사 axios·gpt-researcher·hyperfine·shapez는 「코드 부분 전부 state=running, 데몬처럼 읽힘」을 정확성 감점으로 매김 |
| **줄마다 붙는 「상태의 기준 시각」이 잡음** | 코드만 읽은 세션에서는 모든 줄이 HEAD 날짜나 오늘 날짜다. 「마지막 확인 시각」이 「마지막 수정일」로 바뀌어 쓰이기도 했다. 정말 쓸모 있는 값(판본·sha)은 둘 칸이 없었다 | hyperfine, axios, umami, pocketbase, nanoGPT. 심사 axios(「openspec state의 when은 확인일」) |
| **「최근 소유자 요청」이 OSS와 맞지 않음** | 기여자 PR이나 봇 PR, 이슈를 소유자 요청으로 옮겼다. 커밋 제목이 「원한 것」과 「바뀐 것」 두 칸에 똑같이 들어갔고, 요청자와 구현자, 작성일과 병합일을 구분할 칸이 없었다. 파이프라인은 이것을 「소유자의 「…」 요청에 따라」로 서술했다 | 8개 모두. 심사 5건 모두 정확성 감점(Devin AI 계정 PR #578 포함) |
| **「누가 정했나」가 지키는 장치로 읽힘** | 규칙 대부분이 코드 assert·bail!·검사인데, 결정자 칸에 사람 이름이 들어가자 .41의 사람 장치 패스(`programPerson`, map-reading.ts:975)가 「사람이 지킨다」로 저장했다 | nanoGPT, hyperfine, umami, shapez. 심사 hyperfine(s123·s125), nanoGPT(s184·s482·s483), axios(s361), gpt-researcher(s61) |
| **「다음 관문 2~5줄」 강제** | 로드맵 없는 OSS나 보존된 저장소에서 [추정] 줄을 지어내게 했다. 진짜 관문(열린 PR, 메이저 판본 경계, 막고 있는 외부 의존)은 담을 칸이 없었다 | 8개 모두 |
| **0절이 「대화하는 감독 세션」을 전제함** | 「앞부분이 요약됐는지」는 대화가 없는 세션에서 뜻이 없다. 필요했던 칸은 따로 있었다: 무엇을 읽었나(클론 깊이, sparse 제외, 실행 여부), 프로젝트 생애(활발/유지보수/보존/이관과 후속 저장소) | gpt-researcher, pocketbase, shapez, nanoGPT. 심사 shapez(「유지보수 종료·CE」가 요약에서 빠짐) |
| **1절 요약에 모양이 없음** | 「한 줄 요약」이라서 무엇인지와 핵심 흐름 대신 계획이 섞였다. 지도 요약의 둘째 문장은 계획이나 추정을 골랐다 | 심사 5건 모두(멘탈 모델 3점 이하의 공통 감점) |

### 1.3 형식의 결함

| 문제 | 무엇이 일어났나 | 보인 곳 |
| --- | --- | --- |
| **칸 안의 `\|`** | 코드 조건의 `\|\|`, 꼬리표 안 명령(`git log --format='%h \| %s'`, `grep 'TODO\|FIXME'`)이 표를 깼다. 파이프라인은 `split('\|')`로 칸을 나누므로(map-reading.ts의 행 읽기) 칸이 밀렸다. axios settle의 when이 「!response.status \」로 잘렸고, 4xx ERR_BAD_REQUEST 분기가 지도에서 사라졌다 | hyperfine, shapez. **심사 axios(규칙·조건 2점의 주된 원인)** |
| **12,000자 한도** | 첫 판이 15,000자(hyperfine, pocketbase), 22,600자(gpt-researcher)였다. 「뒤 표부터 빼라」 규칙 때문에 신입에게 가장 쓸모 있는 파일 지도가 먼저 비었다(umami, shapez 6줄). 줄마다 반복되는 경로 꼬리표만 약 1,500자였다(pocketbase). 현황 요청에는 경로 별칭이 없었다 | 8개 모두 |
| **글자 수 세는 법** | Git Bash의 `wc -m`가 바이트를 세서 지나치게 깎았다 | shapez |
| **5절 「최근」의 범위 없음** | 하루 20~30커밋 저장소에서 범위가 정해지지 않았다. dependabot 100건이 섞였다 | dagu, axios |

### 1.4 진단의 결론

- 1.1과 1.3은 **어느 종류에서도 틀린 말의 틀**이다. 공통 핵심을 고친다. 상태는 축으로 나누고, 요청자와 구현자를 짝으로 쓰고, 정한 이와 지키는 장치를 나누고, 관문은 0줄을 허용하고, 0절은 읽은 범위와 생애를 받고, `|`를 금지하고, 경로 별칭과 글자 수 세는 법을 정한다.
- 1.2 가운데 **반복·조건·변형·진입점·조건부 연결·외부 계약·철회 방식·묶음 뜻·유형**은 모든 종류에 있다. 공통 표의 열로 넣는다.
- **플래그·설정 우선순위·오류 코드·공개 API·번들 배선·실행 레시피·모양·프리셋 행렬·시계·목록·상태 기계·신호·저장 스키마·작업 생애·재시도·승인·모델 호출·자원·선언 대 관측**은 종류에 따라 핵심이기도 하고 소음이기도 하다. 프로필 절로 보낸다.

## 2. 원칙

1. **공통 핵심 + 프로필 절.** 현황 v4(0~11절)와 설계 v2 공통 절(0~8절)은 모든 프로젝트가 답한다. 프로필 절(설계 v2의 11~64절)은 여섯 프로필(설계 v3 §10: P1 요청·명령 처리, P2 계약·확장, P3 자료 변환·산출물, P4 상태·반응, P5 작업 실행·조정, P6 자원·배치·변경)에 하나씩 있고, 각 프로필은 3~6개의 짧은 표다. 사실 모델은 하나다. 프로필은 질문과 강조의 묶음일 뿐 다른 지도 문법이 아니다(연구 §3).
2. **프로필은 기록 작성 AI가 고른다. 사용자의 숙제가 아니다.** 0절의 「종류:」 줄에 1~2개를 쓰고, 이유 한 줄과 근거 꼬리표를 붙인다. 범위마다 다르면 범위를 단다(「P1 (전체) · P5 (스케줄러 묶음)」). 기술 이름(PyTorch, React)이 아니라 하는 일로 고른다(연구 §6.2). 근거가 모자라면 「종류: 공통」이고, 그때는 프로필 절이 없다. 고르지 않은 프로필의 절은 제목도 쓰지 않는다. 연구 §5.3이 경계한 「질문 66개」를 피하는 방법이 이것이다.
3. **「없음」과 「확인 못함」을 가른다.** 「없음」은 확인했더니 없다는 뜻이고 근거 꼬리표를 붙인다. 「[모름]」은 확인하지 못했다는 뜻이다(연구 §5.1). 파이프라인은 둘을 다른 값으로 저장한다(시나리오 기록의 `null` / `'unknown'`과 같은 구분).
4. **지어낸 줄은 없다.** 프로필 절은 그 종류에 흔한 것(재시도, 캐시, 상태 기계)을 묻지만, 코드에서 보지 못한 것은 줄을 만들지 않는다. 프로필을 먼저 고른 뒤 칸을 채우면 「원문에 없는 것은 그리지 않는다」가 깨진다(연구 §6.2). 그래서 요청문은 칸을 채우라고 하지 않고 「근거가 있는 줄만」이라고 쓴다. 하한도 예시 값도 두지 않는다(v3 규칙 유지).
5. **표를 지킨다.** 파이프라인은 절 제목(`^\d{1,2}\.\s*`)과 머리 줄의 열 이름(정규식)으로 표를 찾는다. 새 절도 모두 「번호. 제목」과 고정 머리 줄을 쓴다. 프로필 절 번호의 십의 자리는 프로필 번호다(11~14 = P1 … 61~64 = P6). 그래서 지금의 절 제목 인식(`^\d{1,2}\.`)이 그대로 읽는다.
6. **근거 꼬리표를 지킨다.** `[파일]` `[보고]` `[실행]` `[추정]` `[모름]`를 표 줄마다 하나씩 단다(v3 그대로). 현황에도 「경로 약속」 별칭을 허용해 꼬리표 길이를 줄인다.
7. **`|`는 칸 안에 쓰지 않는다.** 코드의 `||`는 「또는」, `&&`는 「그리고」로 바꾸고, 글자 그대로여야 할 때만 `\|`로 쓴다(GFM의 이스케이프). 파이프라인도 `\|`를 칸 구분자로 보지 않게 고친다(4.3). 요청문과 파서를 둘 다 고쳐야 옛 기록도 덜 깨진다.
8. **축을 섞지 않는다.** 상태는 배포 상태 / 활성 조건 / 유지 방침 / 운영 상태의 네 칸이다(설계 v3 §10.2 결정: 셋 + 운영). 규칙은 정한 이 / 지키는 장치 / 장치 위치다. 변화는 원한 이 ↔ 구현한 이다. 묶음은 묶음 뜻(실행 위치 / 구성 / 참여자 / 외부)으로 나눈다.
9. **분량은 상한만 두고, 무엇부터 빼는지 정한다.** 덜 중요한 단계와 조건부터 빼고, 파일 지도는 마지막까지 남긴다. 글자 수는 유니코드 글자로 센다.

## 3. 요청문 전문

### 3.1 현황 기록 요청 v4 (붙여 넣는 글 그대로)

```text
[AgentFlow 현황 기록 요청 v4]
이 프로젝트를 처음 보는 사람이 이어서 일할 수 있게 지금 상태를 아래 0~11절로 써 줘. 1절만 문장이고 나머지는 모두 마크다운 표다(머리 줄 다음에 |---| 줄). 절 제목·순서·열 이름은 아래 그대로 쓴다. 전체 14,000자(유니코드 글자 수, 바이트 아님)를 넘기지 마. 넘칠 것 같으면 덜 중요한 줄부터 빼고 맨 끝 「생략한 것: …」 한 줄에 적어(뺀 것이 없으면 「생략한 것: 없음」). 짧아도 된다. 빈 칸이 꾸민 칸보다 낫다.
첫 줄은 「프로젝트 이름 현황 보고서 (v4 표 형식, 쓴 세션, 기준 시각)」.

공통 규칙
- 근거 표시 — 표 줄마다 하나(꼬리표 칸이 있으면 그 칸에, 없으면 마지막 칸 끝에), 1절은 문장마다: [파일: 경로] 지금 직접 읽은 파일 / [보고: 출처·날짜] 다른 세션·문서·사람·커밋·PR의 말을 옮김 / [실행: 명령] 네가 이 대화에서 직접 돌린 것과 그 결과 / [추정] 네 판단 / [모름]. ‘통과·OK·완료’는 [실행]이 아니면 모두 인용이다. 여러 작업 세션을 감독하는 세션이면 각 세션의 말은 [보고: 세션 이름 문서 시각]으로.
- 「없음」은 확인했더니 없다는 뜻이고 꼬리표를 붙인다. 확인하지 못했으면 [모름]. 흔히 있을 법한 것을 짐작으로 채우지 마.
- 칸 안에 | 를 쓰지 마. 코드의 ||는 「또는」, &&는 「그리고」로 바꾸고, 글자 그대로여야 하면 \| 로. 꼬리표 안의 명령도 같다.
- 「부분 이름」 칸에는 2절의 이름을 그대로. 프로젝트 전체에 걸린 줄은 「전체」.
- 경로는 0절 「경로 약속」의 별칭으로 써도 된다([파일: 별칭], 별칭/하위 경로).

0. 기준
| 오늘 날짜·시각 | 브랜치·커밋 sha·판본 | 읽은 범위 | 대화 앞부분 요약 | 프로젝트 생애 |
한 줄, 칸마다 꼬리표. 읽은 범위는 무엇을 읽고 무엇을 못 읽었나(클론 깊이, 빠진 폴더, 실행했는지). 대화 앞부분 요약은 이 대화의 앞부분이 요약됐는지, 대화가 없으면 「해당 없음」. 프로젝트 생애는 활발 / 유지보수 / 보존(쓸 수는 있음) / 이관(후속 이름) / 모름.
표 아래 두 줄:
「종류: P번호 이름 (· P번호 이름) — 이유 한 줄 [꼬리표]」 — 아래 여섯 가운데 이 프로젝트를 이해하는 중심 1~2개. 범위마다 다르면 「P1 (전체) · P5 (스케줄러 묶음)」처럼. 기술 이름이 아니라 하는 일로 골라. 근거가 모자라면 「종류: 공통 — 이유」.
P1 요청·명령 처리(무엇이 시작시키고 어떤 결과·실패로 끝나나: CLI, 웹 API, 백엔드) / P2 계약·확장(무엇을 제공하고 사용자는 무엇을 지키며 어디를 확장하나: 라이브러리, SDK, 플러그인) / P3 자료 변환·산출물(입력이 어떤 산출물로 바뀌나: 데이터·ML, 컴파일러, 변환 도구) / P4 상태·반응(누가 상태를 갖고 사건·시간에 따라 무엇이 바뀌나: 게임, UI, 앱) / P5 작업 실행·조정(누가 작업을 배정하고 무엇을 기다리고 언제 재시도·종료하나: 에이전트, 자동화, 스케줄러) / P6 자원·배치·변경(무엇을 어디에 두고 어떤 선언·절차로 바꾸나: 인프라, 배포 도구).
「경로 약속: 별칭 = 경로 · 별칭 = 경로 …」(쓰지 않으면 「경로 약속: 없음」).
1. 요약
두 문장: 무엇이고 누가 어떻게 쓰나, 그리고 핵심 흐름 한 줄. 계획·추정은 9·11절에.
2. 부분
| 이름 | 하는 일 한 줄 | 담당 파일·폴더 | 배포 상태 | 활성 조건 | 유지 방침 | 운영 상태 | 꼬리표 |
이름은 프로젝트가 부르는 그대로. 파일 하나하나가 아니라 맡은 일 단위로 5~30개(묶음의 자식 포함). 사람(소유자·메인테이너·기여자)·봇·CI·외부 시스템·설계만 있는 것·폐기된 것도 넣어. 같은 일을 하는 목록(플러그인 21종, 시스템 24개)은 한 줄로 두고 하는 일 끝에 「항목 N · 순서 있음」 또는 「항목 N · 순서 없음」.
상태는 네 칸에 따로 쓴다. 기준은 0절의 sha·시각 하나이고, 다른 때 확인한 칸만 칸 끝에 (그 시각).
- 배포 상태: 배포됨(판본; 판본이 없으면 지금 쓰는 판에 들어 있다는 뜻) / 병합됨·미배포 / 작업 중 / 설계만 / 제거됨 / 모름
- 활성 조건: 기본 / 켜지는 조건을 글자 그대로(옵션·설정·환경변수·플랫폼·빌드 변형) / 꺼짐(코드는 있음, 위치) / 모름
- 유지 방침: — / 폐기 예정(대체) / 보존(쓸 수는 있음) / 실험·예제 / 모름
- 운영 상태: 돌고 있음 / 멈춤 / 상주 아님(부를 때만 돎) / 확인 못함. 돌고 있음·멈춤은 실제로 돈 것을 보거나 보고받았을 때만.
3. 묶음
| 부모 이름 | 자식 이름들 | 묶음 뜻 |
자식은 「·」로 잇는다. 묶음 뜻은 실행 위치(어디서 도나) / 구성(무엇의 일부) / 참여자(밖에서 판단·입력을 주는 사람·봇) / 외부 / 모름. 실행 위치 묶음의 부모는 2절에 없는 이름이어도 된다. 한 부분의 부모는 하나: 실행 위치를 바깥에, 구성을 안쪽에 둔다. 설계만·폐기를 묶음으로 만들지 말고 원래 묶음에 둔 채 2절 상태 칸으로 적어. 마지막 줄은 「그 밖 | 없음 | —」(묶음이 하나도 없으면 그 줄만).
4. 연결
| 보내는 부분 | 받는 부분 | 넘기는 것 | 박자 | 조건·선택 | 경계 | 설계/관찰 | 꼬리표 |
한 줄에 화살표 하나(받는 쪽이 여럿이고 넘기는 것이 같으면 받는 부분을 「·」로 이어 한 줄). 넘기는 것에 통로가 있으면 앞에 쓴다(「POST /api/send: 이벤트」). 박자는 한 번 / 항목마다 / 주기 / 사건 때 / 끝에 한 번 중 하나 뒤에 글자를 붙인다(「주기: 5분」, 「항목마다: 명령마다」). 조건·선택은 있을 때만 흐르면 그 조건을 글자 그대로, 늘 흐르면 —, 여럿 중 하나만 흐르면 「택1: 묶음 이름 · 조건」. 경계는 같은 프로세스 / 자식 프로세스 / 프로세스 사이(파일·소켓) / 네트워크 / 사람 / 모름. 설계는 코드·문서상의 흐름, 관찰은 실제로 돈 것을 본 경우이고, 둘이 다르면 두 줄. 사용자 코드·사람이 부르거나 지시하는 화살표, 결과가 사람·사용자 코드에 돌아가는 화살표도 넣어.
5. 최근 변화
| 날짜 | 원한 이 | 원한 것 | 구현한 이 | 바뀐 부분 이름 | 실제로 바뀐 것 | 깨짐 | 확인 방법 |
새것부터 15줄까지. 날짜는 작성일과 병합일이 다르면 「작성/병합」. 원한 이는 소유자 / 메인테이너 / 기여자(계정) / 이슈 #번호(작성자) / 봇(이름) / 모름. 원한 것은 요청 원문(대화·이슈)을 짧게 「」로. 따로 적힌 요청이 없으면 —(커밋 제목을 원한 것에 옮기지 마). 구현한 이는 이름과 PR·커밋. 깨짐은 깨짐(사용자 쪽 호환이 깨짐) / — / 모름. 봇의 의존성 갱신은 한 줄로 묶어. 확인 방법 칸에 꼬리표.
6. 철회·변경
| 부분 이름 | 옛 결정 | 지금 | 방식 | 깨짐 | 근거·날짜 |
철회·폐기·채택 안 함을 빠뜨리지 마. 방식은 되돌림 / 제거 / 폐기 예정(경고 후 유지) / 옮김 / 기본값 바꿈 / 채택 안 함 / 다시 도입. 옛 동작을 지키는 장치(호환 스위치, 제거된 인자의 안내)가 있으면 지금 칸에.
7. 지켜야 할 것과 하지 않기로 한 것
| 부분 이름 | 규칙 한 줄 | 정한 이·언제 | 지키는 장치 | 장치 위치 |
정한 이는 규칙을 정한 사람·문서(모르면 [모름]). 지키는 장치는 코드 / 검사·CI / 사람 / 없음 / 모름. 코드의 assert·검사가 막으면 정한 이가 사람이어도 장치는 코드다. 장치 위치는 파일·함수, 또는 사람 이름. 믿지 않는 입력·권한·비밀을 지키는 규칙도 넣어.
8. 오류·미해결·할 일
| 부분 이름 | 무엇이 | 언제부터·근거 |
저장소에 평문 비밀이 있으면 그 위치만 적어(값은 [가림]).
9. 다음 관문
| 부분 이름 | 무엇이 확인되면 | 무엇을 한다 | 막고 있는 것 | 언제쯤 |
0~5줄. 관문이 없으면(보존된 저장소 등) 표 대신 「관문 없음: 이유 [꼬리표]」 한 줄.
10. 모르는 것
| 부분 이름 | 무엇을 | 어떻게 확인할 수 있나 |
11. 가장 자신 없는 것
| 부분 이름 | 내용 |
1~3줄.

키·토큰·비밀번호·접속 주소의 비밀 부분·경로 속 사용자 이름은 [가림]으로 바꿔. .env 같은 비밀 파일은 열지 마. 이 요청문은 옮기지 말고 보고서 밖의 말은 쓰지 마.
```

문구 길이는 4,098자다(v3 1,595자). 늘어난 몫의 대부분은 상태 네 칸의 낱말 목록과 프로필 여섯 줄이다. 둘 다 예시 값이 아니라 고를 수 있는 낱말이라서 베껴질 위험이 없다.

### 3.2 설계 기록 요청 v2 (붙여 넣는 글 그대로)

```text
[AgentFlow 설계 기록 요청 v2]
이 프로젝트의 설계를 코드·스키마·설정에서 읽어 아래 표로 써 줘. 현황 보고를 다시 요약하지 마: 상태·이력·철회·관문은 현황 보고의 몫이고, 여기는 무엇이 무엇을 받아 어떤 단계로 무엇을 내는지만 쓴다. 표는 마크다운(머리 줄 다음에 |---| 줄), 절 제목·순서·열 이름은 아래 그대로.
구성: 공통 절 0~8은 모두 쓴다. 프로필 절(11~64)은 0절 「종류」에서 고른 프로필의 절만 쓰고, 고르지 않은 프로필의 절은 제목도 쓰지 마.
분량: 한 덩이 14,000자(유니코드 글자 수, 바이트 아님) 이하. 넘칠 것 같으면 두 덩이로 나눠: 첫째는 0~8절, 둘째는 첫 줄 「프로젝트 이름 설계 기록 v2 이어서」와 0절 다음 프로필 절(8,000자 이하). 그래도 넘치면 4절의 덜 중요한 부분, 5절의 덜 중요한 조건, 2절 필드의 꼬리 순으로 빼(8절 파일 지도와 6·7절은 마지막까지 남겨). 덩이마다 맨 끝에 「생략한 것: …」 한 줄(없으면 「생략한 것: 없음」). 짧아도 된다.
첫 줄은 「프로젝트 이름 설계 기록 v2 (쓴 세션, 날짜·시각; 코드를 어떻게 읽었는지)」.

공통 규칙
- 근거 표시 — 표 줄마다 하나(꼬리표 칸에): [파일: 경로] 이번에 직접 읽은 코드·스키마·설정 / [보고: 출처·날짜] 다른 세션·문서의 말 / [실행: 명령] 이 대화에서 직접 돌린 읽기 명령 / [추정] 네 판단 / [모름]. 코드를 읽지 않은 칸·줄은 [모름]. 이 기록을 쓰려고 코드를 고치거나 검사·프로그램을 새로 돌리지 마(읽기 명령만).
- 「없음」은 확인했더니 없다, [모름]은 확인하지 못했다는 뜻이다. 이 종류의 프로그램에 흔한 것(재시도, 캐시, 상태 기계…)이라도 코드에서 보지 못했으면 줄을 만들지 마.
- 칸 안에 | 를 쓰지 마: ||는 「또는」, &&는 「그리고」, 글자 그대로여야 하면 \|.
- 부분 이름은 현황 보고의 이름 그대로(현황 보고가 없으면 프로젝트가 부르는 그대로). 코드의 이름은 코드에 적힌 그대로.
- 여러 값은 「·」로 잇고 하위 필드의 괄호는 그대로 둔다. 한 칸에 넘치면 다음 줄에 「이름(이어서)」. 다 옮기지 못했으면 끝에 「…」.

0. 기준
| 날짜·시각 | 읽은 브랜치·커밋 sha·판본 | 읽은 범위 |
한 줄. 표 아래 두 줄:
「종류: P번호 이름 (· P번호 이름) — 이유 한 줄 [꼬리표]」 — 현황 보고와 같게(P1 요청·명령 처리 / P2 계약·확장 / P3 자료 변환·산출물 / P4 상태·반응 / P5 작업 실행·조정 / P6 자원·배치·변경 중 1~2개, 범위가 다르면 범위를 괄호로). 현황 보고와 다르게 골랐으면 이유를 덧붙여. 근거가 모자라면 「종류: 공통」이고 프로필 절은 없다.
「경로 약속: 별칭 = 경로 · …」 — 자주 쓰는 파일·폴더의 짧은 별칭. 특정 커밋·브랜치를 읽었으면 경로 앞에 함께. 표에서는 별칭으로 쓴다.
1. 부분 유형
| 이름 | 유형 | 한 줄 |
유형은 하나만: 사람 / 세션 / 루프·엔진 / 행 파일·저장소 / AI 판단 / 타이머·일정 / 계산 / 수집기 / 외부 시스템 / 진입점 / 화면 / 확장 지점 / 상태 기계 / 관문 / 빌드·배포 자동화. 이름이 아니라 하는 일로 고르고(이름이 Agent·timer여도), 맞는 것이 없으면 [모름]. 한 줄 끝에 꼬리표.
2. 산출물
| 이름 | 종류 | 필드·모양 | 만드는 부분 | 읽는 부분 | 있는 곳·쓰기 방식 | 꼬리표 |
부분 사이를 오가는 자료·파일·테이블·메시지마다 한 줄. 종류는 외부 계약(바뀌면 사용자가 깨짐; 판본을 함께) / 내부 자료 / 저장(파일·테이블) / 메시지·신호. 필드·모양은 코드의 이름 그대로. 필드가 없는 배열은 dtype·모양·크기, 넓은 테이블은 키 필드 몇 개와 「그 밖 N개」. 만드는 부분·읽는 부분은 직접 만들고 직접 읽는 부분만(지나가게만 하는 부분은 빼). 있는 곳은 경로(파일이 아니면 메모리·프로세스 경계·DB 이름), 쓰기 방식(덧붙임 / 통째 교체 / 원자 교체)이 있으면 뒤에 괄호로.
3. 부분별 설계
| 이름 | 받는 산출물 | 안의 단계 | 내는 산출물 | 설정 | 꼬리표 |
받는·내는 산출물은 2절의 이름 그대로. 안의 단계는 4절에 줄이 있으면 「4절」, 짧으면 「→」로 이은 한 줄, 읽지 못했으면 [모름]. 설정은 동작을 바꾸는 것 6개까지 「키=값」을 「,」로 잇는다(더 있으면 프로필 절의 설정 표에 두고 「설정 표」). 커밋 sha·판본은 설정이 아니다.
4. 안의 단계
| 부분 이름 | 순번 | 단계 이름 | 하는 일 한 줄 | 쓰는 파일·함수 | 어느 반복 안 | 반복 단위 | 횟수·멈춤 | 조건·분기 | 꼬리표 |
지도의 중심인 부분 3~8개를 골라 그 부분의 단계를 빠짐없이 실행 순서대로 쓴다(순번 1부터). 한 줄에 한 단계. 코드에 없는 단계를 지어내거나 두 단계를 한 줄로 합치지 마. 읽지 않은 단계는 [모름].
- 반복을 여는 단계에는 반복 단위(무엇마다: 명령마다·iter마다·프레임마다)와 횟수·멈춤(「×식」, 「멈춤: 조건」, 둘 다면 「·」로)을 쓴다. 그 반복 안에서 도는 단계는 어느 반복 안에 반복을 연 단계의 순번을 쓴다(중첩이면 가장 가까운 바깥). 반복 밖에서 한 번 도는 단계는 세 칸 모두 —.
- 반복이 아니라 감싸는 단계(훅·미들웨어·트랜잭션) 안이면 어느 반복 안에 「순번 감쌈」.
- 둘 중 하나만 도는 단계는 순번에 a·b를 붙인다(4a, 4b).
- 조건·분기에는 그 단계에서 갈리거나 멈추는 조건과 결과를 쓴다: 가는 순번(「→ 6」), 거부 사유 코드 그대로, 되돌아가면 「→ 2, 최대 3번」. 없으면 —.
- 쓰는 파일·함수에 학습 대상 모델이나 AI 모델이 있으면 그 이름 앞에 「모델:」.
- 순서 있는 목록(시스템·미들웨어 목록 등)이 20개를 넘으면 단계로 펼치지 말고 프로필 절의 목록 표에 둔다.
5. 조건·거부·분기
| 부분 이름 | 조건 | 참이면 | 거짓이면 | 갈리는 때 | 꼬리표 |
한 줄에 조건 하나. 조건은 코드의 식·조건문을 적힌 그대로(길면 뜻이 바뀌지 않게 줄여). 참이면·거짓이면은 결과·사유 코드·가는 곳이고, 다음 검사로 넘어가면 「다음」. 갈래가 셋 이상이면 갈래마다 한 줄. 갈리는 때는 실행 시 / 설정 읽을 때 / 빌드·컴파일 시. 프로그램 전체의 동작을 바꾸는 모드 스위치도 여기에 쓴다.
6. 변형
| 인터페이스·자리 | 변형 | 고르는 조건 | 배타 | 되는 것·안 되는 것 | 꼬리표 |
같은 인터페이스의 여러 구현(어댑터·드라이버·실행 전략·플랫폼 구현·저장 백엔드·실행 모드)마다 한 줄. 인터페이스·자리는 1절의 부분 이름(그 부분 안의 자리면 「부분 이름: 자리」). 배타는 하나만 / 차례로 시도(앞이 안 되면 다음) / 여럿 함께 / 모름. 사용자가 바꿔 끼울 수 있으면 변형 칸이 「사용자 지정」인 줄. 변형이 없으면 「없음」 한 줄.
7. 진입점과 소비자
| 진입점 | 종류 | 누가 부르나 | 받는 부분 | 돌려주는 것 | 꼬리표 |
프로그램이 시작되거나 불리는 곳마다 한 줄. 종류는 명령 / 공개 함수·클래스 / HTTP·WS 경로 / 메시지·사건 / 일정 / 손으로 돌리는 스크립트. 누가 부르나는 사람 / 사용자 코드 / 외부 시스템 / 일정 / 다른 부분(이름). 경로가 많으면 기능 묶음마다 한 줄에 개수.
8. 파일 지도
| 경로 | 속한 부분 | 역할 한 줄 | 꼬리표 |
폴더 단위로 써도 된다. 생성물·테스트·문서·예제는 한 줄씩 묶는다. 실행 때 생기는 디스크 배치는 경로 끝에 「(실행 시)」. 읽지 않은 것은 역할 끝에 「(이번에 안 읽음)」과 [모름].
```

### 3.3 분량 상한과 그 이유

| 기록 | v3/v1 | v4/v2 | 이유 |
| --- | --- | --- | --- |
| 현황 | 12,000자 | **14,000자**, 한 덩이 | 8개 중 5개가 12,000자에 걸렸다. 줄마다 붙던 기준 시각 칸을 없애고 경로 별칭을 허용하면 약 15~20%가 준다(umami 세션 추정 20%, pocketbase 꼬리표 약 1,500자). 대신 열이 늘어난다(2절 +3, 4절 +2, 5절 +3, 6절 +2, 7절 +2). 15,000자이던 첫 판이 별칭으로 12,000~12,500이 되고 열이 늘면 13,500 안팎이라서, 여유 500을 둔 14,000으로 한다. 앱이 한 번에 읽는 몫(`MAP_RECORD_CHARS`, `REPORT_FIRST_CHARS` 12,000)도 14,000으로 올린다(4.4) |
| 설계 공통 | 12,000자 | **14,000자**(0~8절) | 4절 범위를 「중심 부분 3~8개」로 좁히고 목록형은 프로필 표로 보낸다. 대신 6·7절이 새로 생긴다. axios(http.js 하나로 12,000 초과), gpt-researcher(첫 판 22,600) 같은 큰 경우는 범위 규칙으로 줄이고, 생략 순서는 파일 지도를 지키도록 정한다 |
| 설계 프로필 | — | **8,000자**(둘째 덩이) | 프로필 하나가 표 4~6개, 줄 수 15~40이다. 두 개를 골라도 8,000이면 들어간다. 따로 붙여 넣는 둘째 기록으로 받아서 한 기록이 앱의 한 번 읽는 몫(14,000)을 넘지 않게 한다. 덩이를 나누는 이유는 단순히 크기다. 같은 0절과 경로 약속을 다시 쓰게 해서 둘째 덩이만 읽어도 이름이 풀리게 한다 |
| 글자 세는 법 | 정하지 않음 | 「유니코드 글자 수, 바이트 아님」 | shapez 세션이 `wc -m`(바이트)로 지나치게 깎았다 |

합계 최대치는 현황 14,000 + 설계 14,000 + 프로필 8,000 = 36,000자다. 첫 지도 파이프라인은 기록을 4개까지 받고(`MAP_RECORDS`), 한 요청은 65,536바이트(`MAP_BYTES`)를 넘을 수 없다. 한글과 코드 이름이 섞인 기록은 글자당 약 2.2~2.6바이트라서 세 기록을 한 번에 다 보낼 수는 없다. 지금의 나눠 읽기(`first-map-divided`, 남은 구간은 다음 정리에서 읽음)가 이것을 감당하는지는 검증 계획 5.2의 측정 항목이다. 비용 상한(1회 $3)도 함께 잰다.

## 4. 앱 쪽 변화

### 4.1 어떻게 내놓나 — 결정: **한 번에 다 주고 「네 것만 답해」**, 보충은 선택

| 안 | 좋은 점 | 나쁜 점 |
| --- | --- | --- |
| A. 설계 요청 하나에 여섯 프로필 절을 다 싣고, 기록 AI가 0절에서 골라 그 절만 답한다 | 붙여 넣기 한 번으로 끝난다. 코드를 실제로 보는 쪽(기록 AI)이 근거를 대며 고른다(§10.1: 사용자 숙제가 아님). 첫 지도가 바로 프로필 표를 가진다 | 요청문이 약 5,900자다(프로필 절 2,100자). 고르는 판단이 틀릴 수 있다 |
| B. 첫 지도가 신호(§10.3)로 프로필을 제안한 뒤 둘째 요청을 준다 | 요청문이 짧다. 앱의 판정과 기록이 맞물린다 | 붙여 넣기와 정리 실행이 한 번 더 든다(비용 $). 첫 지도가 프로필 없이 나와 첫인상이 약하다. 사람이 다시 대화에 가야 한다(숙제). 앱 신호는 v3 기록으로 2점 문턱도 넘기 어렵다(가설) |

**A를 고른다.** 이유는 넷이다.
1. 판정 근거가 가장 많은 쪽은 코드를 읽은 기록 AI다. 앱의 신호는 기록에서 계산한 이차 근거다.
2. 프로필 절은 짧은 머리 줄 목록이라 AI에게 5,900자는 문제가 아니다. 사람이 읽을 글도 아니다.
3. 「고르지 않은 절은 제목도 쓰지 마」 규칙으로 답의 분량이 프로필 수에 비례한다.
4. B의 둘째 왕복은 A에서도 쓸 수 있다.

**보충은 선택으로 남긴다(S11의 축소판).** 지도가 만들어지면 앱이 §10.3 신호로 프로필 점수를 계산한다. 다음 두 경우에만 지도 정리 칸에 「보충 요청 (P4 상태·반응)」 버튼 하나가 나온다.
- (a) 기록의 「종류」와 앱 판정이 다르고 앱 점수가 문턱(2점, 둘째의 1.5배)을 넘을 때
- (b) 고른 프로필의 절이 「생략한 것」에 있거나 둘째 덩이가 오지 않았을 때

버튼의 글은 그 프로필 절 하나와 0절, 그리고 「이 프로필을 고르지 않았다면 이유를 0절에」 한 줄이다. 보충을 하지 않아도 지도는 완성이다. 프로필 제안 줄(§10.1)은 기록의 「종류」를 근거 인용으로 보인다: `이 기록은 ‘자료 변환·산출물’ 중심으로 읽었습니다 〔파일·2〕 · 보기 변경`.

화면은 지금 그대로 버튼 셋(현황 · 설계 · 시나리오)이다. `RECORD_ASK_EXPLAIN.design`은 이렇게 바꾼다: 「…공통 표 여덟과, 그 AI가 고른 프로젝트 종류의 표만 써 줘요. 길면 두 번에 나눠 오니 둘 다 붙여 넣으세요」.

### 4.2 붙여 넣기 전 점검 (`checkReport`)

- 판 구분: 첫 줄의 「v4 표 형식」 또는 「설계 기록 v2」로 정한다. **`isDesignRecord`는 「경로 약속:」 줄로 판단하지 않는다**(현황 v4에도 생기므로). 첫 줄의 「설계 기록」으로만 본다. 「설계 기록 v2 이어서」는 설계 기록의 둘째 덩이로 보고 프로필 절만 점검한다.
- 새 점검 줄:
  - 「종류」 줄이 없음
  - 「종류」가 고른 프로필과 답한 프로필 절이 다름(고르지 않은 절이 있음 / 고른 절이 없고 「생략한 것」에도 없음)
  - **칸 수가 머리 줄과 다른 표 줄 N**(`|` 깨짐의 신호. 다시 쓰게 할 문장: 「칸 안의 |를 「또는」이나 \|로 바꿔 그 줄만 다시 써 줘」)
  - 14,000자 초과
  - 현황 2절 상태 칸에 낱말 목록 밖의 말(배포 상태·운영 상태는 목록 낱말로 시작해야 한다)
- 꼬리표를 세지 않는 줄에 「종류:」, 「경로 약속:」, 「관문 없음:」, 「들어가는 방식:」, 「생략한 것:」 줄과 프로필 묶음 이름 줄(「[P1 …]」)을 더한다.
- `REPORT_FIRST_CHARS` 12,000 → 14,000.

### 4.3 파이프라인이 읽고 저장할 것

**표 읽기(공통 기반, 먼저)**
1. **칸 나누기**: `line.split('|')`(map-reading.ts의 행 읽기)를 이스케이프되지 않은 `|`로만 나누고(`/(?<!\\)\|/`) 칸 안의 `\|`를 `|`로 되돌린다. v3 기록도 같은 함수로 읽으므로 옛 기록에 `\|`로 적힌 조건이 바로 살아난다. 칸 수가 머리 줄보다 많은 줄은 데이터로 쓰지 않는다. 진단 `{rule:'contract', category:'row-cells'}`를 남기고 원문은 인용 가능한 글로만 남긴다. 지금처럼 밀린 칸으로 when/then을 만들지 않는다(axios settle 손실을 막는다).
2. **열 이름으로 판 가리기**: 2절 머리에 「배포 상태」가 있으면 v4, 「상태 단어」가 있으면 v3다. 4절 「박자」와 「언제·얼마나 자주」는 둘 다 `cadence`(.37 규칙 유지)이고, v4면 박자 종류를 앞말로 나눈다. 5절 「원한 이」가 있으면 v4다. 7절 「지키는 장치」가 있으면 v4, 「누가 정했나」만 있으면 v3다. 절 번호가 아니라 머리 줄로 표를 찾는 지금 방식(`rowsUnder(texts, TITLE)`)을 그대로 쓴다.
3. **프로필 절**: 머리 줄의 절 번호 11~64를 프로필로 본다(십의 자리). 고정 머리 줄과 맞으면 `profileTables`에 담고 3.4의 옮김을 한다. 33절은 열 이름이 가변이라 「키 · 기본값 · … · 꼬리표」의 앞 둘과 마지막을 고정하고 사이를 프리셋으로 본다.

**정리 AI(레시피) 규칙**
- 요약은 1절 두 문장과 0절 「종류」를 1순위 원문으로 삼는다. 9절(계획)과 [추정] 줄로 요약 문장을 만들지 않는다(심사 5건 공통).
- change 주장의 글은 원한 이 칸을 따른다. 「소유자의 「…」 요청에 따라」는 원한 이가 소유자일 때만 쓴다. 원한 것이 —이면 「…가 구현함(PR #)」처럼 요청이 없었다고 쓴다. 지금 프롬프트(server/map-pipeline.mjs)의 해당 문장을 고친다.
- 규칙 주장의 `enforcedBy`는 7절 「지키는 장치·장치 위치」에서만 온다. `programPerson`(map-reading.ts:975, 2463의 사람 장치 패스)은 v4 기록에서는 「지키는 장치 = 사람」인 행에만 적용한다. v3 기록에서도 「누가 정했나」 칸은 `decidedBy`로만 옮기고, 같은 부분에 그 규칙을 막는 코드 조건·단계가 있으면 사람 장치를 주지 않는다(심사 hyperfine·nanoGPT·axios·gpt-researcher의 오기).
- 상태: 배포됨을 `running`으로 옮기지 않는다. `state`는 운영 상태에서만 온다(데몬 오독을 막는다).

**계약·레시피 판 올림**

| 조각 | 내용 | 계약 | 레시피 |

### 4.4 v3 호환

- **옛 기록은 다시 읽지 않는다.** 이미 저장된 읽기(map-reading.16 이하)는 그 판 그대로 보인다(`isMapReading`의 판 분기 유지).
- **새로 붙여 넣는 v3 기록도 읽는다.** 머리 줄로 판을 가리므로(4.3-2) v3 열은 지금 경로로 간다. 바뀌는 것은 둘이다.
  - 「누가 정했나」는 `decidedBy`로만 간다(장치는 조건·단계 앵커나 「장치 미상」).
  - `\|`와 칸 수 진단은 v3에도 적용된다.
- **상태의 호환 값**: 화면과 옛 코드가 읽는 `PartState`를 v4 칸에서 이렇게 유도한다.
  - 운영 상태 돌고 있음/멈춤 → running/stopped
  - 그렇지 않으면 배포 상태 작업 중 → working, 설계만 → unbuilt, 제거됨 → retired
  - 확인 못함 → unknown
  - 나머지(배포됨·병합됨·상주 아님) → null

  v3의 「폐기」는 `retired` 그대로이고 `retention`은 비운다(v3 기록이 '보존'과 '제거'를 가르지 않았으므로 지어내지 않는다).
- **시나리오 대장(`scenarioLedger`)**: 지금 P/R/A/F/O/S/Q 그대로다. 변형·진입점 ID(V·E)는 시나리오 요청 개정 때 더한다(이번 범위 밖).
- **대화용·변경 보고·이해 확인 요청**(`CHAT_REPORT_ASK`, `deltaReportAsk`, `reflectAsk`): 이번에는 v2 그대로 둔다. 변경 보고의 상태 단어는 다음 개정에서 v4 네 칸으로 맞춘다. 그 전까지 변경 보고의 상태 단어는 v3 경로로 읽힌다.

## 5. 검증 계획

### 5.1 기록을 다시 만든다

1. **같은 사본**: r41에 쓴 8개 저장소 사본(같은 sha, 같은 클론 깊이와 sparse 제외)을 쓴다. 기록 차이가 코드 차이에서 오지 않게 하기 위해서다.
2. **기록 세션**: 저장소마다 하위 에이전트 하나(opus 5.5, high)가 현황 v4와 설계 v2를 쓴다. 조건은 r41과 같다(읽기 명령만, 실행 금지, 비밀 가림). 세션에는 요청문만 주고 이 문서·정답표·기대 프로필은 주지 않는다. 각 세션은 r41과 같은 형식의 메모(요청문 마찰 · 표현 제안)를 따로 남긴다.
3. **요청문 준수 측정(프로그램, 비용 0)**: 저장소마다 다음을 잰다.
   - 글자 수(유니코드)
   - 절·열 이름 일치
   - 칸 수가 머리 줄과 다른 줄 수
   - 「종류」 줄과 답한 프로필 절의 일치
   - 「없음」과 [모름]의 수
   - 「생략한 것」 내용
   - 상태 칸 낱말이 목록 안에 있는지
4. **기대 프로필(심사용, 기록 세션에는 주지 않음)**:

   | 저장소 | 기대 |

   | nanoGPT | P3 (+ 학습 루프 범위 P5 또는 없음) |
   | hyperfine | P1 (export 범위 P3 가능) |
   | axios | P2 |
   | umami | P1 (+ 브라우저 스크립트 범위 P4 또는 P3) |

### 5.2 지도로 읽고 맹검 심사한다

1. **두 단계로 나눠 효과를 가른다.**
   - (i) **v4 기록 + 레시피 .41**: 요청문만 바뀐 효과, 그리고 옛 파이프라인이 새 기록을 깨지 않는지(호환) 본다.
   - (ii) **v4 기록 + 레시피 .43**(V1 이후), **.44**(V2 이후): 파이프라인이 새 칸을 쓰는 효과를 본다.
   - 실행은 r41과 같은 `tools/eval-map.mjs`, `EVAL_STORE=exp-<repo>-r43`이다.
2. **크기 측정**: 저장소마다 첫 지도 입력 바이트, 나눠 읽기 횟수, 1회 비용을 잰다. 1회 $3 상한과 월 $200 상한 안인지, 기록 셋(현황 + 설계 두 덩이)이 한 정리에 다 실리는지, 아니면 남은 구간이 다음 정리로 넘어가는지 본다. 넘어가면 `MAP_RECORD_CHARS`·`MAP_BYTES` 조정이나 기록별 나눠 읽기를 정한다.
3. **심사**: r41과 같은 정답표와 같은 8항목 점수표로 맹검 심사한다. 심사자는 판과 레시피를 모른다. umami·pocketbase·dagu는 r41 심사가 없으므로 r41 지도도 같은 심사자에게 함께 맹검으로 매기게 해서 기준선을 만든다.
4. **회귀**: KORU 감독 세션이 v4/v2로 다시 쓴 기록으로 지도를 만들고, 11-03 기록의 지도와 부분·관계·규칙·철회를 비교한다. 줄어든 것이 있으면 이유를 밝힌다.
5. **정리**: 시험이 끝나면 `%TEMP%\af*`를 지운다.
