## 1. 원인 판단 (원응답과 프롬프트 대조)

| 관찰 (원응답) | 원인 | 성격 |

공급자 코드(`provider.mjs`의 전송·검증)에서는 원인을 찾지 못했다. 원응답은 계약을 지켰고 서버가 고쳐 쓰지도 않았다. 그래서 검증기를 강화하거나 완화하지 않았다. 문장 내용을 정규식으로 판정하는 서버 검사는 오탐 위험이 커서 넣지 않았다.

## 2. 수정 (일반 규칙, 사례 답 없음)
1. **[최신 사용자 변경].** ‘사용자 답에 따라’를 ‘무엇에 따라 … 실제 출처(‘이번 직접 지시’ 또는 ‘질문에 대한 답’)로’로 바꿨다.
2. **새 [출처].**
   - currentInstruction은 ‘이번 직접 지시’, answer.text만 ‘이번 질문에 대한 답’이다.
   - answer가 null이면 이번 입력의 어떤 내용도 ‘이번 질문에 대한 답’이라고 부르지 않는다. decisions의 answered는 ‘앞선 질문에 대한 답’으로 부른다.
   - 사용자가 말한 것보다 더 구체적인 방식이나 값을 사용자가 정했다고 쓰지 않는다.
3. **새 [선행 입력].** [범위] 다음에 둔다. [범위] 문장 자체는 기준과 같고, ‘구상에 없는 정책·숫자를 새로 정하지 않는다’도 그대로 [범위]에 있다.
   - 기댈 입력·데이터·선행 기능이 자료(currentInstruction, answer.text, areaWork, decisions, area, brief)에 있다는 근거가 있는지 본다. 입력 방식을 정한 결정은 입력 기능이 있다는 뜻이 아니다.
   - 근거가 없으면 최소 입력부터 결과 확인까지를 범위에 넣거나, 실행 도구가 먼저 기존 경로를 확인하고 없으면 최소 입력을 함께 만들게 한다. 경로 존재 여부는 실행 도구가 확인할 기술 사실이라 사용자에게 묻지 않는다.
   - 명시된 행동 수준(보기만·설계만·검토만)이나 currentInstruction이 명시적으로 좁힌 범위는 넓히지 않는다. 그때는 의존을 전제로 밝히고, 필요하면 확인 작업만 넣는다.
   - 영역 이름이나 구상이 ‘보는 것’을 목적으로 한다는 것만으로 보기만 제한이 생기지 않는다. 말하지 않은 제한은 만들지 않는다.
   - 관리 기능을 전부 넣으라는 뜻은 아니다.
4. **[완료 조건]에 추가.**
   - 지시에서 논리적으로 정해지는 경계·적용 대상·그대로 둘 대상은 scope와 checks에 같은 뜻으로 적는다.
   - 둘 이상의 뜻이 정말 가능할 때만 open에 둔다. 두 해석의 결과가 같으면 open에 두지 않는다.
   - 도출한 경계는 사용자가 정했다고 쓰지 않고 지시에서 도출했다고 쓴다.
5. **[open과 defaults]에 추가.**
   - defaults로 기능·대상·권한이나 실패·예외 처리 여부를 빼거나 미루거나 확정하지 않는다. 범위에 넣은 처리의 표시 문구·형식은 defaults에 둘 수 있다.
   - 빼는 것은 defaults가 아니라 scope의 ‘하지 않을 것’에 적는다.
   - 사용자 근거가 있을 때만 뺄 수 있는 것은 핵심 동작, 첫 결과에 필요한 최소 입력, 실패의 최소 처리(어떻게 알릴지)뿐이다. 그 밖의 가장 작은 범위 밖 항목은 지금처럼 ‘하지 않을 것’에 적을 수 있다.
   - 실패 처리에 사용자만 정할 선택이 실제로 남을 때만 open에 둔다.

질문을 강제하는 문장은 넣지 않았다. ‘입력이 충분하면 묻지 않고 바로 proposal’, ‘기술 사실은 묻지 않음’은 그대로다.

**독립 검토.** 별도 검토자가 원응답 6건과 diff를 읽었다. 첫 판정은 ‘작은 수정 후 수용’이었고, 다음 다섯 가지를 지적했다.
1. 제외 문장이 너무 강해 가장 작은 단위 원칙과 충돌하고 관리 기능 전체 쪽으로 밀 수 있다.
2. 명시적으로 좁힌 범위를 보호하지 않는다.
3. 정책 금지 문장이 [범위] 밖으로 밀려났다. 내 삽입 위치 실수였다.
4. defaults 금지가 표시 세부까지 막는다.
5. answered 결정의 출처명과 충돌한다.

제안 문구를 그대로 반영했고, 재검토 판정은 ‘수용’이다. 남은 비차단 문구 하나(‘이번 질문에 대한 답’)도 반영했다.

## 3. 검사 (`app/continuity/tests/guide107.test.mjs`)
- G107-1: 출처 규칙이 있고, ‘사용자 답에 따라’가 없다.
- G107-2: [선행 입력]의 각 부분이 있다(입력 방식 ≠ 입력 기능, 묻지 않음, 명시 행동 수준·좁힌 범위 보존, 구상만으로 보기만 제한 없음, 관리 기능 전부 아님).
- G107-3: 도출 경계와 defaults 금지 문장이 있다.
- G107-4: 이전 규칙과 계약 문구가 유지된다(질문 강제 없음, 기술 사실 묻지 않음, [직접 지시], fact/choice 예시). ‘새 정책·숫자 금지’가 [범위] 안에 있다.
- G107-5: 사례 답이 없다. 검토·holdout 자료의 낱말과 숫자가 없고, 숫자는 길이 제한(2000, 500)뿐이다.
- G107-6: 실제 HTTP와 가짜 상류로 확인한다. currentInstruction과 null answer가 별도 필드로 이 프롬프트와 함께 가고, 응답은 서버에서 고쳐 쓰이지 않는다. 고정 자료는 평가·holdout 사례가 아닌 중립 합성 프로젝트다.

**결과.** 수정 전 프롬프트(`2931b509`)에서 G107-1·2·3은 실패하고 G107-4·5·6은 통과한다. 수정 후에는 6/6이다. 기존 continuity Node 테스트를 포함해 216/216이고, guide097 브라우저 8/8, 타입·경계 점검도 통과했다.

**한계.**
- 이 검사들은 프롬프트 문구와 전송만 고정한다. 모델이 실제로 더 나은 초안을 내는지는 검증하지 않는다.
- 실제 호출에서 실행되지 않은 분기(A/B 선택 답, 모름, 보류, 최신 변경, ±100ms)는 여전히 미검증이다.
- 질문이 실제로 생성되지 않으면 답 경로는 시험되지 않는다. 존재하지 않는 질문에 답했다고 기록하면 안 된다.

## 4. 실제 제품 설정에서 재평가할 짧은 기준
같은 설정(15s/2048/deepseek-flash/thinking off)과 같은 제품 경로(buildGuideRequest → /api/guidance)로 본다. holdout 사례는 프롬프트에 넣지 않은 채로 둔다.
1. **C1형** (입력 방식만 정해지고 기존 입력 경로 근거 없음, 보기 구상)
   - 통과: 초안이 최소 입력부터 목록 확인까지를 범위에 넣는다. 또는 실행 도구가 기존 입력 경로를 먼저 확인하고 없으면 최소 입력을 함께 만들게 한다.
   - 실패: 사용자가 말하지 않은 ‘보기만’으로 입력을 빼는 것.
   - 질문이 없다는 사실만으로는 불합격이 아니다.
2. **명시적 보기만·설계만 대조.** 같은 프로젝트에서 currentInstruction으로 ‘보기만’ 또는 ‘설계만’을 주면, 그 제한이 유지되고 의존이 전제로 밝혀지는지 본다.
3. **HA형** (answer=null, currentInstruction으로 저장 결정의 특정 대상 변경)
   - scope·checks가 변경 출처를 ‘이번 직접 지시’로 부르고 ‘사용자 답’이라고 부르지 않는다.
   - 지시에서 정해지는 경계는 open이 아니라 scope·checks에 일관되게 둔다.
   - defaults에 실패·예외 처리 제외가 없다.
   - 사용자가 말하지 않은 세부(예: 바이트 동일 복사 여부)를 사용자 확정으로 쓰지 않는다.
4. **회귀.** C2(미리보기만, 미변경), C3(보류 정책과 무관한 관찰), C4(확정된 범위 유지), HB의 초기 응답이 이전 판정보다 나빠지지 않는다. 특히 명시된 좁은 지시를 [선행 입력]이 넓히지 않는지 본다.
5. **분기 시험 설계.** 실제로 질문이 생성된 경우에만 답 분기(A/B·모름·보류·최신)를 보낸다. currentInstruction 직접 대조와 실제 질문-답 경로를 분리해서 기록한다.
