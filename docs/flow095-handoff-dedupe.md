# FLOW095 — 전달 작업문의 같은 요청 원문 반복 정리 (기준 `446358c1`)

## 관찰과 원인 (REUSE093 `HANDOFF_A`, 5,565자)
같은 요청을 두 번 낸 조건에서 현재 요청 원문이 6번 나왔다. 모두 `handoffText`의 서로 다른 경로에서 나온다.

| 위치 | 경로 | 내용 |
|---|---|---|
| 이어가는 목적 | intent goal | MOCK의 goal은 요청 원문 그대로다 |
| 참고 · 앞선 목적 | `continuingLines` | 앞선 작업의 goal(같은 문장) |
| 관련 입력 ×2 | `sourceBlock` | 앞선 요청 원문, 현재 요청 원문(서로 다른 출처, 같은 글자) |
| 이어갈 기준 | `basisLine` | 현재 요청에서 나온 requested 기준 |
| 이전 요청 원문 참조 | `basisLine` | 앞선 요청에서 나온 requested 기준 |

같은 요청을 한 번만 낸 일반적인 경우에도 3번(목적, 입력, 기준) 나온다.

## 표시 계획과 구현 (표시만, 저장·전송 데이터 변경 없음)
1. ‘## 이번 요청과 이전 맥락’에 현재 요청 원문 전문을 한 번 둔다: `이번 요청 원문 [S_…] — 사용자 요청 원문`.
2. 다른 위치의 글이 이 원문과 **정확히 같은 문자열**(`===`, trim이나 정규화 없음)일 때만 본문 자리에 절 참조를 넣는다: `(글자 그대로 같은 본문 생략 — 위 ‘이번 요청과 이전 맥락’ 절의 이번 요청 원문 [S_…] 참조)`. 현재 요청 자신의 입력 블록은 `(본문은 위 … 이번 요청 원문에 있음)`으로 쓴다.
3. 각 항목의 머리줄(출처·기준 ID, 라벨, 상태, r, 출처 ID), 절 위치, 순서, 이후 변경 표시(※)는 그대로 둔다. 앞선 요청의 기준은 ‘이전 요청 원문 참조’ 절에 그대로 남아, 현재 값으로 승격되지 않는다.
4. 그 밖의 모든 글은 전문 그대로다: 한 글자·공백·줄바꿈이라도 다른 원문, 정정된 기준, 확정·보류·답변, 직접 수정, 목적 정정, 보고·자료, 배경 사본. 현재 요청이 없는 작업(경로 요청 없음)은 전과 같다.
- 복사, Markdown 저장, 전체 미리보기는 같은 `handoffText` 하나를 쓴다.
- AI 요청(`buildRequest`)과 저장 데이터(원문, 기준, 이력, 사본, 잠금, 내보내기 기록 형식)는 바꾸지 않았다. 내보내기 기록의 `chars`와 `digest`는 실제로 나간 글을 그대로 기록한다.
- 외부 소비자 영향: Markdown은 사람이나 AI가 읽는 글이다. 참조는 절 이름과 출처 ID를 한국어 문장으로 적어서, 별도 해석 규칙 없이 같은 문서 안에서 찾을 수 있다. 데이터 계약은 바꾸지 않았다.

‘이 절에 이 원문이 있다’를 문자열 포함으로 확인하던 4개 테스트(`fix058` F058-B2, `fix066` F066-P2와 F071, `flow049` FIX053)를 고쳤다. 이제 그 절에는 같은 항목(ID·라벨)과 참조가 있고, 전문은 ‘이번 요청’ 절에 한 번 있다. 그래서 ‘전문이 있거나, 이번 요청 전문이 정확히 그 글일 때의 참조가 있다’로 확인한다. 각 테스트가 지키던 성질은 그대로 검사한다: 어느 절에 어떤 역할로 있는지, 현재 값으로 보이지 않을 것, 정정 전 원문이 보존되고 보이는지.

## 한계
- 참조 대상은 현재 요청 원문 하나뿐이다. 서로 같은 다른 글끼리(예: 같은 보고 두 개)는 묶지 않는다.
- ‘직전에 넘긴 작업’ 절의 이전 작업 값이 현재 ‘이번 작업’과 같아도 그대로 둔다. 과거 기록이고 사용자가 직접 수정했을 수 있다.
- 외부 AI가 절 참조를 실제로 잘 따르는지는 이번에 확인하지 않았다(실제 AI 호출 없음). 독립 평가에 맡긴다.
