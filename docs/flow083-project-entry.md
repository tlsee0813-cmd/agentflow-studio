# FLOW083 — 첫 사용, 내 프로젝트, 요청 흐름 (후보 `flow083/project-entry`)

근거: DESIGN082-B 카드안 + RESEARCH082-A(제품 문서·공개 화면 관찰, 실사용 생성/삭제 검증 없음). 자동 검사는 배선 확인이며 사람이 도움 없이 쓸 수 있다는 증거가 아니다.

## 고객에게 달라진 점
- **첫 방문:** 무엇을 하는 서비스인지 두 문장, 첫 입력 곁에 한계("AI 연결 없음 · 이 브라우저에만 저장 · 복사·저장은 실행이 아님")를 보여 준다. 이름 단계 없이 큰 입력에서 바로 시작한다. 기본 이름은 첫 요청 앞부분으로 붙고 언제든 바꿀 수 있다.
- **예제 둘러보기:** 메모리에만 만든 예제(정상 도메인 경로 + 명시적 MOCK 규칙)이며 저장·목록 등록을 하지 않는다. 배너에서 닫기/내 프로젝트 시작을 고른다.
- **다시 방문:** 새 탭·새 방문은 ‘내 프로젝트’ 목록(이름, 마지막 요청, 최근 활동, 요청/가져온 결과 수, 이어서 하기)부터 보여 준다. 같은 탭 새로고침은 열던 프로젝트를 유지한다. 휴지통만 남아도 목록을 보여 준다.
- **프로젝트 안:** ‘지금 할 일’ 카드에 단계별 주 행동 하나(작업문 복사 → 결과 붙여넣기, 질문이면 답하기)와 보조 행동(Markdown 저장, 다시 정리, 전체 작업문 보기, 새 요청)을 모았다. 복사 성공·실패, Markdown 저장, 미리보기는 서로 다른 안내와 기록을 남긴다(미리보기·실패는 기록 없음). 복사·저장은 전달·실행이 아니라고 말한다.
- **지난 요청과 결과:** 각 항목이 ‘내 요청’인지 ‘가져온 결과 · 구현 보고/관찰·검사 자료’인지, 어느 요청의 작업문에 대한 결과인지, 몇 번 복사·저장했는지를 보여 준다.
- **관리:** 여러 프로젝트 만들기·전환·이름 바꾸기. 프로젝트 전체를 휴지통으로 옮기기·되돌리기·되살리기(원문·기준·요청·결과 전체, 외부 작업 취소 아님). 백업 파일은 지금 프로젝트를 덮지 않는 새 사본으로 추가한다. 이번 버전에는 영구 삭제·휴지통 비우기·개별 요청 삭제가 없다.

## 저장 (root 결정 + Sol 확정 조건)
- **한 키, 한 번 쓰기:** 모든 프로젝트를 새 키 `agentflow.idea015.workspace` 하나의 envelope(`agentflow.workspace.1`)에 둔다.
  - wrapper는 `entryId`, active/trashed, `lifecycle`(휴지통 이동·복원마다 +1), `seq`(저장마다 +1), origin(legacy/new/import)만 더한다.
  - Project 본문과 백업 파일 형식은 그대로다.
  - 한 번의 setItem이라 부분 실패를 줄이지만, 다른 쓰기 주체에 대한 compare-and-swap 보장은 아니다.
- **잠금:** 모든 workspace 쓰기는 Web Locks 공유 잠금(`agentflow.idea015.workspace`) 안에서 최신값 읽기 → 검증·상태 비교 → 저장 순서로 직렬화한다.
  - Web Locks가 없거나 목록이 손상됐으면 보호 없는 쓰기로 대신하지 않는다. 읽기, 백업 파일 저장, 이 탭의 미저장 입력은 유지하고 그 사실을 안내한다.
- **autosave:** 이 탭이 연 lifecycle의 active entry만, 다른 탭이 저장하지 않았을 때(seq 일치)만 고친다.
  - entry 추가, 휴지통 entry 부활, 휴지통 이동 후 복원된 entry에 이동 전 탭이 늦게 저장하는 것은 모두 거부한다.
  - 저장은 비동기 큐로 최신 상태만 쓰고, 화면 전환 전에 큐를 비운다. 미저장 입력은 확인 없이 버리지 않는다.
- **생성·전환·휴지통·복원:** envelope 저장이 성공해야 완료로 처리한다.
  - 용량 부족이면 기존 저장값과 미저장 편집을 그대로 두고 다른 화면으로 넘어가지 않는다.
  - Project.revision은 올리지 않는다.
- **이전 키:** 기존 단일 키 `…project.v1`은 workspace가 없을 때 한 번만 이관하고, 쓰거나 지우지 않는다.
  - v1/v2 원본은 기존처럼 legacy-original 키에 보존한다.
  - 유효한 workspace가 있으면 모든 항목이 휴지통이거나 선택이 없어도 다시 이관하지 않는다.
  - 이관이 기록되지 않은 채 이전 키가 남아 있으면 ‘이전 저장 · 읽기 전용’ 카드로 보이고 저장하지 않는다.
  - 예전 버전 탭이 이전 키에 쓴 내용을 자동으로 동기화한다는 보장은 하지 않는다.
- **손상·용량:** 손상된 workspace를 빈 workspace로 덮어쓰지 않는다. 이관이 wrapper 오버헤드 때문에 용량을 넘어도 내용을 자르지 않는다.
  - 프로젝트당 8MB 한도(FILE_TOO_LARGE)와 브라우저 전체 한도(QUOTA)는 따로 안내한다.
  - 휴지통은 공간을 확보하지 않는다.
- **가져온 사본:** 새 entryId만 받고 Project.id, Task, Source, returnId, resultFile 원문은 그대로다. 결과 파일은 열린 entry 안에서만 맞춘다.
  - 늦은 AI 응답, 파일 읽기, 복사 결과는 entry와 activation epoch가 같을 때만 적용한다. 같은 project ID를 가진 사본끼리 섞이지 않게 하기 위해서다.
- **탭 단위 선택:** 선택은 탭마다(sessionStorage)다. 다른 탭이 선택을 바꿔도 이 탭이 편집하는 대상은 바뀌지 않는다.

## 기존 테스트 갱신 (행동 동등성)
- `browser.state()`/정적 `state()`는 이 탭의 비동기 저장이 끝난 뒤 envelope에서 이 탭이 연 entry를 읽는다. 앱 CSP 때문에 대기는 Python 쪽 polling으로 한다.
- 새 탭·재방문은 목록부터: `open_listed()`로 같은 프로젝트를 열고 기존 단언을 그대로 검사한다(browser test_08/12, ui001 remount, connect039 test_04는 같은 entry를 지정).
- 가져오기 확인 문구는 ‘새 프로젝트 사본으로 불러올까요?’로 단언한다(교체 → 사본).
- connect039 test_05 전반부: 가져오기가 더 이상 브라우저 값을 덮지 않으므로 ‘덮기 전 원본 보존’ 대신 두 가지를 단언한다.
  - 가져온 뒤 이전 키 바이트가 그대로인지.
  - workspace가 생긴 뒤 이전 키에 쓰인 값이 읽기 전용으로만 열리고 저장되지 않는지.
- ui001 test_ui05: Sol 조건 2에 따라 쓰지 못한 백업 사본은 열지 않는다. ‘이 탭에 복구했지만’ 대신 사본 저장 실패 안내와 미저장 입력 유지를 단언한다.
- 질문 우선(ui02) 등 기존 단언은 바꾸지 않았다. 입력 패널은 출력 카드 아래 그대로 두고, ‘지금 할 일’의 ‘＋ 새 요청’으로 언제든 연다.

## FIX084 — 저장·전환 경계 결함 3건 (Sol 재검토 HOLD 대응, 기능 추가 없음)
1. **가져오기와 저장 실패.**
   - 원인: 확인 시점에 미저장이 없어도 `flushSaves()` 중 충돌이 나면 미저장이 생긴다. 그런데도 사본을 열어 입력을 버렸다.
   - 수정: flush 뒤 선택·epoch를 다시 확인한다. flush 중 새로 미저장이 생겼으면(첫 확인창에서 안내하지 않은 경우) 한 번 더 묻고, 취소하면 그대로 둔다.
   - 수정: `create` 중 입력이 바뀌었거나 다른 선택을 했으면 사본은 목록에만 추가하고 화면은 바꾸지 않는다.
   - 테스트: `import_file` 헬퍼는 사본 열림 또는 결과 안내가 나오고 저장이 끝날 때까지 기다린다.
2. **늦은 응답 판정.**
   - 원인: 새 프로젝트의 첫 저장(new → entry)으로 대상이 바뀌어, 같은 프로젝트의 정상 응답이 버려졌다.
   - 수정: 소유 entry는 요청 시점에 entry였을 때만 비교한다. 실제 전환은 activation epoch로 막는다.
   - 수정: 백업 파일을 고른 뒤 취소하는 것은 전환이 아니다. epoch·결과 미리보기를 바꾸지 않는다. 대기 응답은 정상 적용되고 pending은 정리된다.
3. **저장소 접근 거부.**
   - 원인: `window.localStorage` getter나 `getItem`이 던지면 모듈 초기화가 멈췄다.
   - 수정: 거부는 `STORAGE_DENIED`로 처리한다. 빈 저장소로 보지 않고, 마이그레이션·생성·저장을 모두 막는다(무보호 fallback 없음).
   - 결과: 앱은 메모리 입력으로 시작한다. ‘저장소’ 거부 안내와 백업 파일 저장은 그대로 쓸 수 있다.
