## 결론

**023 prompt와 실제 앱 입력을 유지한 채, 같은 `deepseek-flash`의 thinking OFF 대 ON/high만 먼저 비교한다.** 양쪽 모두 8,192 생성 토큰·60초의 같은 실험 한도를 쓴다. 과거 2,048/15초 결과를 새 대조군으로 삼지 않는다. 새 표현 구조·두 단계 호출·다른 모델을 동시에 도입하지 않는다. 8,192/60초는 충분성이 검증된 값이나 제품 기본값이 아닌 이번 대조의 제안값이다.

이번 실험이 식별하는 것은 **동일 prompt/자료/한도에서 reasoning 모드 변경이 도움이 되는가**다. 한 A/B로 prompt·입력 표현·모델 능력·다단 처리의 원인을 모두 판별할 수는 없다. 개선이 없다고 곧바로 두 단계 처리나 더 강한 모델이 필요하다고 결론내리지 않는다.

## 관측을 그대로 실패 정답으로 만들지 않음

첨부 QUALITY024 L1–7은 총괄 지시, L8 이후는 Cloud의 023 관측 보고다. HTTP 200·finish=stop·앱 수용 20건은 보고된 전송/계약 결과이지 의미 품질 합격이 아니다. 이번에 그 20개 raw run을 직접 회수하거나 재검사하지 않았다.

C06의 저장·표시 전반 금지와 Q02의 미제공 코드 미구현 단정은 각각 범위 확대와 근거 없는 외부 상태 주장으로 볼 명시적 발췌가 있다. 단, 실제 코드가 정말 미구현인지와 그 주장을 뒷받침할 입력 근거가 없는지는 다르다.

**C02의 채널 질문은 항상 오답이 아니다.** 전화 업무 감소라는 고객 목표에 관련된다. 선택한 첫 작업이 채널 선택에 실제로 의존하는지, 예약 전이를 몰래 정했는지를 함께 판정해야 한다. 허용 답 목록에 채널이 없다는 것은 합성 후속을 못 했다는 뜻이지 질문 품질 실패의 충분조건이 아니다.

**Q03의 무조건 질문 기준은 과도할 수 있다.** 원문에 담당자가 제안을 보고 공지로 옮기는 현재 업무가 있다. 그 주체를 유지하면서 재입력만 줄이는 최소 작업은 타당한 대안이다. 공개 규칙을 새로 확정/변경하는 답과, 기존 업무를 유지하는 답을 구분한다. 전체 응답이 없는 현재에는 `question:null`만으로 실패 확정하지 않는다.
