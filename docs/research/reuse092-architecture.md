**작은 통합 시험(실제 실행).**
- 빌드: Go 툴체인을 자동으로 받아 70초 만에 빌드했다.
- 색인: 고른 기억 4묶음(AgentFlow `continuity/src`, 위 3개 저장소, 1,383 파일)을 3.2초에 색인했다. 색인 크기는 47MB다.
- 질의 결과:
  - `navigator.locks` → AgentFlow `client/app.ts`(우리가 이미 만든 잠금 코드를 찾음).
  - `spdx case:no` → ecosyste.ms와 deps.dev의 라이선스 처리 위치를 찾음.
  - git 색인 결과에는 `Repository`, `Version`(정확한 커밋), 파일, 줄이 들어 있다.
- 한계: `sms OR twilio`는 0건이었다. 코드 검색은 넣어 둔 것만 찾고 새 후보를 발견하지 못한다.

**AgentFlow 현재 경계와 연결.**
- 공개판은 `connect-src 'none'`이라 외부 조회가 불가능하다. 로컬 서버는 `/api/continuity` 하나와 공급자 경계뿐이다.
- 그대로 쓸 수 있는 길이 있다. FLOW091-C에서 영역 구상(`note` 2000자)이 요청 시점 배경 사본으로 작업문과 AI 입력에 들어간다. `fd82e964`에서 직접 확인했다: 구상에 적은 후보 URL과 ‘거절: …(이유)’가 배경 사본, 작업문, `request.background`에 그대로 실리고 bases에는 들어가지 않는다.

## 3. 가장 작은 end-to-end 실험 (코드 0줄, 다음 배치 전에 먼저)
1. 공간 → 영역(예: 알림) 구상에 정해진 줄 형식으로 적는다: `재사용 후보(사용자 기록·채택 아님): 역할 — URL (검토 전|채택|참고만|거절: 이유, 확인 YYYY-MM-DD 출처)`.
2. 그 영역에서 요청을 보내면 기존 C 계약으로 배경에 실린다. 실행 도구에는 ‘후보 적합성·라이선스·판본을 직접 확인해 보고하라’는 문장만 요청에 넣는다(예: deps.dev skill). AgentFlow는 확인하지 않는다.
3. 돌아온 보고를 보고 사용자가 구상 줄의 상태를 고친다. 다음 요청이 그 결정을 싣는지, 같은 조사가 반복되지 않는지, 거절 이유가 지켜지는지 2~3회 실제 작업으로 본다.
4. 판정 기준. 형식이 지켜지지 않거나 상태를 고치는 데 손이 많이 가면 2단계(구조화)로 간다. 아무도 적지 않으면 기능을 접는다.

## 4. 2단계 후보 (실험 결과가 있을 때만, 새 DB 없이 프로젝트 JSON 안에서)
- **최소 기록 계약** `ReuseNote`:
  - `{id, areaId|null, url(정규화한 URL · 정체성 키는 미확정), kind: repo|package|service|pattern, role(≤200), status: candidate|adopted|reference|rejected, reason(≤1000), facts: {license?, version?, checkedAt, source: user|report:<sourceId>|deps.dev|ecosyste.ms} | null}`
  - AI나 보고 내용은 자동으로 상태를 바꾸지 못한다(bases와 같은 규칙). 보고에서 나온 후보는 ‘제안’으로만 보이고 사용자가 확정한다.
  - 요청 시점 사본은 C의 배경 사본에 포함한다(`background.2`, 명시 이관). 사용자가 할 일은 URL과 한 줄 역할을 붙여넣고 상태를 고르는 것뿐이다.
- **구분.**
  - 직접 개발: 기록, 영역 UI, 작업문 블록.
  - 서비스 연결(서버 모드에서 동의를 받은 뒤, 공개판 제외): deps.dev 정확 키 조회, ecosyste.ms `lookup?repository_url=`.
  - 라이브러리 재사용: 지금은 없음.
  - 아이디어만 참조: 저장소 URL로 같은 저장소 패키지 묶기(대표 정체성 아님), ALLOW/CAUTION/BLOCK 판정은 실행 도구에 위임, 결과에 repo@commit:file:line 출처.
  - Zoekt는 ‘내 저장소 기억’을 원하는 사용자를 위한 로컬 외부 도구로만 둔다. 앱에 넣지 않는다.
- **나중 변경 영향의 빈 곳.** 후보의 라이선스나 판본은 바뀐다. 저장값은 `checkedAt`과 `source`가 있는 과거 사실이고 현재 판정이 아니다(다시 확인은 실행 도구의 몫). 영역 이름 변경이나 보관은 `areaId`로 유지하고, 요청 시점 사본은 C처럼 고정한다. URL 이동(저장소 이름 변경)은 자동 추적하지 않는다.

## 6. 정정 (총괄 검토 반영, 2026-10-15)
1. **하네스 기억.** ‘에이전트가 기억하지 못한다’는 일반 단정은 근거가 부족했다. 확인된 것은 ‘도구·세션을 넘어 현재 결정과 확인 범위를 복원하는 비용이 보고됨’까지다. Codex/Claude 내부 기억 방식은 확인하지 않았다.
2. **전수 카탈로그.** 읽은 서비스에 기능 유사 검색 API가 없다는 것은 한 근거일 뿐이다. 전수 카탈로그의 모든 가치를 기각하지 않는다. 판단은 ‘초기 자체 수집 개발 보류’로 한정한다.
3. **URL 단독 정체성.** URL 하나로는 fork, 같은 저장소의 여러 패키지, 판본, 서비스 엔드포인트, 메커니즘(코드 없이 참고만)의 동일성을 가를 수 없다. 2단계 `ReuseNote`의 정체성 키는 확정하지 않는다. 예를 들어 패키지는 purl과 판본, 저장소는 URL과 커밋, 서비스는 제공자와 엔드포인트, 패턴은 출처 위치처럼 종류별 후보를 실험 결과를 보고 정한다.
