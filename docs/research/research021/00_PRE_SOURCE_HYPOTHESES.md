# RESEARCH021 — 외부 출처 열람 전 문제·가설
작성·열람 기준일: 2026-10-12 (Asia/Seoul). 이 파일은 사용자 설명에 대한 연구자의 문제 재정의이며 고객 조사 결과가 아니다. 외부 웹 원문을 읽기 전에 기록했다. 프로젝트 기본 지침은 이미 대화에 제공되어 있었다.

## 근본 문제
사용자는 AI 도구를 관리하려는 것이 아니라 원하는 변경을 끝내고 싶다. 그러나 요청, 합의한 기준, 내보낸 작업문, 작업자의 보고, 현재 코드가 서로 다른 장소·시점에 있다. 도구나 세션을 바꾸면 무엇을 믿고 이어가야 하는지 다시 판단해야 한다. 초보자는 보고를 실제 완성으로 오인하거나 같은 일을 재요청하고, 전문가는 상세 제어를 얻는 대신 정리·동기화 비용을 부담할 수 있다. 이는 검증할 가설이지 전체 사용자의 확정된 행동 패턴은 아니다.

## 서로 다른 해결 구조
- H1 현재 작업대: 중앙에는 지금 할 행동 하나와 수정 가능한 작업문만 둔다. 근거·기준·고급 설정은 필요할 때 펼친다. 여러 작업이 실제로 동시에 중요하거나 비교 자체가 핵심이면 단일 작업 중심이 불리하다.
- H2 불일치 확인함: 모든 진행을 관리하기보다 요청/계획/보고/관측의 불일치와 근거 부족만 모은다. 아무 불일치가 없으면 조용히 있는다. 관측 자료가 없거나 의미 비교의 거짓 경보가 많으면 가치가 사라진다.
- H3 인계 봉투: 별도 앱을 자주 방문하지 않고 기존 CLI/문서에 목표·기준 버전·제외 범위·미해결점·다음 행동을 작은 묶음으로 전달한다. 같은 도구 한 세션만으로 충분하거나 이 봉투도 자동으로 낡으면 불필요하다.

## 출처가 반박해야 할 주장
큰 캔버스가 있어야 연속성이 좋아진다는 주장, 많은 상태/확인 버튼이 신뢰를 높인다는 주장, 이벤트 수집만으로 요구 충족을 알 수 있다는 주장, 긴 기억 문서가 맥락 손실을 항상 줄인다는 주장, 모든 수정에 사용자 재승인이 필요하다는 주장을 우선 의심한다.

## 탐색 순서
먼저 지정 GitHub 커밋의 소스 지도와 재사용 가능한 과거 조사 범위를 확인한다. 외부 원문은 A 화면·작업/변경/근거 UX → B 세션 인계·요구/실제 상태 불일치 → C 이벤트·감지·연결 메커니즘의 순서로 심층 조사한다. 각 단계에서 업계 밖의 구조적 유사 원리도 찾고, 원리의 한계를 기록한다.
