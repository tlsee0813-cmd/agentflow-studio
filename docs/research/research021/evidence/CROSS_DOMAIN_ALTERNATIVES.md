# 분야를 가리지 않는 원리와 접근 자체가 다른 대안

**분리 원칙:** 원문에서 확인한 사실은 각 원문 링크, Studio에 적용하는 연결은 ‘제안/가설’로 표시한다. 이 조합이 검색 결과에 없다고 배제하지 않았고, 새롭다고 채택하지도 않았다. 아래는 기능 목록이 아니라 고객이 다음 행동을 결정하는 서로 다른 구조다.

## 원리 → 구조적 유사성 → 행동 → 성립하지 않는 조건

| 원리/근거 | 우리 문제와 닮은 구조 | 고객 상호작용 제안 | 깨지는 조건·유지 부담 |
|---|---|---|---|
| 장부 대사 [B04][B05] | 의도/장부 기록과 외부에서 실제 일어난 일이 별개의 증거 | ‘계획 반영됨’ 옆에 ‘실제 코드 확인 자료 없음’; 보고/관측이 어긋나는 부분만 열어보기 | 자연어 의미를 숫자처럼 정확 매칭할 수 없음. 자료 없음은 불일치 아님 |
| 예외만 검토하는 자동 대사 [B06] | 대부분의 정상 흐름은 조용히 진행하되 결정을 바꾸는 차이만 다룰 필요 | 명시적이고 좁은 사용자 수정은 진행; 충돌/외부 증거 불일치만 확인 | AI 확신도를 승인·구현 진실로 쓰면 안 됨. 오경보가 많으면 확인함의 가치 하락 |
| 의료 인계의 수신자 요약 [B07] | 송신자의 완전한 설명보다 수신자가 이해한 다음 행동이 중요 | 새 도구 인계에서 목표·기준·실패 시 행동을 짧게 재진술; 같은 세션 작은 수정은 생략 | 재진술은 준수/검증 증거 아님. 매번 승인 버튼으로 바뀌면 역효과 |
| 공공 신청의 요약→국지 수정→복귀 [A07][A09] | 이미 준 정보를 다시 질문하면 고객이 다른 곳을 찾아다님 | 현재 작업문에서 필요한 기준 하나만 수정하고 원래 작업으로 복귀 | 아직 목표가 모호하면 요약을 먼저 확정할 수 없음. 바뀐 답의 영향 질문은 필요 |
| 복잡한 task list를 쓰지 않는 선택 [A08] | 모든 작업에 전체 보드가 필요한 것은 아님 | 고정 순서의 짧은 작업은 이전 중단 위치로 복귀, 독립 작업이 늘 때만 목록 확장 | 실제 다중 작업·담당자 조정이 중요하면 한 장 화면만으로 부족 |

회계 데이터·의료 정보·정부 서비스의 조직 책임 체계를 가져오는 것이 아니다. 공통으로 가져오는 것은 **분리된 관측, 책임 있는 인계, 국지 수정, 필요한 때만 드러나는 예외**다.

## 대안 H1 · 현재 작업대가 제품의 중심

고객은 Studio를 열어 ‘지금 할 일’과 수정 가능한 인계문을 보고, 하나의 행동으로 기존 도구에 넘긴다. 돌아오면 최근 인계와 그 보고를 연결해 다음 행동을 만든다. 초보자의 흐름에 맞는 기본 후보이며, 화면/현재 데이터 경계의 변경 비용이 가장 작다. 전문가용 기준·근거·수동 조정은 접어서 보존한다.

장점은 바로 다음 행동으로 이어지기 쉽다는 것, 약점은 CLI 작업 중 Studio 왕복이 여전히 필요하다는 것이다. 여러 독립 작업이 동시에 중요한 사용자에게는 좁은 화면이 답답할 수 있다. **추천은 H1을 기본으로 유지하되, 필요 없는 방문은 H3로 줄이는 것**이다. 고객이 작업대를 사용했다는 실증은 아직 없다.

## 대안 H2 · 불일치 확인함만 제공

고객은 기존 Claude/Codex에서 계속 일하고, Studio는 요청·계획·보고·관측 중 중요한 차이가 있을 때만 보여준다. 개발 과정 전체를 관리하려고 하지 않는다. 전문가에게 별도 관리 도구 비용을 줄일 가능성이 있다.

장점은 정상 때 조용하다는 것, 약점은 관측 정보·대응 관계·유효 기간을 먼저 확보해야 한다는 것이다. 현재 앱의 외부 관측 부재에서 이를 주화면으로 만들면 ‘모름’ 배지나 추측이 늘어날 수 있다. [P03][P05]

**판정:** 지금은 전체 제품 방향 전환으로 채택하지 않는다. H1의 작은 예외 영역으로만 개념을 가져온다. CONNECT001이 실제 관측 가능 범위를 확인하고, 다음 행동을 바꾸는 유의미한 차이가 충분할 때 재검토한다. 측정 목표는 TBD이며, 모든 차이를 경고하거나 매 이벤트마다 모델을 호출하지 않는다.

## 대안 H3 · 앱보다 인계 봉투/문서를 제품의 중심으로

고객은 기존 CLI/문서에서 작업하고 필요할 때만 작은 인계 자료를 만든다. 최소 제품은 독립 작업판 없이도 작동해야 한다. 현재 앱은 이 봉투의 작성·수정·백업 도우미가 될 수 있다. 이미 같은 도구 한 세션으로 충분한 고객에게는 생성조차 생략할 수 있어야 한다.

장점은 도구 전환과 설치·관측 권한 부담이 작고, Claude-only/Codex-only/혼합에 중립적이라는 점이다. 약점은 오래된 봉투, 반환 보고의 대상 혼동, 자동 관측 부재다. 텍스트만으로 모든 후속 변화를 자동 동기화한다고 약속하면 안 된다.

**판정:** H1과 병행할 작은 출력 형태로 우선 검토한다. 동시에 비교 대조군으로는 **H3만으로 충분한가**를 유지한다. H3-only가 실제로 더 빠르고 오류가 적다면 기능이 적다는 이유로 버리지 않는다. AGENTS/CLAUDE native 지침으로 충분한 고객에게는 중복 문서 생성을 줄인다. [B01][B03]

## 세 대안의 비교 기준 — 아직 점수를 만들지 않음

| 기준 | H1 현재 작업대 | H2 확인함 | H3 인계 중심 |
|---|---|---|---|
| 처음 방문한 초보자 | 다음 행동 안내 가능 | 무엇을 비교할지 모르면 어려움 | 인계문 작성 지원이 필요 |
| 기존 CLI 숙련자 | 왕복 부담 가능 | 관측이 정확할 때 가치 | 최소 개입 대조군 |
| 실제 코드 접근 불가 | 정직한 미검증 흐름 가능 | 강한 제약 | 사용 가능하나 외부 사실 보장은 못 함 |
| 현재 앱 변경량 추정 | 화면 재배치 중심 | 연결/대응/경보 정책 필요 | 기존 출력 개선 중심 |
| 주 유지 비용 | UI 상태·버전·복귀 | 관측 누락/오경보/권한 | 낡은 기준·내용 누락 |

이 표는 정성적 추론이다. 소요 시간, 오류 감소, 비용 절감 수치를 만들지 않았다. 구현 지시 전에 다음 작은 사례에서 어떤 행동을 돕는지가 분명해야 한다: **‘요구 하나를 고친 뒤, 이미 준 금지를 보존하고, 실제 반영 여부를 과장하지 않은 다음 작업을 이어가기’.** 이 목표에 불필요한 화면/에이전트/세션/모델 호출은 추가하지 않는다.
