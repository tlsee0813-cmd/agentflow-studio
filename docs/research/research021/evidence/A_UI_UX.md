# A · 고객 화면, 현재 작업, 변경과 근거

## A의 질문과 결론

**연구 질문:** 고객이 돌아왔을 때 ‘어디까지 됐고 지금 무엇을 누르면 되는가’를 알아내는 비용을 줄이려면, 더 많은 상태를 보여줘야 하는가 아니면 현재 행동을 좁혀야 하는가?

**제안 결론:** H1의 현재 작업대를 기본으로 삼되, H3의 인계 문서로 바로 나갈 수 있게 한다. 전체 프로젝트를 항상 펼치는 작업판, 모든 변경을 승인받는 흐름은 현재 범위에서 우선순위가 낮다. 이는 실제 Studio 사용성 실험의 결론이 아니라 다음 구현 지시용 설계 판단이다.

## 강한 후보를 실제 읽은 수준으로 비교

### Lovable — 작업 화면 안에서 편집·미리보기·복원을 분리

2025년 공식 versioning 화면을 실제 시각적으로 읽었다. 왼쪽 Chat/History, Latest/Saved, 날짜별 항목이 있고 오른쪽은 결과 미리보기다. 과거 버전을 보고 있을 때 Previewing 상태와 Exit/Restore가 분리되어 있다. 반복되는 일반적 변경 제목은 식별력이 약해 보였다. 이것은 공개 역사 화면이지 2026년 계정의 작동 화면을 직접 테스트한 결과가 아니다. [A02]

현재 Plan 문서는 직접 수정·선택 부분 수정·이전 계획과의 차이를 설명한다. Build 문서는 진행 상세와 후속 요청 큐, 중단 후 남을 수 있는 부분 변경을 설명한다. Studio에 그대로 옮길 것은 Build 실행 버튼이 아니라 **읽기/수정/실제 수행의 경계를 누르는 행동에 맞춰 보여주는 방식**이다. [A03][A04]

**최소 적용 가설:** 중앙 작업문은 바로 수정할 수 있고, 펼친 상세에 ‘왜 이 작업인가/이전 인계에서 바뀐 점’을 둔다. 복사 전 비교는 실제 생성될 인계 기준으로 한다. 과거 기록을 선택해 읽는 것만으로 현재 기준을 바꾸지 않는다. ‘취소’는 아직 제출하지 않은 편집 버퍼 취소인지, 진행 중 AI 요청 중단인지 명확히 나눈다.

**배제/비용:** 전체 Lovable 식 IDE·파일 트리·실행 큐를 만들 이유는 없다. 복원 UI가 있다는 사실로 안전한 복원을 보장하지 않는다. 실제 2026-05-27 restore 장애가 공식 기록에 남아 있고 되돌린 배포로 해결됐다. 따라서 복구 결과를 검증 없이 성공 색으로 만드는 패턴은 피한다. [A05]

### GOV.UK + DWP — 답변을 다시 수집하지 말고 필요한 곳만 수정

공식 예제의 구조는 항목 이름/값/해당 항목 Change다. 수정 후 기존 요약으로 돌아오고, 새 답 때문에 필요한 질문만 따라간다. 미입력도 구별해 표시한다. 복잡한 비순차 작업이 아닌 단순한 순차 흐름에는 task list 자체가 불필요하다는 별도 지침도 있다. [A07][A08]

DWP 담당자 Mel Johnson의 2016년 글은 사용자가 제출 전 답을 다시 찾아다니는 관찰에서 요약과 직접 수정 기능을 만들었다고 설명한다. 수정 후 요약 복귀가 시간 감소에 도움이 됐다는 실무 보고다. 해당 글의 전체 서비스 개선 수치를 이 기능 단독의 효과나 Studio의 기대 효과로 계산하지 않았다. [A09]

**최소 적용 가설:** ‘인계 준비’ 시점에 결과 하나를 읽으며 필요한 부분만 고친다. 사용자가 직접 ‘이 문장을 이렇게 변경’했다고 저장하면 그것이 명시적 수정이다. 다시 ‘정말 이 수정에 동의하나요’를 요구하지 않는다. 원문 출처, 고급 조건, 과거 전체 이력은 필요할 때 펼친다. 문서 전체를 표의 짧은 값 칸에 욱여넣지는 않는다.

**실패 조건/비용:** 아직 사용자의 목표가 불명확한데 요약 페이지를 먼저 보여주면 검토할 내용만 늘어난다. 정부 서비스의 최종 제출 확인을 매 대화마다 복제하지 않는다. 화면 상태·키보드 포커스·수정 후 복귀 지점에 관한 UI 테스트가 유지 비용이다.

### Linear — 활동 신호는 요약하되 작업 수용 판정과 분리

공식 개발 문서는 AgentSession을 실행 생명주기 단위로 정의하고 활동으로 상태를 갱신한다. 외부 링크, 행동/응답/오류 같은 activity, 대체되는 일시적 activity를 제공한다. AgentPlan은 preview다. 이 실행 상태를 고객의 요구 충족이나 issue acceptance와 동일시하면 안 된다. [A06]

**최소 적용 가설:** 정상 중간 신호는 한 줄 진행 표시로 교체하고, 에러/사용자 선택 필요/인계 완료 같은 의미 있는 경계만 남긴다. Studio의 `taskStatus`와 저장 경고가 가진 의미를 먼저 보존한다. ‘계획에 반영’과 ‘외부 실행 완료’처럼 서로 다른 대상에는 같은 완료 아이콘 하나를 붙이지 않는다.

**배제/비용:** Linear API·agent OAuth·실시간 activity 플랫폼은 지금 UI001 의존성이 아니다. 중간 신호를 줄이면 상세 진단 경로가 필요하므로, 전문가용 접힘 영역에서 원 기록에 접근할 수 있어야 한다. 진행 로그를 모두 지우자는 제안이 아니다.

### Instalanding — 첫 화면 표현의 참고, 작업 연속성의 근거는 아님

같은 도메인의 검색 색인은 one-shot HTML 라이브러리·COPY/VIEW DEMO를 설명한다. 하지만 원페이지와 연결 자료를 충분히 열지 못했다. 가입·편집·실패·복구·내보내기 흐름은 확인되지 않았다. 브랜드 자산이나 HTML을 복제할 허락도 확인하지 못했다. 따라서 ‘여기처럼 만들면 작업 UX가 좋아진다’는 강한 추천은 배제한다. [A01]

## 현재 앱의 실제 코드에 대입한 고객 흐름

아래는 **읽은 HTML/클라이언트 코드(P06/P07)를 바탕으로 한 제안**이다. 실제 사용자가 이 순서로 행동했다는 관찰은 아니다. 원 코드는 입력·작업·기준·이력·저장 경고·백업·복사 대안 등을 이미 갖고 있다. [P06][P07]

| 순간 | 기본 화면에서 필요한 것 | 상세 조정 | 없어지면 안 되는 보호 |
|---|---|---|---|
| 빈 프로젝트 | 설명 입력 한 곳, 예시 한 문장, 실제 AI/안내 모드 구분 | 자료 종류·제약·환경 | 키를 붙여넣게 유도하지 않기, 유료 요청 동의 경계 |
| 질문 필요 | 막는 질문 하나와 짧은 이유 | 관련 기준/출처 | 이미 답한 질문 반복 방지, 보류가 동의가 아님 |
| 인계 준비 | 지금 넘길 일, 바로 편집, 복사 | 조건/검사/출처/전후 비교 | 원문·수동 필드·stable ID 보존 |
| 요청 처리 중 수정 | ‘편집 중인 값’과 ‘응답 대상 버전’ 구별 | 버전·제외된 낡은 AI 이유 | 뒤늦은 응답으로 현재 값을 덮지 않기 |
| 보고 받음 | 보고의 대상 인계와 아직 확인 안 된 점 | 원 보고·검사 조건·외부 링크 | 보고=구현 완료 자동 승격 금지 |
| 실패/재개 | 남아 있는 입력, 실패한 작업, 가능한 다음 행동 | 진단·백업 선택 | 저장 실패를 ‘저장됨’으로 말하지 않기, 새 AI 자동 재호출 금지 |

## 변경·출처·되돌리기를 작은 범위로 유지

네 작업 필드의 전후 비교만 필요하면 새 diff 라이브러리보다 현재 값/직전 인계 스냅샷의 텍스트 비교가 작다. 객체 배열까지 바뀌는 경우에만 K01–K04의 objectHash/diff 메커니즘을 검토한다. ‘원래대로’ 버튼은 **아직 반영하지 않은 이번 편집을 취소**하는 의미부터 제공하고, 이미 저장한 기준·외부 코드·다른 탭까지 되돌린다고 약속하지 않는다. [P04][P05][K01][K02]

새 source/revision 계약이 필요한 표시는 IDEA020 합의 후 연결한다. UI001은 ‘변경 적용 완료’ 값을 추측해 만들거나 코어 타입을 먼저 바꾸지 않는다. 화면 단순화로 실질적인 조건을 누락시키는 것도 금지한다.

**판단 기준 제안:** 새 사용자가 ‘지금 복사할 내용’과 ‘아직 실행되지 않은 것’을 혼동하지 않고, 전문가가 필요한 조건 하나를 기존 자리에서 수정할 수 있는가. 클릭 수·오류율·완료 시간 목표값은 측정 전 TBD다.
