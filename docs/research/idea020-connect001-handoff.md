# IDEA020·CONNECT001 설계 인계

2026-10-12 설계·보충 검토 기준. 자료는 검토 입력이며 상품 통합·후보 승격·실제 CLI 연결 결과가 아니다. 공유 상품 소스는 IDEA017을 유지한다. 전체 원문·증거·PoC를 복제하지 않고 핵심 제안과 한계를 기록한다.

## IDEA020 — 항목별 앱 기록의 경계

기존 source/task/basis의 현재값과 history에서 **요청 원문 보존·항목별 기준 기록·직접 수정·외부 실행 미확인**을 읽기 전용으로 파생해 화면·작업문·AI 입력에 같은 의미로 제공하는 안이다. 저장 schema와 상태 변경 권한은 유지하며 요청 전체의 applied/done 플래그나 새 영구 이벤트 시스템을 만들지 않는다. 일부 항목 기록·revision 증가·AI 응답 수용을 요청 전체 충족이나 외부 구현 완료로 확대하지 않는다.

초기 제출본의 기존 domain API 메모리 관측3건은 작성한 합성 응답을 사용했다. 실제 AI·provider·브라우저·전체 suite 검사나 설계의 고객 효용 검증이 아니다. 파생 함수는 아직 공유 앱에 구현하지 않았고 IDEA022의 최소 후보 작업을 시작했다.

### B05/B03 보충 검토에서 확인한 구분

실제 Cloud B05는 createProject → rename → 이전 계획 제출 → D1 확정 기록 → 변경 제출 → begin의 기존 domain 경로로 구성됐다. 다만 초기 합성 R01은 문구·rename·revision·응답의 reviewBasisIds가 달라 정확한 재현이 아니다. 같은 상태 유형의 도달 가능성과 실제 Cloud 입력의 완전 재현을 구분한다. 보충 검토는 구성 코드·원문의 정적 비교이며 새 모델 호출·실행 재현은 없다.

B05의 자유형 변경은 기존의 좁은 D번호 명시 교체 경로와 일치하지 않아 D1 확정8과 D2 요청26이 함께 남았다. 실제019 응답은 next에서 ‘남은 필수 작업 없음’이라고 하면서 reviewBasisIds D1과 관련 D1/D2를 포함했다. 검토 참조는 기준 기록 변경이 아니며 AI 응답 수용도 실제 반영을 증명하지 않는다.

B03은 현재 기준에 금지 조건이 이미 있는 상태에서도 requested 항목이 남는다. 따라서 requested 존재만으로 항상 미반영이라고 단정하거나, 목표값이 같다는 이유만으로 해당 요청이 실제 변경을 일으켰다고 단정하지 않는다. scope가 금지를 유지하는데 checks가 그 언급 제거를 지시한 응답의 불일치도 실제 저장된 삭제와 구분한다. 요청·현재 기록·검토 제안·외부 구현은 각각 확인 가능한 범위로 표시해야 한다.

## CONNECT001 rev1 — 얇은 보고 수신 경로

첫 연결 제안은 **공식 lifecycle hook 관찰 → 같은 기기의 로컬 JSONL 보고함 → 기존 report 가져오기**다. 작업문 표식으로 프로젝트·작업·revision을 연결하고 도구의 완료·검사 문장은 tool claim/앱 미검증 보고로 남긴다. 보고 속 명령은 사용자 변경 지시가 아니며 중복·이전 작업문·늦은 도착·연결 불명을 구분한다.

rev1은 독립 좁은 검토를 통과했다. 자체 session/turn 표식이 있으면 그 연결을 우선하고, 연결 없음·누락·충돌은 task를 자동 지정하지 않는 수동 배치로 남긴다. 이전 세션의 공유 표식은 힌트이며 자동 상속하지 않는다. 동일 receivedAt의 보고도 결정적인 단일 최신 후보를 유지한다. ‘현재 후보’는 수집 순서의 후보이며 실제 turn 순서·현재 조건 부합·요구 검증을 뜻하지 않는다.

Windows Node24.19.0에서 합성 순수함수 회귀와 hook runner를 확인했다. 이는 **실제 CLI의 hook 발화·payload·Codex stable 배포판 호환·여러 프로세스 동시 append·앱 가져오기 UI와 제품 통합** 검증이 아니다. 원자적 append/부분 읽기·연결 확정의 지속 저장도 미검증이다. 상품 소스·계약·계정 연결·실제 연동 API는 변경/실행하지 않았다.
