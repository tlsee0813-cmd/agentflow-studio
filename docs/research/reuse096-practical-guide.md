# REUSE096 — 재사용 판단 실용 지침 (선택형)

작성 2026-10-15 KST. 제품 기능이 아니다. 앱이 작업문에 자동으로 넣지 않고, 프롬프트나 형식을 강제하지 않는다. 사용자가 필요할 때 골라 쓰는 문안이다.

## 언제 쓰나
- 쓴다: 새 기능, 새 의존성, 상당한 자체 구현이 걸린 요청.
- 생략한다: 작은 문구·색상 변경, 이미 범위가 분명한 수정.

## 앱 계약과의 관계 (충돌 판단)
- 이 지침을 **요청 원문에 붙여 넣으면** 그 요청의 일부가 되어 실행 범위에 들어간다. 영역 구상에만 적으면 FLOW091-C 배경 사본(‘이번 요청 범위와 구분’, 지시 아님)으로만 간다. 적용하려면 요청에 붙인다.
- 우선순위는 그대로다: 현재 요청과 금지, 직접 확정한 기준 > 이 지침 > 배경. 지침이 원래 권한을 넓히지 않는다.
  - 예: 요청이 ‘문서만 읽으세요’면 ③의 ‘기존 코드 확인’도 읽기 가능한 자료로만 한다.
  - 예: 요청이 검토만이면 ⑧의 검증도 제안으로만 남긴다.
- FLOW094 중립 MOCK, FLOW095 절 참조, 보고는 검증 완료가 아니라는 원칙, 과거 지시를 적용하지 않는 원칙과 맞는다. 충돌하는 문구는 발견하지 못했다.

## 외부 작업문에 붙일 수 있는 문안
1. 프로젝트 목적, 현재 기술, 기존 결정, 이번 완료 조건과 금지를 먼저 따른다.
2. 검토만 요청했으면 검토만, 구현은 허용된 범위만 한다. 새 설치, 비용, 외부 전송, 배포 권한은 없다.
3. 기존 코드, 도구, 이미 한 조사부터 확인한다.
4. 부족한 부분에만 OSS·서비스·부분 코드·메커니즘 후보를 소수(기본 최대 2개) 찾는다. 수를 채우거나 무조건 채택하지 않는다.
5. 읽은 URL, 버전·커밋·파일, 확인일, 못 읽은 부분을 적는다.
6. 실제로 쓸 부분에 대해, 선택에 필요한 것만 확인한다: 라이선스 조건, 호환성, 추가 의존성.
7. 대체할 직접 구현, 남길 부분, 그 이유를 적는다. 메커니즘 참고와 코드 복사를 구분한다.
8. 설치·빌드 성공은 실제 적합성이나 안전을 보증하지 않는다. 실행이 허용되지 않았으면 검증은 제안만 한다.
9. 후보, 채택 결정, 실제 사용, 검증을 나눠 적는다. 결정은 사용자 또는 위임받은 범위가 하고, 자동으로 완료되지 않는다.
10. 미확인은 추측하지 않는다. 필수 조건이 미확인이면 그 조건에 의존하는 행동만 보류한다.
11. 새 판단은 과거 작업문, 배경 사본, 보고 원문을 덮어쓰지 않는다.
12. 필요한 근거가 모이면 원래 작업으로 돌아간다. 판단이 안 되면 한계와 남은 확인을 보고하고, 조사를 끝없이 넓히지 않는다.

보고에는 최소 세 줄을 권한다(형식 강제 아님):
- 실제로 쓴 것과 쓰지 않은 것(검토만이면 후보).
- 직접 남긴 부분과 대체 경계.
- 실제로 확인한 것과 미확인.
