# 질적 조사에서 얻은 제품 가설 — RESEARCH010 / IDEA011–012

2026-10-11에 완료한 다섯 주제의 연구와 설계 토론을 총괄이 요약했다. 커뮤니티 경험은
아이디어 신호이며 소프트웨어 감사나 시장 빈도 자료가 아니다. 명백한 동일 작성자/재게시 중복을
별개 고객으로 세지 않는다. 출처를 전부 복구하거나 경험 수를 합산하는 작업보다 반복되는
독립 불편과 실용적인 반례를 제품 판단에 사용한다.

| 조사 주제 | 유용한 신호 | 반례와 제약 |
|---|---|---|
| 처음 구상·질문 | 작은 관찰 가능한 행동과 중요한 제약을 보여주면 의도를 구체화하기 쉽다 | 한 사용자에게 16질문이 도움 됐다. 질문 수만 줄이는 목표는 부적절하다 |
| 기존 코드·검사 | 테스트가 통과해도 데이터 이전·최종 동작·요구 의미가 어긋날 수 있다 | 좋은 기존 예제와 작은 검사로 해결된 사례도 있다. 101개 주장 감사 도구는 잡음 때문에 버려졌다 |
| 문맥·인계·변경 | 기록 없음, 검색 실패, 오래된 기록, 기록 불이행은 서로 다른 문제다 | 명시적인 작은 checkpoint만으로 충분한 작업도 있다 |
| 모델·effort·여러 에이전트 | 의도한 설정과 실제 동작, 기다리는 상태를 놓치는 불편이 있다 | 고정 모델/터미널을 선호하거나 18에이전트 조율이 부담인 사례도 있다. 제한된 병렬 작업은 도움 됐다 |
| 단순한 대안 | 작은 단계와 가벼운 규격이 큰 관리 체계보다 낫기도 하다 | Paperclip/Orca 같은 통합이 주의 부담을 줄이는 사례도 있어 CLI만으로 항상 충분하다고 단정하지 않는다 |

## 현재 탐색 방향

AI 개발 도구의 실행 편의 기능을 복제하는 대신, 모호한 의도에서 갈라지는 고객 결과를
직접 비교하고 고른 결과를 구현 뒤와 다음 변경에도 다시 사용하는 흐름을 탐색한다.
IDEA011의 Product Rehearsal과 Decision Reconciliation 제안을 묶어 IDEA012를 만들었다.
고객 상황·행동·기대 결과를 보존하며 diff는 확인할 후보를 찾는 신호로 사용한다.
실제 동작 판단에는 실제 앱의 관찰이 필요하다.

IDEA012의 대기예약 예시는 '자동 배정'과 '참여 확인 후 예약'을 비교한다. 관련 없는 알림 수정이
배정 순서를 바꾸는 장면은 이전 결정을 다시 쓰는 가설을 드러낸다. 이 장면은 준비한 모의 예시다.
실제 결함 탐지나 실제 안전성 검증을 주장하지 않는다.

## 버려야 할 과장과 다음 확인

미리 준비한 쉬운 양자 선택, 모의 녹색 통과, 유도하는 선택지, 첫 시연의 호응은 반복 사용 가치의
증거가 부족하다. 차이가 없으면 새 승인을 요구하지 않는 경로, 둘 다 아닌 답, 보류와 수정도 필요하다.
모든 변경에 승인 절차를 늘리는 제품은 관리 부담을 만들 수 있다.

반면 '되돌릴 수 없는 외부 결과만 가치 있다', '예측이 처음과 같으면 기존 문서만으로 충분하다'는
배제 규칙도 확정하지 않았다. 다음 실험은 어느 상황에서 도움이 되는지 진단하는 용도다.
강한 기존 AI 대화·작은 시제품·README 절차와 비교하고, 두 번째 실제 변경에서 사용자가
자발적으로 이전 장면을 다시 찾는지 본다. 약하면 기능 확장보다 템플릿이나 기존 도구 절차로 줄인다.

캔버스, 그래프, 자동 effort, 보조 모델, MCP는 확정 요구가 아니다. Codex/Claude의 빠른 개선과
불확실한 비공개 로드맵을 전제로 영구 고객 가치를 단정하지 않는다.
