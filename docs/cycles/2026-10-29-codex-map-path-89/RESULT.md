# 89 결과 — 첫 자료 진전, 결합 후보 반려

**기존 첫 지시 자료는 완결·의미·저장 화면까지 좁게 통과했지만, micro 자료의 공개 API 진입점 누락으로 이 실행 경로 후보 전체는 수용하지 않는다.** 제품 코드와 provider는 그대로이며 공개73을 갱신하지 않았다.

## 실제 수행과 판단

| 자료 | 새 CLI 실행 | 형식·private 적용 | 의미 판단 | 정상 제품 UI |
|---|---:|---|---|---|
| 기존 실제 작업 지시 | 80.743초 · 1 invocation | 최종 JSON,5부분,skipped0 | A1–A5: 총괄·독립 Sol PASS | 1280×720,DPR1.25 정상 import·인용 왕복·재열기·export에서 전체 project 필드 동일 |
| micro-javascript 고정 자료 | 52.603초 · 1 invocation | 최종 JSON,5부분,skipped0 | M1/M4: 총괄·독립 Sol FAIL; M2/M3 PASS | 미실행·미수용 |

두 실행 모두 기존 CLI `0.164.0-alpha.11.1`에 Sol High를 요청했다. 90초 한도를 유지했고 exit0·turn.completed·이번 최종 메시지와 파일의 바이트 일치·관측 도구0·오류 event0을 확인했다. 원자료/ask와 map.6 지침은76과 동일하다. CLI 내부 transport 재시도 횟수는 확인되지 않으므로 ‘모든 내부 요청이 단1회’라고 쓰지 않는다. 출력 교정·alias 수선·재제출은 없다.

첫 자료는 요구와 기존 오류, 작업자 운영 절차, 내포된 합성 예문을 구별했다. 철회의 정확한 이전 대응·동결 항목·판본·수동 정정 조건과 공유 집계·과거 이력·호환 책임을 보존했다. 같은 응답의 정상 파일 가져오기 후 실제 PC에서 ‘원함’ 주장과 인용을 읽었고, 같은 근거 버튼·선택 URL·카메라로 돌아왔다. reload 후 내보낸 project 전체 필드는 원래 private 적용 사본과 같았다. JSON 파일의 공백 형식 때문에 파일 바이트 hash는 다르며, byte-identical 저장이라고 주장하지 않는다.

micro는 eval→Parser/AST→Compiler/bytecode→VM→Python 반환과 globals·한도·예외·문서 한계를 유지했다. 그러나 공개 사용 진입점 `JSContext`와 Python `microjs` import가 지도 summary/parts/claims/relations에 없었다. 사용 예문의 문맥 생성은 material에만 남았다. 고정 M1/M4는 사용자가 어떤 공개 인터페이스에서 실행을 시작하는지도 읽을 것을 요구한다. 내부 흐름이 맞거나 노드가5개라는 이유로 이 누락을 통과시키지 않았다. 고정된 이름의 노드를 강제한 판정도 아니다.

## 원인과 다음 경계

관측한 사실은 API 정보의 누락과 사용 예문의 material 분류다. 현재 검증기가 출력된 API 주장을 삭제한 것은 아니다. 출력 자체가 누락했으므로 material 배타 규칙이 원인이라고 확정할 수 없다. 다음은 API 사용법의 근거와 예문 속 가상 동작을 구별하는 좁은 설계 판단이다. 이번 실패 응답을 고쳐 적용하거나 같은 호출을 다시 보내지 않는다. 기존77/79/81/82의 완료 연구와 실패 실험은 재실행하지 않는다.
