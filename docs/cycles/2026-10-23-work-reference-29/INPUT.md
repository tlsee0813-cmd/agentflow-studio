# 29 · 작업문을 고치며 그 부분 설명 읽기
2026-10-23 KST · 착수 판단·검증 계약. 현재 배정은 [ACTIVE](../ACTIVE.md).

## 왜 다음으로 하는가
홈→지도→한 부분 이해→필요한 직접 편집→인계→지도 복귀가 하나의 흐름이어야 한다. 25에서 현재 설명을 읽고 U/N 작업문을 고치려면 약1900~2500px 떨어진 편집 위치로 이동했다. 27은 설명 편집 쪽에 현재 작업문 대조를 붙였지만, 작업문 편집에서 소유 부분의 설명을 가까이 읽는 반대 방향 공백은 남았다. 이는 지도 카드 표현28과 독립적인 사용 흐름의 공백이다.

기준은 통합27의 정확 후보 `6b96543fdf980ff45f0e1b67f83e8a0a561a1542`다. 28 연구 CSS는 포함하지 않는다. 새 전면 편집기나 자동 정리 엔진을 만들지 않고 기존 수동 네 칸과 읽기 컴포넌트를 연결한다.

## 총괄 선택
편집기 안에 기본 접힌 **이 작업의 부분 구상·설명 읽기**를 둔다. 실제 편집 Task의 `areaOf(project,t)`만 참조한다. 지도 선택이나 새 요청 대상이 A여도 편집하는 작업이 B면 B의 설명이다. 미지정·보관·없는 소유자를 다른 영역으로 대체하지 않는다. 작업을 바꾸려면 기존 명시 이어가기를 사용한다.

내용 폭이 충분한 PC에서는 열린 참고와 기존 입력을 나란히 읽고, 좁으면 한 열을 유지한다. 닫으면 빈 옆 열이 남지 않아야 한다. 읽기만으로 실행·조건·작업값을 바꾸지 않는다. 설명을 복사 적용하는 버튼, 새 승인 단계, 새 라우트나 지도 배치 변경은 없다.

## 첫 글자에서 생기는 핵심 반례
기존 계획 fingerprint에는 수동 작업문이 포함된다. 첫 U/N 입력만으로도 설명이 이전 기준이 될 수 있다. 일반 현재 설명 컴포넌트를 그대로 새로 그려 본문을 이력 안으로 숨기면 참고를 옆에 둔 의미가 사라진다.

따라서 참고를 실제 펼칠 때 **그 설명 entry의 프로젝트·작업·영역·판본**을 기억한다. 본문·출처는 선택한 기록을 계속 읽고, 현재성은 실제 상태와 대조해 갱신한다. 작업문 변경 후에는 이전 기준이며 현재 인계 참고로 제외됨을 표시한다. 새 설명이 도착해도 읽던 본문을 조용히 교체하지 않고 새 설명이 있음을 구분하며 명시 닫기/재열기로 다시 선택한다. 이 기억은 표시용 탭 상태일 뿐 저장된 설명이나 인계 validity를 바꾸지 않는다.

프로젝트·작업·소유 부분이 바뀌면 참고를 닫고 초기화한다. 같은 작업의 화면 재구성만으로 새 판본을 선택하지 않는다. 선택 기록이 없어졌으면 빈 상태이며 임의 최신 기록으로 대체하지 않는다. 적용된 설명이 없고 보류만 있다면 이를 현재 본문으로 올리지 않는다. 현재 사용자 구상과 읽고 있는 설명의 시점도 구분한다.

## 기존 요소 재사용과 변경 경계
`renderWork`, `refreshPreview`, `areaIdea`, `DescriptionView`, `descriptionEvidence` 및 기존 출처 표현을 활용한다. 설명 정정 기능이 섞인 `understandingPanel`을 통째로 넣어 새로운 편집 흐름을 만들지 않는다. 원문·이전·미반영 기록은 필요할 때 읽는다.

네 입력 DOM·커서·선택·직접값은 그대로 두고 참고 표현만 갱신한다. 같은 표시 결과라면 매 키 입력마다 본문을 교체하지 않는다. 현재성 변경 때도 읽던 본문의 펼침·스크롤을 보존한다. 저장 형식·의존성·서버·인계 정책은 바꾸지 않는다. 넓은 PC에서의 동시 읽기와 좁은 폭의 한 열은 실제 화면으로 검증해야 한다.

## 최소 검증 장면
1. B가 현재인 채 A를 읽거나 새 요청 대상으로 둬도 편집 B에 A 참고가 나타나지 않는다. 기존 명시 이어가기로 A를 연 뒤에는 A만 참조한다.
2. 표시30일 설명을 읽으며 U만 7→30으로 수정한다. 본문은 남고 이전 기준 표시로 바뀌며 입력 DOM·focus·selection·N/S/C가 보존된다. 이어 N만 고치고 S/C의 실제 보관7·배포금지를 유지한다.
3. 새 설명이 같은 작업/영역에 도착하면 읽던 판본은 바뀌지 않고 새 기록과 구분된다. 명시 재열기만 최신 상태를 선택한다. 다른 프로젝트/작업 전환 후 누출되지 않는다.
4. 이전 기준·보류-only·미지정/보관 소유를 현재 설명으로 오인시키지 않는다. 펼치기·읽기 자체로 프로젝트 자료가 변하지 않는다.
5. 실제 전달에는 U/N 수정과 S/C 유지가 들어가고, stale 설명은 기존 정책대로 제외된다. B·과거H·원보고 보존과 출발 지도 복귀를 대조한다.

PC1280×720·1440×900에서 참고 전문/내부 스크롤을 읽으며 U/N을 수정할 수 있어야 한다. 원시 요소 표시만으로 ‘같이 읽기 쉬움’을 합격 처리하지 않는다. 작은 보조 검사·전체 CI·Cloud 정상 UI·독립 코드 검토를 구분한다. 첫 실패와 수정후 실행을 보존한다.

## 조사와 선택 근거
권위/작업문 전용 [Web Pro](https://chatgpt.com/c/6ad9e4e7-e8b4-83e8-b1f4-aebabc8d27b4)의 3분48초 조사, Sol의 정확 코드 경계 확인, Astra의 첫 입력 반례 검토를 총괄이 대조했다. 다른 후보는 기존 reader로 이동 후 복귀였으나 기억·왕복 부담을 덜 줄이고 Origin 상태를 늘리므로 우선하지 않는다.

공식 원문도 총괄이 재확인했다. [VS Code 편집기 비교](https://code.visualstudio.com/docs/sourcecontrol/staging-commits)는 가까운 inline preview와 폭에 따른 나란히/한 열 비교를 제공한다. [GitHub 리뷰 당시 판본 읽기](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/viewing-a-pull-request-review)는 당시 기록과 현재를 구분한다. [Dify quick start](https://docs.dify.ai/en/quick-start)는 선택한 노드의 설정 패널을 연다. 이 자료에서 **편집 가까이 필요할 때 읽기·정확 소유자·읽는 판본 구분**을 추론해 적용하며 Git stage/revert, Dify 실행 의미를 가져오지 않는다. Pro는 문서·코드 조사이며 이 사이클에서 외부 제품을 직접 조작한 것은 아니다.

## 완료 판단
설명 참고를 추가한 사실만으로 채택하지 않는다. 읽던 설명의 존재와 시점, 실제 편집 대상, 직접 입력 보존과 정상 인계·복귀가 함께 작동해야 한다. 긴 참고가 입력을 더 밀어내거나 작업 바뀜을 숨기면 수정 또는 보류한다. main·공개 체험판은 변경하지 않으며 공유 근거는 GitHub delivery 새 `docs/transfer/work-reference-29/` 접두사에 둔다.
