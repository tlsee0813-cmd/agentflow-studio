# 지도 읽기24 — 기존 흐름 한정 수용, 제품 무변경
2026-10-23 KST. [관측 계약](INPUT.md) · [사전 비교](RESEARCH.md). 현재 배정은 [ACTIVE](../ACTIVE.md).

두 PC에서 기존 모두 보기·실제 관계 끝점의 위치 찾기·이전 보기·작업/지도 복귀로 세 흐름을 완료했다. 이번 자료에서 진행을 막는 새 반례는 찾지 못해 새 버튼·자동 맞춤·최소 줌 제한은 추가하지 않는다. **전체 지도 가독성이 충분하다는 수용은 아니다.** 네 부분만 있는 표본에서도 전체 맞춤 후 이름이 매우 작다는 문제가 남는다.

## 원본과 실제 관측
[고정57파일·8PNG·압축 원시 자료](https://github.com/tlsee0813-cmd/agentflow-studio/tree/b1f291c630708a89fe0db08f23008ff1262b7604/docs/transfer/map-reading-24/independent-a/normal-ui-v0). 정확689c 제품과 기존 Cloud Node22.16/PW1.57/Chromium154를 재사용했다. 예약·알림·기록과 예약의 실제 자식 ‘예약 가능 여부’, 자식→알림 관계를 정상 UI로 만들었다. 양PC에 명시 MOCK 요청1개씩을 사용했다. 숨은 데이터 주입은 없다.

1280×720/1440×900에서 패널을 열 때 카메라는 그대로이고 지도폭은974→660/1134→820으로 줄었다. 선택 카드 등2개가 clip 밖에 걸리지만 패널의 이름·소속·구상은 읽을 수 있고 화면 밖 표시가 생겼다. 다른 보이는 부분으로 전환하고 모두 보기→자식정보→정확한 작업 읽기→지도 복귀를 수행했다. 이 경로는 각각6click, nativewheel1/0회였다.

pan1회와＋1회 뒤 실제 화면 밖 끝점을 관계 목록에서 찾아 최소 이동하고 이전 보기로 돌아왔다. 7click+pan1회이며 전체맞춤과 원래 카메라 복원을 구별했다. 부모 접기→실제 자식 끝점→작업 읽기/복귀→위치찾기 전 보기에서는 원래 접힘도 돌아왔다(7click, wheel1/0회). 행동 수는 이해도나 효율 점수가 아니다.

각 폭에서 작업 복귀2쌍/위치 찾기 복귀3쌍의 matrix·선택·접힘·scroll·패널을 대조했다. 돌아온 뒤 보조 fit/focus/scroll은 없었다. focus는 사용한 호출 버튼으로 돌아오는 범위다. 준비 완료 후 project 전체는 notice 외 동일했다. 최신 child/collector0, console/pageerror0, 서버 명시 종료−15는 별도로 기록했다. source/served/disk후 해시 연결이 있다. 전체 회귀·새 빌드·새 CI·실제AI·사람 대상 평가는 하지 않았다.

## 실패·측정 경계
첫 실행은 다른 부분으로의 전환과 실제 화면 밖 위치 찾기 조건을 충족하지 못해 최신 실행의 근거로 합치지 않았다. 당시 원시/코드를 보존했다. plane rect 변화와 카메라 matrix 변화를 구분하도록 파생 측정을 바로잡았다. transform:none 후손의 상속 배율을 빠뜨린 clientclip 계산도 저장된 축정렬 matrix로 보정했다. 이는 새 브라우저 실행이 아니다. 잘못 이름 붙인 locate 샷은 위치 찾기 직후 증거로 사용하지 않았다.

Astra는 gzip 원해시와 복귀5쌍을 확인했다. 별도 Sol은 최소14파일542541바이트만 회수하고 메모리에서 압축을 풀어 원 SHA를 대조했다. 실제 양수·축정렬 표본의220기하 객체 보정과 카드/정보80항목 결론이 일치했다. 단1280 fit의 설명문 RangeInside4개는 true→false로 바뀐다. Range 경계와 실제 글자 잉크는 다르므로 글자 잘림 여부도 자동 확정하지 않는다.

[별도 회수·배율 보정 대조 영수증](https://github.com/tlsee0813-cmd/agentflow-studio/tree/410064fce7d38cce04c04c0e5a5da8b8b5b4184e/docs/transfer/map-reading-24/independent-review)도 공유한다.

## 총괄 화면 판단과 다음 선택
총괄은1280 전체/우측패널/맞춤 및1440 접힌 관계의4PNG를 직접 봤다. 포함 틀·실제 자식 끝점·접힌 내부관계는 구분되지만 전체맞춤의 작은 이름과 넓은 빈 공간은 눈에 띈다. 제목15px×scale의 환산은7.04/8.88px이고, 실제 텍스트 읽기는 패널/상세에 의존한다. **네 부분 수준에서도 이 부담이 생기는 점은 다음 공간 품질 검토의 구체 근거**다. Dify도 줄어든다는 이유로 문제를 없애거나 카드가 항상 보인다고 하지 않는다.

우선25에서 정정된 설명과 현재 작업문을 대조해 실제 필요한 값만 수정·인계하는 흐름을 본다. 공간 전용 Pro/Sol은 병렬로 초기 생성 배치의 빈 공간과 낮은 배율의 표현을 비교한다. 기존 저장 좌표를 자동 재배열하거나 일부가 숨는데도 전체맞춤이라고 부르는 변경은 보류한다. 수용한 것은 기존 탐색의 한정 작동이며 UI 품질의 최종 확정이 아니다.
