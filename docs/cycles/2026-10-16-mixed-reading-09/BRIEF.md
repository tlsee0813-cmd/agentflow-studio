## 나눌 조사
1. 정보량/공간: 5개 큰 역할과 실제 변경 부분의 위치를 파악하면서 한 묶음만 더 펼치는 기본을 비교한다. 390에서 모든 상세와 모든 선 라벨을 한꺼번에 우겨 넣는 대신, 전체를 잃지 않고 선택 부분을 읽는 실제 메커니즘을 최대2후보로 비교한다. 이름만 남기거나 손으로 긴 문장을 재조합해야 하는 안의 손실을 적는다.
2. 외부 관계/범위: 접힌 상대에 닿는 집계선에서 실제 관계 끝점·전달 종류를 확인하고, 한 부분 준비로 이어질 때 무엇을 기본/선택/집중에 남겨야 하는지 비교한다. 관계가 있다는 이유로 상대 전체가 변경되거나 수정 대상이 되지 않아야 한다.

Dify와 기존 yFiles/Structurizr/IcePanel 조사에서 이미 확인한 원칙을 반복 요약하지 않는다. 관련 오픈소스·다른 분야의 구체적 동작을 좁게 추가 비교하고 공식 문서/고정 코드/실제 UI 관측을 구분한다. 수를 채우는 조사와 SDK 도입 결정은 하지 않는다. 각 연구는 후보의 실패 장면과 원문 링크를 함께 반환한다. 총괄이 입력/반례·코드 재사용 감사와 통합한 뒤 구현 계약을 만든다.

## 판단할 작은 장면
‘전체의 큰 역할·변경 위치 파악 → 전달할 내용만 펼침 → 작업문과 미리보기 선택 → 접힌 요청 맥락의 실제 관계 끝점 확인 → 선택 부분의 준비를 편집 → 원래 혼합 깊이로 복귀’ 한 흐름을 후보 비교에 사용한다. 기존에 접기/복귀가 동작한다는 이유만으로 요약과 상세의 의미가 이어진다고 판정하지 않는다.
지도 위치/깊이/선택/실제 배율·읽기 위치와 준비 편집은 별도 보존한다. 실제 조작·AI 정적 평가·사람 이해는 구별한다. 구체적 화면 크기/최소 관측은 선택 후 고정하며 기존 검사 수를 복제하지 않는다.
