# AgentFlow 재진입 입구·전체 흐름 검토

**조사 기준일:** 2026-10-23  
**분류:** 문서·코드 조사. 이번 답변에서 체험본을 독립 조작하지 않았습니다.

AgentFlow의 고정 근거는 현재 제품 `395df224…`, 35 검증본 `3a008c5…`, 36 작성자 후보 `c0a7c91…`로 구분했습니다. 이 커밋들은 조사 대상 스냅샷이지 기능 최초 도입일을 뜻하지 않습니다. 35의 `REPORT.md`는 읽었지만, `validated-v0`의 PNG들은 이 환경에서 실제 시각 판독하지 못했습니다. 따라서 화면의 실제 대비·시선 순서·클릭 표적 크기는 판정하지 않고, 코드와 35 독립 실행 기록만 사용합니다. 36은 여전히 미수용 작성자 후보이므로 현재 동작으로 계산하지 않았습니다.    

## 결론

**프로젝트 카드 입구 자체보다, 입장 직후 다음 한 건을 고르는 근거가 여러 층에 분산된 것이 공통 막힘 후보입니다.**

현재 코드는 다음 세 상태를 데이터와 문구상으로는 비교적 정확히 구별합니다.

- 지금 앱에서 이어가는 작업
- 그것과 별개로 작성 중인 미전송 입력
- 답을 기다리는 질문이나, 보고를 받은 뒤 아직 후속 작업문이 없는 기록

문제는 이 세 상태가 **프로젝트 카드 → 전체 지도 → 영역/작업 상세 → 작성 화면**의 서로 다른 위치에서 드러난다는 점입니다. 따라서 재진입 사용자는 프로젝트를 연 뒤에도 “무엇을 이어야 하는가”를 바로 고르는 대신 여러 표식과 기록을 조합해 해석해야 할 가능성이 있습니다. 이는 경로가 없는 문제가 아니라 **선택 근거의 분산**입니다.

### 현재 근거와 판정

| 지점 | 확인된 근거 | 좁은 판정 |
|---|---|---|
| 프로젝트 목록 | 카드는 프로젝트 이름·목적·최근 작업 기록 시각·영역 수를 보여주며, 카드에서 열면 저장된 마지막 상세 화면이 아니라 그 프로젝트의 전체 공간부터 시작합니다.   | **적절한 프로젝트 선택 입구**입니다. 여기에 작업·질문·보고 상태를 모두 넣을 필요는 없습니다. |
| 전체 공간 첫 화면 | 지도에는 `앱에서 이어갈 작업` 표식이 있고, 별도로 `이어 볼 기록`이 답 없는 활성 질문과 후속 작업문 없는 보고를 모읍니다. 반면 하위 기록의 `기록된 질문`에는 답변된 질문도 포함되며, 코드도 이를 전체 미결 수나 완료 수로 보지 말라고 명시합니다.  | 필요한 신호는 있으나 **현재 작업과 실제 미답이 서로 다른 입구**입니다. 처음 들어온 사용자가 둘을 결합해 한 건을 골라야 합니다. |
| 한 작업의 상세 | 작성 중인 별도 입력이 있으면 그 입력을 여는 행동과, 지금 읽는 작업을 실제 편집 대상으로 전환하는 행동을 분리합니다. 또한 어느 작업·보고의 후속 작업문이 바뀌는지 명시합니다.  | 상세에 도착한 뒤의 의미 구분은 강합니다. **막힘은 그 상세를 고르기 전**에 있을 가능성이 큽니다. |
| 35 독립 기록 | 프로젝트 카드 재진입 후 저장값과 지도 카메라는 유지됐습니다. 다만 1280×720의 장문 작업 reader에서는 별도 미전송 초안 입구가 첫 화면 아래에 있었습니다.  | 복귀 정확성은 확인됐지만, 복귀한 지점에서 다음 한 건을 발견하는 것은 별개입니다. fit·카메라 복구만으로 통과 처리하면 안 됩니다. |
| 36 후보 | 작성자 후보는 지도 카드에 `읽을 이유`를 추가하고 일부 수치를 상세로 옮겼지만, 독립 검증·통합 전입니다. 작성자도 `기록된 질문`이 실제 미답 전체가 아니며 기본 fit에서 글자가 지나치게 작아질 수 있다고 기록했습니다.  | 현재 제품의 해결책으로 간주할 수 없습니다. 이번 관측에서는 35의 수용 동작을 기준으로 해야 합니다. |

따라서 **확인된 숨김**은 장문 작업에서 별도 초안 입구가 첫 화면 아래였다는 점입니다. 그 밖의 “지도가 얼마나 과하게 읽히는가”는 코드상 위험은 보이지만, PNG를 직접 읽거나 독립 조작하지 않았으므로 실제 시각 부담으로 확정하지 않습니다.

## Dify·Linear에서 가져올 수 있는 기제만 좁게 대조

Dify의 현재 공식 소스에서 Studio 앱 카드는 이름·앱 유형·설명·작성자·수정 시각으로 대상을 식별하고, 카드 전체가 같은 앱 ID의 workflow/configuration 공간으로 이어집니다. 공식 빠른 시작 문서에서도 앱을 만든 뒤 곧바로 해당 workflow canvas에 들어갑니다. 즉 카드는 “다음 세부 작업을 모두 설명하는 곳”이 아니라 **대상을 고르고 동일 대상의 한 편집 공간으로 넘기는 곳**입니다. AgentFlow도 카드에 상태를 더 쌓기보다, 카드 뒤의 전체 공간에서 다음 한 건을 분명히 만드는 편이 이 비교에 맞습니다.   [Dify Docs](https://docs.dify.ai/en/guides/application-orchestrate/creating-an-application?utm_source=chatgpt.com)

Linear는 프로젝트 개요에 그 프로젝트의 최신 업데이트를 직접 보여주고, 건강 상태와 짧은 설명으로 현재 상태·문제·다음 단계를 요약하며, 과거 기록은 별도 Updates 탭으로 넘깁니다. 여기서 맞는 기제는 대시보드나 상태 체계를 복제하는 것이 아니라, **같은 프로젝트 상세의 첫 층에서 현재 판단에 필요한 한 신호를 먼저 두고 기록 전체는 뒤로 미루는 것**입니다. [Linear](https://linear.app/docs/initiative-and-project-updates?utm_source=chatgpt.com)

두 제품을 합쳐도 “프로젝트 카드에 현재 정보 전부를 넣는다”는 결론은 나오지 않습니다. 공통점은 **가벼운 대상 선택 → 같은 대상의 상세 → 첫 상세에서 현재 행동의 의미가 분명함**입니다.

## 1. 다음에 관측할 재진입 과제 하나

기존 총괄 또는 독립 관측자에게 아래 문장만 제시합니다.

> **전에 목적과 구조를 만든 프로젝트로 돌아와, 지금 이어갈 작업 한 건을 정해 새 인계가 가능한 상태로 준비하세요.**

프로젝트 안의 정답 영역·작업 번호, 클릭 순서, 사용할 버튼은 알려주지 않습니다. 실제 외부 AI 호출이나 전달까지 할 필요는 없으며, 한 작업을 정하고 그 대상의 작업문이 새 인계 직전 상태가 되면 종료합니다.

이 과제는 “사용자가 무엇을 이어야 할지 찾는가”만 봅니다. 지도 fit 여부, 저장된 카메라 복구, 프로젝트 카드 클릭 성공은 보조 사실이지 과제 성공 기준이 아닙니다.

## 2. 관측 기준 4개

| 관측 기준 | 통과로 기록할 것 | 오인으로 기록할 것 |
|---|---|---|
| **같은 프로젝트와 한 작업의 연속성** | 프로젝트를 연 뒤, 사용자가 근거를 말하며 한 작업을 선택하고 그 작업의 상세·편집 대상으로 이어감 | 지도가 복구됐다는 이유만으로 다음 작업을 찾았다고 처리함 |
| **현재 작업 vs 별도 미전송 초안** | 편집 전에 “현재 이어가는 작업”과 “작성 중이지만 아직 보내지 않은 별도 입력” 중 무엇을 열었고, 어느 기록이 바뀔지 구별함 | 초안을 열었으므로 현재 작업을 이어갔다고 판단하거나, 현재 작업을 바꾸면 초안 대상도 자동으로 바뀐다고 예상함 |
| **변화 vs 기록된 질문·실제 미답** | 목적·영역 설명·수동 작업문·초안·보고 연결 등 실제 저장 상태의 전후 차이를 ‘변화’로 기록함. 실제 미답은 답 없는 활성 질문, 후속 작업문 없는 보고처럼 근거가 있는 항목만 셈 | `기록된 질문 N개`를 미답 N개로 세거나, 답변됨·시험 입력·이전 기준 질문까지 현재 미답으로 포함함 |
| **사용자 결정 vs 외부 주장** | 사용자가 직접 쓴 목적·영역 구상·수동 수정·명시 답변·명시 채택만 사용자 결정으로 분류함 | 가져온 보고, evidence 원문, AI/MOCK 요약·제안, 외부 정리를 저장했다는 이유만으로 사용자 결정 또는 검증된 사실로 승격함 |

특히 세 번째 기준에서 **질문 총수는 관측값일 뿐 미답 수가 아닙니다**. 현 코드도 답변된 질문을 하위 기록에 포함하며, `이어 볼 기록`은 더 좁은 규칙으로 따로 계산합니다. 

## 3. 공통 막힘 하나

> **프로젝트로는 쉽게 돌아오지만, ‘현재 작업·별도 초안·실제 후속 필요 기록’이 서로 다른 층과 입구에 있어 다음 한 건을 고르기 전에 상태를 재구성해야 한다.**

이 막힘은 “카드 정보 부족”으로 단정하면 안 됩니다. 프로젝트 카드는 현재도 목적 식별과 동일 프로젝트 진입 역할을 수행합니다. 실제 확인할 곳은 **카드 직후 전체 공간에서, 사용자가 불필요한 기록을 열지 않고 한 작업을 고를 수 있는가**입니다.

## 4. 필수 수정 여부

**현재 자료만으로 필수 수정은 정하지 않는 편이 맞습니다. 관측을 먼저 해야 합니다.**

이번 검토는 독립 조작이 아니고 PNG도 직접 판독하지 못했으므로, 지도 상단이나 카드에 새 표시를 넣으라는 구현 결론까지 내릴 근거가 부족합니다. 위 과제를 1280×720과 1440×900에서 수행했을 때 다음 중 하나가 재현되는지를 먼저 기록해야 합니다.

- 별도 초안을 현재 작업으로 오인한다.
- 질문 총수를 실제 미답 수로 사용한다.
- 한 작업을 고르기 위해 무관한 영역·기록을 반복해서 연다.
- 외부 보고나 정리를 이미 채택된 사용자 결정으로 취급한다.

그중 하나가 두 해상도에서 같은 지점에 반복될 때에만 작은 수정 후보를 정하는 것이 타당합니다. 36의 `읽을 이유` 행은 아직 그 수정으로 채택된 것이 아닙니다.
