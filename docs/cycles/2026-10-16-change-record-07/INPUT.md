## 지도 대상과 사건의 분리

지도에는 다음 **프로그램 역할 세 대상**까지만 후보로 둔다. 이름·묶음은 읽기용 해석이며 전체 VS Code 구조나 코드 파일과 일대일 대응하는 확정 모듈 트리가 아니다.

관계는 **P1이 P3을 호출 / P2가 P3을 호출** 두 개다. 부모 커밋에서도 이 호출 관계는 이미 있었고, E3에서 상태 객체를 넘기는 방식과 계산 책임의 배분이 바뀌었다. 새 관계 두 개가 생겼다고 그리지 않는다. 호출선은 사건 시간선·실행 성공·포함 관계가 아니다.

E2~E7은 이 대상들과 연결해서 읽을 **사건 기록**이며 대상의 자식 기능으로 넣지 않는다. E3은 두 소비부와 계산 부분 모두에 실제 수정이 있지만, 수정 표시를 구현 완료·최종 수용 색으로 바꾸지 않는다. E5/E6의 대상은 해당 파일의 변경이므로 제안 역할 전체가 사라졌다고 표시하지 않는다. 요청·Bot·PR도 프로그램 부분으로 만들지 않는다.

## 동결과 관측 한계

구조·patch 대조는 1월 16일 E2~E4 구간, 고정 8a83069와 부모 c7e0a659…를 기준으로 한다. E5~E7은 뒤에 이어진 기록으로 반드시 남기되, 그 이후 제품의 실제 코드 상태를 재구성한 척하지 않는다. 나중 PR 본문의 표시문구 공통화·시간 형식 개선을 이 고정 커밋에 섞지 않는다. 커밋에는 다른 리뷰에 대응한 Windows 지연 처리·테스트 정리도 있어 전체 커밋을 E2 하나의 성과로 묶지 않는다.

이 표본은 **한 업데이트 표시 기능의 두 화면 소비부**에 관한 공개 사람–Copilot 작업 기록이다. 두 독립 사업 기능의 요구 변경, 전체 AI 대화, 실제 되돌림 완료, 최종 수용, CI/실행 성공, 정확한 추정 품질, 제품 반영, 다른 AI 세션의 인수·수락은 확인하지 않았다. 커밋은 고정되지만 이슈/댓글/PR은 편집 가능한 원문이며 이번 입력은 감사 시 관측에 한정한다. 부족한 정보를 가짜 미결 문제나 사용자 승인 숙제로 채우지 않는다.

## 다음 시안의 핵심 세 장면과 짧은 문장 후보

1. **전체 목적에서 두 화면과 공통 부분 찾기.** 세 역할을 보고 같은 사용자 목적을 위한 연결임을 읽는다. 사람용 문장: “다운로드가 얼마나 남았는지 알리려는 기능입니다. 두 화면이 같은 계산을 사용합니다.” 추정 가능 조건과 ‘1월 16일 변경 구간’이라는 시점은 가까이 유지한다.
2. **한 부분에서 지시·실제 변화·주장을 대조하기.** 선택한 부분의 바깥 두 소비부 또는 공통 계산을 남기고 E2/E3/E4를 구별한다. 사람용 문장: “공통 계산은 이미 있었습니다. 이번에는 두 화면에 흩어진 입력 확인과 경과 시간 계산을 그쪽으로 모았습니다.” Bot 답변만으로 완료를 채우거나 실제 diff를 거대한 기본 보고서로 펼치지 않는다.
3. **나중 기록까지 보고 좁은 준비 후 전체로 복귀하기.** E5/E6/E7을 숨기지 않고, 필요할 때 목적·선택 범위·확인된 변화·확인되지 않은 후속 상태를 담은 준비를 한다. 사람용 문장: “뒤에 두 화면 파일의 변경을 되돌려 달라는 요청이 있었고 PR은 병합되지 않았습니다. 실제로 어디까지 되돌렸는지는 이 자료에서 확인하지 않았습니다.” 준비는 다음 확인 범위를 정리하는 제안이며, 재구현 지시나 실제 인계·수락으로 표시하지 않는다.

세 장면은 내용 범위를 정하기 위한 제안이다. 배치·패널·선택 방식은 확정하지 않으며 혼합 깊이나 새 엔진을 이 입력에 강제로 추가하지 않는다.
