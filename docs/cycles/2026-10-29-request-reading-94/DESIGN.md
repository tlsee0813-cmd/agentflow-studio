# 94 설계 — 동결 요청문을 구별해서 읽기

**선택한 설계이며 구현·수용 전이다.** 기준은93 문서 `4a188df9ae4631e4f0a81ff957c03abe9b48b024`, runtime `d881b0ae8d892f6d65cfdce63a6924377ec567d7`, app `81c5a4e6e6428440427d97caa392ba156063e467`이다. 공개73은 유지하고 UI75·93 수리를 포함한다.

93의 실제 화면에서4013자 저장 요청문과12515자 검토 요청문은 접근·복귀가 가능했지만 긴 원자료와 반복 Markdown이 한 본문으로 이어졌다. 맡긴 일과 원자료의 구별을 읽는 사람에게 맡기는 부담이 남았다. 작은 검색창이나 글꼴 변경을 완전한 구조 읽기면의 대체 성공으로 취급하지 않는다.

## 근거와 선택

현재 RequestSnapshot의 text는 전체 동결 원문이다. 선택 항목의 scope에는 설명·대상·출처 메타데이터만 있고 유지 조건·전체/범위 미정·전제 검토·제외 항목·전체 원자료 본문은 따로 없다. 현재 plan으로 이를 보충하면 과거 요청문이 다른 판본으로 바뀐다. scope와 text의 식별자 일치는 전체 내용이 같은 구조라는 증명이 아니다.

따라서 **새 요청문을 만드는 순간, 같은 원문에 붙는 읽기 구간을 함께 동결한다.** 이후 화면은 그 원문의 구간을 읽는다. 생성된 문장·자료·순서·공백과 복사 payload는 바꾸지 않는다. 과거 요청문에는 구조를 추정하거나 소급 생성하지 않는다. 기존57의 범위 검토·71의 요청 대응·87의 현재 분석 자료 목록·93의 복귀 수리를 재구현하는 일이 아니다.

읽기 전용 경계 검토 원본 SHA256: `386f1324d658635b87e0e9a71c90b318f35263539ed0b327ea0904759641ea3a`. 기존 소스와 완료 결과를 회수했으며 새 연구·모델 호출·UI 실험은 아직 없다.

## 동결과 검증 계약

- RequestSnapshot에 명시적으로 버전이 있는 선택적 읽기 manifest를 추가한다. 이름과 세부 타입은 구현에서 정하되 생성 시점의 문서 구간만 담고 두 번째 수정 가능한 본문은 만들지 않는다.
- 구간 단위는 **JavaScript 문자열의 UTF-16 code unit offset**이다. 한국어·emoji·줄바꿈을 포함한 text의 정확한 길이에 바인딩하고, 정수·범위·순서·중복·전체 포괄·surrogate pair 중간 경계를 검증한다. 화면용 구간을 순서대로 합치면 원문 전체와 정확히 같아야 한다. 구분자와 마지막 결과 요청 문장도 빠뜨리지 않는다.
- 생성 함수가 알고 있는 서두, 선택 항목, 제외 항목, 전제 후보, 유지 조건, 전체 구상의 미정, 선택 범위 검토의 미확인, 검토 자료, 마지막 안내를 구별한다. 검토 없는 예제·옛 생성 경로의 차이도 유지한다. 자료별 경계·이름은 같은 생성 시점에 기록하고 전체 검토 자료를 선택 항목 refs로 축소하지 않는다.
- 유효한 종류/순서/필수 구간과 해당 생성 제목·본문의 대응을 검증한다. 원자료 안의 같은 제목·반복 문장·Markdown·가짜 요청문은 새 구간을 만들지 않는다. 부분 문자열 검색으로 위치를 다시 찾지 않는다.
- 읽기 manifest는 생성 당시의 구조와 정확한 본문 대응을 뜻한다. 모델 의미의 정확성, 자료의 진실, 구현·실행 확인을 뜻하지 않는다. 가져온 파일의 메타데이터를 독립 검증된 사실로 승격하지 않는다.
- 잘못된 새 manifest는 파일/프로젝트 경계에서 원자적으로 거절한다. 잘못된 구간만 버려 유효한 문서처럼 표시하거나, 조용히 원문 fallback으로 성공 처리하지 않는다. 기존 저장 내용과 원본 보존 규칙을 지킨다.

## 저장과 과거 판본

새 파일과 envelope를 `.4`로 구별한다. 기존 `.1/.2/.3`는 기존 허용 범위를 유지하며 새 manifest를 그 구판에 허용하지 않는다. `.3`의 authoring과 zero 분석은 `.1/.2`와 구별해야 한다. 다른 프로젝트를 저장해 envelope를 올리는 일로 구판에서 거절하던 다른 항목을 유효하게 만들지 않는다. 구판별 출처 표지를 유지한다.

기존 snapshot은 text·scope·labels·origins·observations·attached를 그대로 보존하고 원문 reader를 유지한다. 새 snapshot의 구조도 저장·재열기·내보내기·가져오기 뒤 같아야 한다. 수리93 앱은 `.4`를 지원하지 않으므로 원본을 그대로 둔 채 거절하는 경계를 확인한다. 자동 과거 자료 재해석이나 저장소 초기화는 하지 않는다.

## PC 읽기 경험

새 요청문의 기본 화면은 맡긴 일·유지 조건·미정·전제 후보·원자료의 경계를 명료하게 보여 준다. 제외 항목과 전제 후보가 새 요청에 포함된 것처럼 보이면 안 된다. 같은 문서 안의 구간 이동을 제공하고 읽기 폭을 불필요한 새 sidebar로 줄이지 않는다.

실행을 맡기는 본문과 유지/미정/범위 경고는 기본으로 읽힌다. 긴 검토 원자료는 개수·정확한 이름과 ‘자료이며 작업 지시가 아님’을 드러내며 펼쳐 읽을 수 있게 한다. 숨겨진 자료도 전체 원문 복사에 포함된다는 점을 복사 행동에서 이해할 수 있어야 한다. 원문 전체 보기와 정확한 전체 복사는 계속 접근 가능하다. Markdown을 실행 가능한 HTML로 해석하는 엔진은 추가하지 않는다.

화면에서 접거나 보기 방식을 바꾸는 것은 문서를 수정하거나 전송하는 일이 아니다. 복사 안내 갱신으로 펼침 상태·읽던 구간·문서 위치·키보드 초점이 초기화되지 않아야 한다. 읽기/원문 보기가 있다면 각각의 위치를 같은 열기 안에서 유지한다. 다른 요청문·닫았다 다시 열기·다른 세션에는 이전 상태나 늦은 복사 완료가 새지 않는다. 수리93의 실제 opener 복귀와 긴 초안의 text·역선택·scroll, zero 자료 목록 복귀를 보존한다.

## 완료 조건과 범위

새 계약의 의미 있는 반례를 검사한다: 같은 제목을 가진 원자료, 반복 구절, 가짜 구분 제목·코드 fence, 한국어/emoji/줄바꿈, 검토한 자료와 선택 refs의 차이, 잘못된 순서·겹침·누락·범위·문자 경계, 나중에 바뀐 현재 plan, 여러 프로젝트가 섞인 구판 저장. 원문/복사·전체 저장 묶음의 보존을 확인한다. 구현 구조를 그대로 따라가는 검사 수로 완료를 선언하지 않는다.

실제 저장 사본의 과거 요청문과 공개 micro 자료에 기반한 새 긴 요청문을 정상 UI로 대조한다. 새 의미 생성은 필요하지 않다. 기존 모델 결과 재생과 검토자 합성 입력을 구별한다. 두 PC 크기에서 섹션 이동·자료 펼침·원문 전환·복사·닫기·재열기·저장 왕복을 실제 읽고, 별도 독립 실행과 정확한 최종 빌드/CI를 확인한다. 완료된93 전체 flow와 모델 실패 실험을 단순 재실행하지 않고 바뀐 경계만 검증한다.
