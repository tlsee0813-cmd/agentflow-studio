# 실제 기록 1건 — 병렬 연구 회수와 총괄 판단

2026-10-15 · 상태: 입력·연구 회수 완료, 읽기 비교와 새 구현은 미실행

## 범위

[동결 INPUT](INPUT.md)의 E01~E10만 사용했다. 합성 도서관 예제를 개발한 실제 AI 작업 기록이며, 실제 도서관 고객 기록은 아니다. 이후 UI02 fix3의 성공이나 새 환경 검증을 이 입력의 과거 상태에 덮어쓰지 않는다. 이 사이클은 기존 지도 전체를 재설계하기 전에, 선택한 부분의 기록을 읽을 때 근거와 상태가 왜곡되지 않는지 검토한다. 구조·작업·세션을 같은 계층의 자식 노드로 섞지 않는다.

Pro 두 세션에 서로 다른 좁은 질문을 병렬 배정했다. 하나는 통과 범위와 잔여 미결, 하나는 자료별 이름과 변경 지시의 차이다. 내부 Astra High가 공식 원문 네 개를 독립 대조하고 결합 제안을 반박했다. 총괄은 아래처럼 범위를 다시 좁혔다. 이 문서는 구현 배정표가 아니다.

## 받은 대안

| 질문 | 대안 가 | 대안 나 | 얻은 구분 |
|---|---|---|---|
| 통과와 미결 | H1 아래 범위별 결과표, 선택한 근거 상세 | 보완·판단 항목 목록, H1의 확인 범위를 짧게 병기 | 근거 대조와 개입 지점 찾기는 서로 다른 읽기 과업이다. 한 과업의 개선으로 다른 과업의 통과를 주장하지 않는다. |
| 자료별 이름 | A3에서 ‘의미 시안: 내 목록 / 캔버스·INPUT: 내 대여 목록’ 병기 | E01에서 자료 비교를 펼치고 작성자 설명·미확인 요청/승인을 구별 | 현재 표본은 표기 차이와 설명만 확인했다. 변경 전후·승인된 정정으로 그려서는 안 된다. |

공식 근거에서 가져온 것은 GitHub의 실행 상태/결론 및 검토 의견의 구별, Wikidata의 자료별 이름 병기 참고, MediaWiki의 특정 판 열기/비교다. 실제 서비스 조작 경험이나 AgentFlow 화면의 우위를 입증한 것은 아니다. [원문 대조와 반박](SOURCE_REVIEW.md)에 고정 출처·판 번호·확인 한계를 남겼다. 특히 GitHub의 줄별 상세는 코드 줄에 관한 것이며 임의 로그 줄 주석으로 확대하지 않는다. Wikidata 별칭 도움말도 확정 정책으로 인용하지 않는다.

## 총괄의 조건부 후보

전체 지도는 부분별 펼침과 외부 관계를 보존하는 비교 기준으로 유지한다. 그 위에서 선택한 부분을 읽는 공간만 다음에 비교한다. 기본 후보는 ‘확인할 부분’ 목록과 선택한 항목의 근거 읽기다. 모든 범위표와 사건을 한꺼번에 붙이는 결합안은 채택하지 않는다.

목록에는 다음 두 종류를 처음 읽는 자리에서 구별한다.

- **확인된 누락:** H1의 지정 화면 위치에 미결 참조가 없음. 어떤 위치·어떤 버전·어떤 방식의 검사인지 연결한다.
- **아직 확인하지 않은 것:** 독립 브라우저 미실행, 이름 변경 지시 미확인, 읽기 효용 미검증. 실패나 실행 지시로 바꾸지 않는다.

H1의 기존 독립 Node 5개 통과는 같은 자리에서 그 범위와 함께 보존한다. 작성자 단언 수·독립 사례 수·이미지 수를 합산한 점수나 전체 완료 배지를 만들지 않는다. 상세에서는 선택한 판단을 설명하는 자료만 연다. 원문, 전달 발췌, 검토 요약을 구별하며 해당 근거를 읽었다는 사실을 승인·수신·이해 완료로 바꾸지 않는다.

명칭은 자료명을 주어로 병기한다. 화살표·‘이전/현재’ 열로 정정 사건을 만들어 내지 않는다. 이번 A3의 같은 식별자는 병기의 근거지만, 다른 프로젝트에서 비슷한 이름을 자동으로 병합할 근거는 아니다. 비교를 닫으면 읽던 대상·펼침·위치를 보존한다. 기존 UI03 넓은 본문은 이 과업에 도움이 되는지 시험할 후보로만 유지한다.

## 이 선택을 바꿀 반례

1. ‘실패 알림 정책 미정’은 합성 사례의 내용이고 ‘미결 표시 누락’은 실제 시안의 결함이다. 예제의 정책을 결정해야 표시 결함을 닫을 수 있는 것처럼 읽히면 실패다.
2. 비슷한 두 이름이 서로 다른 기능 범위를 가리킨다고 밝혀졌을 때 자동으로 합치거나 정정 전후로 고정하면 실패다.
3. 목록 순서를 우선순위·의존성·이미 승인된 작업 배정으로 읽거나, 미실행을 실패로 읽으면 목록 후보를 줄이거나 결과표 후보로 돌아간다.
4. 근거를 읽고 돌아오려면 전체 지도를 다시 탐색해야 하거나 원래 선택을 잃으면 집중 공간의 이점이 없다.

## 다음 읽기 비교의 경계

2026-10-16 추가 사용자 지시에 따라 [전체 제품 목적 대조](PRODUCT_LENS.md)를 실시했다. 현재 표본의 정확한 검증 읽기는 제품의 일부다. 비교에서는 프로젝트 목적·선택 대상·관련 영역의 이해, 확인 목록을 모두 사용자의 숙제로 바꾸지 않는지, 근거를 읽고 판단·원래 보기로 돌아갈 수 있는지를 함께 본다. 현재 후보를 고수하기 위한 장식 수정에 머무르지 않는다. 별도 Pro 두 세션이 공간·탐색 및 기록·근거 읽기의 다른 사이트·오픈소스 메커니즘을 병렬 조사 중이며, 결과 수신 전 채택으로 기록하지 않는다. 원문·코드·조작 검증을 구분해 회수한 뒤 이 선택을 바꿀지 총괄이 판단한다.

동결 입력의 같은 기록을 두 표현에 놓고 다음을 관찰한다. 무엇이 어느 범위에서 통과했는지, 무엇이 실패이고 무엇이 미확인인지, 두 이름 사이의 변경 지시가 확인됐는지를 답할 수 있어야 한다. 질문은 정답을 포함해 유도하지 않는다. 답하지 못함·잘못 읽음·실행하지 않음을 따로 남긴다.

가 후보는 범위표 중심, 나 후보는 확인할 부분 목록과 선택 근거 중심이다. 비교하는 정보는 같고 누락 여부·근거까지 가는 과정·복귀 상태를 본다. 단순히 한 안에 정보를 더 많이 넣어 우수하다고 판정하지 않는다. **이 읽기 비교와 실제 화면 구현은 아직 실행하지 않았다.** 이번 연구 결과만으로 제품 구조를 일반화하거나 전체 수집기·실행 워크플로·새 데이터베이스를 개발하지 않는다.
