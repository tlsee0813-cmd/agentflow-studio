# 근거 읽기 메커니즘 — 원문 대조와 두 후보의 한계

2026-10-16 · 후속 표현 후보 검토 · 구현·원격 쓰기 없음

## 판단과 확인 범위

**A 판단본문+인용, B 자료·검사범위 대조면을 같은 기록으로 작게 비교하는 방향은 타당하다.** 목록은 보류하고 전체 맥락과 근거 접근의 공통 조건을 맞추는 것도 적절하다. 다만 A는 읽기 쉬운 서술이 근거보다 강한 판단을 만들 위험, B는 다른 검사를 동등한 조건으로 정렬할 위험이 있다. 둘 중 하나를 최종 제품 화면으로 채택할 근거는 아직 없다. 현재 기록에 없는 상충 발화를 만들거나 세 안과 여러 평가자 조합을 의무화할 필요도 없다. 기존의 ‘정보를 정확히 읽는가’에 더해 ‘프로그램을 이해하고 필요한 판단을 할 수 있게 되는가’를 비교해야 한다.

공식 설명 네 페이지와 지정 커밋의 코드·문서 네 파일을 직접 읽었다. Zotero와 Hypothesis는 설명과 이벤트 처리, Langfuse는 비교 기능 설명·peek 상태 문서·실행 없는 항목 분기까지 확인했다. 제품을 설치하거나 실제 클릭·스크롤·키보드 복귀를 실행하지 않았다. 공식 문서가 설명하는 기능, 코드가 요청하는 동작, 실제 화면에서 성공한 행동은 서로 다른 근거다. Pro 원 대화 전체가 아닌 총괄이 전달한 주장·제안을 대조했다. 코드의 직접 도입, 의존성·라이선스 적합성 검토는 이번 범위에 포함하지 않는다.

## 원문에서 확인된 메커니즘

**Zotero:** 노트에 넣은 주석은 PDF 페이지 연결과 인용을 포함할 수 있고, 여러 자료의 주석을 한 독립 노트에 모을 수 있다. 주석의 Show on Page와 인용의 Show Item은 원문 맥락과 서지 항목을 여는 서로 다른 행동이다. 페이지 이동은 가능한 경우에 수행되며 외부 리더 모두를 보장하지 않는다. 지정 `index.web.js`의 `onOpenAnnotation`은 `attachmentURI`와 `position`을 부모 쪽으로 전달한다. 이는 위치 전달의 코드 근거다. 정확한 커서 위치로 돌아오기, 원래 노트의 스크롤 복원, 여러 원문 왕복 성공까지 증명하지 않는다. ‘판단본문’ 자체는 Zotero의 기능 사실이 아니라 AgentFlow에 적용하려는 제안이다. [공식 설명](https://www.zotero.org/support/pdf_reader), [고정 코드](https://github.com/zotero/note-editor/blob/7439a18414ffa6e90918283da9e4dbd35fce1a97/src/index.web.js)

**Hypothesis:** 공식 설명은 원문 강조를 눌러 주석을 보거나 사이드바에서 주석을 탐색하는 방식을 설명한다. 지정 `ThreadCard.tsx`는 카드 클릭을 원문 위치 이동에 연결하되, 내부 버튼·링크에서 발생한 클릭에는 카드의 기본 스크롤을 덧붙이지 않는다. 카드 자체의 Enter/Space도 별도로 다룬다. 따라서 참고할 것은 ‘근거 읽기와 다른 조작이 서로 원치 않는 이동을 일으키지 않게 한다’는 구분이다. 모든 내부 링크가 절대 이동하지 않는다는 주장은 과도하다. 해당 링크의 자체 동작까지 이 가드가 막지는 않는다. [기본 설명](https://web.hypothes.is/help/annotation-basics/), [고정 카드 코드](https://github.com/hypothesis/client/blob/57a5dc18712922cc08a1cfa5aa146b6c88d7f8df/src/sidebar/components/ThreadCard.tsx)

원문 연결을 잃은 주석은 삭제되지 않으며, 원래 선택 문구에 취소선이 표시된다는 설명도 확인된다. 상위 주석이 사라져 답글의 연결을 잃는 경우도 있다. 여기서 취소선은 결정 철회나 주장 반박을 뜻하지 않는다. AgentFlow에서 같은 표시를 복제하면 ‘근거 위치를 못 찾음’이 ‘이전 결정을 폐기함’으로 읽힐 수 있다는 것은 타당한 **위험 가설**이다. 실제 오독을 관측한 결과는 아니다. 연결 상태와 내용의 유효성은 따로 표시해야 한다. [연결을 잃은 주석 설명](https://web.hypothes.is/help/what-are-unanchored-annotations/)

**Langfuse:** 비교 기능 설명은 같은 데이터 항목의 두 실험 결과를 안정적인 식별자로 맞추고 기준 실험과 후보를 대조한다. 이는 비교 대상을 계속 식별할 근거이지, 서로 다른 검사 묶음의 점수를 바로 비교해도 된다는 근거가 아니다. peek README는 통합된 표의 항목 전환 중 필터·정렬·페이지·검색 상태를 유지한다고 설명한다. 닫으면 초기화되는 것은 그 내부 표의 문맥이다. 패널 폭의 저장이나 URL의 확대 상태까지 모두 같은 수명으로 일반화하면 안 된다. 이 파일은 문서 근거이며 해당 상태 훅 전체를 독립 실행하지 않았다. [비교 기능 설명](https://langfuse.com/changelog/2025-11-06-compare-view-baseline-support), [고정 peek 문서](https://github.com/langfuse/langfuse/blob/abc652fcfb7ff55fe4bc696292db157182819e19/web/src/components/table/peek/README.md)

`peek-experiment-item-detail.tsx`는 `traceId`가 없을 때 선택 실험에 해당 항목 실행이 없다는 문구를 반환한다. 이 분기를 실패로 표시하지 않는다는 Pro 설명은 맞다. 다만 모든 데이터 누락의 원인이 미실행이라고 판정하는 일반 규칙은 아니다. AgentFlow에서는 기록 미수신·원본 접근 불가·검사 미실행·실패를 확보된 근거대로 구분해야 한다. [고정 실험 항목 코드](https://github.com/langfuse/langfuse/blob/abc652fcfb7ff55fe4bc696292db157182819e19/web/src/components/table/peek/peek-experiment-item-detail.tsx)

## A와 B를 반박할 핵심 조건

**A의 본문은 사실상 편집된 결론이다.** 인용이 붙어도 그 문장이 자료의 범위를 넘을 수 있다. 예를 들어 H1의 ‘수정 완료’라는 문장은 기존 독립 다섯 검사 통과만 연결해 놓고 INPUT 9의 누락을 가릴 수 있다. 문장별 인용이라는 형식보다 결론의 범위가 맞는지가 우선이다. ‘목록 복귀는 독립 상태 검사에서 복원, 지정 위치의 미결 표시는 보완 대기’처럼 실제로 함께 성립하는 사실을 읽을 수 있어야 한다. 한 출처가 문장 전체를 지지하지 않으면 근거를 나누거나 문장을 좁혀야 한다. 인용이 많은 화면을 더 신뢰할 만한 화면으로 자동 판정하지 않는다.

**B의 ‘중립’은 행과 열을 고르는 순간 제한된다.** 작성자 84단언, 독립 5사례, 새 13사례를 나란히 놓으면 비교 가능한 표본처럼 보일 수 있다. 같은 H1이라는 버전 일치만으로 범위·환경·검사 목적까지 일치하지 않는다. 비교는 통과 수의 경쟁보다 ‘어떤 위치와 행동을 어떤 방식으로 확인했는가’에 맞춰야 한다. 대응하지 않는 셀은 미실행과 구별되는 ‘이 범위의 비교 대상 아님’일 수 있다. 셀을 펼친 뒤 상대 자료가 남아 있어도 의미상 비교 불가능하면 장점이 없다. 정확한 대응이 불가능한 자료를 억지로 대칭 배열하지 않는지가 핵심이다.

**공통 공간 조건 역시 가설이다.** 전체 지도, 본문, 원문 미리보기를 모두 계속 보이게 하면 좁은 화면에서 내용이 밀려 날 수 있다. 보존해야 하는 것은 모든 패널의 동시 노출보다 프로젝트 목적·선택 대상·관련 부분과 돌아갈 위치다. 미리보기와 실제 원문 이동은 명시적으로 구분하되, 미리보기가 원본 전체나 최신 자료를 보장한다고 오해시키지 않는다. 전달 발췌만 있는 명칭 설명은 원문인 척 열지 않는다. 외부 원문으로 나갔다 돌아오는 복귀 조건도 별도로 관측해야 한다.

## 전체 제품 목적에 연결할 최소 비교

현재 자료는 시안 개발의 검사 기록이라 두 표현 모두 QA 화면으로 수렴하기 쉽다. 프로그램 목적과 구성보다 검사 묶음이 주 탐색 단위가 되고, 사용자에게 매번 사실 감사를 요구한다면 최종 목적과 멀어진다. 근거는 잘못된 정리를 바로잡거나 범위를 정해 이어 맡길 때 필요한 지원이지, 사용자의 모든 시간을 차지할 기본 과업은 아니다. 대상의 의미와 관련 영역을 짧게 이해한 뒤 필요한 근거만 여는지 확인해야 한다. 자동 정리의 책임을 사용자의 인용 검수로 넘기지 않는다.

다음 비교는 동일한 동결 기록, 동일한 목적 설명과 실제 출처로 A/B 두 표현만 둔다. 첫 질문은 통과 수가 아니라 ‘이 부분은 무엇이며 무엇까지 확인됐는가’로 잡는다. 이어 필요한 근거를 확인하고, 무엇은 보완 대상이며 무엇은 아직 모르는지 설명한 뒤 원래 대상에 돌아오게 한다. 사용자에게 없는 결정을 내리도록 요구하거나 답을 문항에 넣지 않는다. 인계 원문이 없는 표본에서는 다음 담당자에게 필요한 범위를 읽는 것까지만 보며 실제 위임 성공을 주장하지 않는다.

목록 후보 보류는 적절하지만 영구 폐기 판단은 아니다. A가 과도한 서술 결론을 만들거나 B가 비교 조건을 숨기면 둘 다 줄이거나 다른 표현을 다시 검토할 수 있다. 기존 기록의 범위 차이를 진짜 상충 주장으로 꾸미지 않는다. 확인되지 않은 충돌을 추가해 특정 화면의 필요성을 증명하는 것도 피한다. 이번에는 근거까지의 접근, 범위 오독, 불필요한 이동, 대상 맥락 보존만 관측하고 차이가 없으면 그 한계를 기록한다. 메커니즘의 존재와 AgentFlow에서의 우수성은 끝까지 별개다.
