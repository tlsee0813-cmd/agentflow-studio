# Zotero 갱신 메커니즘 원문 대조와 적용 조건

2026-10-16 · 소스 읽기·조건부 판단 · UI·테스트 실행·코드 이식 없음

**A 사용자 표시명/보기 묶음 지속과 B 기준 이후 양측 변경 반영을 제품 전체의 양자택일로 두는 것은 부적절하다.** A는 사용자 조정의 권위·지속 범위에 관한 정책이고 B는 변경을 판별하는 방법이다. 함께 적용될 수 있지만, 모든 필드에서 장점을 합쳐 자동 해결할 수 있다는 뜻도 아니다. 무엇을 바꾼 것인지와 같은 대상인지 먼저 확인해야 한다.

## 핵심 주장 대조

고정 커밋 `db41b99fddcc52d38897c59c161b6adaca036afb`의 Zotero 파일 두 개와 공식 동기화 문서를 직접 읽었다.

- **기준 JSON과 두 변경 집합: 확인.** [`syncLocal.js` 1940–2220행](https://github.com/zotero/zotero/blob/db41b99fddcc52d38897c59c161b6adaca036afb/chrome/content/zotero/xpcom/sync/syncLocal.js#L1940-L2220)은 기준→현재 로컬, 기준→새 원격의 diff를 계산한다. 같은 변경은 중복 적용하지 않고 다른 필드·다른 집합 원소의 변경을 구분한다. 반환값은 적용할 원격 변화·충돌 쌍·로컬 미동기화 여부다. 이 함수만으로 저장·화면·전체 동기화 성공까지 확인한 것은 아니다.
- **비중첩 자동 반영: 조건부로 정확.** 코드가 판별하는 비중첩은 필드와 원소 수준이다. 서로 다른 필드가 의미상 독립이라는 보장은 없다. 태그 종류 차이, 같은 작성자 배열, `lastRead` 최신값 등 별도 규칙도 있어 ‘동일하거나 비중첩이면 모두 같은 방식’이라는 요약은 거칠다. 양쪽 모두 휴지통인 item과 non-item 충돌에는 원격 변화 적용 예외가 있다. non-item 전체를 매번 원격 사본으로 교체한다는 뜻은 아니다.
- **기준 캐시가 없으면 집합 추가 중심: 확인.** 같은 파일의 `_reconcileChangesWithoutCache`는 member/property-member 삭제를 건너뛰고 추가를 반영한다. 컬렉션·태그·관계의 제거가 되살아날 수 있는 보수적 합집합이다. 일반 item 필드 차이는 충돌로 남기되 non-item·양쪽 휴지통 item·`lastRead` 등의 예외가 있다. 따라서 ‘기준 없이도 사용자 조정을 안전하게 보존한다’는 적용 근거는 되지 않는다. 사용자가 일부러 풀어 놓은 묶음을 복구해 버릴 수 있기 때문이다.
- **옛 URI와 병합 연결: 확인 범위를 좁혀야 한다.** [`mergeItems.mjs`](https://github.com/zotero/zotero/blob/db41b99fddcc52d38897c59c161b6adaca036afb/chrome/content/zotero/mergeItems.mjs)의 `mergeItems`·`moveRelations`는 병합 대상으로 전달된 항목의 관계를 이동하고 같은 라이브러리의 참조를 새 대상으로 바꾸며 대체 관계를 남긴다. ‘병합 실행 경로에서 옛 식별 연결을 보존한다’는 근거다. **이 파일은 사람이 병합을 확인·승인했다는 UI 근거가 아니다.** 분할 후 옛 기록을 어느 새 부분에 귀속할지 자동 판단한다는 근거도 없다.

[공식 Web API 동기화 문서](https://www.zotero.org/support/dev/web_api/v3/syncing#conflict_resolution)는 버전에 묶인 기준 JSON을 저장하고 양측의 변화를 비교하며, 충돌하지 않는 변화를 자동 병합하는 원칙을 설명한다. 동시에 상세 충돌 해결은 문서에 완전히 기술하지 않았다고 밝힌다. API 버전은 오래된 데이터의 덮어쓰기를 막는 장치이지 발언 의도·사용자 승인·프로그램 정체성의 증거가 아니다.

라이선스는 같은 `syncLocal.js` 머리말에서 **AGPL v3 또는 이후 버전**으로 확인했다. 이번 결과는 메커니즘 연구이며 이식 가능성·라이선스 의무의 법률 판단은 하지 않았다.

## 우리 선택에 대한 반박과 좁은 적용

**표시 조정:** 사용자가 붙인 표시명이나 보기 묶음이고 같은 구성의 연속성이 확인된다면, AI가 다른 표현을 썼다는 이유만으로 되돌리지 않는 A의 방향이 맞다. B의 변경 비교는 그동안 실제 기능·관계에 새 정보가 생겼는지를 찾는 데 함께 쓸 수 있다. 여기서 ‘사용자 우선’을 대상 전체의 모든 정보를 영구 고정한다는 뜻으로 확대하면 자동 갱신이 멈춘다.

**작업 기준 조정:** 범위·목적·실제 포함 관계를 바꾼 경우에는 이름 유지와 다른 영향이 생긴다. 로컬이라는 이유로 참이 되거나 원격이라는 이유로 최신 결정이 되지 않는다. 다른 필드에 기록됐더라도 의미가 충돌할 수 있으므로 B만으로 자동 수용하면 안 된다. 반대로 차이마다 사용자 승인을 요구하면 지도 관리 숙제가 된다. 판단을 가르는 기준은 위치나 화자가 아니라 조정의 의미, 연결 대상, 근거와 영향이다. 불확실한 일부를 남기는 것이 모든 갱신을 멈추는 것과도 다르다.

**FIX058의 역할:** 이번에는 로컬 `REAL_CHANGE_CANDIDATE.md`를 읽었으며 그 문서가 인용한 원 개발 파일·코드·대화는 재검증하지 않았다. 문서상 `Task.intentEdit`와 `manual.*` 분리는 목적 정정과 직접 작업 지시를 같은 값으로 취급하면 안 된다는 유용한 반례다. 그러나 사용자 원발화·변경 의도·실제 인계 수신/수락이 빠져 있어 A/B 중 무엇이 실사용에서 성공했는지 판정하는 표본은 아니다. 구현 담당 전환이 기록됐다는 사실도 요청 변경 때문에 인계됐다는 인과로 바꾸지 않는다.

다음 비교는 같은 대상의 **보기 조정인지 작업 기준 변경인지 확인 가능한 한 연쇄**에서 자동으로 이어져야 할 것과 판단을 남겨야 할 것을 구별하는 데 한정하는 것이 타당하다. 캐시·식별 단서가 없는 경우를 확정 변화처럼 채우지 않는다. 기본 공간 지도에는 현재 설명·중요 변화·필요 판단만 남기고 차이 집합과 원문은 필요한 상세에서 읽게 한다는 제품 방향을 유지한다. 새 병합 엔진·승인함·분할 귀속 기능을 이번 연구의 개발 목록으로 만들 근거는 없다.
