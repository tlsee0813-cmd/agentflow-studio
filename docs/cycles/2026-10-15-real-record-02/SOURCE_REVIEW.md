# 실제 기록 후속 연구 — Pro 제안의 원문 대조와 반박

2026-10-15 · 연구 판단 초안 · 설계 확정·추가 구현·원격 쓰기 없음

## 결론과 확인 범위

총괄의 결합안은 검토할 가치가 있지만, 현재 근거로 두 대안보다 낫다고 채택하기는 이르다. 보완 판단 목록, 확인 범위 요약, 상세 범위표와 사건 기록을 함께 두면 서로 다른 과업을 지원할 수 있다. 동시에 사용자가 읽어야 할 구획과 오갈 단계도 늘어난다. ‘개입 찾기에는 목록, 근거 대조에는 표’라는 조건부 권고를 합쳤다는 이유만으로 두 과업의 장점이 자동 보존되지는 않는다. 이번에는 **하나의 목록을 기본으로 두고 선택한 항목의 근거만 여는 후보** 정도로 좁혀 비교하는 편이 낫다. 넓은 읽기 공간도 그 후보의 한 표현이지 확정된 해법은 아니다.

공식 원문 네 곳을 직접 열람했다. GitHub의 지정 blob 주소 두 개는 접근 시간이 초과됐지만 같은 커밋 SHA의 raw 문서 두 개는 읽었다. 따라서 고정 문서의 내용은 확인했으나 GitHub의 실제 상호작용이나 현행 화면을 조작한 것은 아니다. Wikidata와 MediaWiki는 현재 도움말 본문을 읽었고 반환된 판 식별자는 각각 `2515832598`, `8524540`이었다. 아래 Pro 주장의 대조 대상은 총괄이 전달한 요약이며 Pro 원 대화 전체를 독립 열람한 것은 아니다. 기존 실제 기록의 E10 동결점을 유지하며 이후 수정 결과로 입력을 갱신하지 않는다.

## 공식 사실과 제안의 경계

**Checks:** 실행 중의 상태와 완료 후 결론을 구분한다는 주장은 확인된다. 고정 원문은 완료 상태에 결론이 붙으며, 성공 외에 취소·중립·건너뜀·시간 초과 등의 결론을 설명한다. 또한 검사에 빌드 로그·시험 결과·주석·상세 링크를 포함할 수 있다고 한다. 다만 ‘로그 결과 줄 주석’은 좁혀 고쳐야 한다. 해당 원문은 검사가 특정 **코드 줄**을 가리킬 때 Files 탭에도 상세가 나타난다고 설명한다. 임의의 로그 줄에 주석을 붙이는 기능까지 입증하지 않는다. 이것은 실행 완료와 성공의 구별에 참고할 사실이며, 프로젝트 전체 완료 상태를 정하는 모범 규칙은 아니다. [고정 Checks 원문](https://raw.githubusercontent.com/github/docs/688c35b8cfab458944d717e91c52810b8e39eb4c/content/pull-requests/reference/status-checks.md)

**Reviews:** Comment는 명시적 승인·변경 요청 없이 의견을 남기는 선택, Approve는 병합 준비를 알리는 선택, Request changes는 작성자가 병합 전에 다룰 피드백을 표시하는 선택이라는 설명이 확인된다. 검토 대화가 시간선에 나타난다는 주장도 맞다. 그러나 이것이 모든 검토의 실제 수락·이해·수행이나 프로젝트의 최종 완료를 증명하지 않는다. 이 사례에 가져올 것은 ‘결과 반환’과 ‘누가 어떤 범위를 수용했는가’를 분리하는 원칙 정도다. AI 기록자에게 GitHub의 세 결정형을 그대로 붙이는 것은 별도 설계 제안이다. [고정 Reviews 원문](https://raw.githubusercontent.com/github/docs/688c35b8cfab458944d717e91c52810b8e39eb4c/content/pull-requests/reference/pull-request-reviews.md)

**Aliases:** 항목에 대표 이름 외의 대체 이름을 여러 개 둘 수 있고, 설명이 다르면 여러 항목이 같은 별칭을 가질 수 있다는 설명을 확인했다. 따라서 두 자료의 이름을 함께 남기는 참고 사례로는 적절하지만, 이름이 같거나 비슷하면 같은 기능으로 합칠 수 있다는 근거는 아니다. 더구나 이 도움말에는 제안 지침과 작업 중이라는 표시가 있다. 확정 정책이나 보편적 명명 원칙으로 인용하지 않는다. 현재 A3는 자료에서 같은 식별자를 가진다는 별도 근거가 있으므로 병기가 가능하다. 그 근거가 없는 다른 사례까지 자동으로 확장하면 안 된다. [Aliases 원문](https://www.wikidata.org/w/index.php?title=Help:Aliases&oldid=2515832598)

**History:** 두 판을 골라 비교하거나 날짜를 눌러 특정 판을 여는 기능은 확인된다. 그러나 이 기능은 기록된 판의 비교다. 자료 두 개의 표시 차이를 변경 지시나 승인 이력으로 만들어 주지 않는다. 또한 도움말은 문서 원문의 판 이력과 렌더링된 화면의 이력이 같지 않을 수 있다고 경고한다. 여기서는 자료를 특정하여 여는 방식만 참고하고, 확인되지 않은 과거 화면·요청·승인을 채우지 않는다. [History 원문](https://www.mediawiki.org/w/index.php?title=Help:History&oldid=8524540)

## 결합안이 실패할 수 있는 이유

첫째, ‘보완 판단 목록’은 이미 누군가 실행할 일을 결정했다는 인상을 줄 수 있다. 하지만 표본에는 기능 누락, 검사 미실행, 사람 읽기 효용 미검증, 명칭 변경 지시 미확인이 섞여 있다. 이들은 모두 같은 보완 행동을 요구하지 않는다. 특히 독립 브라우저 미실행은 결함 확정이 아니고 명칭 지시 미확인은 당장 고쳐야 할 기능도 아니다. 목록에서 ‘남은 일’ 하나로 평탄화하면 원래 표가 유지하던 범위와 증거 수준을 잃는다. 미실행이나 미확인을 실패 배지로 바꾼다면 결합안은 오히려 후퇴다.

둘째, 목록의 통과 범위 요약이 너무 짧으면 H1의 기존 5개 통과와 새 위치별 실패가 서로 충돌하는 것처럼 보인다. 이를 피하려고 모든 검사명·범위·버전·주장을 목록에 넣으면 상세 표가 목록 안에 다시 생긴다. 반대로 전부 숨기면 상세를 열기 전에 판단을 요구하게 된다. 최소한 H1, 검사 범위, 증거 종류와 ‘기존 5개 통과 / INPUT 9 위치별 누락’의 공존은 처음 읽는 자리에서 구별돼야 한다. 구체적인 집계와 원문 대조는 선택 후 읽을 수 있다. 이 경계를 구현 전에 문장 수준으로 시험해야 한다.

셋째, 사건 기록과 범위표를 상세에서 같이 보여도 대응이 자동으로 명료해지지는 않는다. 한 표 행의 ‘통과’가 작성자 로그인지, 독립 Node 결과인지, 통합자의 좁은 수용인지 바로 연결되지 않으면 두 자료를 왕복하며 해석해야 한다. 현재 확보한 것이 요약이나 전달 발췌라면 이를 ‘원문’이라고 부르는 것도 과장이다. 상세는 원문·발췌·검토 요약의 종류를 표시하고, 선택한 판단이 어느 기록의 어느 범위에 기대는지 연결해야 한다. 연결되지 않는 자료를 많이 넣는 것은 정보 보존이지 읽기 개선의 증거가 아니다.

넷째, 동일 ID 아래 자료별 명칭을 병기해도 ‘내 목록 → 내 대여 목록’처럼 화살표나 이전/현재 열을 쓰면 정정 이력으로 읽힐 수 있다. 기본 표현은 ‘의미 시안: 내 목록 / 캔버스·입력: 내 대여 목록’처럼 자료 이름을 주어로 삼아야 한다. 비교 펼침은 두 자료의 표시와 짧은 작성자 설명을 확인하는 행위여야 한다. 같은 ID라는 이유만으로 기능 범위가 같다는 결론까지 자동 생성하지 않는다. 이후 범위 차이가 발견되면 동일성 판단을 다시 열어야 하며 별칭 병기가 그 논의를 봉쇄해서는 안 된다.

## 수정 추천과 다음 비교의 실패 조건

목록을 기본으로 삼는다면 제목은 ‘보완 지시’보다 **판단이 남은 항목**에 가까워야 한다. 각 항목에는 무엇의 상태인지와 현재 증거 범위를 짧게 붙이고, 실행 배정·수용·완료는 확인된 기록이 있을 때만 표시한다. 세부 표와 사건 자료는 해당 항목의 판단을 설명하는 범위로 한정한다. 사용자가 지금 해야 할 행동을 찾는 과업과 이미 받은 주장의 근거를 대조하는 과업을 별도로 관측한다. 어느 하나를 잘했다고 다른 하나도 개선됐다고 결론내리지 않는다.

두 반례를 반드시 남긴다. ‘실패 알림 정책 미정’은 합성 예제의 내용이고 ‘그 미결 참조의 화면 표시 누락’은 실제 시안의 결함이다. 앞의 정책을 결정해야 뒤의 구현 결함을 닫을 수 있는 것처럼 보이면 실패다. 또 이름이 비슷해도 기능 범위가 다른 자료를 주었을 때, 같은 항목으로 자동 병합하거나 변경 전후로 단정하면 실패다. A3의 이번 병기 성공은 그 반례를 면제하지 않는다.

비교에서는 사용자가 세 질문에 답할 수 있는지만 우선 본다. 무엇이 실제로 통과했고 어느 방식으로 확인됐는가, 무엇은 실패이고 무엇은 아직 확인하지 않았는가, 두 이름 사이에 확인된 변경 지시가 있는가. 기본 목록에서 필요한 단서를 못 찾거나 상세를 열어도 범위가 뒤섞이면 결합 후보를 줄인다. UI-03의 넓은 읽기 공간은 이 과업을 돕는지 관찰할 후보로 유지한다. 이번 원문 대조는 화면 우위·사람 이해도·최종 채택을 입증하지 않는다.
