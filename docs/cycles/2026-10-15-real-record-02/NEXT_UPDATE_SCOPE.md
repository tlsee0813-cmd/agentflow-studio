## 선택을 바꿀 한 장면

사용자가 프로그램의 한 부분에 익숙한 이름을 붙이거나 보기 위한 묶음을 조정한 뒤, 외부 AI의 다음 작업 기록이 들어온다. 사용자는 전체 그림에서 같은 부분의 작업이 이어졌음을 이해하면서 자신의 조정이 어디까지 유지되고 실제 구성에 무엇이 달라졌는지 알 수 있어야 한다. 이번 질문은 QA 근거를 더 정교하게 읽는 방법에서 **자동 정리와 사용자 조정이 함께 지속되는 경험**으로 옮긴다. 현재 reading-study fix1 종료의 선행 조건이 아니다.

**읽은 세 문서 안에서는 이 장면의 실제 기록을 찾지 못했다.** 저장소 전체나 비공개 대화에도 없다는 결론은 아니다. 위 GitHub 링크는 이동 가능한 브랜치이며 열람한 내용은 blob 해시로 구별한다. 현재 v0/fix1 검토에서 확인한 문장별 대상 명시의 효용과 B 모바일 비교 상대 미노출은 입력 표현의 주의점으로만 이어받는다. 사용자 조정 보존이 검증됐다는 증거로 확대하지 않는다.

## 조사 질문 두 개

- **무엇을 보존하고 무엇을 갱신할까?** 이름·보기 묶음 조정과 실제 기능 범위·포함 관계 변경을 어떻게 구별하는가. 사용자가 지정한 이름을 보존하더라도 새 기능 변화는 반영해야 하고, AI가 예전 용어를 썼다는 이유만으로 새 구성요소를 만들거나 사용자 조정을 되돌리면 안 된다. 반대로 이름이 비슷하다는 이유만으로 다른 기능을 합쳐서도 안 된다. 이는 고정 우선순위 규칙 확정이 아니라 기존 도구 메커니즘 조사에서 확인할 구별이다.
- **어떤 차이만 사용자의 판단을 필요로 할까?** 근거가 충분한 연속 작업은 자동으로 같은 부분에 이어지고, 의미가 갈리는 변화만 관련 맥락과 함께 드러나는가. 모든 기록의 승인·대응표 작성·지도 수선을 사용자에게 요구하는 후보는 제품 목적에 맞지 않는다. 외부 AI에 조정 내용이 전달됐거나 반영됐다는 주장은 별도 근거가 있어야 한다.

## 관측에 필요한 최소 입력

짧은 하나의 전후 연쇄면 충분하다. (1) 프로그램 목적과 해당 부분·이웃 관계가 드러나는 조정 전 상태, (2) 사용자가 실제 무엇을 바꿨는지 확인되는 발화 또는 조작 기록과 조정 후 상태, (3) 그 뒤 들어온 AI 작업 기록 및 같은 대상인지 판단할 수 있는 기능·범위·출처 단서가 필요하다. 이름 조정 하나 또는 묶음 조정 하나부터 택하며 둘을 의무적으로 한 표본에 넣지 않는다. 발언 의도가 확인되지 않으면 ‘보기 취향’ 또는 ‘작업 기준 변경’으로 임의 분류하지 않는다. 실제 발생 순서와 수신 순서가 다르다면 구분하되, 없는 시각을 만들지 않는다.

실제 표본을 확보하지 못한 동안에는 위 조건을 명시한 **합성 경계 사례**로 메커니즘의 논리적 차이만 비교할 수 있다. 기존 E01에 가상의 사용자 지시나 승인 사건을 덧붙이지 않는다. 합성 결과를 자동 정리 품질·실사용 효용의 관측으로 보고하지 않는다.

## 진행·중단 조건

진행은 위 최소 연쇄가 확보되거나 합성임을 표시한 논리 비교 범위가 정해졌을 때 가능하다. 기존 메커니즘은 사용자 조정의 보존 범위, 새 기록 연결 근거, 불확실할 때의 처리, 사용자 개입량으로 대조한다. 실제 읽기에서는 사용자가 전체 목적·대상의 연속성·새 변화·필요한 판단을 설명할 수 있는지와 반복 정리 부담을 관측한다. 모든 근거를 항상 펼쳐 놓거나 기술적 식별자를 사용자가 관리하도록 요구하지 않는다.

사용자 조정의 원문이나 대상 연결 단서가 빠지면 실제 사례 판정을 멈추고 입력 부족으로 남긴다. 후보 간 차이가 없는 입력이면 검사 수나 표현 장식으로 우열을 만들지 않는다. 변경 처리 엔진·연결기·모든 충돌 유형 구현이 필요해지면 범위를 넘은 것으로 중단한다. 이 메모는 새 개발 목록이나 현 시안 수정 요구가 아니다.
