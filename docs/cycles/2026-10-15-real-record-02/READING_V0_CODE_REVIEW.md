## 먼저 보완할 점

**최우선 실제 렌더링 확인: 미리보기의 `hidden` 속성과 CSS가 충돌할 위험.** HTML `113행`은 `.pv-body{display:flex}`를 선언하고 `229·610행`은 해당 요소를 `hidden` 속성으로 숨긴다. 이 속성을 명시적으로 우선하는 CSS 규칙은 없다. 넓은 화면에서 닫힌 본문이 실제로도 숨는지 확인해야 한다. `browser_check.py`의 snap·닫힘 판정은 `pvBody.hidden` 속성을 읽으며, overflow 검사도 `[hidden]`의 자손을 먼저 제외한다. 따라서 속성은 true인데 author CSS 때문에 실제 본문이 남는 경우를 잡지 못할 수 있다. 좁은 화면의 `.preview.closed{display:none}`와도 구분해야 한다. 이 감사자는 브라우저를 실행하지 않았으므로 실제 노출 여부는 root의 별도 브라우저 관측으로 확정한다. 수정·재검사 시에는 속성값뿐 아니라 실제 계산 스타일·레이아웃·닫힌 미리보기의 표시/조작 가능성도 판정해야 한다.

1. **링크 검사에서 빈 실행을 성공 처리할 수 있다 — 재사용 전 보완 권장.** `checks/check_links.sh:7–17`은 URL 추출 결과가 0개여도 `fail=0`이므로 종료 0이다. 파일 읽기·추출 실패도 별도로 판정하지 않는다. 예상 링크 집합/개수 11개와 추출 성공을 확인한 뒤 HTTP 결과를 판정해야 한다. 현재 제출본에는 실제 11개 PASS가 있어 이번 결과를 빈 검사로 판단하지 않는다. `static_check.py:116`도 허용 집합의 **부분집합** 여부를 검사하므로 링크 누락 전체를 대신 검출하는 계약은 아니다. 이 경로를 실제로 변형·실행한 결과가 아니라 코드에서 확인한 한계다.
2. **변형 검사의 성공 원인을 더 좁혀야 한다 — 현재 5개 검출은 유효.** `mutation_check.py:23–29`는 nonzero 종료와 어떤 `FAIL` 행이 있으면 검출 성공으로 센다. 변형별 기대 실패 이름을 대조하지 않으므로 공통 탐색·조작 중단도 성공 조건을 만족할 수 있다. 기대 검사 실패와 환경/fatal 중단을 구분하고 변형별 원본 JSON·로그를 보존하는 편이 낫다. 제출 로그에는 복원 제거→초점/스크롤, 같은 탭→새 탭/팝업, 출발 미갱신→표현 B 출발, 시트 가림→hit/geometry, 스크롤 잔존→새 미리보기 scrollTop의 의도 관련 실패가 각각 남아 있다. 현 5/5를 폐기할 근거는 없다. 실제 기록은 모두 exit 1이며, 코드 조건 자체는 정확히 1만 요구하지 않는다.
3. **열린 상태의 viewport 변경 뒤 복귀는 미검사 위험이다 — 기능 실패 확정 아님.** HTML `596·606–614·647행`은 열기 당시 버튼의 화면상 `top`을 저장하고, 닫을 때 그 숫자로 복귀한 뒤 `preventScroll`로 초점만 돌린다. resize 처리에서는 시트 여백만 바꾸며 저장한 높이를 새 viewport/헤더 범위로 보정하거나 `arrangeSheet()`를 다시 호출하지 않는다. 예를 들어 높은 화면 아래쪽에서 연 뒤 높이를 줄이면 옛 좌표가 새 viewport 밖이 될 수 있다. 향후 복귀 계약에는 새 가시 범위로 좌표 보정 또는 의미상 출발점 재배치를 명시할 필요가 있다. 현재 203개 검사는 각 고정 viewport의 새 context를 사용해 resize 도중 복귀를 검사하지 않는다.

## 실패·fatal·실행 묶음

- **`browser_check.py:242–261`:** viewport 내 예외는 `조작 시나리오가 중단 없이 끝남`의 FAIL로 추가하고 다음 viewport를 진행한다. 하나라도 실패하면 종료 1이다. Playwright import·setup·launch·close·JSON 쓰기 등 바깥 예외는 정상 종료로 바꾸는 `finally/sys.exit`가 없어 Python nonzero로 전파된다. 이전 UI02 검사기에서 발견한 fatal 예외의 false exit 0 형태는 이 코드에서 찾지 못했다. 다만 setup 실패 시 구조화된 JSON 없이 traceback만 남을 수 있고, 정확한 기대 검사 집합 203개를 별도로 검증하는 계약은 없다.
- **`mutation_check.py`:** 교체 지점은 정확히 한 번 존재해야 한다. subprocess timeout은 잡아 성공으로 바꾸지 않으므로 nonzero로 중단된다. 다섯 변형의 검사 목적은 분명하지만 앞서 적은 실패 원인 분류·증거 보존은 보완 대상이다.
- **`run_all.sh:4–13`:** 정적·브라우저·링크의 종료 코드를 각각 저장한 뒤 세 코드가 모두 0일 때만 성공한다. 변형 검사는 별도 실행이며 REPORT도 이를 구분한다. `set -e` 부재 자체는 이 설계의 false pass가 아니다. 다만 실행 경로의 기존 logs/shots를 덮어쓰고 브라우저 JSON의 존재만 보고 이동하므로, fatal 때 이전 실행 파일을 새 근거로 오인하지 않게 빈 출력 폴더·실행별 식별자를 쓰는 것이 좋다. 이번 감사에서는 이 묶음을 원본 폴더에서 실행하지 않았다.

## 버전·외부 의존·검사 수준

HTML은 데이터·스타일·동작이 내장된 단일 파일이며 외부 스크립트·스타일·폰트·fetch 의존을 코드에서 찾지 못했다. 외부 GitHub 링크 11개는 입력의 고정 커밋 `1ec44cc…`, 역사적 자료 `666437a…`, 재실행 설명 R1 `3847a9b…`에 묶여 있다. R1의 동결 이후 정보와 최초 JSON이 아님을 알리는 문구도 있다. 링크 HTTP 검사는 원격 접근이 필요하고 검사 실행에는 Python·Playwright/Chromium·curl이 필요하지만, 화면의 숨은 실행 의존으로 섞여 있지는 않다. 브라우저 코드는 기본 설치 Chromium을 실행하며 런타임을 설치·고정하는 스크립트는 아니다.

작성자가 이미 명시했듯 `browser_check.py`는 `https://github.com/**` 요청을 로컬 스텁으로 응답한다. 확인한 것은 고정 URL의 새 탭 열기와 **읽기 페이지가 그대로 남는 상태**다. 실제 GitHub 내용·인증/차단·그곳에서 읽고 돌아오는 사용자 왕복은 미실행이다. 이는 누락을 새로 발견한 결함이 아니라 보존해야 할 알려진 제한이다. raw 11개 HTTP 200도 그 실제 브라우저 왕복의 대체 증거가 아니다.

복귀 검사는 f14/f19의 고정 위치 열기→Esc/닫기, 열린 채 실제 휠 이동 뒤 닫기, f13의 열린 A→B, f19의 선택 B→A 및 일부 키보드 경로를 확인한다. 모든 25개 사실·양방향 열린 전환·resize·원문 왕복을 전수 검사한 것은 아니다. 전환 후 닫기 검사는 새 B 버튼의 초점·화면 내 존재를 확인하지만 정확한 기존 화면 높이 복원까지 같은 강도로 검사하지 않는다. `setRep()`는 선택 사실이 화면 안일 때만 그 사실을 위치 기준으로 쓰고, 화면 밖이면 화면 위쪽 사실을 기준으로 쓴다. 선택 유지와 위치 기준을 항상 같은 것으로 설명해서는 안 된다.

정적 T07은 작성자가 지정한 핵심 문자열, T08은 숫자 집합과 앞선 문단 맥락, T09는 버전 표기의 존재를 검사한다. 부정문 제외 규칙도 문자열 휴리스틱이다. 따라서 23 PASS는 모든 서술의 출처 지지·A/B 의미 동등성·공정한 밀도를 독립 입증하지 않는다. 상태 표기·문맥·정보량의 의미 대조와 사람 Q1~Q5는 별도 과업으로 남긴다.

## 허용 범위에서 재실행한 것
