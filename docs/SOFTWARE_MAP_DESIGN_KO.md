# AgentFlow 소프트웨어 지도 — 전체 구성·묶음·표현 설계

> v1.1 · 통합 설계53 · 2026-10-25 · 설계 제안, 제품 구현 아님
>
> 기준: `b6cec94a4e6898eca30ecd1d2169a475396630e8`의 v1.0과 사용자 전달 외부 검토. 게임·웹 시각안51은 국소 표현 실험으로 보존하며 전체 설계의 대표로 삼지 않는다.

**이 제품은 사용자가 만드는 소프트웨어를, 그 사람이 이해하고 다음 일을 이어갈 수 있는 구성으로 정리한다.** 프로젝트의 기억은 하나로 이어지되 그 기억을 읽는 묶음과 모습은 여러 가지일 수 있다. 무엇을 원했는지, 무엇이라고 해석했는지, 어떤 부분이 있고 어떻게 맞물리는지, 무엇이 보고됐고 확인됐는지를 같은 대상에서 되찾는다.

전체 선택 순서는 **어떤 대상인가 → 왜 함께 묶는가 → 어떤 관계를 읽는가 → 어떤 모습이 알맞은가 → 사용자의 행동이 어디까지 바꾸는가**다. 게임·웹·CLI를 배타적인 프로젝트 종류로 나누고 각각 고정 화면을 주는 방식은 채택하지 않는다. 이번에는 1–3절의 전체 구성을 유지하면서, 4절의 읽기와 행동, 5절의 변화 중 연속성, 7.4절의 여섯 장면을 연결했다. 정확한 버튼 배치·픽셀 규격은 이후 시각 설계에서 정한다.

## 1. 전체 설계의 골격

| 구별할 층 | 결정하는 것 | 결정하지 않는 것 |
|---|---|---|
| 프로젝트의 성격 | 목적, 사용자·호출자, 제공 형태, 작동 환경과 주요 질문 | 장르에 따른 고정 노드 목록·배치 |
| 대상의 뜻 | 기능·자료·규칙·접점·구현·실행 등이 무엇을 가리키는지 | 그 대상의 영구 위치나 한 가지 부모 |
| 묶음의 기준 | 어떤 책임·구성·위치·관심으로 함께 읽는지 | 단지 가까이 놓였다는 이유로 실제 포함·동일성 확정 |
| 표현의 역할 | 포함, 전달, 조건, 계약, 변화 중 무엇을 쉽게 읽힐지 | 프로젝트 전체에 한 그림 문법 강제 |
| 자세히 보는 범위 | 개요, 국소 내부, 반복 목록, 관련 근거 중 지금 펼칠 것 | 모든 가지의 깊이를 맞추거나 없는 내부 생성 |

‘연구용 측정 도구’는 펌웨어이면서 라이브러리·CLI·데스크톱 프로그램일 수 있다. ‘자동화’는 사용 목적이기도 하고 같은 프로그램 내부의 동작 방식이기도 하다. 이 단어들을 한 분류 트리의 형제 항목으로 고정하면 한 프로젝트가 여러 칸에 걸린다.

프로젝트의 성격은 **여러 단서를 함께 가진 설명**으로 다룬다. 예를 들어 `측정·분석 / 장치와 연구자가 사용 / 장치·PC에서 작동 / 라이브러리·명령·보기 제공`이라고 읽을 수 있다. 모든 단서를 입구에서 사용자가 작성하게 하지 않는다. 기록에 있는 것부터 정리하며, 빈 단서 때문에 지도를 만들지 못하는 관문은 없다.

### 기본 화면의 기준

처음에는 사용자가 정한 구성과 목적을 따른다. 그것이 없다면 기록에서 설명할 수 있는 **책임의 묶음**을 기준 개요로 제안한다. 책임은 ‘백업을 만들어 복원할 수 있게 보관한다’, ‘측정값을 분석 가능한 형태로 만든다’처럼 그 묶음이 왜 존재하는지를 설명한다. 같은 책임 안에는 행동·자료·규칙·구현이 서로 다른 역할로 들어갈 수 있다.

별도로 쓰거나 전달하는 제품이 명확하면 큰 범위로 구별한다. 그러나 패키지가 여럿이거나 배포가 나뉜다는 이유만으로 첫 화면을 빌드 구조로 바꾸지 않는다. 한 업무 책임이 여러 패키지·장치·서비스에 걸쳐 있을 수 있다. 파일·패키지·실행 위치는 필요할 때 다른 관점에서 읽는다.

자연스러운 책임 묶음이 없는 항목 집합은 목록으로 시작한다. 독립적인 변환기·명령·검사 규칙을 억지로 큰 상자 몇 개에 나누지 않는다. **기준 개요는 돌아갈 구성 방식이지 반드시 상자 지도여야 한다는 뜻이 아니다.**

## 2. 무엇을 하나의 부분으로 보는가

부분의 이름은 사용자의 말과 프로젝트 어휘를 먼저 쓴다. 아래는 고정 노드 팔레트가 아니라, 뜻을 섞지 않기 위한 판정 질문이다.

| 판정 질문 | 구별할 대상 | 묶음에서의 예 |
|---|---|---|
| 무엇을 할 수 있게 하려는가? | 목적·기능·책임 | 복원하기, 문서 변환, 측정 |
| 무엇을 다루거나 기억하는가? | 자료·상태·모델·정의 | 문서, 측정 기록, 중간 표현, 백업 목록 |
| 어떤 조건을 지켜야 하는가? | 정책·규칙·제약 | 보존 기간, 타입 규칙, 보정 범위 |
| 누구 또는 무엇과 만나는가? | 역할·접점·계약·외부 대상 | 플러그인 계약, 명령 옵션, 장치 인터페이스 |
| 무엇이 그것을 맡는가? | 구현 모듈·패키지·서비스·드라이버 | 파서, 렌더러, 센서 드라이버 |
| 어느 실행·판본·설치를 말하는가? | 판본별 정의 / 설치 인스턴스 / 개별 발생을 구별 | 특정 작업 실행, 설치된 센서, 보고서에 쓴 자료 판본 |
| 왜 그렇게 생각하는가? | 사용자 의도·결정·담당 보고·관측 근거 | 원문 발언, 구현 보고, 실행 결과 |

같은 단어가 여러 뜻을 가질 수 있다. ‘검색’은 기능일 수도 있고 검색 모듈일 수도 있다. 이름이 같다고 합치지 않고, 같은 것을 가리킨다는 근거가 있으면 사용자의 표현·담당 표현·코드 이름을 한 대상의 이름으로 연결한다. 아직 뜻이 정해지지 않았다면 넓은 이름과 원문을 남긴다.

### 개발 대상과 사용 중인 자료를 먼저 구별한다

우리 프로젝트가 직접 만들거나 바꾸는 범위, 그 범위가 의존하는 외부 도구, 동작을 설명하는 사례 자료를 나눈다. 같은 Krita 레이어라도 ‘레이어 기능 개발’과 사용자가 그린 그림의 실제 층은 다른 범위다. 분석 도구가 DuckDB를 사용한다면 DB 엔진 내부를 자기 프로젝트의 부분으로 자동 복제하지 않는다. 내부를 수정하거나 내부 제약을 질문할 때 관련 범위만 펼친다.

한 대상에 여러 역할이 있을 수 있어도 모든 사실 관계가 자유롭게 겹치는 것은 아니다. 원본에서 정한 포함·연결·범위 제약은 유지하고, 관점별 관심 묶음만 그 제약 위에서 유연하게 모은다. 부모의 상태·권한·활성 여부도 근거 없이 모든 자식에게 전파하지 않는다.

### 분리와 유지의 판단

**따로 다룰 이유가 확인되면 나눈다.** 다른 약속을 갖거나, 적용 범위가 다르거나, 독립적으로 교체·변경하거나, 서로 무엇을 주고받는지 설명할 수 있을 때다. 예를 들어 ‘문서’와 ‘PDF 출력’은 같은 이름으로 합칠 대상이 아니다. 하나는 다루는 내용이고 다른 하나는 그 내용의 특정 산출 표현이다.

**함께 읽어야 뜻이 완성되면 같은 책임 안에 둔다.** 백업 보관 행동·백업 목록·보존 기간 규칙은 성질이 달라도 함께 읽을 이유가 있다. 같은 종류라는 이유로 모든 자료를 ‘데이터’ 창고에, 모든 규칙을 ‘정책’ 창고에 먼저 보내지 않는다.

다음 경계는 유지한다: 기능과 구현 / 규칙과 검사 처리 / 자료와 저장 수단 / 같은 대상의 다른 표시와 별개 대상의 공유 / 제품 역할과 개발 담당 / 구성과 발생과 증거 / 포함과 관점 분류와 임시 관심. 분류 전 구절도 원문으로 남기며, 모든 구절을 즉시 노드로 바꾸지 않는다.

## 3. 무엇을 묶고, 무엇을 연결하는가

### 3.1 세 가지 묶음

| 묶음 | 뜻과 지속성 | 기본 표현 | 무엇을 바꾸면 달라지는가 |
|---|---|---|---|
| 구성 묶음 | 한 책임을 설명하거나 실제 구현을 이루는 관계. 어떤 구성 관계인지를 밝힘 | ‘책임별 구성’, ‘펌웨어 내부’처럼 기준을 밝힌 포함 면 | 구성에 대한 현재 해석을 정정하거나, 채택한 요구를 바꿀 때. 요구 변경은 구현 변경과 별개 |
| 관점 묶음 | 실행 위치·제공 계약·자료 수명 등 기준에 맞는 대상을 다시 모은 보기 | 기준을 밝힌 열·띠·목록. 기준 개요의 위치로 이어짐 | 보기 기준이나 그 기준이 읽는 정보가 달라질 때. 저장해 다시 읽을 수 있음 |
| 질문별 함께 보기 | 한 질문에 필요한 대상과 참고 자료를 함께 읽음 | 질문 제목과 국소 관계. 참고 대상은 원래 범위로 이어짐 | 질문 범위·참고가 달라질 때. 저장·고정해도 질문으로 남음 |

‘측정 기능을 이룬다’, ‘장치에서 돌아간다’, ‘이번 오류와 관련된다’는 서로 다른 묶음 이유다. 같은 사각형 안에 있다는 사실만으로 셋을 같게 만들지 않는다. 사용자가 읽는 제목과 관계가 먼저 구별을 설명하고, 색·테두리는 보조한다.

책임별 구성도 유효한 구성이다. 구현만 ‘진짜 구조’로 취급하지 않는다. 다만 **이 경계 안에 있다는 뜻**을 범위 제목에서 읽게 한다. ‘값을 해석하기 · 책임별 구성’ 안의 규칙은 책임을 설명하고, ‘펌웨어 내부’ 안의 처리는 구현 구성을 설명한다. 내부에서 묶는 기준이 바뀌면 그 경계에서 제목을 다시 밝힌다. 모든 카드에 분류 설명을 반복하지 않는다.

다른 범위의 공유 대상은 가장자리나 바깥 관계 목록에 `기록 형식 — PC 읽기 구현이 사용`처럼 원래 범위와 관계가 드러나는 참조로 둔다. 내부 부분과 동일한 포함 면으로 그려 소유를 오인시키지 않는다. 색을 보지 않아도 이름·관계·위치로 구별할 수 있어야 한다.

### 기준에 맞는 항목과 참고로 둔 항목

‘PC에서 동작’만으로는 어떤 사실을 모았는지 부족하다. 필요한 자리에서 `PC 실행 계획`, `PC 구현 보고`, `PC 실행 관측` 중 실제 기준과 대상 판본을 밝힌다. 계획과 보고와 관측을 한 목록의 확정 사실로 합치지 않는다. 근거가 없는 항목은 ‘PC가 아님’으로 판정하지 않는다.

자동 관점의 구성원은 기준에 따라 계산한다. 비교하려고 장치 항목을 더하면 **그 관점 위에서 읽는 질문의 참고**가 된다. 같은 장면에 나란히 놓을 수 있지만 기준에 맞는 구성원과 구별하며, 재계산해도 참고가 사라지지 않는다. 항목의 사실이 틀렸으면 해당 설명에서 정정하고, 보기 기준이 틀렸으면 기준을 고친다. 저장한 질문은 출발 범위·조건·참고를 보존하고, 새 기록이 와도 임의로 대상을 추가하거나 질문의 뜻을 바꾸지 않는다.

### 3.2 묶음을 정하는 순서

1. **사용자가 이미 정한 구분을 찾는다.** ‘수집과 분석은 따로’, ‘이건 같은 문서’ 같은 발언과 이후 정정을 우선한다. 서로 다른 시점의 말을 동시에 현재 결정으로 만들지 않는다.
2. **현재 대상과 관계를 구별한다.** 같은 대상의 두 이름인지, 기능과 구현인지, 정의와 실행본인지부터 확인한다.
3. **함께 책임지는 결과를 한 문장으로 적는다.** 그 문장을 설명하는 데 꼭 필요한 내부와, 바깥에서 쓰는 대상을 가른다. 묶음 이유가 ‘이름이 비슷함’뿐이면 아직 구조로 확정하지 않는다.
4. **묶음의 경계를 시험한다.** 하나를 바꾸거나 다른 구현으로 바꿔도 약속이 같은가? 외부와 주고받는 것이 다른가? 다른 수명·범위가 있는가? 차이가 중요하면 하위 부분 또는 별도 묶음으로 나눈다.
5. **다른 기준과 충돌하면 관점을 나눈다.** 책임 구조를 패키지 트리나 배포 위치에 맞추려고 뒤틀지 않는다. ‘무엇을 하나’와 ‘무엇이 맡나’를 대응시킨다.
6. **이유가 약한 정리는 후보로 남긴다.** 첫 개요에는 제안된 묶음임을 한 번 알리고 사용할 수 있게 하되, 기존 구성을 크게 바꾸는 합치기·나누기·공유 추출은 이전과 이후를 비교할 수 있게 한다.

사용자가 매번 분류표를 채우는 흐름은 만들지 않는다. 묶음을 고칠 때는 “같은 부분”, “별개 구현”, “여기서 사용”, “이 질문에서만 함께”처럼 바꾸려는 뜻을 확인한다. 배치를 옮긴 행동만으로 의도나 실제 소속을 변경했다고 단정하지 않는다.

### 3.3 둘 이상의 묶음에 걸치는 부분

**대상의 정체성, 관계, 화면의 자리를 분리한다.** 하나의 전역 부모로 모든 관점을 해결하지 않는다. 한 보기에서 읽기 쉬운 주표시 자리를 두더라도 그것이 유일한 실제 소속을 증명하지는 않는다.

- 소속이 확인된 공유 대상은 그 소속을 유지하고 다른 묶음에는 참조 입구를 둔다.
- 독립된 책임·계약을 가진 공통 부분이라면 별도 범위를 둘 수 있다. 사용하는 곳이 두 군데가 됐다는 이유만으로 ‘공통’ 영역을 자동 생성하지 않는다.
- 같은 규칙을 각자 구현한 경우 규칙과 구현을 구별한다. 두 구현을 하나의 노드로 합치지 않는다.
- 같은 라이브러리 계열이라도 판본별 정의를 구별하고, 설치·실행은 해당 판본의 정의와 연결한다.
- 정체성이나 소속이 아직 불분명하면 특정 자식에 임의 연결하지 않고 알려진 범위까지만 남긴다.

묶음을 접어도 바깥 연결의 대상과 뜻을 잃지 않는다. 개요의 집약선은 관계가 있다는 요약이고, 선택하면 원래 끝점·동사·조건을 읽는다. 여러 관계를 한 선으로 합쳤다고 호출 순서나 데이터 흐름 하나로 해석하지 않는다.

## 4. 어떤 모습으로 보여주는가

**표현은 장르가 아니라 지금 읽어야 할 관계가 고른다.** 한 프로젝트에 아래 표현을 섞어 쓸 수 있지만, 한 화면이 모든 관계를 동시에 설명하려고 하지는 않는다.

| 읽으려는 질문과 근거 | 선택하는 모습 | 계속 남기는 기준 |
|---|---|---|
| 무엇이 무엇의 일부인가? | 크기와 깊이가 다른 포함 면, 작은 부분 이름 | 묶음 이유·현재 범위·바깥 접점 |
| 무엇이 들어와 어떻게 바뀌고 나가는가? | 전달·변환의 흐름. 분기·반복은 근거가 있을 때만 | 다루는 자료, 처리 정의와 특정 실행의 구별 |
| 어떤 조건에서 달라지는가? | 같은 조건을 맞춘 대안·규칙 비교 | 바뀐 조건과 달라지는 대상, 원안과 조합 초안 |
| 무엇을 제공하고 무엇을 요구하는가? | 계약·입출력·버전의 정렬된 표 또는 목록 | 제공자·사용자·필드/명령의 정체성 |
| 어디에서 어떤 구현이 동작하는가? | 위치별 띠와 구현·설치의 대응 | 업무 책임과 구현을 잇는 관계, 정의와 실행본의 구별 |
| 같은 종류가 많이 반복되는가? | 이름·속성·예외를 읽는 목록과 국소 선택 | 반복군의 기준, 다른 행동을 가진 예외 |
| 무엇이 언제 실제로 일어났는가? | 실행별 시간축·분기·재시도 기록 | 실행 식별자·시점·관련 정의. 기록 없으면 발생을 만들지 않음 |
| 원한 것과 보고된 것이 같은가? | 선택 대상 옆에서 원문·보고·관측을 직접 대조 | 적용 범위와 근거, 다음에 달라질 판단 |

### 선택이 경쟁할 때

기준 개요는 전체의 책임과 위치를 기억할 수 있게 유지한다. 특정 질문을 풀 때만 관련 범위를 다른 모습으로 읽는다. 현재 질문이 계약 비교라면 표가 중앙에 오고, 전체 위치는 짧은 경로나 작은 맥락으로 남는다. 다시 전체를 읽을 때는 출발했던 범위·선택·접힘을 복원한다.

자료가 성기면 가장 적은 가정을 요구하는 이름·구절 묶음부터 시작한다. 구조가 희박한데 흐름을 그리기 위해 순서를 만들지 않는다. 반대로 입력·변환·산출이 명시됐다면 해당 범위에서는 흐름을 시작점으로 쓸 수 있다. 관심을 받았다는 이유로 매번 기본 배치를 다시 계산하지 않는다.

### 공통 시각 문법

- 전체에서는 이름과 묶음의 관계가 먼저 읽힌다. 모든 부분에 설명 카드·상태 문장·출처 칸을 붙이지 않는다.
- 안으로 들어가면 선택한 범위만 넓히고 바깥과의 접점은 가까운 가장자리에 남긴다. 모든 부분을 같은 비율로 줄이지 않는다.
- 관계의 제목은 선이 교차하는 중앙보다 대응하는 접점 가까이에 둔다. 읽을 자리가 부족하면 국소 관계 목록으로 풀며 카드 글자를 관통하지 않는다.
- 같은 대상은 이름과 참조로 이어진다. 표현이 바뀌어도 ‘같은 것’과 ‘그것을 맡는 구현’이 다른 관계임을 읽을 수 있어야 한다.
- 강조는 현재 선택·관련성·판단 이유를 위해 쓴다. 프로젝트마다 수십 개의 도형이나 예제 전용 아이콘을 외우게 하지 않는다.
- 기본 화면은 현재 상황을 읽는 자리다. 긴 원문·수정·비교는 집중해서 읽는 장면으로 이어지며, 작성 중인 내용과 출발 맥락을 보존한다.
- 휠 확대는 카메라 변화다. 다른 의미 층으로 들어가는 것은 명시적인 이동이다. 보기용 배치 변경과 내용·소속 정정도 구별한다.

### 4.1 같은 자리에서 읽고, 필요한 내용으로 들어간다

돌아오는 기준 개요는 안정적으로 둔다. 부분을 **선택**하면 같은 자리에서 짧은 현재 설명과 관련 관계를 읽는다. **안으로 들어가기**는 그 부분의 내부 범위를 펼치는 명시 행동이다. **내용을 살펴보기**는 ‘기록 형식 확인’, ‘두 구현 비교’, ‘이 실행 확인’처럼 질문을 가리키며 알맞은 표·비교·시간축을 연다. 선택 하나가 상황마다 확대·진입·보기 교체를 번갈아 일으키지 않는다. 표의 행에서도 선택과 내용 열기의 뜻은 같다.

표현을 직접 고를 수는 있지만 여덟 종류의 보기를 먼저 이해할 필요는 없다. 내용을 여는 입구는 선택한 대상에서 답할 수 있는 질문으로 제안한다. 근거가 없으면 실제 실행 시간축 대신 설계 흐름이나 관련 원문으로 이어진다.

장면을 열 때는 출발 범위·선택·카메라·접힘·읽던 위치와 작성 중 초안을 함께 기억한다. 여러 장면을 거치면 바로 전 장면으로 돌아갈 수 있고 기준 개요로도 돌아갈 수 있다. 잠깐 기록을 읽으려고 펼친 경로는 돌아올 때 원래 접힘으로 복원한다. 사용자가 직접 바꾼 접힘·배치는 그 보기의 새 상태로 남긴다. 내용이 바뀌어도 예전 화면을 그림처럼 재생하는 것이 아니라, 같은 맥락에서 현재 설명을 읽게 한다.

현재 구성 경로와 ‘어디에서 이 장면으로 왔는가’는 구별한다. 질문에서 기록 형식을 열었다고 기록 형식이 질문의 구성 자식이 되지는 않는다. 돌아가기에는 출발 장면 이름을 쓰고 구성 경로에는 실제 읽는 범위의 관계를 쓴다.

### 4.2 행동의 이름이 바뀌는 범위를 말한다

아래는 동작의 뜻을 정하는 표다. 매번 여러 효력을 고르게 하는 확인 창의 목록이 아니다. 정정은 현재 설명에서, 변경안은 앞으로 할 일을 적는 자리에서 시작한다.

| 행동 | 바뀌는 정보와 다른 보기에 미치는 영향 | 계속 보존하는 것 |
|---|---|---|
| 보기에서 위치 옮기기 | 현재 보기의 배치. 같은 보기를 다시 열면 유지 | 구성 관계·실행 위치·다른 보기의 배치 |
| 이 질문에 참고 추가 / 참고 빼기 | 해당 질문의 읽기 대상. 고정한 질문에도 유지 | 대상의 소속·사실과 문제의 적용 범위. 참고 제거는 문제 해결이 아님 |
| 현재 설명 바로잡기 | 대상·범위를 지정한 해석과 그 해석을 쓰는 요약·관점이 갱신됨 | 원문, 다른 판본의 주장, 실제 프로그램 상태 |
| 앞으로의 변경안 쓰기 | 별도 초안과 관련 대상. 질문에서 나갔다 와도 이어 쓸 수 있음 | 현재 요구·구조 해석·구현/검사 상태 |
| 변경안을 현재 요구로 채택하기 | 앞으로 지켜야 할 의도와 관련 차이. 기존 요구와 대안은 이력으로 남음 | 현재 구현이 이미 바뀌었다는 주장은 만들지 않음 |
| 같은 대상으로 정리 / 넓은 대상을 나누기 | 정체성 해석·대응 관계와 현재 표시. 이전 식별자는 계속 열림 | 원래 보고의 대상·범위·판본, 작성 중 초안. 상세 규칙은 5절 |
| 질문 저장·고정하기 | 질문의 보관과 다시 여는 입구 | 질문이라는 의미, 출발 범위와 참고. 구성의 새 부분이 되지 않음 |
| 내 정정을 되돌리기 | 그 정정이 만든 연결·해석의 효력을 되돌리는 새 기록 | 이후 도착한 보고·다른 정정·초안. 프로젝트 전체를 과거로 되감지 않음 |

정정은 관련 원문에 연결하되 원문에 없는 말을 원문이 뒷받침하는 것처럼 바꾸지 않는다. 사용자가 새 사실을 알려주면 그 정정 자체가 새 출처다. 현재 요구의 채택, 담당 구현 보고, 실행 관측은 서로 다른 기록이다.

명확한 새 기록은 해당 대상의 보고·요약에 반영할 수 있다. 매 수신마다 사용자의 ‘적용’ 승인을 요구하지 않는다. 다만 기존 정정과 충돌하거나 범위가 불분명하면 해당 쟁점을 남긴다. **정리 정보의 갱신과 읽는 장면의 교체는 분리한다.** 새 정보가 선택의 뜻·비교 조건을 바꿀 때는 가까운 변화 입구를 두고, 읽는 중인 비교·카메라·작성 내용을 자동 교체하지 않는다. 사용자가 변경을 열거나 돌아왔을 때 같은 맥락에서 갱신 내용을 읽는다.

### 4.3 여러 모습이 한 제품으로 읽히는 기준

시각적 통일은 모든 화면을 같은 카드 격자로 만드는 데서 얻지 않는다. **범위 제목과 출발 경로 → 중심 내용 → 선택한 대상의 설명 → 필요한 원문·작성**이라는 읽는 순서를 유지한다. 포함 면이 표로 바뀌어도 대상 이름·선택 강조·관계 동사의 어휘는 이어진다. 현재 정보와 앞으로의 안은 자리와 제목으로 구별하고, 색은 보조한다.

개요는 관계를, 국소 장면은 한 질문을, 원문은 근거를 맡는다. 비교와 작성이 길어지면 그 내용에 집중하는 장면으로 옮기며, 작은 지도 옆에 문서·폼·상태 패널을 계속 쌓지 않는다. 새 변화는 관련 대상 곁의 짧은 이유로 발견하고 자세한 판정은 그 안에서 읽는다. 모든 새 기록에 배지를 만들거나 모든 카드를 상태표로 바꾸지 않는다.

## 5. 적은 자료에서 복잡한 프로젝트까지

### 이름 몇 개와 구절만 있을 때

이름이 있는 부분과 아직 자리 없는 구절을 함께 둔다. 구절이 가리키는 대상을 확실히 정할 수 없으면 인용을 보존한다. ‘보통 이런 프로젝트에는…’라는 질문을 제안할 수 있지만 실제 구성처럼 놓지 않는다. 구상·설계·구현 보고·관측의 빈칸을 채우기 위해 노드를 생성하지 않는다.

### 부분이 많아질 때

접는 기준은 임의의 ‘몇 개’가 아니라 **읽을 책임의 경계와 반복성**이다.

| 유지해서 보여줄 것 | 접거나 다른 표현으로 보낼 것 |
|---|---|
| 묶음이 맡는 일과 현재 선택의 위치 | 선택하지 않은 묶음의 세부 구현 |
| 외부가 쓰는 접점과 공유 대상의 참조 | 모든 사용처로 향하는 개별 선 |
| 현재 판단에 영향을 주는 예외·차이 | 같은 계약을 따르는 동질적인 반복 정의 |
| 사용자가 찾던 부분의 경로와 관련 변화 | 원문 전체·세부 검사 기록 |
| 원문 의미를 바꾸는 미정·충돌 | 단순히 아직 구체화되지 않은 미래 구상 |

반복군은 종류·계약·변경 방식이 같은지 확인해 묶는다. 이름이 비슷하다는 이유만으로 합치지 않는다. ‘검사 규칙 여러 개’라는 요약은 각 규칙을 삭제한 것이 아니며 목록·검색에서 모두 접근된다. 예외가 발견되면 관련 질문에서 그 예외를 펼친다. 예외가 많으면 더 작은 하위군 또는 비교 표로 전환한다.

접힌 부모는 내부의 중요한 판단거리를 짧게 남긴다. ‘설정 연결 전’처럼 실제 다음 행동을 바꾸는 이유를 보여주되 모든 미정을 경고로 올리지 않는다. 오래됐거나 언급이 적다는 이유로 안정·완료라고 부르거나 숨기지 않는다.

| 남은 내용 | 개요에 남기는 이유 또는 상세로 보내는 이유 |
|---|---|
| 언젠가 일괄 변환을 지원할지 미정 | 지금 하려는 작업을 바꾸지 않으면 구상·상세에 보관 |
| 입력 파일이 이미 보정됐는지 몰라 처리 방식을 정할 수 없음 | 관련 범위를 접어도 ‘이미 보정된 입력 처리 미정’처럼 결정 대상을 남김 |
| 장치와 PC가 서로 다른 기록 형식을 전제함 | 양쪽에서 같은 쟁점으로 연결. 전체에서는 고유 쟁점 1건으로 셈 |
| 완료 보고가 있으나 해당 판본의 검사는 없음 | 보고와 검사 범위를 구별. 검사 부재만으로 실패나 긴급 경고를 만들지 않음 |

한 쟁점이 여러 곳에 나타나도 표시 수를 문제 수로 합산하지 않는다. 같은 쟁점인지 판단한 근거와 관련 범위를 유지한다. 펌웨어 쪽만 해결되면 그 범위의 판단만 갱신하며 PC 쪽까지 닫지 않는다. 이름이 비슷해도 독립적인 결론이 필요하면 별도 쟁점으로 나누고 원래 질문과 연결한다.

책임 하나가 커져도 글자를 일괄 축소해 한 화면에 넣지 않는다. 읽을 수 있는 크기를 유지하며 범위를 좁히거나 반복군을 목록으로 연다. 밖에 남은 범위는 경로·검색·이동으로 접근한다. 관계 라벨이 이름을 가리거나 끝점·조건을 함께 읽을 수 없으면 선택한 범위의 관계 목록으로 풀고, 원래 양 끝점과 동사를 유지한다. hover만이 관계를 읽는 유일한 방법이 되지 않는다. 최소 글자 크기와 실제 표시 한계는 이후 1280·1440 화면과 긴 한글 이름에서 정하며, 근거 없는 픽셀 수를 지금 확정하지 않는다.

### 새로운 기록이 구조를 바꿀 때

기존 대상에 관한 새 보고는 그 대상 가까이에 쌓인다. 이름 변경은 이전 이름과 연결하고, 분할·합치기·공유 추출은 전후의 대응을 남긴다. 사용자가 읽는 중에는 선택·카메라·접힘을 유지한다. 새 사실을 받는 것과 전체 배치를 고치는 것은 별개의 변화다.

**이력은 원래 범위를 지키고, 현재 이해는 대응 관계로 이어진다.** 넓은 ‘보정’이 규칙·펌웨어 처리·PC 처리로 나뉘었다면 다음과 같이 다룬다.

| 남겨야 할 것 | 분할 뒤의 동작 |
|---|---|
| ‘보정 완료’라는 옛 보고 | 당시 넓은 범위에 남김. 원문에 근거가 있는 후속 대상에만 관련성을 연결하며 세 대상의 완료로 복사하지 않음 |
| 옛 대상·보고 링크 | 분할 전 범위와 현재 대응을 함께 열기. 후속이 여러 개면 하나로 자동 이동하지 않음. 옛 범위를 현재 세 대상의 새 부모로 만들지도 않음 |
| 작성 중 초안 | 원래 범위·내용·작성 맥락에서 계속 쓰고 저장 가능. 후속 대상의 정정·요구로 반영할 때만 명확한 대상 지정. 분할 자체가 작성 중단의 관문은 아님 |
| 저장한 질문 | 질문·원래 참고는 유지. 바뀐 대상의 대응을 보여주되 후속 셋을 조용히 새 구성원으로 넣지 않음 |
| 읽던 자리 | 같은 범위의 대응 지점에서 이어 읽음. 선택 대상이 사라졌다고 첫 화면으로 초기화하거나 임의 자식으로 보내지 않음 |

일대일 개명·대체라면 이전 이름과 바뀐 사실을 남기고 현재 대상으로 이어갈 수 있다. 합치기는 동일 대상이라는 해석을 정리하는 일이며 두 구현을 앞으로 통합하는 계획과 다르다. 병합해도 이전 ID·별칭·원문의 범위·서로 충돌하는 주장은 남는다. 모든 보고가 서로를 확인해 준 것으로 합산하지 않는다. 후속 기록이 쌓인 분할·병합을 되돌릴 때도 해당 관계를 현재부터 정정하고 후속 ID와 기록을 삭제하거나 복제하지 않는다.

### 도착한 시각과 다루는 시점이 다를 때

보고는 **대상·다룬 범위·관련 판본/시점·출처 종류**와 연결하고 도착 시각은 별도로 남긴다. 이 정보가 항상 모두 있을 필요는 없다. 펌웨어에 관한 보고임은 알지만 판본을 모르면 그 범위에서 읽고, 판본에 의존하는 판단에만 ‘판본 확인 전’을 드러낸다. 판본이 없어도 유효한 이름 설명이나 원문 참조까지 막지는 않는다.

오늘 도착한 v1 보고가 현재 v2의 완료·문제 해결을 뜻하지 않는다. v1의 결과를 v2에도 적용할 근거가 있다면 그 범위의 연결 판단을 더하고 원래 보고의 판본을 고쳐 쓰지 않는다. 같은 범위·판본의 충돌도 수신 순서나 더 큰 버전 번호만으로 해결하지 않는다. 이전 보고의 낡음과 문제의 해결은 별개의 상태다.

한쪽 가지는 구현까지 있고 다른 쪽은 구상뿐이어도 된다. 깊이를 맞추려고 빈 컨테이너를 만들지 않는다. 구성의 세부 깊이, 구현 대응의 자세함, 근거의 양은 서로 다른 축이다. 근거가 적다고 부분이 작거나 중요하지 않은 것은 아니다.

## 6. 실제 오픈소스로 시험한 묶음 규칙


이 표는 개발 종류의 완전한 목록이 아니다. **같은 이름·공유·순서·실제 포함·정의와 실행·물리 연결이 서로 다른 묶음을 요구하는지** 시험할 대표 자료다. 원본 요소·관계는 공식 문서에서 확인했고, 화살표 오른쪽의 묶음과 화면 선택은 AgentFlow의 설계 제안이다. 저장소 실행이나 코드 전체 분석을 했다는 뜻은 아니다.

### 특히 강한 반례 세 가지

**같은 이름의 재등장은 같은 대상의 증거가 아니다.** Collector의 processor는 같은 설정을 여러 파이프라인이 참조해도 각 파이프라인의 인스턴스와 상태가 따로 생긴다. ‘하나로 합친 뒤 여러 곳에서 참조’라는 일반 규칙만으로는 틀린다. 먼저 정의·설정·사용 자리·실행을 구별해야 한다. [O1]

**함께 움직이는 것은 포함과 다르다.** Krita의 필터 적용, Clone의 원본 참조, Group의 구성은 서로 다른 관계다. ‘영향받는다’는 이유만으로 안쪽에 넣으면 보기 좋은 그림이 틀린 소유 구조를 만든다. [K1]

**같은 소프트웨어라도 사용 목적에 따라 드러낼 내부가 다르다.** DuckDB 엔진을 개발하는 프로젝트에는 파서·바인더·계획기가 중요한 부분이다. DuckDB로 CSV를 요약하는 개인 도구에는 ‘입력 / 집계 / 출력’과 DuckDB 의존 관계가 먼저다. 성숙 OSS를 그대로 작은 프로젝트의 빈 골격으로 복사하지 않는다. [D1]

## 7. 복합 프로젝트에 전체 규칙을 적용한다

아래는 위 OSS의 관점을 대입하기 위한 **합성 설계 사례**다. 실사용 기록이나 자동 추출 결과가 아니다.

### 7.1 측정 도구: 하나의 목적, 여러 제공 형태

목적은 ‘현장에서 모은 값을 믿고 분석해 비교한다’다. 펌웨어·분석 라이브러리·CLI·데스크톱 보기가 한 저장소에 있어도 프로젝트를 네 장르로 쪼개지 않는다.

기준 개요의 책임 묶음:

```text
측정 도구
├ 측정하기
│  ├ 센서 읽기
│  ├ 읽지 못한 값 처리
│  └ 측정 주기
├ 값을 해석하기
│  ├ 단위 변환
│  ├ 보정 규칙
│  └ 유효 범위 판단
├ 기록을 보관·교환하기
│  ├ 측정 기록 형식
│  ├ 장치 임시 기록
│  └ PC 보관
├ 분석·비교하기
│  ├ 기간 집계
│  └ 요약 결과
└ 결과를 읽기
   ├ CLI 보고서
   └ 데스크톱 비교 보기
```

이것은 구현 소유 트리가 아니다. 각 묶음은 하나의 책임을 설명하며, 장치·PC의 실제 구현은 대응 관계로 읽는다.

| 같은 대상·범위 | 기준 개요에서 | 구현·위치 관점에서 | 특정 질문에서 |
|---|---|---|---|
| 보정 규칙 | 값을 해석하기의 규칙 | 규칙을 적용하는 라이브러리와 대응. 펌웨어 적용 여부는 별도 근거 | ‘두 번 보정되나?’에서 양쪽의 적용 보고를 비교 |
| 측정 기록 형식 | 기록을 보관·교환하기의 계약 | 장치의 작성 구현과 PC의 읽기 구현이 참조 | 판본·필드·읽기/쓰기 호환성 표 |
| 요약 결과 | 분석·비교하기의 산출 자료 | CLI와 데스크톱이 각각 표시 | 같은 결과를 표시하는지, 서로 다른 판본인지 구별 |
| 특정 장치에서의 측정 실행 | 구성의 새 형제가 아님 | 실행이 발생한 장치 인스턴스와 그 장치의 펌웨어 판본에 연결 | 오류 시점과 기록이 있을 때만 시간축 |

‘보정 규칙’은 같은 대상이 여러 보기에서 다시 나타난다. ‘라이브러리의 보정 처리’는 그 규칙과 연결된 별개 구현이다. ‘특정 센서의 보정 결과’는 또 다른 발생이다. 같은 이름 세 개를 한 카드로 합치지 않는다.

기준 공간에서는 책임을 읽고, 기록 형식을 살펴볼 때는 계약 표, 잘못된 측정값을 볼 때는 관련 부분의 국소 흐름이 적합하다. 둘을 오가도 대상 이름·출발 범위·사용자 정정은 이어진다. 프로젝트에 장르 하나를 먼저 고르게 할 필요가 없다.

### 7.2 문서 변환 도구: 아직 구조가 없는 초기 구상

합성 발화: ‘마크다운을 PDF와 docx로’, ‘표가 깨지면 안 돼’, ‘이미지 상대경로’, ‘표지 템플릿’, ‘나중엔 폴더째로?’

처음에는 `읽어들이기 / 내용과 모양 보존 / 내보내기`라는 잠정 책임과 관련 구절을 둔다. 입력·변환·산출 관계가 명시돼 있으므로 짧은 흐름으로 읽을 수 있다. 내부 변환 엔진·스케줄러·클라우드 저장은 만들지 않는다. ‘폴더째로’는 아직 단일 실행의 확장인지 배치 작업 제품인지 정해지지 않은 구절로 남긴다.

PDF와 docx는 같은 문서 내용의 서로 다른 산출 형식이다. 출력 정의와 실제로 생성된 파일도 구별한다. 템플릿 수가 늘면 템플릿 정의 목록으로 읽고, 깨지는 특정 표는 관련 규칙·출력 형식과 함께 보는 예외로 펼친다.

CLI가 추가돼도 ‘읽어들이기’와 ‘보존’의 정체성을 버리지 않는다. 새 접점과 어떤 구현을 쓰는지 연결한다. 독립적으로 제공되는 온라인 변환 서비스가 나중에 생긴다면 그때 근거를 가지고 큰 범위를 구별한다. 웹이라는 단어만으로 새 제품 틀을 즉시 만들지 않는다.

### 7.3 기본 책임 지도보다 다른 표현이 나은 경우

독립 명령·플러그인·수치 알고리즘의 카탈로그에서는 자연스러운 상위 책임이 약할 수 있다. 이 범위는 계약·입력·결과·상태를 비교하는 목록을 기본으로 둔다. 관계가 없는 항목을 배치하기 위해 선을 그리지 않는다.

특정 장애의 원인은 시간·순서·동시성에 있을 수 있다. 책임 지도만으로 이를 설명하지 않고 해당 실행의 기록을 열어 구성과 대응시킨다. 반대로 실제 실행 기록이 없으면 설계된 흐름을 읽을 수는 있어도 ‘이 순서로 발생했다’고 표시하지 않는다.

### 7.4 하나의 프로젝트가 변하는 여섯 장면

이 장면들은 같은 측정 프로젝트의 **합성 설계 시나리오**다. 자동 정리 성공이나 실제 사용 결과가 아니다. 시작 시점에는 넓은 ‘보정’, 범위가 불명확한 옛 ‘보정 완료’ 보고, 저장한 질문 ‘두 번 보정되나?’, 작성 중인 ‘계수를 장치별로 저장할까?’ 초안이 있다. 장치·PC의 관련 보고가 들어오며 더 정확한 구별이 가능해진다.

```text
책임별 개요에서 이어보기
   → 보정의 변화 읽기 → 같은 규칙·두 구현 비교
                           → 입력 조건 확인 → 정정 / 변경안 작성
   ← 출발 개요로 복귀 ← 읽던 비교와 초안 유지
                           ↑ 늦은 옛 판본 보고는 관련 기록에 도착
```

**① 돌아오면 내가 보던 곳부터 읽는다.**

- 입력: 마지막 선택 ‘보정’, 접힘·카메라·초안, 그사이 도착한 펌웨어 v2와 PC 라이브러리 0.9 보고.
- 화면: ‘책임별 구성’ 개요와 이전 선택을 복원한다. 관련 변화의 짧은 입구가 그 부분에 남고 긴 변경 보고서가 지도를 대신하지 않는다.
- 행동과 효력: ‘이어서 보기’로 설명과 작성 중 초안에 접근한다. 방문 자체는 구성·완료 판단을 바꾸지 않는다. 변화 수는 실제 읽지 않은 기록을 뜻할 때만 사용하며 전체 기록 수와 혼용하지 않는다.
- 이어짐: 설명을 닫으면 같은 개요다. 초안의 내용·대상은 그대로 남는다.

**② 변화가 무엇인지 읽고 비교할 대상을 잡는다.**

- 입력: v2 보고에는 장치 쪽 보정 처리, 0.9 보고에는 PC 쪽 처리 내용이 있다. 아직 이 보고만으로 독립 검사가 됐다고 할 수 없다.
- 화면: ‘보정’ 선택 아래 짧은 현재 설명과 두 보고를 읽는다. 어떤 범위·판본의 주장인지 관련 줄에서 구별하며 상태 칸을 모든 카드에 늘리지 않는다.
- 행동과 효력: ‘장치·PC 처리 비교’를 열면 두 보고가 다루는 구현을 나란히 읽는다. 비교를 열었다는 이유로 넓은 보정이 자동 분할되거나 두 구현이 실제 실행됐다고 확정되지 않는다.
- 이어짐: 출발 개요와 선택이 경로로 남는다. 보고의 원문을 잠깐 열어도 비교 조건·읽던 위치로 돌아온다.

**③ 같은 규칙과 두 구현을 구별해 현재 정리를 바로잡는다.**

- 입력: 사용자의 규칙 설명과 두 보고의 근거를 대조하니 하나의 규칙을 서로 다른 구현이 맡는 것으로 정리할 수 있다.
- 화면: 위에서는 보정 규칙을 읽고 아래에서는 `펌웨어 처리 ↔ 규칙 ↔ PC 처리`의 대응을 읽는다. 위치 기준은 ‘보고된 구현 위치’이며 실제 배포·실행 확인과 구별한다. 규칙을 양쪽에 복제하지 않는다.
- 행동과 효력: ‘규칙과 두 구현으로 정리’를 선택하면 현재 정체성 해석과 관련 보기를 갱신한다. 소프트웨어를 새로 나누는 구현 지시는 아니다. 옛 ‘보정 완료’는 분할 전 범위에 남고 각 후속의 완료로 번지지 않는다.
- 이어짐: 옛 링크는 원래 범위와 셋의 대응을 연다. 질문과 초안은 원래 범위에서 계속 열리며, 초안을 새 대상에 조용히 옮기지 않는다. 개요의 기존 책임 자리를 유지하며 바뀐 부분만 읽을 수 있게 한다.

**④ 입력 조건 하나가 현재 판단을 바꾼다.**

- 입력: 샘플 기록의 일부에는 ‘장치에서 보정됨’ 표기가 있다. 모든 파일에 표기가 있다는 근거는 없다.
- 화면: ‘입력 파일 조건 확인’으로 보정 여부를 나타내는 필드·표기 없는 경우·양쪽 처리 보고를 같은 범위에서 비교한다. 전체 필드 목록은 필요할 때 연다. 표가 없는 모든 파일을 원시값이라고 단정하지 않는다.
- 행동과 효력: ‘이 질문에 기록 형식 참고’를 더한다. ‘이미 보정된 입력을 PC가 어떻게 처리하는가’라는 쟁점을 규칙·장치·PC에서 찾을 수 있으나 고유 쟁점은 하나다. 이 장면의 판단 기준은 재보정 여부이며 단순히 기록이 새롭다는 사실이 아니다.
- 이어짐: 책임 소속은 바뀌지 않는다. 돌아가면 같은 두 구현 비교와 조건을 읽는다. 관련 책임을 접어도 짧은 판단 이유가 남는다.

**⑤ 잘못 읽은 것은 고치고, 앞으로 바꿀 것은 안으로 남긴다.**

- 입력: PC 0.9 보고는 표기를 검사하지 않고 모든 입력을 보정한다고 명시한다. 현재 요약은 ‘원시값만 보정한다고 보고됨’으로 잘못 정리돼 있다.
- 화면: 현재 설명의 해당 문장에서 정정을 시작한다. ‘앞으로의 처리’는 별도 초안 자리다. 보고를 독립 실행 관측처럼 보이게 하지 않는다.
- 행동과 효력: ‘보고 내용 바로잡기’는 출처를 연결한 현재 해석을 ‘모든 입력을 보정한다고 보고됨’으로 바꾼다. ‘이미 보정된 파일은 건너뛰기’는 새 변경안으로 남는다. 이를 현재 요구로 채택하더라도 PC 구현이 이미 고쳐졌다는 상태는 만들지 않는다.
- 이어짐: 관련 요약·관점은 같은 정정을 사용한다. 기존 ‘계수를 장치별로 저장할까?’ 초안은 별도로 이어 쓸 수 있고, 새 초안은 PC 처리와 기록 형식을 다룬다. 다른 대안·원문을 덮지 않는다.

**⑥ 늦은 보고가 와도 내 생각을 잃지 않고 돌아간다.**

- 입력: 변경안을 쓰는 동안 펌웨어 v1의 ‘보정 완료’ 보고가 늦게 도착한다.
- 화면: 작성 내용과 비교 장면을 유지한다. 필요한 변화 입구에서 ‘이전 판본 보고’를 읽을 수 있다. 새 보고를 연 뒤 닫아도 같은 초안으로 돌아온다.
- 행동과 효력: 보고는 v1 범위에 연결한다. v2와 PC 0.9의 판단을 덮거나 이중 보정 쟁점을 해결로 바꾸지 않는다. ‘개요로 돌아가기’에서 원래 접힘·카메라와 현재 정리를 함께 읽는다.
- 이어짐: 옛 선택이 분할됐으면 대응을 보이며 임의 후속을 선택하지 않는다. 관련 묶음에 ‘이미 보정된 입력 처리 미정’과 연결된 초안 입구가 남는다. 사용자는 어디까지 알게 됐고 무엇을 다음에 정할지 이어갈 수 있다.

### 7.5 문서 변환기에 같은 규칙을 다시 적용한다

초기 문서 변환기에는 실행 위치나 구현명이 아직 없을 수 있다. 따라서 여섯 장면의 고정 레이아웃을 복사하지 않고 **변하는 정보와 행동의 효력**을 대입한다. 넓은 ‘표 보존’ 발언을 보존 규칙·PDF 출력·docx 출력의 관계로 정리하더라도 근거 없는 렌더러 내부를 만들지 않는다. 예전 ‘표 변환 완료’ 보고는 원래 출력 형식·판본이 확인되는 범위에 남는다.

병합 셀이 있는 문서가 발견되면 보존 조건과 두 출력의 보고를 비교한다. PDF 결과만 확인했다고 docx까지 해결됐다고 하지 않는다. 두 출력에서 같은 보존 질문을 열 수 있지만, 서로 독립적인 실패 원인이 확인되면 하위 쟁점을 나눈다. 늦은 이전 PDF 판본의 보고는 현재 docx 판단을 덮지 않는다. ‘나중에 폴더째로’ 구상은 지금 단일 문서 변환을 막지 않으면 개요 경고로 올리지 않는다.

여기서 유지되는 것은 장치·PC라는 모양이 아니라 **선택 → 관련 질문 → 조건 비교 → 해석 정정 또는 변경안 → 맥락을 가진 복귀**다. 질문에 맞는 기준이 없으면 비교 대상의 구절부터 읽는다. 분류를 완성해야만 사용을 시작할 수 있는 설계로 만들지 않는다.

## 8. 대화 기억과 판단을 구조 가까이에 둔다

구조는 기억의 각주가 아니고, 대화도 구조의 각주가 아니다. 사용자가 만들고 있는 대상에서 서로 만난다. 원문 발언 → 현재 해석과 적용 범위 → 담당 보고 → 관련 관측을 연결하되 하나의 상태로 뭉개지 않는다.

‘요청 있음’은 접수나 실행 중의 증거가 아니고 ‘보고 받음’은 완료의 증거가 아니다. 확인되지 않은 곳을 실패로 칠하지 않는다. 반대로 보고가 약속한 범위와 사용자가 원한 범위가 다르면 관련 부분에서 구체적으로 드러낸다.

해석을 고치는 일과 새 요구를 만드는 일은 다르다. 원문은 보존하고 현재 해석·적용 범위를 수정한다. 기존 두 대안에서 고른 조합은 원안을 덮지 않는 새 초안으로 남긴다. 지도에서 이름·위치를 옮겼다는 이유로 소프트웨어 수정 지시를 자동 발송하지 않는다.

돌아온 사용자에게는 마지막으로 보던 부분과 관련 변화·남은 판단부터 연결한다. 모든 변경의 긴 보고서를 첫 화면으로 만들지 않는다. 담당 세션·개발 활동은 제품 역할과 구별해 해당 부분의 작업 맥락에서 읽는다. 수집 hook·MCP·작업 전송은 이 전체 표현 설계를 지탱할 후속 범위이며 이번 구현 대상은 아니다.

| 경계가 무엇을 뜻하는지 화면에서 알 수 있어야 함 | 채택. 3.1절의 범위 제목·공유 참조로 표현. 책임 구성도 유효하며 구현만 실제 구조라는 위계는 두지 않음 |

| 여러 표현으로 진입하고 돌아오는 규칙 | 채택. 4.1절의 선택/내부/내용 행동, 구성 경로와 방문 경로의 구별. 여덟 보기 선택을 선행 과제로 만들지 않음 |
| 넓은 대상 분할·늦은 보고·초안의 연속성 | 채택. 5절과 7.4절. Opus의 판본 미상 보고 전면 배제는 수정: 판본에 의존하는 판단만 보류하고 유효한 설명·참고까지 막지 않음 |

| 최소 크기·읽기 한계 설정 | 방향 채택. 임의 px 확정은 유보. 범위·목록·관계 끝점의 읽기 정책을 먼저 정함 |
| 한 사례가 변하는 여섯 장면과 타 사례 대입 | 채택. 측정 도구의 분할/정정/초안을 연결하고 문서 변환기로 같은 효력을 대조. 분야별 새 화면을 늘리지 않음 |

### 행동과 이력에서 참고한 공식 메커니즘

- [Notion 연결 데이터](https://www.notion.com/help/data-sources-and-linked-databases)는 공유 내용 수정과 연결된 보기의 필터·정렬 설정을 구별한다. AgentFlow에는 ‘대상 변경’과 ‘읽는 자리 변경’의 분리를 가져온다. 동기화가 초안 충돌을 모두 해결한다는 뜻은 아니다.
- [GitHub Projects](https://docs.github.com/en/issues/planning-and-tracking-with-projects/learning-about-projects/about-projects)는 담당자 그룹 간 드래그가 실제 이슈 담당자도 바꾸는 반례다. AgentFlow의 기본 배치 드래그에는 이 효력을 가져오지 않는다.
- [GitHub PR 대화](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/commenting-on-a-pull-request)는 outdated와 resolved를 구별한다. 오래된 범위의 근거라는 사실을 문제 해결로 읽지 않는 데 참고한다.
- [Onshape 판본과 이력](https://cad.onshape.com/help/Content/Document/versions_and_history.htm)은 보존된 판본을 열고 비교하는 일과 현재 작업에 병합하는 일을 구별한다. 과거 범위 보존에 참고하되 모든 AgentFlow 탐색을 분기·병합 작업으로 만들지는 않는다.
- [Figma 원본 수정과 인스턴스 복귀](https://help.figma.com/hc/en-us/articles/360038665934-Edit-main-components)는 Pro가 확인한 출발 맥락 복귀 사례다. 개별 수정 가능한 인스턴스를 AgentFlow의 동일 대상 표시와 동일시하지 않는다.

위는 공식 문서의 메커니즘 조사와 AgentFlow에 대한 선택이다. 해당 제품을 이번에 직접 조작해 초안·카메라 보존 전체를 검증한 것은 아니다.

### 정보구조 도구에서 가져온 메커니즘

### 후속 설계의 판정 장면

새 종류의 프로젝트를 추가할 때마다 새 전용 화면을 만드는 대신 아래 같은 질문으로 체계가 견디는지 확인한다.

1. 처음 보는 분야에서도 대상의 뜻과 묶음의 이유를 설명할 수 있는가?
2. 같은 책임이 여러 구현·패키지·장치에 걸쳐도 정체성을 잃지 않는가?
3. 같은 대상의 다른 표시와 별개 구현·판본·실행을 구별하는가?
4. 같은 것끼리 반복되는 범위는 목록으로, 관계가 중요한 범위는 맥락으로 읽히는가?
5. 깊이와 근거가 비대칭인 초기 프로젝트도 추측한 구조 없이 쓸 수 있는가?
6. 개요·내부·계약·실행·원문 사이를 오가며 무엇을 보는지와 돌아갈 곳을 유지하는가?
7. 실제로 중요한 예외와 다음 판단을 접힌 개요에서도 놓치지 않는가?
8. 같은 표시를 옮기는 일, 현재 해석 정정, 미래 요구 변경이 서로 다른 효력을 유지하는가?
9. 대상 분할·병합과 지연 수신을 지나도 과거 보고 범위·옛 링크·작성 중 초안이 이어지는가?

이는 사람에게 사용 기록 제출을 요구하는 관문이 아니다. 총괄과 설계 담당이 자료를 대입해 판단할 기준이다. 실제 로그의 자동 정리 정확도와 임의 규모의 화면 가독성은 별도 확인이 필요하며, 이 문서 개정만으로 구현 성공이나 사용성 합격을 주장하지 않는다.
