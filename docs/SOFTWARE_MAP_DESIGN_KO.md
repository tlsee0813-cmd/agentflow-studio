# AgentFlow 소프트웨어 지도 — 전체 구성·묶음·표현 설계

> v1.0 · 연구52 · 2026-10-25 · 설계 제안, 제품 구현 아님
>
> 기준: `da5fc28750f3a60fa13306c6c3093f33ab9649d3`. 게임·웹 시각안51은 국소 표현 실험으로 보존하며 전체 설계의 대표로 삼지 않는다.

**이 제품은 사용자가 만드는 소프트웨어를, 그 사람이 이해하고 다음 일을 이어갈 수 있는 구성으로 정리한다.** 프로젝트의 기억은 하나로 이어지되 그 기억을 읽는 묶음과 모습은 여러 가지일 수 있다. 무엇을 원했는지, 무엇이라고 해석했는지, 어떤 부분이 있고 어떻게 맞물리는지, 무엇이 보고됐고 확인됐는지를 같은 대상에서 되찾는다.

이번 개정은 장르별 예제를 늘리는 대신 **어떤 대상인가 → 왜 함께 묶는가 → 어떤 관계를 읽는가 → 어떤 모습이 알맞은가**의 선택 규칙을 정한다. 게임·웹·CLI를 배타적인 프로젝트 종류로 나누고 각각 고정 화면을 주는 방식은 채택하지 않는다.

## 1. 전체 설계의 골격

| 구별할 층 | 결정하는 것 | 결정하지 않는 것 |
|---|---|---|
| 프로젝트의 성격 | 목적, 사용자·호출자, 제공 형태, 작동 환경과 주요 질문 | 장르에 따른 고정 노드 목록·배치 |
| 대상의 뜻 | 기능·자료·규칙·접점·구현·실행 등이 무엇을 가리키는지 | 그 대상의 영구 위치나 한 가지 부모 |
| 묶음의 기준 | 어떤 책임·구성·위치·관심으로 함께 읽는지 | 단지 가까이 놓였다는 이유로 실제 포함·동일성 확정 |
| 표현의 역할 | 포함, 전달, 조건, 계약, 변화 중 무엇을 쉽게 읽힐지 | 프로젝트 전체에 한 그림 문법 강제 |
| 자세히 보는 범위 | 개요, 국소 내부, 반복 목록, 관련 근거 중 지금 펼칠 것 | 모든 가지의 깊이를 맞추거나 없는 내부 생성 |

‘연구용 측정 도구’는 펌웨어이면서 라이브러리·CLI·데스크톱 프로그램일 수 있다. ‘자동화’는 사용 목적이기도 하고 같은 프로그램 내부의 동작 방식이기도 하다. 이 단어들을 한 분류 트리의 형제 항목으로 고정하면 한 프로젝트가 여러 칸에 걸린다.

프로젝트의 성격은 **여러 단서를 함께 가진 설명**으로 다룬다. 예를 들어 `측정·분석 / 장치와 연구자가 사용 / 장치·PC에서 작동 / 라이브러리·명령·보기 제공`이라고 읽을 수 있다. 모든 단서를 입구에서 사용자가 작성하게 하지 않는다. 기록에 있는 것부터 정리하며, 빈 단서 때문에 지도를 만들지 못하는 관문은 없다.

### 기본 화면의 기준

처음에는 사용자가 정한 구성과 목적을 따른다. 그것이 없다면 기록에서 설명할 수 있는 **책임의 묶음**을 기준 개요로 제안한다. 책임은 ‘백업을 만들어 복원할 수 있게 보관한다’, ‘측정값을 분석 가능한 형태로 만든다’처럼 그 묶음이 왜 존재하는지를 설명한다. 같은 책임 안에는 행동·자료·규칙·구현이 서로 다른 역할로 들어갈 수 있다.

별도로 쓰거나 전달하는 제품이 명확하면 큰 범위로 구별한다. 그러나 패키지가 여럿이거나 배포가 나뉜다는 이유만으로 첫 화면을 빌드 구조로 바꾸지 않는다. 한 업무 책임이 여러 패키지·장치·서비스에 걸쳐 있을 수 있다. 파일·패키지·실행 위치는 필요할 때 다른 관점에서 읽는다.

자연스러운 책임 묶음이 없는 항목 집합은 목록으로 시작한다. 독립적인 변환기·명령·검사 규칙을 억지로 큰 상자 몇 개에 나누지 않는다. **기준 개요는 돌아갈 구성 방식이지 반드시 상자 지도여야 한다는 뜻이 아니다.**

## 2. 무엇을 하나의 부분으로 보는가

부분의 이름은 사용자의 말과 프로젝트 어휘를 먼저 쓴다. 아래는 고정 노드 팔레트가 아니라, 뜻을 섞지 않기 위한 판정 질문이다.

| 판정 질문 | 구별할 대상 | 묶음에서의 예 |
|---|---|---|
| 무엇을 할 수 있게 하려는가? | 목적·기능·책임 | 복원하기, 문서 변환, 측정 |
| 무엇을 다루거나 기억하는가? | 자료·상태·모델·정의 | 문서, 측정 기록, 중간 표현, 백업 목록 |
| 어떤 조건을 지켜야 하는가? | 정책·규칙·제약 | 보존 기간, 타입 규칙, 보정 범위 |
| 누구 또는 무엇과 만나는가? | 역할·접점·계약·외부 대상 | 플러그인 계약, 명령 옵션, 장치 인터페이스 |
| 무엇이 그것을 맡는가? | 구현 모듈·패키지·서비스·드라이버 | 파서, 렌더러, 센서 드라이버 |
| 어느 실행·판본·설치를 말하는가? | 판본별 정의 / 설치 인스턴스 / 개별 발생을 구별 | 특정 작업 실행, 설치된 센서, 보고서에 쓴 자료 판본 |
| 왜 그렇게 생각하는가? | 사용자 의도·결정·담당 보고·관측 근거 | 원문 발언, 구현 보고, 실행 결과 |

같은 단어가 여러 뜻을 가질 수 있다. ‘검색’은 기능일 수도 있고 검색 모듈일 수도 있다. 이름이 같다고 합치지 않고, 같은 것을 가리킨다는 근거가 있으면 사용자의 표현·담당 표현·코드 이름을 한 대상의 이름으로 연결한다. 아직 뜻이 정해지지 않았다면 넓은 이름과 원문을 남긴다.

### 개발 대상과 사용 중인 자료를 먼저 구별한다

우리 프로젝트가 직접 만들거나 바꾸는 범위, 그 범위가 의존하는 외부 도구, 동작을 설명하는 사례 자료를 나눈다. 같은 Krita 레이어라도 ‘레이어 기능 개발’과 사용자가 그린 그림의 실제 층은 다른 범위다. 분석 도구가 DuckDB를 사용한다면 DB 엔진 내부를 자기 프로젝트의 부분으로 자동 복제하지 않는다. 내부를 수정하거나 내부 제약을 질문할 때 관련 범위만 펼친다.

한 대상에 여러 역할이 있을 수 있어도 모든 사실 관계가 자유롭게 겹치는 것은 아니다. 원본에서 정한 포함·연결·범위 제약은 유지하고, 관점별 관심 묶음만 그 제약 위에서 유연하게 모은다. 부모의 상태·권한·활성 여부도 근거 없이 모든 자식에게 전파하지 않는다.

### 분리와 유지의 판단

**따로 다룰 이유가 확인되면 나눈다.** 다른 약속을 갖거나, 적용 범위가 다르거나, 독립적으로 교체·변경하거나, 서로 무엇을 주고받는지 설명할 수 있을 때다. 예를 들어 ‘문서’와 ‘PDF 출력’은 같은 이름으로 합칠 대상이 아니다. 하나는 다루는 내용이고 다른 하나는 그 내용의 특정 산출 표현이다.

**함께 읽어야 뜻이 완성되면 같은 책임 안에 둔다.** 백업 보관 행동·백업 목록·보존 기간 규칙은 성질이 달라도 함께 읽을 이유가 있다. 같은 종류라는 이유로 모든 자료를 ‘데이터’ 창고에, 모든 규칙을 ‘정책’ 창고에 먼저 보내지 않는다.

다음 경계는 유지한다: 기능과 구현 / 규칙과 검사 처리 / 자료와 저장 수단 / 같은 대상의 다른 표시와 별개 대상의 공유 / 제품 역할과 개발 담당 / 구성과 발생과 증거 / 포함과 관점 분류와 임시 관심. 분류 전 구절도 원문으로 남기며, 모든 구절을 즉시 노드로 바꾸지 않는다.

## 3. 무엇을 묶고, 무엇을 연결하는가

### 3.1 세 가지 묶음

| 묶음 | 뜻과 지속성 | 기본 표현 | 무엇을 바꾸면 달라지는가 |
|---|---|---|---|
| 구성 묶음 | 현재 설계에서 한 책임·구성 범위로 다루는 관계 | 이름 있는 포함 면과 내부 부분 | 실제 구성 또는 합의된 정리 기준을 수정할 때 |
| 관점 묶음 | 실행 위치·제공 계약·자료 수명 등 이름 있는 기준으로 다시 모은 보기 | 관점 제목이 있는 열·띠·목록. 기준 개요의 위치는 보조로 연결 | 기준이나 멤버십을 바꿀 때. 저장해 다시 읽을 수 있음 |
| 임시 함께 보기 | 지금의 질문에 필요한 대상을 모음 | 질문 제목과 선택 윤곽·국소 연결 | 질문의 범위가 바뀔 때. 원래 소속은 그대로 |

‘측정 기능을 이룬다’, ‘장치에서 돌아간다’, ‘이번 오류와 관련된다’는 서로 다른 묶음 이유다. 같은 사각형 안에 있다는 사실만으로 셋을 같게 만들지 않는다. 사용자가 읽는 제목과 관계가 먼저 구별을 설명하고, 색·테두리는 보조한다.

### 3.2 묶음을 정하는 순서

1. **사용자가 이미 정한 구분을 찾는다.** ‘수집과 분석은 따로’, ‘이건 같은 문서’ 같은 발언과 이후 정정을 우선한다. 서로 다른 시점의 말을 동시에 현재 결정으로 만들지 않는다.
2. **현재 대상과 관계를 구별한다.** 같은 대상의 두 이름인지, 기능과 구현인지, 정의와 실행본인지부터 확인한다.
3. **함께 책임지는 결과를 한 문장으로 적는다.** 그 문장을 설명하는 데 꼭 필요한 내부와, 바깥에서 쓰는 대상을 가른다. 묶음 이유가 ‘이름이 비슷함’뿐이면 아직 구조로 확정하지 않는다.
4. **묶음의 경계를 시험한다.** 하나를 바꾸거나 다른 구현으로 바꿔도 약속이 같은가? 외부와 주고받는 것이 다른가? 다른 수명·범위가 있는가? 차이가 중요하면 하위 부분 또는 별도 묶음으로 나눈다.
5. **다른 기준과 충돌하면 관점을 나눈다.** 책임 구조를 패키지 트리나 배포 위치에 맞추려고 뒤틀지 않는다. ‘무엇을 하나’와 ‘무엇이 맡나’를 대응시킨다.
6. **이유가 약한 정리는 후보로 남긴다.** 첫 개요에는 제안된 묶음임을 한 번 알리고 사용할 수 있게 하되, 기존 구성을 크게 바꾸는 합치기·나누기·공유 추출은 이전과 이후를 비교할 수 있게 한다.

사용자가 매번 분류표를 채우는 흐름은 만들지 않는다. 묶음을 고칠 때는 “같은 부분”, “별개 구현”, “여기서 사용”, “이 질문에서만 함께”처럼 바꾸려는 뜻을 확인한다. 배치를 옮긴 행동만으로 의도나 실제 소속을 변경했다고 단정하지 않는다.

### 3.3 둘 이상의 묶음에 걸치는 부분

**대상의 정체성, 관계, 화면의 자리를 분리한다.** 하나의 전역 부모로 모든 관점을 해결하지 않는다. 한 보기에서 읽기 쉬운 주표시 자리를 두더라도 그것이 유일한 실제 소속을 증명하지는 않는다.

- 소속이 확인된 공유 대상은 그 소속을 유지하고 다른 묶음에는 참조 입구를 둔다.
- 독립된 책임·계약을 가진 공통 부분이라면 별도 범위를 둘 수 있다. 사용하는 곳이 두 군데가 됐다는 이유만으로 ‘공통’ 영역을 자동 생성하지 않는다.
- 같은 규칙을 각자 구현한 경우 규칙과 구현을 구별한다. 두 구현을 하나의 노드로 합치지 않는다.
- 같은 라이브러리 계열이라도 판본별 정의를 구별하고, 설치·실행은 해당 판본의 정의와 연결한다.
- 정체성이나 소속이 아직 불분명하면 특정 자식에 임의 연결하지 않고 알려진 범위까지만 남긴다.

묶음을 접어도 바깥 연결의 대상과 뜻을 잃지 않는다. 개요의 집약선은 관계가 있다는 요약이고, 선택하면 원래 끝점·동사·조건을 읽는다. 여러 관계를 한 선으로 합쳤다고 호출 순서나 데이터 흐름 하나로 해석하지 않는다.

## 4. 어떤 모습으로 보여주는가

**표현은 장르가 아니라 지금 읽어야 할 관계가 고른다.** 한 프로젝트에 아래 표현을 섞어 쓸 수 있지만, 한 화면이 모든 관계를 동시에 설명하려고 하지는 않는다.

| 읽으려는 질문과 근거 | 선택하는 모습 | 계속 남기는 기준 |
|---|---|---|
| 무엇이 무엇의 일부인가? | 크기와 깊이가 다른 포함 면, 작은 부분 이름 | 묶음 이유·현재 범위·바깥 접점 |
| 무엇이 들어와 어떻게 바뀌고 나가는가? | 전달·변환의 흐름. 분기·반복은 근거가 있을 때만 | 다루는 자료, 처리 정의와 특정 실행의 구별 |
| 어떤 조건에서 달라지는가? | 같은 조건을 맞춘 대안·규칙 비교 | 바뀐 조건과 달라지는 대상, 원안과 조합 초안 |
| 무엇을 제공하고 무엇을 요구하는가? | 계약·입출력·버전의 정렬된 표 또는 목록 | 제공자·사용자·필드/명령의 정체성 |
| 어디에서 어떤 구현이 동작하는가? | 위치별 띠와 구현·설치의 대응 | 업무 책임과 구현을 잇는 관계, 정의와 실행본의 구별 |
| 같은 종류가 많이 반복되는가? | 이름·속성·예외를 읽는 목록과 국소 선택 | 반복군의 기준, 다른 행동을 가진 예외 |
| 무엇이 언제 실제로 일어났는가? | 실행별 시간축·분기·재시도 기록 | 실행 식별자·시점·관련 정의. 기록 없으면 발생을 만들지 않음 |
| 원한 것과 보고된 것이 같은가? | 선택 대상 옆에서 원문·보고·관측을 직접 대조 | 적용 범위와 근거, 다음에 달라질 판단 |

### 선택이 경쟁할 때

기준 개요는 전체의 책임과 위치를 기억할 수 있게 유지한다. 특정 질문을 풀 때만 관련 범위를 다른 모습으로 읽는다. 현재 질문이 계약 비교라면 표가 중앙에 오고, 전체 위치는 짧은 경로나 작은 맥락으로 남는다. 다시 전체를 읽을 때는 출발했던 범위·선택·접힘을 복원한다.

자료가 성기면 가장 적은 가정을 요구하는 이름·구절 묶음부터 시작한다. 구조가 희박한데 흐름을 그리기 위해 순서를 만들지 않는다. 반대로 입력·변환·산출이 명시됐다면 해당 범위에서는 흐름을 시작점으로 쓸 수 있다. 관심을 받았다는 이유로 매번 기본 배치를 다시 계산하지 않는다.

### 공통 시각 문법

- 전체에서는 이름과 묶음의 관계가 먼저 읽힌다. 모든 부분에 설명 카드·상태 문장·출처 칸을 붙이지 않는다.
- 안으로 들어가면 선택한 범위만 넓히고 바깥과의 접점은 가까운 가장자리에 남긴다. 모든 부분을 같은 비율로 줄이지 않는다.
- 관계의 제목은 선이 교차하는 중앙보다 대응하는 접점 가까이에 둔다. 읽을 자리가 부족하면 국소 관계 목록으로 풀며 카드 글자를 관통하지 않는다.
- 같은 대상은 이름과 참조로 이어진다. 표현이 바뀌어도 ‘같은 것’과 ‘그것을 맡는 구현’이 다른 관계임을 읽을 수 있어야 한다.
- 강조는 현재 선택·관련성·판단 이유를 위해 쓴다. 프로젝트마다 수십 개의 도형이나 예제 전용 아이콘을 외우게 하지 않는다.
- 기본 화면은 현재 상황을 읽는 자리다. 긴 원문·수정·비교는 집중해서 읽는 장면으로 이어지며, 작성 중인 내용과 출발 맥락을 보존한다.
- 휠 확대는 카메라 변화다. 다른 의미 층으로 들어가는 것은 명시적인 이동이다. 보기용 배치 변경과 내용·소속 정정도 구별한다.

## 5. 적은 자료에서 복잡한 프로젝트까지

### 이름 몇 개와 구절만 있을 때

이름이 있는 부분과 아직 자리 없는 구절을 함께 둔다. 구절이 가리키는 대상을 확실히 정할 수 없으면 인용을 보존한다. ‘보통 이런 프로젝트에는…’라는 질문을 제안할 수 있지만 실제 구성처럼 놓지 않는다. 구상·설계·구현 보고·관측의 빈칸을 채우기 위해 노드를 생성하지 않는다.

### 부분이 많아질 때

접는 기준은 임의의 ‘몇 개’가 아니라 **읽을 책임의 경계와 반복성**이다.

| 유지해서 보여줄 것 | 접거나 다른 표현으로 보낼 것 |
|---|---|
| 묶음이 맡는 일과 현재 선택의 위치 | 선택하지 않은 묶음의 세부 구현 |
| 외부가 쓰는 접점과 공유 대상의 참조 | 모든 사용처로 향하는 개별 선 |
| 현재 판단에 영향을 주는 예외·차이 | 같은 계약을 따르는 동질적인 반복 정의 |
| 사용자가 찾던 부분의 경로와 관련 변화 | 원문 전체·세부 검사 기록 |
| 원문 의미를 바꾸는 미정·충돌 | 단순히 아직 구체화되지 않은 미래 구상 |

반복군은 종류·계약·변경 방식이 같은지 확인해 묶는다. 이름이 비슷하다는 이유만으로 합치지 않는다. ‘검사 규칙 여러 개’라는 요약은 각 규칙을 삭제한 것이 아니며 목록·검색에서 모두 접근된다. 예외가 발견되면 관련 질문에서 그 예외를 펼친다. 예외가 많으면 더 작은 하위군 또는 비교 표로 전환한다.

접힌 부모는 내부의 중요한 판단거리를 짧게 남긴다. ‘설정 연결 전’처럼 실제 다음 행동을 바꾸는 이유를 보여주되 모든 미정을 경고로 올리지 않는다. 오래됐거나 언급이 적다는 이유로 안정·완료라고 부르거나 숨기지 않는다.

### 새로운 기록이 구조를 바꿀 때

기존 대상에 관한 새 보고는 그 대상 가까이에 쌓인다. 이름 변경은 이전 이름과 연결하고, 분할·합치기·공유 추출은 전후의 대응을 남긴다. 사용자가 읽는 중에는 선택·카메라·접힘을 유지한다. 새 사실을 받는 것과 전체 배치를 고치는 것은 별개의 변화다.

한쪽 가지는 구현까지 있고 다른 쪽은 구상뿐이어도 된다. 깊이를 맞추려고 빈 컨테이너를 만들지 않는다. 구성의 세부 깊이, 구현 대응의 자세함, 근거의 양은 서로 다른 축이다. 근거가 적다고 부분이 작거나 중요하지 않은 것은 아니다.

## 6. 실제 오픈소스로 시험한 묶음 규칙


이 표는 개발 종류의 완전한 목록이 아니다. **같은 이름·공유·순서·실제 포함·정의와 실행·물리 연결이 서로 다른 묶음을 요구하는지** 시험할 대표 자료다. 원본 요소·관계는 공식 문서에서 확인했고, 화살표 오른쪽의 묶음과 화면 선택은 AgentFlow의 설계 제안이다. 저장소 실행이나 코드 전체 분석을 했다는 뜻은 아니다.

| 실제 프로젝트·확인한 재료 | 책임으로 읽는 묶음 제안 | 다른 질문에서의 묶음·표현 | 이 사례가 바꾼 규칙 |
|---|---|---|---|
| [Krita](https://github.com/KDE/krita): Paint·Vector·Clone·File Layer, Group Layer, Filter Layer·Filter Mask, Transparency·Transform·Selection Mask | 내용 공급 / 합성 경계 / 결과 가공 / 편집 범위 | 색·형태·가시성·원본 갱신의 관점에서 관련 기능을 다시 모음. 실제 문서의 레이어 트리는 별도 사례 자료 | 영향받는 층을 필터의 자식으로 두지 않는다. 참조 원본을 Clone의 자식으로 두지 않는다. 기능 설계와 사용자의 그림 내용은 별개 [K1] |

### 특히 강한 반례 세 가지

**같은 이름의 재등장은 같은 대상의 증거가 아니다.** Collector의 processor는 같은 설정을 여러 파이프라인이 참조해도 각 파이프라인의 인스턴스와 상태가 따로 생긴다. ‘하나로 합친 뒤 여러 곳에서 참조’라는 일반 규칙만으로는 틀린다. 먼저 정의·설정·사용 자리·실행을 구별해야 한다. [O1]

**함께 움직이는 것은 포함과 다르다.** Krita의 필터 적용, Clone의 원본 참조, Group의 구성은 서로 다른 관계다. ‘영향받는다’는 이유만으로 안쪽에 넣으면 보기 좋은 그림이 틀린 소유 구조를 만든다. [K1]

**같은 소프트웨어라도 사용 목적에 따라 드러낼 내부가 다르다.** DuckDB 엔진을 개발하는 프로젝트에는 파서·바인더·계획기가 중요한 부분이다. DuckDB로 CSV를 요약하는 개인 도구에는 ‘입력 / 집계 / 출력’과 DuckDB 의존 관계가 먼저다. 성숙 OSS를 그대로 작은 프로젝트의 빈 골격으로 복사하지 않는다. [D1]

## 7. 복합 프로젝트에 전체 규칙을 적용한다

아래는 위 OSS의 관점을 대입하기 위한 **합성 설계 사례**다. 실사용 기록이나 자동 추출 결과가 아니다.

### 7.1 측정 도구: 하나의 목적, 여러 제공 형태

목적은 ‘현장에서 모은 값을 믿고 분석해 비교한다’다. 펌웨어·분석 라이브러리·CLI·데스크톱 보기가 한 저장소에 있어도 프로젝트를 네 장르로 쪼개지 않는다.

기준 개요의 책임 묶음:

```text
측정 도구
├ 측정하기
│  ├ 센서 읽기
│  ├ 읽지 못한 값 처리
│  └ 측정 주기
├ 값을 해석하기
│  ├ 단위 변환
│  ├ 보정 규칙
│  └ 유효 범위 판단
├ 기록을 보관·교환하기
│  ├ 측정 기록 형식
│  ├ 장치 임시 기록
│  └ PC 보관
├ 분석·비교하기
│  ├ 기간 집계
│  └ 요약 결과
└ 결과를 읽기
   ├ CLI 보고서
   └ 데스크톱 비교 보기
```

이것은 구현 소유 트리가 아니다. 각 묶음은 하나의 책임을 설명하며, 장치·PC의 실제 구현은 대응 관계로 읽는다.

| 같은 대상·범위 | 기준 개요에서 | 구현·위치 관점에서 | 특정 질문에서 |
|---|---|---|---|
| 보정 규칙 | 값을 해석하기의 규칙 | 규칙을 적용하는 라이브러리와 대응. 펌웨어 적용 여부는 별도 근거 | ‘두 번 보정되나?’에서 양쪽의 적용 보고를 비교 |
| 측정 기록 형식 | 기록을 보관·교환하기의 계약 | 장치의 작성 구현과 PC의 읽기 구현이 참조 | 판본·필드·읽기/쓰기 호환성 표 |
| 요약 결과 | 분석·비교하기의 산출 자료 | CLI와 데스크톱이 각각 표시 | 같은 결과를 표시하는지, 서로 다른 판본인지 구별 |
| 특정 장치에서의 측정 실행 | 구성의 새 형제가 아님 | 실행이 발생한 장치 인스턴스와 그 장치의 펌웨어 판본에 연결 | 오류 시점과 기록이 있을 때만 시간축 |

‘보정 규칙’은 같은 대상이 여러 보기에서 다시 나타난다. ‘라이브러리의 보정 처리’는 그 규칙과 연결된 별개 구현이다. ‘특정 센서의 보정 결과’는 또 다른 발생이다. 같은 이름 세 개를 한 카드로 합치지 않는다.

기준 공간에서는 책임을 읽고, 기록 형식을 살펴볼 때는 계약 표, 잘못된 측정값을 볼 때는 관련 부분의 국소 흐름이 적합하다. 둘을 오가도 대상 이름·출발 범위·사용자 정정은 이어진다. 프로젝트에 장르 하나를 먼저 고르게 할 필요가 없다.

### 7.2 문서 변환 도구: 아직 구조가 없는 초기 구상

합성 발화: ‘마크다운을 PDF와 docx로’, ‘표가 깨지면 안 돼’, ‘이미지 상대경로’, ‘표지 템플릿’, ‘나중엔 폴더째로?’

처음에는 `읽어들이기 / 내용과 모양 보존 / 내보내기`라는 잠정 책임과 관련 구절을 둔다. 입력·변환·산출 관계가 명시돼 있으므로 짧은 흐름으로 읽을 수 있다. 내부 변환 엔진·스케줄러·클라우드 저장은 만들지 않는다. ‘폴더째로’는 아직 단일 실행의 확장인지 배치 작업 제품인지 정해지지 않은 구절로 남긴다.

PDF와 docx는 같은 문서 내용의 서로 다른 산출 형식이다. 출력 정의와 실제로 생성된 파일도 구별한다. 템플릿 수가 늘면 템플릿 정의 목록으로 읽고, 깨지는 특정 표는 관련 규칙·출력 형식과 함께 보는 예외로 펼친다.

CLI가 추가돼도 ‘읽어들이기’와 ‘보존’의 정체성을 버리지 않는다. 새 접점과 어떤 구현을 쓰는지 연결한다. 독립적으로 제공되는 온라인 변환 서비스가 나중에 생긴다면 그때 근거를 가지고 큰 범위를 구별한다. 웹이라는 단어만으로 새 제품 틀을 즉시 만들지 않는다.

### 7.3 기본 책임 지도보다 다른 표현이 나은 경우

독립 명령·플러그인·수치 알고리즘의 카탈로그에서는 자연스러운 상위 책임이 약할 수 있다. 이 범위는 계약·입력·결과·상태를 비교하는 목록을 기본으로 둔다. 관계가 없는 항목을 배치하기 위해 선을 그리지 않는다.

특정 장애의 원인은 시간·순서·동시성에 있을 수 있다. 책임 지도만으로 이를 설명하지 않고 해당 실행의 기록을 열어 구성과 대응시킨다. 반대로 실제 실행 기록이 없으면 설계된 흐름을 읽을 수는 있어도 ‘이 순서로 발생했다’고 표시하지 않는다.

## 8. 대화 기억과 판단을 구조 가까이에 둔다

구조는 기억의 각주가 아니고, 대화도 구조의 각주가 아니다. 사용자가 만들고 있는 대상에서 서로 만난다. 원문 발언 → 현재 해석과 적용 범위 → 담당 보고 → 관련 관측을 연결하되 하나의 상태로 뭉개지 않는다.

‘요청 있음’은 접수나 실행 중의 증거가 아니고 ‘보고 받음’은 완료의 증거가 아니다. 확인되지 않은 곳을 실패로 칠하지 않는다. 반대로 보고가 약속한 범위와 사용자가 원한 범위가 다르면 관련 부분에서 구체적으로 드러낸다.

해석을 고치는 일과 새 요구를 만드는 일은 다르다. 원문은 보존하고 현재 해석·적용 범위를 수정한다. 기존 두 대안에서 고른 조합은 원안을 덮지 않는 새 초안으로 남긴다. 지도에서 이름·위치를 옮겼다는 이유로 소프트웨어 수정 지시를 자동 발송하지 않는다.

돌아온 사용자에게는 마지막으로 보던 부분과 관련 변화·남은 판단부터 연결한다. 모든 변경의 긴 보고서를 첫 화면으로 만들지 않는다. 담당 세션·개발 활동은 제품 역할과 구별해 해당 부분의 작업 맥락에서 읽는다. 수집 hook·MCP·작업 전송은 이 전체 표현 설계를 지탱할 후속 범위이며 이번 구현 대상은 아니다.

### 정보구조 도구에서 가져온 메커니즘

[Backstage System Model](https://backstage.io/docs/features/software-catalog/system-model/)은 서로 다른 구성요소·자원을 하나의 기능 경계로 읽는 근거다. AgentFlow가 같은 기업용 분류체계나 API 등록 절차를 요구한다는 뜻은 아니다.

[Structurizr의 모델·뷰](https://docs.structurizr.com/dsl/language)와 [그룹](https://docs.structurizr.com/dsl/cookbook/groups/)은 대상과 표시를 분리하는 근거다. 단일 그룹 경로를 모든 관점의 소속으로 확대하지 않는다. [배포 보기](https://docs.structurizr.com/dsl/cookbook/deployment-view/)에서는 구성요소 정의와 배포 인스턴스도 구별해야 한다.

[Archi 공식 안내서](https://www.archimatetool.com/downloads/archi/Archi%20User%20Guide.pdf)의 모델 개념·뷰의 도형·시각 그룹 구별은 Pro가 확인한 참고 근거다. 총괄이 이 도구를 직접 조작하거나 해당 PDF의 화면 가독성을 검증한 것은 아니다.

- Sol6.1 High: 기존 설계의 미결정·축 혼합과 새 본문 모순을 좁게 읽는 담당. 화면 실행·사용성 실험과 다르다.

원출처의 구조 사실, AgentFlow의 묶음 제안, 합성 적용 사례를 구별한다. 이 설계는 모든 소프트웨어 분야의 실사용 합격을 선언하는 문서가 아니라, 새 분야를 추가해도 특정 장르 틀부터 다시 만들지 않도록 하는 전체 기준이다.


### 후속 설계의 판정 장면

새 종류의 프로젝트를 추가할 때마다 새 전용 화면을 만드는 대신 아래 같은 질문으로 체계가 견디는지 확인한다.

1. 처음 보는 분야에서도 대상의 뜻과 묶음의 이유를 설명할 수 있는가?
2. 같은 책임이 여러 구현·패키지·장치에 걸쳐도 정체성을 잃지 않는가?
3. 같은 대상의 다른 표시와 별개 구현·판본·실행을 구별하는가?
4. 같은 것끼리 반복되는 범위는 목록으로, 관계가 중요한 범위는 맥락으로 읽히는가?
5. 깊이와 근거가 비대칭인 초기 프로젝트도 추측한 구조 없이 쓸 수 있는가?
6. 개요·내부·계약·실행·원문 사이를 오가며 무엇을 보는지와 돌아갈 곳을 유지하는가?
7. 실제로 중요한 예외와 다음 판단을 접힌 개요에서도 놓치지 않는가?

이는 사람에게 사용 기록 제출을 요구하는 관문이 아니다. 총괄과 설계 담당이 자료를 대입해 판단할 기준이다. 실제 로그의 자동 정리 정확도와 임의 규모의 화면 가독성은 별도 확인이 필요하며, 이 문서 개정만으로 구현 성공이나 사용성 합격을 주장하지 않는다.
