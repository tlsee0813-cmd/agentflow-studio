# 29 단일 읽기 스크롤 회귀 보완

원 검사 56CB는 바깥 body의 scrollTop만 비교해 설명 내부 source-raw가 스크롤되는 상태에서 실제 읽던 위치가 사라지는 결함을 놓칠 수 있었다. 별도 Cloud 관측에서 이 결함이 보고됐고, 제품 담당은 컴포넌트 안 source-raw의 중첩 스크롤을 없애 이 텍스트 자료를 바깥 body에서 읽도록 하는 fix2를 작성했다. 설명·구상·텍스트 기록만 이 범위에 포함하며, JSON 원문 textarea의 내부 읽기 위치는 보존 대상에 추가하지 않는다. 이 작성자는 해당 Cloud 관측을 직접 실행하지 않았다.

검사는 별도 폴더에서 보완했다. 원 56CB, 이전 CI 응답과 작성자 증거는 변경하지 않았다. 동일 fixture와 네 장면·양 PC를 유지하며 새 장면이나 모바일 검사를 늘리지 않았다.

- 선택 설명의 실제 높이·overflow를 읽어 별도 내부 스크롤이 없는지 확인한다.
- SUMMARY와 body·viewport의 실제 hit 가능한 교집합과 남은 양수 스크롤 범위를 측정한 뒤 native wheel을 보낸다. 실제 body scroll 이벤트와 위치 안정화를 확인한다. 움직이지 않는 휠에 scrollend를 무조건 요구하지 않는다.
- 첫 U 키 입력 직후 다른 클릭으로 보정하지 않고 DOM·초점·선택 범위·본문과 바깥/내부 위치를 함께 비교한다.
- 같은 긴 r2를 명시적으로 닫고 다시 열면 처음부터 읽는 대조를 둔다. 다시 body를 양수 위치로 읽은 뒤 B0의 정확한 H 보고를 받고도 pinned r2·원문 글줄·body 위치가 보존돼야 한다. 새 r3는 명시 재열기로만 선택하고 처음부터 읽는다.

독립 정적 검토에서는 첫 번째로 보이는 글줄을 매번 다시 고르면 안내문·페이지 위치 변화 때문에 다른 줄을 비교할 수 있다는 지적을 받았다. 최초에 저장한 text와 lineIndex의 같은 Range만 다시 검사하도록 수정했다. 안내문이 그 줄을 가리면 다른 글줄로 대신 통과하지 않고 실제 cover·clip·hit를 남긴다. 수신 후 body 위치 비교는 참고로 재접근하기 전에 수행하며, 그 줄을 보이게 하려고 body를 직접 스크롤하지 않는다.

원 검사에서 발견된 reach(BODY)의 무효 작은 휠 준비 실패와 실제 제품의 중첩 읽기 위치 소실을 구분한다. fix2에는 큰 컨테이너 전체를 완전히 보이게 하려는 reach(BODY)를 넣지 않았다. 일반 controls의 기존 도우미는 재작성하지 않았다.

로컬 AST와 변경 경계 검사만 통과했다. 기존 fixture 문자열이 바뀌지 않았음을 AST로 대조했으며 추가 Node 실행은 하지 않았다. 서버·브라우저·지원 Node22 실행은 하지 않았다. 실제 UI 결과는 Cloud/CI가 확인해야 한다. 이전 709e CI는 기존 AREA17 단계에서 실패해 신규29가 실행되지 않았으며, 그 CI 결과를 이 새 경계의 수용으로 쓰지 않는다.
