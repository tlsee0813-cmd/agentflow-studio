# 사이클21 — 빈 프로젝트에서 첫 변경까지
2026-10-23 KST. 독립 화면 검증을 마친20 수정후보 df726e5898f24e23d69e47651d3bf6cbea302412를 선관측 기준으로 고정한다. 20의 양OS CI와 최종 통합 판정은 별도 진행 중이다. 이 관측은 제품 변경 없이 병렬 진행하며20 수용을 선행 선언하지 않는다. 아래는 전체 방향 문서의 질문을 일괄 구현하는 계획이 아니다.

## 목적과 범위
준비된 지도 입력 없이 목적→첫 구성→정확한 부분 요청→인계→수신→다음 요청이 한 흐름으로 이어지는지 확인한다. PC1280×720,1440×900. 사용자 프로젝트는 사용하지 않고 정상 새 프로젝트로 만든 명시 합성 사례 하나를 쓴다: 도서 예약 서비스, 중복 예약 방지, 예약/알림 두 부분, 예약의 하위 예약 가능 여부, 하위→알림의 명시 관계. UI로 입력한 내용만 실제 프로젝트 사실이다.

## 최초 관측과 재현을 구분
1. 먼저 화면의 문구·접근성 정보로 목표 행동을 선택한다. selector 정답을 단계 시작 전에 제공하지 않는다. 현재 화면·선택 문구·기대·실제 결과를 남긴다. 작업자는 코드/이전 검증 경험이 있으므로 초행 사용자나 블라인드 실험이라고 쓰지 않는다.
2. 단계마다 ‘기존 지식으로 선택 / 화면 탐색 후 선택 / 경로 도움 후 수행 / 수행 못함’을 기록한다. 막힌 뒤 코드/selector를 확인한 시점은 명시한다. 이후 자동 회귀는 조작 가능성의 증거이며 발견성 관측과 구분한다.
3. 두 root와 child 생성에서 실제 부모 의도와 결과를 확인한다. 먼저 기능을 추가하지 않고 메뉴 이동·되돌아감·잘못 생성/취소를 관측한다. 선택 부분과 전역 추가의 차이를 Dify의 문맥 내 추가 기준과 비교한다.
4. 요청 전 목적·현재 부분·정확한 요청 대상을 어디에서 확인했는지, 목적/조건을 재입력하거나 긴 기록을 다시 찾아야 했는지 기록한다. 클릭 수를 단일 품질 점수로 삼지 않는다.

## 완주 검증
정상 홈의 새 프로젝트로 시작한다. 초기 프로젝트 JSON/소스·저장소 주입은 금지한다. 목적은 한 번 입력하고 두 부분과 실제 자식 하나, 명시 관계 하나를 화면에서 만든다. 해당 자식에 요청을 작성한 뒤 결과 파일용 실제 인계를 복사 또는 다운로드한다. 일반 작업문 복사는 H 생성을 대신하지 않는다.

그 실제 내보내기에 포함된 project/task/H/anchor를 사용해 명시 합성 return.2를 작성한다. 입력 자체는 합성이며 실제 AI 실행·의미 추출·완료 증거가 아니다. 짧은 현재 설명과 남은 질문을 포함하고, 유효한 형식으로 정상 파일입력에서 수신한다. 자동 적용/보류 상태를 화면에서 읽고 정확한 report/H→당시 사본→현재 부분 설명을 구별한다. 필요한 근거만 열어 같은 자식의 후속 요청을 작성·인계한다. 원래 목적·포함·관계·다른 부분을 보존하며 지도 복귀까지 관측한다. 파일을 만들기 위해 실제 내보낸 템플릿을 해석하는 단계와 UI 발견성 관측은 분리한다.

## 판정과 다음 구현
데이터/대상/근거가 잘못되면 기능 결함이다. 경로를 알고 따라가야 완주하거나 목적·대상을 다시 조립해야 하면 완주 성공과 별개로 경험의 공백이다. 최초 공백 한 곳만 구현 후보로 좁힌다. 공백이 없다면 새 기능을 억지로 만들지 않고 다음 전체 관문을 다시 판단한다. 일반 AI/엔진, 새 온보딩 wizard, 전역필수폼, 자동 의미 관계, 템플릿의 사용자 사실화는 범위밖이다.

증거는 GitHub delivery 새접두사, 현재 상태는 ACTIVE, 결과는 해당사이클 RESULT에 보존한다. main/public 불변, 기존 Cloud 환경 사용, 로컬 서버 금지 경계 유지. 사람 사용 기록을 새 관문으로 요구하지 않는다. Dify 목적 차이를 구분한 제한 조작 비교와 에이전트 관측으로 평가한다.
