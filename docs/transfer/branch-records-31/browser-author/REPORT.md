# 31 분기 기록 진입 — 검사 작성자 기록

제품 `a4b7265a63691c584cd76b5fe17b985f12879b47`에 맞춘 신규 검사이며, 독립 UI 수용 판정이 아니다. 변경 파일은 `branch-records31_browser.py`와 기존 검사를 유지한 CI 단계 한 개다. 실제 HTTP/Chromium 실행은 Cloud/CI에 넘긴다. 로컬에서는 Python AST, 내장 JavaScript 구문, 공개 도메인 함수로 만든 합성 복구 입력 및 정확한 H 반환만 검사했다. 제품·서버·브라우저·유료 AI는 실행하거나 수정하지 않았다.

| 장면 | 실제 준비와 판단 |
| --- | --- |
| 1. 같은 이름의 두 부모 | P 아래 M을 거친 L/H/S의 질문·유효 설명·보류·이전 기준을 구별한다. P 기록을 닫고 패널을 깊게 읽은 다음 Q 정보로 갔다가 P 신호를 눌러, 과거 닫힘/스크롤 메모보다 명시적 열기가 우선하는지 확인한다. 실제 돌아온 신호 초점에서 Enter·Space, 패널에서 Escape를 사용한다. |
| 2. 실제 보고 행 왕복 | P 하위 L의 정확한 보고 T를 열고, 현재 B와 미전송 L 입력을 유지하며 원래 P 호출행으로 돌아오는지 확인한다. 이름 입력 중 Escape는 패널을 닫지 않으며, 미저장 값도 남아야 한다. |
| 3. 이전 work/records 출발점 | B0의 실제 H 파일을 정상 선택·수신한다. 현재 B 유지와 실제 새 T/원문/H를 확인한다. work 결과 읽기 및 records 소유 부분 찾기로 만든 이전 위치 출발점에서 다른 P 신호를 눌러, P의 보고 왕복이 과거 출발점에 묶이지 않는지 본다. |
| 4. 호출자 수명 | P→Q 신호, 같은 P 정보, 연결·기록 모드, 새 프로젝트와 원래 프로젝트 재진입을 구별한다. 마지막에는 실제 빈 지도 배경을 끌어 원 신호와 정보 버튼을 화면 밖으로 보낸 뒤 닫으며, 카메라를 바꾸지 않고 sr-only 전체 공간 제목에 초점이 가는지 확인한다. |

각 장면을 1280×720, 1440×900에서 실행하도록 작성했다. 8개는 예정 수이며 통과 수가 아니다. 읽기 행동 전후에는 저장된 프로젝트 전체(currentTask·draft·대상·수동 작업문·구상·원문·좌표·포함·관계 포함), 지도 변환 행렬, 접힘 상태를 비교한다. 선택 패널/선택 부분의 명시적 변화만 허용한다. 신호 및 돌아온 호출자에는 실제 ancestor clip과 hit 검사를 먼저 적용한다. 복귀 실패 후 맞춤·스크롤·초점 보정으로 통과시키지 않는다.

초기 자료 준비와 기존 위치 찾기 이후의 새 출발점 준비에는 기존 명시적 접기·전체 맞춤을 사용한다. 이는 새 신호가 카메라를 옮겨도 된다는 뜻이 아니다. 보존 기준은 이 준비가 끝난 직후 잡는다. 패널 깊은 읽기는 실제 패널 여백을 클릭해 초점을 둔 뒤 기존 End 키 동작으로 만든다. 일반 작은 컨트롤 접근은 기존 RECEIVED20의 native wheel/clip 도우미만 재사용하며, 과거 테스트 클래스를 상속하지 않는다.

합성 구조는 P→M→L/H/S와 Q→B다. P와 Q의 이름은 같고 ID는 다르다. L에는 질문 1개와 유효 설명, H에는 보류만, S에는 실제 작업문 수정 후 이전 기준 설명이 있다. 현재 작업은 B이고 미전송 요청 대상은 L이다. 늦은 반환은 별도 B0의 정확한 H이므로 같은 현재 작업 수신의 기존 T 전환 정책을 잘못 금지하지 않는다. 공개 함수로 만든 입력을 정상 복구 파일 가져오기로만 연다. UI 저장소나 제품 DOM/상태를 주입하지 않는다.

같은 부모를 계속 읽는 도중 신호 자체가 사라지는 장면은 미검증이다. 다른 정보/프로젝트로 이동하는 장면을 그 반례와 같다고 세지 않는다. 제목 fallback은 보이지 않는 제목의 실제 초점 확인이지 가시 텍스트 읽기 성공이 아니다. 사람의 발견성, 낮은 배율 전체 가독성, 모든 개발 미결, 실제 AI 품질도 이 검사로 주장하지 않는다.

마지막 작성자 점검에서 새 프로젝트의 entry가 실제로 달라졌는지, pan 후 원 신호와 정보 버튼이 단지 일부 잘린 상태가 아니라 가시 교집합 0인지 단언을 보완했다. 이전 `892ff4a6…` 검사 원문과 receipt는 `v0-before-precondition-checks`에 보존했다.

별도 Sol 정적 검토는 `D4E0…`의 프로젝트 재진입 다음 nav-space/정보 클릭이 오래된 caller를 먼저 지워 거짓 통과할 수 있다고 지적했다. 해당 보정·맞춤을 제거하고 원 카드 재진입 직후 area/owner P를 확인해 바로 닫도록 한정 수정했다. Sol은 최종 `9CA4CCE0…` 실제 해시와 delta를 직접 대조하여 이 공백 해소를 확인했다. 원 D4E0와 receipt는 `v1-before-independent-review-D4E0`에 남겼다. 정적 clean은 Cloud 실제 실행이나 제품 통합 승인이 아니다.

작성 중 순수 점검 스크립트에서 두 준비 오류가 있었다. 첫째, module seed를 함수 표현식 검사에 넣어 구문 오류가 났고, module을 제외하여 수정했다. 둘째, `draftTarget`을 문자열로 잘못 비교한 점검 단언을 실제 `{area: ID}` 구조로 고쳤다. 브라우저 검사나 제품 실패가 아니며, 앞선 점검 스크립트 전문은 동결하지 않았다. 이후 점검의 실제 stdout/stderr/exit를 별도로 보존한다. 독립 Sol 정적 검토와 Cloud 실제 실행 결과는 이 작성자 기록과 분리한다.
