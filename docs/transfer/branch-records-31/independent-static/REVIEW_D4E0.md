## 수정 또는 범위 한정이 필요한 한 지점

검사 198–199행은 원 프로젝트로 돌아온 뒤 `nav-space`와 `node-info-P`를 누르고 닫는다. 제품 `openSpace` 334–340행과 정보 버튼 1409행은 각각 `branchRecordCaller`를 지운다. 따라서 프로젝트 전환에서 이전 P 호출자가 잘못 살아남아도 이 준비가 먼저 지워 거짓 통과할 수 있다. 프로젝트 경계의 호출자 수명 자체를 검증했다고 할 수 없다.

제품 `openEntry` 201–211행은 정상 홈 카드 재진입에서 이미 전체 공간을 열고, `recallMap` 149–155행은 선택 P와 패널 모드·메모를 복구한다. 실제로 복구된 P 패널을 확인하고 별도 nav-space/정보 호출 전에 닫아 `node-info-P` 초점을 검사하면 이 경계를 구별할 수 있어 보인다. 이는 정적 판단이며 실제 UI 전제는 아직 실행하지 않았다. 정상 UI에서 그 패널 상태를 만들 수 없다면 검사·보고 범위를 재진입 데이터 보존과 새 정보 호출자 확인으로 한정해야 한다. ## 맞는 경로와 검사 범위

- 공개 domain API로 만든 합성 입력을 정상 파일 가져오기로 준비한다. 다른 현재 작업 B와 별도 B0의 정확한 H 반환을 사용하므로 기존 같은 작업 수신 정책과 충돌하지 않는다. borrowed `select`의 명시 file 경로도 이 fixture와 맞는다.
- `map-fit` 1577행과 `toggleBranch` 1436–1438행은 기존 located/origin을 지우지 않는다. 그러므로 test03의 fit/fold 준비 후 다른 P 신호를 여는 경계는 기존 work/records 출발점이 남은 실제 제품 경로다.
- 원 보고 T 식별, 저장 프로젝트 전체 불변, 지도 행렬·접힘 불변, 원 호출행의 실제 clip/hit·초점·세로 위치를 함께 검사한다. 보고 복귀 실패 뒤 맞춤·초점 보정으로 성공시키는 경로는 찾지 못했다.
- 입력 Escape, 실제 반환 초점의 Enter/Space, 빈 배경 pan과 화면 밖 대체 초점은 제품 이벤트 경로와 맞는다. 제목 대체점은 sr-only 초점 확인이며 가시 텍스트 읽기 성공으로 주장하지 않는다.
- workflow는 보존 원문 대비 정확히 7줄 추가·삭제 0이다. CRLF, 기존 단계와 실행 예산은 유지됐다.

INPUT의 Tab 접근 자체와 신호 진입 직후 첫 기록·소유자 줄의 실제 가시성은 이 스크립트가 별도로 확인하지 않는다. 소유 ID 목록은 DOM 조회이며 보고 행은 이후 native reach로 접근한다. 이를 작성자 검사 통과 범위로 확대하지 말고 독립 Cloud 관측과 구분해야 한다. 같은 호출 세션의 신호 소멸은 작성자 보고가 이미 미검증으로 명시했다.
