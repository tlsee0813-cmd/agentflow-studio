# GUIDE097 — 영역 구상에서 첫 요청 초안까지 (개발용 수직 흐름)

작성 2026-10-15 KST. 기준 source `0e884307`, 브랜치 `feat/area-guidance097`. 공개 배포 없음. main/dev/PR2/gh-pages 변경 없음.

## 1. 판단

**구현 가능하다.** 새 인증 설계는 필요 없다. 이미 있는 continuity 개발 서버의 경계를 그대로 쓴다.
- localhost Host/Origin 확인, `X-AgentFlow-Request` 헤더, 128 KiB 한도
- 서버 쪽 키, `ALLOW_PAID_AI` 명시 동의, 같은 limiter
- 화면 상단 연결 메뉴의 전송 동의

**차단 사항(이번 범위 밖).** 공개 정적 사이트(Pages)에서는 실제 AI를 쓸 수 없다. 키를 둘 서버가 없고 CSP가 `connect-src 'none'`이기 때문이다. 공개본에 실제 AI를 붙이려면 인증·프록시를 따로 설계해야 한다. 정적 빌드에서는 같은 기능이 브라우저 MOCK 규칙으로만 동작하며, AI로 표시하지 않는다. 이번에는 배포하지 않았다.

## 2. Pro 추천에서 빠진 기존 기능과 계약 (코드 근거)

**빈 곳은 ‘요청을 보내기 전’ 단계 하나다.** 기존 경로는 요청 원문이 있어야 시작하고, 시작하면 Task·Source(사용자 요청 원문)·Basis(requested)를 만든다. 영역 구상만으로 `/api/continuity`를 부르면, 앱이 쓴 문장이 사용자 요청 원문과 기준으로 영구 기록된다. 이는 원문 출처 계약 위반이다. 그래서 저장하지 않는 미리보기 계약(`guidance.1`)을 따로 두었다.

**경로 혼동 주의.** 구형 INIT 앱 경로(`app/server/app.mjs`, `/api/interview`, `app/server/providers/deepseek.mjs`의 `callDeepSeek`·`systemPrompt`)는 쓰지 않았고 바꾸지도 않았다. 공용으로 쓰는 것은 기존 continuity가 이미 쓰던 `readLimitedBody`, `config.mjs`, `errors.mjs`, `limiter.mjs`, `static-files.mjs`뿐이다.

## 3. Pro 추천과 다르게 한 점

1. **질문의 답을 바로 ‘이미 정한 답’(answered 기준)으로 저장하지 않는다.**
   - 이유: 채택 전에는 프로젝트를 바꾸지 않는다는 요구가 있다. 또 사용자가 초안을 고쳐 답과 다르게 바꿀 수 있다.
   - 답은 채택한 초안 원문에 들어간다. 사용자가 그 초안을 보내면 이후 모든 문맥에 requested 기준으로 남는다. 다음 안내는 이 영역의 요청 원문을 읽으므로 같은 질문을 다시 하지 않는다(G097-2).
2. **‘첫 작업문’을 별도로 만들지 않는다.** 채택한 초안은 그 영역을 대상으로 기존 요청 입력칸에 들어간다. 작업문은 기존 ‘작업문 준비하기’가 만든다. 그 결과 질문·배경 사본·오래된 응답 차단·수동값을 다시 만들지 않았다.
3. **저장 형식을 바꾸지 않는다(project.5 유지).** 안내 상태(질문·답·초안·고친 내용)는 탭 메모리에만 프로젝트와 영역별로 둔다.
   - 한계: 새로고침하면 채택 전 안내 상태는 사라진다. 프로젝트와 요청 입력칸은 기존대로 보존된다.

## 4. 계약 `guidance.1` (GUIDE098에서 `guidance.2`: proposal에 `defaults` 추가, 12장)

요청은 사용자가 쓴 자료만 담고, 써 넣을 Source·Task·Basis는 없다.
- `ticket{projectId,revision,requestId,areaId}`, `projectName`
- `brief`(목적, 없으면 null)
- `area{id,name,note}`(ticket.areaId와 같아야 함)
- `decisions`: confirmed·deferred·answered 기준의 현재 값. 자르지 않는다.
- `areaWork`: 이 영역의 요청 원문과 직접 고친 scope·checks. 최신순, 최대 5개. 크기를 넘으면 오래된 것부터 빼고, 빠진 만큼 화면의 ‘읽은 자료’에 표시된다.
- `answer`: 질문과 사용자 답(provided·unknown·deferred). 없으면 null.

응답은 `{question, proposal}`이며 정확히 하나만 null이 아니다.
- `answer`가 있으면 question은 거절한다. 질문은 많아야 하나라는 것을 코드로 강제한다.
- `proposal{goal,scope,checks,open[]}`, 추가 키는 거절한다.
- 응답 봉투의 ticket은 요청 ticket과 같아야 한다. 다른 영역의 응답은 거절한다.

화면은 응답을 다음 조건이 모두 맞을 때만 적용한다.
- 같은 프로젝트 활성화
- 같은 대기 요청
- 요청에 쓴 자료(목적·영역·결정·영역 요청·답)의 digest가 지금과 같음

요청 입력칸에 글을 쓰는 것은 digest에 들어가지 않으므로 응답을 막지 않는다.

## 5. 사용자 흐름

1. 영역 화면에 ‘무엇을 요청할지 같이 정하기 · 선택’이 보인다. 요청이 없는 영역에서는 펼쳐져 있고, 요청이 있는 영역에서는 접혀 있다. 지도 패널에도 같은 버튼이 있다.
2. ‘질문 또는 초안 받기’를 누르면 결과가 둘 중 하나다.
   - 질문 하나: 선택지, 직접 답, 모름, 보류로 답할 수 있다.
   - 바로 초안: 목적·구상·결정·영역 요청에 답이 이미 있을 때.
3. 초안을 고칠 수 있다. 고친 내용은 영역 전환, 중단, 실패, 늦은 응답 뒤에도 남는다. 고친 상태에서는 ‘다시 받기’ 대신 ‘고친 내용 되돌리기’가 나온다.
4. ‘이 초안으로 요청 쓰기’를 누르면 초안이 이 영역의 요청 입력칸에 들어간다. 아직 보내지 않은 상태다. 사용자가 확인한 뒤 ‘작업문 준비하기’로 보내면 기존 경로가 이어진다.
   - 작성 중인 요청이 있으면 넣지 않고 알린다. 초안도 그대로 남는다.
5. 숙련자는 기존 ‘＋ 이 영역에 새 요청’을 그대로 쓴다.

## 9. 남은 제한

- 실제 AI 품질은 미검증이다. 프롬프트는 후속 실제 검증에서 바뀔 수 있다.
- 안내 상태는 탭 메모리에만 있다. 새로고침하면 채택 전 상태가 사라진다.
- 공개 정적 사이트의 실제 AI는 차단 사항이다(1장).
- 질문의 답은 사용자가 초안을 보낼 때 그 원문으로만 남는다. answered 기준으로 따로 기록하지 않는다.
- 결정(decisions)은 영역 구분 없이 프로젝트 전체를 보낸다. 관련성 판단은 모델 몫이다.

## 10. GUIDE097-R1 — 독립 검토 3건 수정

각 건마다 회귀를 먼저 쓰고, 수정 전 빌드(`e5373409`)에서 실패하는 것을 확인했다. 수정 후 통과를 다시 확인했다.

**R1 기다리는 동안 고친 초안이 응답에 덮임 (`app.ts`)**
- 수정 전: 기존 초안에서 ‘다시 받기’를 누르고, 대기 중에 초안을 고친 뒤 응답이 오면 `g.text=g.base=…`가 고친 내용을 덮었다. 브라우저 test_04에서 실제 지연 HTTP로 재현했다. 요청을 브라우저에서 붙잡았다가 실제 로컬 MOCK 서버로 보냈고, ‘(기다리는 동안 직접 고침)’이 사라졌다.
- 수정: 초안 편집마다 세대(`gen`)를 올리고, 요청을 보낼 때의 세대를 기억한다. 응답이 왔을 때 세대가 바뀌었으면 화면을 바꾸지 않는다. 같은 글자로 되돌아온 편집도 사용자 편집으로 친다. 응답은 `incoming`에 보관하고 안내 문구를 띄운다.
- 사용자가 고르는 방식:
  - ‘내 초안 유지’: 기본값이다.
  - ‘새 응답으로 바꾸기 · 지금 초안 버림’: 명시적으로 눌러야만 화면 내용을 버린다. 앱이 버리는 쪽을 자동으로 고르지 않는다.
- 같은 원칙이 적용되는 경우: 질문 응답, 영역 전환 중 도착, 중단, 실패. 전부 test_04와 test_03에서 확인했다.

**R2 MOCK이 금지·보류를 긍정 결정으로 읽음 (`mock.ts`)**
- 수정 전: 구상·결정·요청 문장에서 단어만 보고 상태를 버렸다. 그래서 confirmed ‘예약은 자동 확정하지 않는다. 접수만 받는다.’와 deferred ‘예약 즉시 확정은 보류한다.’가 질문 없이 ‘그 자리에서 예약이 확정됩니다’가 됐다. G097-8에서 재현했다.
- 수정: 부정어 예외를 늘리지 않았다. MOCK은 자기 질문의 선택지 라벨이 정확히 일치할 때만 그 갈래(바로 확정 / 확인 뒤 확정)를 쓴다.
  - 자유 답·인용 답: ‘사용자 답변 원문을 따릅니다: ‘…’’로 그대로 둔다.
  - 확정 방식을 이미 언급한 기존 기록(구상, 사용자 결정, 이 영역의 요청·직접 고친 범위): 다시 묻지 않고 종류·상태 표시와 함께 원문을 인용한다. 예: ‘[D1 사용자 확정] ‘…’’. 초안은 그 원문을 따르라고만 쓴다.
  - 보류 결정: ‘아직 정하지 않은 것’에 ‘D2 사용자 보류 — 정하지 않음’으로 남긴다.
  - 확정 방식을 언급했는지는 주제어(확정·승인·수락·참여 확인)로만 판단한다. 긍정인지 부정인지는 판단하지 않는다.
- 선택지 답 두 갈래의 범위·완료 조건 차이는 그대로다(G097-1).
- 기존 테스트 변경: G097-2의 두 기대값을 바꿨다. 이전에는 자유 문장(‘공방이 확인 후 확정’, ‘예약은 즉시 확정’)에서 확인 대기·즉시 확정 초안을 기대했다. 바로 그 읽기 방식이 R2 결함이므로, 원문 인용 초안을 기대하도록 바꿨다. 이유는 테스트 주석에도 적었다.

**R3 빈 수동값 검증 불일치 (`validation.ts`)**
- 수정 전: 작업 편집(`editTask`)은 빈 문자열·공백을 허용하는데, 안내 요청 검증만 영역 요청의 scope/checks를 거절했다. 그래서 안내 전체가 실패했다(`INVALID_DATA`). G097-9에서 재현했다.
- 수정: 빈 값을 허용한다(`text(…,6000,true)`). 길이 6000자 초과·제어문자 거절과, 요청 원문의 빈 값 거절은 그대로다.
- 확인: 빈 scope와 공백 checks를 직접 편집한 뒤 HTTP 안내 요청이 200을 돌려받는 것까지 확인했다.

**무게 판단:** 새 기능, 스키마 변경, UI 재설계는 없다. UI에 더한 것은 보관된 응답을 고르는 버튼 2개뿐이다. 공급자·권한·정적 네트워크 경계, 채택 전 쓰기 0, 채택 후 requested 경계는 바꾸지 않았다.

## 11. GUIDE097-R2 — 입력 경계 2건

두 건 모두 회귀를 먼저 썼다. 수정 전(`6fae21a7`)에 실패하는 것을 기록하고, 수정 후 통과를 확인했다.

**R2-1 확정 관련 보류 결정 7개면 MOCK 응답이 계약 위반**
- 수정 전: MOCK이 보류 결정마다 `open` 항목을 하나씩 만들었다. 보류 6개는 open 6개로 통과했지만, 7개는 open 7개라 `validateGuideReply`(최대 6)가 `INVALID_DATA`로 거절했다. 유효한 프로젝트 입력에서 자기 응답이 계약을 어긴 것이다.
- 수정: 상한(6)은 그대로 두고, 보류 결정 ID를 모두 한 항목에 묶는다. 예: `확정 방식 관련 사용자 보류 — 정하지 않음: D2 / D3 / …`.
- 범위 줄의 인용:
  - 들어가는 만큼 원문 전체를 인용하고, 나머지는 `외 N건: 기준 Dx, …`처럼 ID로 모두 이름을 붙인다.
  - 항목 길이(500)·필드 길이(2000)를 넘는 경우에만 건수와 원문 위치(기준 목록 등)를 적는다. 그 기록 자체는 프로젝트에 있고 작업문의 기준 목록에 전문으로 나간다.
- 확인: 보류 6·7·40개에서 open 1개, 계약 통과, 모든 결정 ID가 범위나 open에 나오는 것(G097-10).

**R2-2 긴 자유 답의 끝 조건이 잘림**
- 수정 전: 444자 자유 답 끝의 "예약 확정 처리는 금지하고 접수만 받으세요."가 300자에서 잘렸다. 그런데도 "원문은 기록에 그대로"라고 적었다. 실제로는 답 원문이 안내 메모리에만 있었고 채택할 때 지워져, 복원할 기록이 없었다.
- 수정(현 계약 재사용):
  - 초안 문장(`proposalText`)에 "안내 질문과 사용자 답변 원문" 절을 붙여, 질문과 답 전체를 자르지 않고 넣는다.
  - 채택하면 이 초안이 기존 요청 입력칸으로 가고, 보내면 사용자 요청 원문(Source)과 requested 기준이 된다. 이후 모든 작업문에 그대로 나간다.
  - 별도 저장 필드는 만들지 않았다.
- MOCK 쪽:
  - 300자 이하 자유 답은 범위 줄에 그대로 인용한다.
  - 더 긴 답은 범위 줄에 옮기지 않고, "이 요청 끝의 ‘안내 질문과 사용자 답변 원문’ 전문을 그대로 따릅니다"라고만 쓴다.
  - 긴 기존 기록은 "원문이 길어 기준 Dx의 전문을 따름"으로 실제 기준 ID를 가리킨다.
  - 문자열을 자르는 코드(`slice(0,300)`)는 없앴다.
- 명시적 한계: 초안 전체가 요청 한 건의 한도(12,000자)를 넘으면 채택하지 않고 알린다. 자르지 않으며, 초안은 그대로 남아 사용자가 줄일 수 있다. 화면의 답 입력칸은 2,000자 제한(기존)이다.
- 확인:
  - G097-11: 긴 한글 답이 초안·요청 기록·작업문에 전체로 남는다. 긴 확정 결정은 기준 ID로 가리키고, 작업문에는 기준 자체가 전문으로 나간다.
  - 브라우저 test_05: 실제로 입력 → 채택 → 보내기 → 저장 상태와 내려받은 작업문에 끝의 금지 문장이 있다.

유지한 것: 선택지 두 갈래, 확정·보류 보호, 기다리는 동안의 편집 보존. 스키마는 바꾸지 않았다.

## 12. GUIDE098 — 실제 AI 시험 뒤 최소 개선

**근거:** 클라우드 실제 호출 11회(`fbdcbf1e`, 증거 커밋 `f03e0594`의 `docs/evidence/guide097-ai-fbdcbf1/`)의 원문을 읽었다. 앞선 진단과 같았고, 하나를 더 확인했다.
- C4-B: 사용자의 자유 답은 선택지를 고르지 않았는데, 모델이 첫 선택지(흐름 정리)를 목표로 확정했다. C1-A에서 목록·휴대폰을 정한 것과 같은 유형이다.
- C4-INITIAL: 그 시점의 핵심 충돌은 구상의 미정 휴대폰 아이디어와 확정된 네트워크 금지였다. 모델은 이를 세 번째 선택지로만 두고 산출물 형태를 물었다.

**프롬프트(`GUIDE_PROMPT`, 일반 규칙만):**
- [질문]: 0~1개. 목적 달성을 막는 문제나 사용자만 정할 결정이 있을 때만 묻고, 미정 구상과 확정 결정의 충돌을 먼저 다룬다. 표시·형식·이름 같은 세부는 묻지 않고 defaults로 보낸다. 입력이 충분하면 바로 초안을 낸다.
- [최신 사용자 변경]: 답이 기존 결정의 특정 대상을 명시적으로 바꾼 부분만, 그 대상에 한해 반영한다. 언급하지 않은 조건과 실행 권한은 그대로다. 인용·가정·제3자 제안·미정 구상·이전 선택지는 변경이 아니다. 저장된 결정은 기록으로 남고, 수동 편집이나 재승인을 조건으로 만들지 않는다.
- [선택지와 자유 답]: 자유 답은 어떤 선택지도 고른 것이 아니다.
- [범위]: 목적에 쓸모 있는 가장 작은 완결 단위다. 입력 → 핵심 동작 → 결과 확인이 이어져야 한다.
- [모름·보류]: 모름은 그 사실을 확인한다. 보류는 그 선택에 의존하는 처리만 멈추고, 탐지·관찰·보고는 유지한다.
- [완료 조건]: 목표·범위와 대조한다. 나누거나 고르는 작업이면 보존 관계(부분들의 합이 입력과 같은지)와 선택 규칙 충족을 확인한다.
- [open과 defaults]: 둘을 구분한다. 금지·권한·외부 영향·데이터 변경·핵심 범위 선택은 defaults에 넣지 않는다.
- fact와 choice 출력 예시를 분리했다. 선택지가 있으면 choice다.
- 네 사례의 정답 문장이나 도메인 단어는 프롬프트에 넣지 않았다(G098-3이 도메인 단어 부재를 검사).

**계약(guidance.2, 저장되지 않는 응답):**
- proposal에 `defaults`(필수, 최대 6개, 각 1~500자)를 추가했다.
- 같은 점을 open과 defaults에 함께 넣으면 거절한다.
- fact + options 거절은 그대로다. 실제 C2 응답 원문을 회귀 자료로 쓴다.
- 요청 형식은 같지만 버전을 올렸다. 그래서 구버전 클라이언트와 서버는 400으로 서로 거절한다.
- 저장 project 스키마는 바꾸지 않았다.

**초안 문장(`proposalText`):**
- defaults가 있을 때만 "AI가 정한 기본값 (사용자 결정 아님 · 바꿀 수 있음)" 줄을 open과 따로 보여 준다.
- 답 절에 다음 설명을 붙였다: "저장된 기준은 기록으로 그대로 두고, 이번 요청에서는 답이 명시적으로 바꾼 대상만 답을 따르며, 인용·가정·제3자 제안은 변경이 아니고 바꾸지 않은 조건과 실행 권한은 그대로."
- 무조건 우선 문구와 재승인 조건은 넣지 않았다.

**MOCK:** defaults는 항상 빈 배열이다. 사용자 대신 세부를 채우지 않는다.

**검증 구분:**
- G098-1~4는 계약·렌더링·프롬프트 구조 검사다. 변경 전 `fbdcbf1e`에서는 4개 모두 실패했다.
- 의미 품질은 이 테스트나 MOCK 통과로 판단하지 않는다. 총괄 클라우드의 실제 호출 전후 비교로 다시 확인한다.
- 이 세션에서는 키 조회와 실제 호출을 하지 않았다.

**하지 않은 것:** Judge 호출, 자동 재시도, 자연어 정규식 검증, 사례별 분기, validator 완화, 질문 수 확대, 저장 체계 변경.

## 13. GUIDE098-M — MOCK 자유 답 완료 조건의 모순 제거

- 수정 전(`ec9011d3`): 예약 영역에서 자유 답을 넣으면 MOCK 완료 조건이 "답변 원문에 적힌 대로 예약이 접수·확정되는지 확인"으로 고정돼 있었다. 그래서 설계만이나 문서 읽기만 요청한 답에도 구현·동작 검사를 암시했다. G098-5가 실패했다.
- 수정: 자유 답을 해석할 수 없는 MOCK 경로에서만 완료 조건을 중립 문장으로 바꿨다. "답변 원문이 요청한 행동과 범위만 다뤘는지, 원문이 요청하지 않은 구현·실행·배포나 정책을 새로 하지 않았는지 확인하고, 실제로 확인한 것과 못 한 것을 나눠 보고합니다."
- 유지: 선택지 라벨로 알려진 두 갈래의 범위·완료 조건 차이. 실제 AI 프롬프트와 스키마는 바꾸지 않았다.
- 후속 UX 과제(이번에 추가하지 않음, 기록만): 안내 초기 단계에서 사용자가 명시적인 요청 문장을 따로 넣을 입력칸이 없다.

## 14. GUIDE099 — 초기 직접 요청을 구상과 구분하기

**문제:** 안내는 미정 구상(area.note)과 기존 결정만 읽었다. 사용자 입력은 AI가 한 질문의 답으로만 받을 수 있었다. 그래서 이미 정한 이번 요청이나 조건 변경을 처음부터 표현할 방법이 없었다.

**화면:**
- 안내 패널을 열면 선택 입력 "이번에 맡기거나 바꿀 일"과 기존 생성 버튼이 바로 보인다. 패널 안에 접힌 칸을 하나 더 두지 않았다.
- 설명 문구: "영역 구상은 그대로 두고, 이번 요청이나 바뀐 조건만 적으세요."
- 비워 두면 이전처럼 목적·구상으로 질문 0~1개 또는 초안을 낸다.
- 요청 입력칸(composer)의 내용은 읽거나 복사하지 않는다.
- 입력은 안내 상태와 같이 탭 메모리에만 있다. 새로고침하면 사라진다는 것을 화면에 적었다. 영구 저장은 범위 밖이다.

**계약 `guidance.3`:**
- 요청에 필수 nullable 필드 `currentInstruction`을 추가했다. 값은 사용자 입력 원문 그대로이며, 공백만 있으면 null이다.
- 구상, 최근 요청, 답과 섞지 않는다. 답은 실제 질문에 대한 답으로 따로 남는다.
- 길이는 요청 초안과 같은 12,000자 제한이다. 전체 요청은 128 KiB 제한이며, 오래된 영역 요청만 먼저 빠진다. 결정과 지시는 자르지 않는다.
- 넘으면 보내지 않고 화면에 알린다. 입력칸도 maxLength로 자르지 않는다.
- 응답 계약과 저장 project 스키마는 그대로다. 구버전(guidance.1·2) 요청은 400으로 거절한다.

**초안과 채택:**
- `proposalText`가 "이번에 맡기거나 바꿀 일 (사용자 직접 입력 원문)" 절에 원문을 한 번 그대로 넣는다.
- 설명을 함께 붙인다:
  - 저장된 기준은 기록으로 두고, 명시적으로 바꾼 대상만 따른다.
  - 직접 입력과 나중 답이 다르면 답이 명시적으로 바꾼 대상만 답을 따르고, 나머지 입력은 유지한다.
  - 인용·가정·제3자 제안·AI 기본값은 변경이나 권한이 아니다.
- 채택하면 기존 요청 입력칸으로 간다. 입력칸에 초안이 이미 있으면 덮지 않는다.
- 보내면 requested 요청 기록이 된다. 확정 결정으로 저장하지 않는다.

**상태:**
- 지시가 요청 자료와 digest에 들어간다. 그래서 기다리는 동안 지시를 고치면 늦은 응답은 적용하지 않는다.
- 지시가 질문·답·초안을 만든 때와 달라지면 다음과 같이 한다.
  - "바뀌기 전 입력으로 만든 것" 안내를 띄운다.
  - 이전 답으로 다시 받기와 그 질문에 답하기를 숨긴다.
  - "바뀐 입력으로 새로 받기"는 이전 질문·답을 보내지 않는다.
- 직접 고친 초안이 있으면 새 응답은 보관만 하고, 바꿀지는 사용자가 고른다(R1 기제 재사용).
- "초안 버리기"는 입력한 지시를 지우지 않는다.

**MOCK:** 직접 지시가 있으면 질문하지 않는다. 지시를 해석해 설계하지 않고, 원문을 그대로 따르라는 중립 초안을 낸다. 지시가 없으면 예약 선택지 동작은 그대로다.

**실제 AI 프롬프트:** [직접 지시] 규칙을 추가했다.
- 지시가 범위와 행동 수준을 정한다.
- 구상·이전 요청·기본값으로 지시를 넓히지 않는다.
- 명확하면 질문 없이 초안을 낸다.
