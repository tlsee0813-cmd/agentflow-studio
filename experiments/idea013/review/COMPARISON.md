# 첫 비교 기록 — 미실행 양식

이 문서는 모델에 보내지 않는다. 현재 응답·판정은 모두 비어 있다. 평가는 모델이 아니라 사람이 두 응답과 원문을 함께 읽어 수행한다. 6개 개발 사례와 별도 4개 미공개 사례는 나누어 보고하며 작은 첫 실험을 모집단 성능이나 제품효용의 증명으로 해석하지 않는다.

## 읽는 순서

가능하면 평가자에게 baseline/enhanced 이름 대신 X/Y로 제시하고, 사례마다 좌우를 번갈아 배치한다. 매핑은 기록해 둔다. 가림을 하지 못했다면 '비가림 평가'라고 적는다. 첫 판단을 적은 뒤 개발용 관찰 메모와 대조하면 특정 기대 장면에 끌리는 것을 줄이는 데 도움이 될 수 있다. 이는 제안한 평가 절차이지 검증된 편향 제거 기법은 아니다.

1. **고객에게 유용한가:** 답이 실제 행동·결과·완료 기준을 바꾸는가. 명확할 때 진행하고 근거가 없을 때 필요한 정보를 묻는가. 질문 수와 장면 수 자체는 점수가 아니다.
2. **비교가 정직한가:** 같은 상황에서 합리적인 해석을 보여주는가. 원문·확정·추정·제안·미정이 구분되는가. 기존 확정을 침범하거나 한쪽으로 몰아가지 않는가.
3. **다음 행동이 가능한가:** 고객이 짧게 판단할 수 있고 작은 다음 작업이나 확인 기준이 남는가. 누락과 불필요한 부담은 무엇인가. diff·모의 장면·단위 검사 요약을 실제 앱 검증으로 확대하지 않는가.

구조 실패는 별도로 표시하고 raw 원문도 읽는다. JSON 형태가 잘못됐어도 어떤 내용이 유용하거나 위험했는지 메모할 수 있다. 다만 사람이 고쳐 유효한 성공 응답으로 집계하지 않는다. HTTP 오류·빈 응답·중단도 원래 요청 행을 남긴다.

## 사례별 비교

`판정`은 X 우세 / Y 우세 / 비슷함 / 둘 다 미흡 / 비교 불가 중 하나로 적는다. 점수 합계로 중대한 실패를 가리지 않는다. 근거에는 원문 sourceId와 실제 응답의 짧은 표현 또는 해당 필드 위치를 적는다.

## 결과 뒤 내릴 결정

**기본안이 충분하거나 개선안의 추가 부담이 크면:** 더 강한 구조화를 채택하지 않고 유능한 일반 기획 대화와 짧은 진행을 우선한다. 장면을 모든 변경의 필수 절차로 만들지 않는다.

**중요한 차이는 찾지만 장면이 편향되거나 길다면:** 발견과 표현을 구분하여 다음 개선 범위를 좁힌다. 같은 상황인지, 선택의 합리적인 목적을 균형 있게 보여주는지부터 살펴본다.

**낯선 사례에서도 유용한 차이와 적절한 비질문 경로를 함께 보인다면:** 작은 다음 품질실험의 근거로 삼는다. 실제 제작자가 판단하는 데 도움이 되는지, 개발 후 같은 기준으로 확인할 수 있는지는 별도 검증이 남는다.

**둘 다 충분한 근거 없이 정책을 지어내거나 중요한 확정을 침범하면:** 프롬프트 문구만 계속 늘리는 대신 필요한 입력·대상 작업·제품 가설을 다시 검토한다. 이 결과는 리허설 제품이나 현재 방향의 영구 확정이 아니다.

어떤 결과든 첫 응답을 지우거나 '가장 좋은 재실행'만 비교하지 않는다. 다음 개선은 새로운 실행으로 구분한다. 미공개 4사례를 읽고 개선에 사용한 뒤에는 그 사례들을 새 미공개 검증이라고 재사용하지 않는다.
