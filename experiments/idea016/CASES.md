# IDEA016 — 합성 고객 흐름 6개

실제 고객 조사·실사용 결과가 아니다. 회차는 각 2~3개 계획 단계이며 실제 질문에 대한 답변 재정리까지 사례당 최대 3회다. 중요한 질문 때문에 끝까지 못 간 사례를 완료로 꾸미지 않는다.

## C01 — 동네 빵집 — 충분히 명확한 문구 수정

짧고 충분한 요청에는 재승인·기술 선택 없이 바로 쓸 작업문이 나오는가.

### 계획 단계 1: label / 합성 D+0 / request

빵집 픽업 주문 화면의 버튼 문구를 “주문”에서 “픽업 예약”으로 바꿔 주세요. 클릭 동작과 주문 데이터는 그대로 두고, 화면과 접근성 이름에 새 문구가 보이면 끝입니다. 실제 배포는 하지 마세요.

### 계획 단계 2: return / 합성 D+2 / report

이틀 뒤 받은 작업 결과입니다. 버튼 화면 문구와 접근성 이름을 픽업 예약으로 바꿨다고 합니다. 수정 파일 1개, 기존 단위 검사 통과라고 적혀 있었고 제가 코드나 브라우저를 직접 확인하지는 못했습니다.

### 실제 질문이 나왔을 때만 사용할 허용 값

아래 값은 첫 prompt로 보내지 않는다. 실제 질문이 묻는 값만 선택하고, 관계없는 값이면 선택하지 않는다.

- label (provided): 버튼 화면 문구와 접근성 이름은 “픽업 예약”입니다. 클릭 동작과 주문 데이터는 유지합니다.

- code (unknown): 현재 파일 이름과 테스트 도구는 모릅니다. 실행 도구가 저장소에서 확인해야 합니다.

### 관찰

- 첫 응답부터 수정 대상·유지 범위·완료 조건이 있어 붙여넣을 수 있는가.

- 이미 적은 문구와 배포 여부를 다시 묻지 않는가.

- 돌아온 통과 보고를 Studio의 실측이나 전체 완료로 쓰지 않는가.

## C02 — 초보 공방 운영자 — 예약 성립의 중요한 모호함

예약이 언제 확정되는지 실제 결과가 달라지는 한 가지만 확인하고 작은 작업으로 이어지는가.

### 계획 단계 1: idea / 합성 D+0 / request

작은 도자기 공방이에요. 취소로 수업 자리가 나면 대기한 사람에게 알아서 이어 주는 기능이 필요해요. 제가 일일이 전화하는 일을 줄이고 싶어요. 코드는 잘 몰라요. 먼저 만들 작은 작업으로 적어 주세요.

### 계획 단계 2: empty-label / 합성 D+3 / request

사흘 뒤 이어서 부탁드려요. 대기자가 한 명도 없을 때 담당자 화면에 “대기 중인 분이 없어요”라고 보이게 해 주세요. 앞서 제가 답한 범위 밖의 예약 규칙은 새로 정하지 말아 주세요.

### 실제 질문이 나왔을 때만 사용할 허용 값

아래 값은 첫 prompt로 보내지 않는다. 실제 질문이 묻는 값만 선택하고, 관계없는 값이면 선택하지 않는다.

- confirmation (provided): 자리가 생겼다는 안내만 보내고, 대기자가 참여하겠다고 답한 뒤에 예약을 확정하고 싶어요. 안내만으로 예약이 생기면 안 됩니다.

- order (provided): 대기 순서는 신청한 순서로 합니다.

- reply-window (unknown): 답을 얼마나 기다릴지는 아직 정하지 못했어요. 제가 정한 시간처럼 쓰지 말아 주세요.

- existing-system (unknown): 현재 예약 시스템의 서버나 알림 연동 방식은 모릅니다. 실행 도구가 기존 코드를 확인해야 합니다.

### 관찰

- 자동 확정과 참여 응답 뒤 확정의 차이를 쉬운 한 질문으로 확인하는가.

- 질문 없이 중요한 값을 확정·삭제·보류하면 좋은 최소 질문으로 평가하지 않는다.

- 실제 질문과 연결된 합성 답만 사용하고, 답이 없거나 모르면 그 값은 미정으로 남는가.

- 답을 준 뒤 같은 재승인을 강요하지 않고 실행할 작은 작업이 생기는가.

## C03 — 숙련자 서점 재고 도구 — 수동 범위·완료 조건 유지

사용자가 직접 정한 작업문을 그대로 보존하면서 다음 작은 변경을 붙일 수 있는가.

### 계획 단계 1: csv / 합성 D+0 / request

독립서점 재고표에서 현재 필터에 보이는 행만 CSV로 내려받게 하려 합니다. 기존 TypeScript 프로젝트를 먼저 확인해 주세요. 열은 품목명, 수량 순서이고 저장소 구조나 API는 바꾸지 않습니다. 품목명에 쉼표와 따옴표가 있어도 두 열로 다시 읽혀야 합니다.

응답 뒤 고객의 수동 작업문 편집:

scope: 내가 정한 범위: 기존 CSV 생성 함수와 그 단위 검사만 수정. 화면 구조, API, 데이터 저장 형식은 수정하지 않는다.

checks: 내 완료 기준: 필터 결과가 0행이면 헤더만. 품목명에 쉼표·따옴표·줄바꿈이 있어도 두 열로 재파싱. 기존 입력 원본은 변경되지 않는다.

### 계획 단계 2: bom / 합성 D+2 / request

이틀 뒤 같은 CSV 작업을 이어갑니다. 한글이 깨지는 도구가 있어서 파일 앞에 UTF-8 BOM을 붙이는 작은 변경만 추가해 주세요. 제가 직접 써 둔 수정 범위와 완료 기준은 그대로 사용하세요.

### 실제 질문이 나왔을 때만 사용할 허용 값

아래 값은 첫 prompt로 보내지 않는다. 실제 질문이 묻는 값만 선택하고, 관계없는 값이면 선택하지 않는다.

- columns (provided): CSV 열은 품목명, 수량의 두 열입니다.

- scope (provided): 기존 CSV 생성 함수와 단위 검사만 수정합니다. 화면 구조, API, 저장 형식은 변경하지 않습니다.

- code (unknown): 실제 함수 경로는 이 시험에 제공되지 않았습니다. 실행 도구에서 찾아야 합니다.

### 관찰

- 첫 작업문 내 수동 scope/checks가 AI 문구보다 우선하는가.

- 다음 요청의 previousWork에 수동 값이 정확히 들어가고 최종 작업문에도 보존되는가.

- 제공하지 않은 함수·파일 이름을 현재 코드 사실로 지어내지 않는가.

## C04 — 독립 편집팀 — 구현 보고와 다음 요구 분리

돌아온 결과가 새 요구·승인·실측으로 승격되지 않고 다음 요청과 연결되는가.

### 계획 단계 1: search / 합성 D+0 / request

원고 검수 목록에서 제목 일부로 찾는 검색을 추가해 주세요. 권한과 공유 범위는 그대로 둡니다. 메일 자동 발송은 이번 범위가 아닙니다. 검색어를 지우면 전체 목록으로 돌아오면 됩니다.

### 계획 단계 2: report / 합성 D+4 / report

나흘 뒤 구현자가 보낸 요약을 붙입니다. 제목 검색을 추가했고 검사 4개가 통과했다고 합니다. 검수 담당자에게 자동 메일을 보내면 편할 것 같아 다음 할 일로 추천했다고도 적었습니다. 저는 화면과 검사를 직접 확인하지 않았습니다.

### 계획 단계 3: sort / 합성 D+4 / request

이제 검색 결과를 마감일이 가까운 순으로 정렬하는 작은 변경만 이어서 해 주세요. 마감일이 없는 원고는 뒤로 보냅니다.

### 실제 질문이 나왔을 때만 사용할 허용 값

아래 값은 첫 prompt로 보내지 않는다. 실제 질문이 묻는 값만 선택하고, 관계없는 값이면 선택하지 않는다.

- email (provided): 메일 자동 발송은 이번 작업에서 하지 않습니다. 구현자가 추천했을 뿐 제가 요청한 기능이 아닙니다.

- verification (provided): 구현자의 통과 요약만 받았고 제가 직접 화면이나 검사를 확인하지는 않았습니다.

- sort (provided): 마감일 오름차순이고 마감일 없는 원고는 뒤로 보냅니다.

### 관찰

- report 출처와 실제 새 request를 구별하고 report에서 새 기준을 만들지 않는가.

- 실행 도구의 추천을 사용자 승인처럼 다음 작업에 끼워 넣지 않는가.

- 4개 통과는 합성 구현자 주장이고 Studio가 검증했다고 쓰지 않는가.

## C05 — 악기 대여점 — 기존 확정 기간의 명시적 변경

기존 기준의 명확한 변경에 재승인을 요구하지 않고 ID·이력·무관한 조건을 보존하는가.

### 계획 단계 1: period / 합성 D+0 / request

악기 대여점의 반납 완료 기록을 보관 기간이 지난 뒤 목록에서 숨기는 작업을 준비해 주세요. 실제 삭제나 운영 실행은 하지 않습니다.

합성 고객이 화면에서 직접 기록하는 기준 (AI가 확인한 값이 아님):

D1 / confirmed: 반납 완료 기록은 30일 뒤 목록에서 숨긴다. 실제 데이터 삭제는 하지 않는다.

응답 뒤 고객의 수동 작업문 편집:

checks: 수동 완료 조건: 실제 데이터를 삭제하지 않고 목록 표시만 바뀌는지 확인한다. 운영 환경 실행은 제외한다.

### 계획 단계 2: explicit-change / 합성 D+3 / request

D1을 60일로 변경해줘

### 실제 질문이 나왔을 때만 사용할 허용 값

아래 값은 첫 prompt로 보내지 않는다. 실제 질문이 묻는 값만 선택하고, 관계없는 값이면 선택하지 않는다.

- period (provided): D1의 30일을 60일로 변경하라는 요청입니다. 실제 데이터 삭제를 하지 않는 조건은 유지합니다.

- deployment (provided): 실제 삭제와 운영 실행은 요청하지 않았습니다.

### 관찰

- D1이 60일로 한 번만 바뀌고 ID·이전 30일 값·출처가 보존되는가.

- 이미 명시한 기간 변경을 다시 승인하라고 질문하지 않는가.

- 기준 변경 전 AI 작업문은 제외되고 사용자 수동 완료 조건은 남는가.

## C06 — 동네 수리교실 — 긴 과거 요청 끝의 연락처 제약

전송 전 발췌 손실과 전달된 제약의 모델 미반영을 분리해 관찰한다.

### 계획 단계 1: long-original / 합성 D+0 / request

동네 수리교실 운영을 돕는 작은 웹 도구를 만들고 싶어요. 주민이 고장 난 생활용품을 가져오면 자원봉사자가 함께 고쳐 보는 행사입니다. 지금은 담당자 한 명이 종이에 회차별 신청과 준비물을 옮겨 적습니다. 이번에는 다음 회차 목록과 신청자 목록을 한 화면에서 찾는 첫 작업만 준비해 주세요. 외부에 배포하거나 실제 주민 자료를 옮기는 일은 아직 하지 않습니다.
지난 행사에서는 의자, 우산, 작은 장난감처럼 종류가 다른 물건이 섞였습니다. 같은 회차라도 필요한 준비물이 달라서 담당자가 메모를 읽을 수 있어야 했습니다. 준비물은 자동 추천하지 않아도 됩니다. 처음에는 사람이 적어 놓은 메모를 보는 것으로 충분합니다. 이 설명은 왜 목록이 필요한지 알려 드리는 배경이지, 물건 종류마다 별도 화면을 만들어 달라는 뜻은 아닙니다.
주민은 별명을 적어 신청하고 담당자는 신청한 회차와 가져올 물건 설명을 확인합니다. 이번 첫 작업에 결제나 회원 등급은 없습니다. 신청자가 바뀌면 담당자가 수동으로 목록을 고칩니다. 빈자리 자동 배정이나 다른 행사로 자동 이동하는 기능도 이번에는 만들지 않습니다. 기존 프로젝트가 있다면 먼저 실제 파일과 자료 구조를 확인하고 그 안에서 가장 작은 변경을 해 주세요. 제가 쓰지 않은 파일 이름이나 서버 구조를 이미 존재하는 것처럼 가정하지 마세요.
당일에는 진행자가 태블릿으로 회차와 준비 메모를 봅니다. 목록에 아무도 없으면 빈 회차라는 사실을 알 수 있으면 됩니다. 화면을 예쁘게 꾸미는 것보다 어느 회차를 보고 있는지 헷갈리지 않는 것이 먼저입니다. 시제품 확인에는 가상의 주민과 물건만 씁니다. 실제 행사에서 사용했다는 보고나 실제 개인정보 처리에 대한 허가는 이 요청에 포함하지 않습니다.
마지막으로 나중에 안내 파일이나 명단 내려받기를 붙여도 꼭 이어갈 조건입니다. 외부로 나가는 참가자 명단에는 별명만 쓰고 전화번호와 이메일은 절대 넣지 않습니다. 참가자 연락처를 다운로드 파일에 포함하는 기능은 만들지 않습니다.

### 계획 단계 2: small-label / 합성 D+2 / request

담당자 화면 제목의 문구만 “회차 목록”에서 “다가오는 수리교실”로 바꿔 주세요. 목록 동작은 바꾸지 마세요.

### 계획 단계 3: export-roster / 합성 D+5 / request

닷새 뒤 작업을 이어갑니다. 다음 주 회차의 참가자 명단을 행사 진행자에게 전달할 CSV로 내려받는 작은 기능을 추가해 주세요. 원래 정한 명단 공개 범위를 지켜 주세요.

### 실제 질문이 나왔을 때만 사용할 허용 값

아래 값은 첫 prompt로 보내지 않는다. 실제 질문이 묻는 값만 선택하고, 관계없는 값이면 선택하지 않는다.

- privacy (provided): 외부로 나가는 참가자 명단에는 별명만 쓰고 전화번호와 이메일은 절대 넣지 않습니다. 참가자 연락처를 다운로드 파일에 포함하는 기능은 만들지 않습니다.

- deployment (provided): 실제 주민 자료 이전이나 외부 배포는 아직 요청하지 않았습니다.

- format (provided): 행사 진행자에게 전달할 CSV입니다.

### 관찰
