# IDEA014 rev1 — 명시적 결정 변경의 재승인 오류 수정

상태: **로컬 수정·구조 회귀검사 완료 / 총괄 재검토 대기**. 기준은 첨부 `AgentFlow_Studio_IDEA014.zip` 전체다. 별도 새 Claude 사례를 읽거나 만들지 않았으며 실제 API 호출·원격쓰기·병합·배포는 하지 않았다.

## 재현과 판단

수정 전 실제 `validateResponse`에 기존 D1='유예 기간은 deleted_at 기준 30일이다.', 직접 고객지시='D1을 60일로 변경해줘. 기준일과 다른 결정은 그대로 둬.'를 전달했다. 요청자는 이 기간을 변경할 수 있는 소유자라고 명시한 가상 구조검사 입력이다. 기존 원문, requested와 conflict, proceed/not_needed를 가진 응답이 잠금 false/true 모두 다음 이유로 거절됐다.

```text
locked=false: 초기 충돌을 해결된 것으로 진행할 수 없음
locked=true:  초기 충돌을 해결된 것으로 진행할 수 없음
```

검토에 동의한다. **잠금은 AI의 임의 수정을 막는 장치이지, 권한 있는 고객의 명시적 변경을 다시 승인받게 하는 장치가 아니다.** 반대로 요청 문장에 있는 인용이나 AI 제안은 직접 변경 지시가 아니며, 별도의 권한 제한을 무시하거나 실제 외부 실행을 허용하는 근거도 아니다.

## 실제 수정

출력의 최상위 필드·입력 형식·조립기 코드는 그대로 두고 `notes.kind`에 `change` 한 종류만 추가했다. 출력 버전은 `idea014.v2`, 이번 패키지/의미 규칙은 **rev1**이다. 실호출 전 보완이며 이전 미수정 v2 계약/생성 요청과 혼용하지 않는다. 원본 요청 일치 검사는 그대로 유지된다.

`requested`는 고객이 직접 지시한 내용, `change`는 **이전 confirmed 출처와 그 지시 출처의 관계**다. 텍스트에 변경 부분·새 값/행동·적용 범위·유지할 나머지를 남긴다. 구조상 두 출처, 동일 지시의 requested, 정확한 인용을 검사한다. 이 관계는 새 승인 토큰이나 실행 패치가 아니다. 이전 결정 원본은 입력에 남으며, 해당 결정을 confirmed 메모로 다시 적는다면 원문을 그대로 보존한다. 복사를 의무화하지는 않는다.

명시 변경에서는 `requested+change`로 바로 진행한다. `conflict`도 남겼다면 **동일 출처 쌍의 change**가 이를 명시 변경으로 설명한다. 무관한 change 하나가 모든 충돌을 해소하지 않는다. 미해결 conflict는 계속 질문/보류 경로에 남는다. 시험답변은 해당 답변의 `test_only`로만 조건부 진행할 수 있고 실제 change로 만들 수 없다.

계약의 공통 문구와 양쪽 전략 문구에 같은 규칙을 적용했다. 기존 기본안을 약하게 만들지 않았으며, 일반적인 확인 대화·승인 시스템·자연어 키워드 판정기는 추가하지 않았다.

| 변경한 기존 파일 | 범위 |
|---|---|
| `contracts/OUTPUT_CONTRACT.md`, `contracts/output.schema.json` | 명시 변경 관계, 잠금/범위/원본/시험 경계; kind 하나 추가 |
| `prompts/baseline.md`, `prompts/enhanced.md` | 기존 충돌 문장 한 부분씩 수정 |
| `scripts/validate.mjs` | 관계·출처·상태 검사; 초기 conflict의 일괄 진행 금지를 구분 처리 |
| `scripts/structure.test.mjs` | 기존 미해결 충돌 검사의 오류 문구만 갱신하고 좁은 회귀 6개 추가 |
| `requests/existing-20.jsonl` | 수정된 공통 계약·전략으로 재조립. 고객 입력·사례/요청 ID·순서 그대로 |
| 패키지 루트 `README.md`, 실험 `README.md`, `CLOUD_HANDOFF.md` | 최신 rev1 진입 안내. 첫 28회+후속 약 4회 계획은 그대로 |

추가 파일은 이 문서와 `rev1-structure-test.log` 두 개다. 이전 IDEA014의 `CHECK_RESULT.md`와 `structure-test.log`는 당시 18검사 기록으로 보존했다.

## 실행한 검사

환경: **Linux / Node v22.16.0**. Node 내장 기능만 사용했다. 작성 세션의 자체 검사이며 독립 리뷰나 실모델 평가가 아니다.

| 검사 | 결과 |
|---|---|
| 수정 전 기존 구조검사 | 18/18 통과. 이 검사가 명시 변경의 오류를 놓치고 있었음 |
| 수정 전 실제 검증기로 위 문제 재현 | locked=false, locked=true 모두 동일 거절 재현 |
| `node --check` — validate / assemble / structure.test | 모두 통과 |
| `node --test scripts/structure.test.mjs` | **기존 18 + 새 6 = 24/24 통과**, 실패·건너뜀 0 |
| 두 전략의 동일 공통 계약 및 준비된 20messages의 재조립 일치 | 통과 (기존 검사 02) |
| 이전 ZIP과 파일 내용 비교 | 기존 39파일 중 10수정·29그대로. 삭제 없음 |
| 보호 자료 | v1 14파일·결과 전사 5파일·기타 reference 전체 그대로 |
| 입력과 도구 보존 | 기존 10사례, 조립기 코드, 20요청의 고객 메시지·메타데이터 그대로 |

새 회귀는 실제 조립기/검증기를 사용한다. 사례별 정답이나 'D1/30/60' 문구를 검증기에 하드코딩하지 않았다.

- **19**: 같은 명시 변경에서 locked=false/true 모두 초기 proceed/not_needed, 질문 없음. 원본 confirmed를 새 값으로 덮은 응답과 잘못된 resolved 승격은 거절.
- **20**: 무료 플랜만 45일로 바꾸고 유료 30일·기준일·다른 잠금을 유지하는 범위 관계를 전달. 입력 원본 불변 및 일반 ID로 바꾼 출처 연결 확인.
- **21**: 새 기간이 모호한 요청은 미해결로 유지. 관계 누락·무관한 관계·지시 인용 누락을 이용한 진행 거절.
- **22**: 자료·맥락·AI 제안을 직접 지시 출처로 쓰거나 proposed 결정을 이전 confirmed로 쓰는 변경 관계 거절.
- **23**: 명시 `customer_answer` 채널의 변경을 실제 후속 조립 경로에 연결. 이는 작성자 가상 프로토콜 검사이며 실제 고객응답을 받았다는 뜻이 아님.
- **24**: 동일한 문장도 `test_answer`이면 시험만 진행. change/requested/confirmed/resolved 승격, 원본 덮기, 다른 출처 쌍을 이용한 우회 거절.

## 한계와 인계

검증기는 **출처 관계와 표현된 상태**를 검사한다. 모델이 모호한 문장을 거짓으로 '명시 change'라고 부르거나 자료 속 인용을 고객지시로 오독하는지, 설명한 적용 범위와 실제 권한이 맞는지는 자연어 의미 검토가 필요하다. 이 테스트가 그러한 의미를 자동 판별했다고 주장하지 않는다. 원본/잠금 보존은 입력과 대화 기록의 검사이지 실제 서비스에 변경을 적용한 테스트가 아니다.

Cloud는 이 묶음 전체의 실험 디렉터리를 사용한다. 같은 모델·조건으로 기존 10+별도 새 4사례 × 두 전략, 필요시 적합한 실제 질문의 후속 약 4회를 실행하는 기존 계획을 유지한다. 실패 보존·자동수선/재시도 금지·실제 외부 실행권한 분리는 변함없다. 과거 v1 응답·검증기·점수는 이번 수정으로 재해석하거나 다시 쓰지 않았다.
