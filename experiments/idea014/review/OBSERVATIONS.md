# 다음 비교에서 사람이 볼 것

이 파일과 CUSTOMER_WORDING.md, 과거 reviewer-original.json은 **평가자 자료**다. 모델 입력으로 보내지 않는다. 기존 10사례는 모두 공개 개발/회귀 자료다. 과거 4개를 다시 미공개라고 표시하지 않는다. 다음 새 4개는 별도로 준비해 Cloud에서만 추가한다.

## 한 응답을 읽는 방법

구조검사 pass/failed 옆에 의미 판단을 따로 남긴다. JSON이 실패해도 표시된 본문을 읽을 수 있으면 비교에서 버리지 않는다. 각 쌍마다 `기본안 우세 / 개선안 우세 / 비슷함 / 서로 다른 강점 / 둘 다 부족 / 비교 불가` 중 하나와 실제 문장 근거 한두 개를 적는다. 구조 실패·통신 실패 때문에 판단할 수 없는 부분은 비교 불가로 남긴다. 일부 성공 응답만 대표본으로 고르지 않는다.

질문 개수 대신 **답이 결과를 바꾸는가**, 출처와 상태가 맞는가, 단정한 결과가 공통 전제에서 나오는가, 양쪽 목적과 대가가 진지한가, 이미 정한 일과 후속 범위를 존중했는가를 본다. 모든 메모·부차적 위험을 채우는 체크리스트가 아니다. 더 짧고 정확한 proceed/need_info가 장면보다 낫다면 그렇게 판정한다.

## 후속 약 4회

실제 첫 질문에서 쌍으로 비교할 수 있는 것부터 선택한다. 가능한 경우 두 사례 × 두 전략으로, 하나는 명시적 선택, 하나는 모르겠음/보류와 범위 제한을 볼 수 있다. 예상해 둔 질문이 실제로 나오지 않았으면 억지로 후속을 만들지 않는다. 각 실제 질문에 답이 되는 명시적 시험답변을 사람이 작성한다. 같은 의도를 주되 질문의 구체적 내용과 맞아야 한다.

모르는 답을 확정·동의로 바꾸지 않는지, 이미 준 제한을 다시 여는지, 새 기능/운영 실행을 조용히 보태는지, 해결된 부분의 작은 확인 기준이 실제로 구체화되는지 본다. 구조가 깨진 첫 응답은 원형대로 보존하고 자동수선해서 후속에 넣지 않는다. 후속 선정은 첫 비교에서 실패를 제외해 점수를 다시 계산하는 근거가 아니다.

## 다음 판단

기존과 새 사례를 나눠 읽는다. 기존 오류를 문구로 회피하는 데 그치거나 새 사례에서 거짓 장면이 반복되면 개선으로 보지 않는다. 더 정확하고 부담이 적은 기본안이 낫다면 기본안을 택한다. 양쪽 모두 장면을 만드는 과정에서 오류가 커지면, 기본 경험을 짧은 정리+확인 항목으로 낮추고 장면을 선택적으로 제공하는 방향을 검토한다.

고객 효용, 전반적 우월성, 실제 앱 검증을 이 합성 비교로 주장하지 않는다. 작성자 사례와 사전 평가 메모를 읽은 검토는 독립/가림 평가가 아니다. 새 4개가 미공개였다는 사실도 전체 평가를 자동으로 블라인드 시험으로 만들지는 않는다.
