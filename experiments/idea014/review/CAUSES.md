# IDEA014 — 짧은 원인 분석과 수정 판단

## 읽은 범위

첨부 `IDEA013_RESULTS_RELAY.zip`의 화면 전사본에 표시된 첫 20응답과 후속 4응답, 실패 이유, 비가림 평가, 이전 Claude 4사례를 읽었다. 이것은 **실제 호출 결과를 표시한 화면의 전사본**이다. 원래 HTTP 응답 파일·헤더·정확한 출력 바이트·분실된 증거 ZIP을 회수한 것이 아니다. 제공된 전사 파일은 고치지 않았다.

보존 위치는 패키지 루트 `reference/idea013-relay/`와 `reference/idea013-v1/`이다. 아래 `R:L숫자`는 `reference/idea013-relay/idea013-comparison-visible.txt`의 실제 파일 줄 번호다. 원문 표현의 근거는 해당 줄에 있는 표시 응답이며, 평가자의 의견과 내 판단을 구분했다.

기존 v1 검증기를 바꾸지 않고 표시 문자열을 JSON으로 디코딩해 다시 검사했다. 첫 응답 baseline 7/10, enhanced 8/10, 후속 4/4를 재현했다. 상세는 `reference/legacy-visible-check.json`. API 재실행도, v2로 과거 점수를 갱신한 것도 아니다.

## 통과를 위한 완화가 아닌 이유

v1 응답·프롬프트·검증기와 점수는 그대로 둔다. v2는 버전이 다른 계약이다. 같은 옛 응답에서 버전이나 kind만 자동 교체하지 않는다. requested/confirmed/context의 의미를 분리하고 confirmed 출처는 오히려 하나로 좁혔다. 정확한 인용, 존재하는 출처, 추가 키 거절, 시험답변의 실제 확정 승격 금지, 보류 보존 검사는 유지한다. 두 전략은 동일한 v2 계약·출력 구조·사례 입력을 쓴다.

기본안에도 사실 확인·불필요한 질문 중단·균형 잡힌 예시·후속 범위 준수를 적용했다. 개선안의 차이는 **명확한 진행 → 사실 확인 필요 → 의미 있는 갈림길**의 선택 순서와 결과를 한 축으로 점검하는 절차다. v1 대비 변화는 계약과 프롬프트를 함께 고친 반복이므로 어느 한 조항의 독립 효과나 전반적 우월성으로 해석하지 않는다.

구조검사는 원문 인용의 포함 관계와 출처 종류까지 본다. 인용이 주장을 논리적으로 뒷받침하는지, 사실에 맞는 기술인지, 대안이 균형 잡혔는지, 최신 범위 제약을 문장으로 지켰는지는 사람이 읽어야 한다. 이를 판별하는 척하는 키워드 검사나 자동 모델 채점기를 만들지 않았다.

## 제품 가설에 대한 반론

이번 결과는 '장면이 구체적이면 더 좋은 판단을 돕는다'는 가설에 조건을 붙인다. 구체성은 숨은 가정을 고객에게 사실처럼 전달하는 위험도 키웠다. 따라서 고정된 두 장면을 제품의 필수 입구로 삼는 것은 아직 지지하지 않는다.

다음 비교에서 기존 오류를 고쳤더라도 새 사례에서 장면의 발명·재승인 부담이 계속되면, **짧은 요구 정리와 최소 확인 항목을 기본으로 하고 유효한 경우에만 장면을 펼치는 방식**이 대안이다. 구조통과가 늘고 고객이 읽는 문장이 여전히 틀렸다면 개선으로 판정하지 않는다. 반대로 기본안이 더 단순하고 정확하면 기본안을 택할 수 있다. 이 패키지는 실행 준비이며 해당 효과는 아직 미측정이다.
