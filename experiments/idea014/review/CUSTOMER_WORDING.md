# 고객 문장에서 바뀌어야 할 것

아래는 **작성자가 만든 수정 목표 예시**다. 실제 IDEA014 모델 응답·고객 답변·실행 결과가 아니다. 프롬프트·messages에는 넣지 않는다. 같은 뜻의 더 좋은 문장이나 다른 유효한 판단을 허용한다.

## 명시한 작은 변경 — DEV02

“모바일을 포함해 회비 내역 화면의 버튼 문구만 ‘입금 기록’으로 바꾸는 요청입니다. 위치·색·클릭 동작·저장 데이터·다른 화면은 유지합니다. 추가로 정할 것은 없습니다. 변경 후 두 화면의 문구와 기존 입력창이 그대로 열리는지 확인하면 됩니다.”

이 범위는 `requested/U1`이지 AI가 보탠 assumption이 아니다. 이미 고객이 준 조건을 다시 승인받지 않는다. 기존 회원 초대·권한 제외 결정은 유지한다.

## 합리적인 두 결과 — DEV01

“사진을 요청한 뒤 아직 고객 답이 없는 문의를 생각해 보겠습니다. 직원이 ‘지금 할 일’을 열 때, **회신을 기다리는 문의를 기본 목록에 남길지**가 다릅니다. 아래는 제안하는 표시 방식이며 현재 구현된 기능은 아닙니다.”

A: 기본 목록에서는 빼서 지금 처리할 문의에 집중합니다. 기다리는 문의를 살펴보려면 별도 조회 경로가 필요합니다.

B: 기본 목록에 접힌 한 줄로 남겨 대기 중인 문의도 함께 살펴봅니다. 그만큼 기본 목록에는 항목이 더 남습니다.

“어느 방식이 업무에 맞나요? 직접 기준을 적거나 모르겠음·보류도 가능합니다. 고객이 나중에 답했을 때의 재등장 규칙은 이 장면에서 결정하지 않았습니다. 고객 화면의 접수 상태는 어느 안에서도 자동 변경하지 않습니다.”

비교는 **회신 전** 같은 시점에서 끝난다. ‘숨기면 영원히 재등장하지 않음’, ‘B만 고객 회신을 놓치지 않음’을 추가하지 않는다. 이 축이 실제 업무에 덜 중요하다면 다른 유효한 축을 택하거나 작은 사실 확인으로 바꿔도 된다.

## 사실을 먼저 확인 — SYN-C2

“30일 기준·nightly 실행·기존 soft delete 흐름은 유지하고, 명시하신 cascade 허용도 다시 묻지 않겠습니다. 다만 `invoices.billing_contact_user_id`가 참조한다는 사실만 있고 삭제 옵션은 없습니다. 해당 FK 정의와 컬럼의 NULL 허용 여부를 확인할 작은 스키마 조각이 필요합니다. 그 전에는 청구 행이 삭제되는지, 사용자 삭제가 막히는지, 참조를 비우는 안이 가능한지 단정하지 않겠습니다.”

자료에서 cascade라고 제시된 문서·댓글과 미제공 invoice를 구별한다. 확인을 받기 전에 '청구 이력이 안전하다', '개인정보가 완전히 파기된다'고 쓰지 않는다. 이것은 운영 삭제를 실행하는 승인이 아니다.

## 오래된 재고 자료 — DEV05

“이전 파일을 현재 수량에 어떻게 반영할지 보려면, 먼저 파일의 수량이 ‘그 기준일의 남은 재고’인지 작성 기준을 확인할 필요가 있습니다. 이미 기록한 입출고 이력은 유지합니다. 같은 파일 재업로드와 파일에 없는 품목의 처리 규칙은 아직 정해진 것으로 보지 않겠습니다.”

이것은 가능한 첫 확인의 예다. 파일 의미를 명시한 공통 가정 아래 다른 합리적인 한 축을 비교하는 것도 가능하다. 다만 재업로드 사이의 입출고를 무시하며 '차이가 0'이라고 하거나 누락 품목을 자동 유지·삭제한다고 채워 넣어서는 안 된다. 필요 없는 상세 정책을 한 번에 모두 질문하지 않는다.

## diff의 좁은 범위 — DEV06

“제공된 diff에서는 표시 조건은 같고 ‘저장 완료’를 ‘저장됨’으로 바꿨습니다. 이 범위에서 동료와 다시 정할 제품 규칙은 보이지 않아 다음 작업으로 넘어갈 수 있습니다. 서버 저장 성공·실패 처리 자체를 검증했다는 뜻은 아니며, 그 부분은 이번 자료로 확인되지 않았습니다.”

D1은 유지할 요구이고, 코드가 실제로 D1을 지킨다는 실행 증거는 아니다. 제안 상태의 이메일 기능은 새 결정으로 만들지 않는다.

## 장애 첫 응답과 범위를 좁힌 후속 — SYN-C4

초기 예: “카드 문자와 관리자 화면만으로는 승인·저장·조회 중 어느 단계의 문제인지 알 수 없습니다. 우선 영향받은 거래 한 건의 PG 상태와 대응하는 주문 유무를 같은 기준으로 대조해 주세요. 나머지 피해 건도 같은 방식으로 확인한 뒤, 운영자가 고객 안내나 처리 후보를 판단하도록 정리할 수 있습니다. 원인은 아직 미정이고 주문 등록·취소를 지금 자동 실행하자는 뜻은 아닙니다.”

후속이 '아직 모르니 확인 항목만'인 경우의 예: “원인 판단은 보류합니다. 확인할 것은 문제 거래의 PG 상태와 표시 시각·비교용 거래 식별자, 그 거래에 대응하는 기존 주문 유무입니다. 필요한 값은 가린 자료로 확인할 수 있습니다. 과거 서버 기록이 없다면 해당 시점 서버 도달 여부는 미확인으로 남깁니다.”

후속에는 로깅 코드 변경 준비·새 결제 시험·수동 주문·취소 절차를 추가하지 않는다. 실제 시험답변이었다면 이 내용도 `test_only`로 표시한다. 정보가 들어오면 원인을 더 좁힐 수 있을 뿐 자동으로 확정된다고 말하지 않는다.
