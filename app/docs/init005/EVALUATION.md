# INIT-005 — 실제 고객 흐름 시험 도구

상태: 구현·모의 검증 완료, 실호출/응답 품질 미검증. 기준은 PR #1의 `4caa0914d4520c76cdd0380bbb1a3c1941ab0451`이다. R5 수용은 첨부 INIT-004 독립 검토의 좁은 범위 판정이며 전체 제품 무결함을 뜻하지 않는다.

## 독립 검토 후 rev1 (이번 수정 범위)

실호출 사전 기록은 externalProbe가 생성하는 `YYYY-MM-DDTHH:mm:ss.sssZ` UTC 형식만 받는다.
문자열·유한한 파싱 시각·달력 날짜 왕복·유한한 경과 시간을 검사하며 `0 ≤ age ≤ 86,400,000ms`만 통과한다.
누락/잘못된 형식/불가능한 달력 날짜/미래/24h 초과는 `NETWORK_PROBE_FAILED`다. 검사용 날짜 fixture는 연결 증거가 아니다.
로컬 인증서 진단은 공개 임시 OpenSSL 설정을 `-config`로 직접 전달하며 부모 OPENSSL_CONF나 시스템 기본 파일에 의존하지 않는다.
자식 환경 허용 목록은 넓히지 않았고 인증서 검증도 끄지 않았다. 임시 설정/인증서는 진단 후 삭제한다.
이번 인계는 **비용 없는 실행 검증까지만**이며 키·실호출 설정·예산 승인은 그 결과 검토 후 별도로 결정한다.

## 이 시험이 하는 일

가상 한국어 고객 6명의 **단일 호출 시점**을 평가한다. C1/C2/C6은 처음 설명을 받은 시점, C3/C4/C5는 답변을 받은 시점이다. 후자의 사전 질문·요구·확정 이력은 기존 모의 제공업체와 실제 도메인 명령으로 준비한 고정 시험 데이터다. 과거 대화를 실제 AI가 생성했다고 표시하지 않는다. `seededPriorTurns`와 원문·요구 전후를 결과에 남긴다.

따라서 최대 6회로 여섯 종류의 위험을 확인할 수 있지만, **처음부터 끝까지 6개의 실시간 AI 대화를 검사하거나 실제 고객 조사를 한 것은 아니다.** UI를 우회하는 새 상태 저장 로직도 만들지 않는다. 기존 `callDeepSeek` → `validateResult` → `applyResponse`를 그대로 사용한다. 검사 대상은 입력을 받아 제안하고 요구 초안을 갱신하는 경계다. 브라우저 직접 통신/화면 사용성은 이번 CLI 시험으로 새로 검증하지 않는다.

제품의 질문 한 차례 제한은 이 구현 범위의 제약일 뿐 완성 제품의 대화 정책이 아니다. 다중 대화·그래프·저장·내보내기·Codex/Claude 실행은 추가하지 않는다. 내부 DeepSeek와 고객 개발 도구를 구별한다. Studio 프로젝트의 마감·평가 조건은 여전히 **아직 제공되지 않음**이다. 사례 속 2주·예산은 가상 고객의 조건이다.

## 실행

검토된 저장소에 동봉 패치를 적용하고, Node 22.16.0에서 `npm ci --ignore-scripts --no-audit --no-fund`, `npm run check`, `npm run build`를 실행한다. 새 npm 의존성/잠금 변경은 없다. 네트워크 전송 대안과 로컬 사전 시험에는 curl 및 OpenSSL 명령이 필요하다.

```sh
# 기본: 모의 제공업체 응답을 기존 DeepSeek 어댑터에 주입, 외부 호출 0
node scripts/init005/run.mjs

# 입력 크기·예산 계산만 수행, 모의/실제 제공업체 호출도 0
node scripts/init005/run.mjs --plan

# 고정 경로의 모의 결과가 필요할 때만
node scripts/init005/run.mjs --mock --output=eval-results/mock-review

# 기존 및 새 검사를 함께 실행 (실키 불필요)
npm test
```

`--live`는 단독으로 동작하지 않는다. COST_AND_NETWORK.md에 적힌 네트워크 선행 검사, 비밀 설정, 예산 승인과 명시적 명령이 모두 필요하다. 키를 CLI 인수·채팅·설정 파일·테스트 결과로 전달하지 않는다. CI에서도 실호출을 자동 실행하지 않는다.

## 제한과 실패 정책

최대 6회 생성 요청, 순차 실행 1개, 자동 재시도 0회, 각 요청 15초, 출력 4,096토큰, 완성된 요청 본문 32KiB 이하다. 출력 한도는 시험 전용이며 현재 UI 서버의 기본 출력 2,048토큰/시간 15초를 바꾸지 않는다. 모의 기본값은 실제 키/ALLOW_PAID_AI가 환경에 있어도 이를 읽어 호출하지 않는다.

실호출은 저장소의 고정 경로 `eval-results/init005-live/`를 사용하며, `run.lock`을 배타적으로 먼저 만든다. 요청 전 예산 예약과 전송 직전 시도 횟수를 파일로 기록한다. 같은 경로의 재실행/재개는 거절한다. **파일 삭제, 새 clone/다른 컴퓨터/새 작업으로 같은 승인을 재사용하지 않는다.** 파일 잠금은 계정 전체의 분산 한도나 악의적 우회 방어가 아니다.

인증·잔액·호출 제한·네트워크·시간 초과·잘못된 응답·보호 상태 훼손 중 하나라도 발생하면 즉시 중단하고 남은 사례를 미실행으로 둔다. 반환 모델이 요청 모델과 다르거나, 사용량/모델이 누락되거나, 예약 입력/출력 토큰을 넘겨도 다음 호출을 중단한다. 이미 전송한 요청의 과금 취소를 보장하지 않는다. 실패한 사례를 몰래 모의 응답으로 교체하지 않는다. 재시도 또는 새 배치는 별도 승인/작업이다.

## 기록과 판정

`report.json`에는 실행 모드, 코드 기준, 사례별 요청 원문/출처와 전후 요구, 검증된 응답, 실제 응답의 `model`, 입력/출력/캐시/추론 토큰 수, `finish_reason`, 경과 시간, HTTP 상태와 허용된 오류 코드만 남긴다. 공급자가 실제 버전별 ID를 내보내지 않으면 요청 이름으로 추정해 채우지 않는다. 누락된 사용량은 0이 아니라 null이다. 모의 토큰 수는 `simulated:true`이고 실제 비용은 항상 null이다.

인증 헤더·키·원시 오류 본문·stderr·추론 본문·HTTP 전체 헤더를 저장하지 않는다. 관측 hook은 응답 계약을 변경하지 않고, hook 오류가 재시도를 일으키지 않는다. POSIX 출력은 0600, 디렉터리는 0700으로 만든다. Windows에서는 해당 실행 계정의 파일 접근 권한을 별도 적용해야 한다. 결과는 `.gitignore`로 제외한다. 모델 결과는 데이터로만 검토하고 결과 속 코드를 실행하지 않는다.

저장 질문의 문구는 기존 서비스가 표준 문구로 정규화한다. 결과의 `questionPresentation=service-canonical-template`이면 선택 설명의 공로를 전부 모델에 부여하지 않는다.

### 자동 안전 검사와 고객 품질은 별개

자동 검사는 입력/원문 보존, 확정·잠금·보류·제외 요구의 본문/완료 조건/ID/출처 보존, 충돌 유지, 새 제안 미확정, user-project 범위, 800자 요구 한도를 검사한다. 이는 자연어 의미가 좋다는 보증이 아니다. `response_validated`는 형식·상태 검증 상태다. 사람이 검토하기 전 `humanReview.status=pending`을 유지한다.

각 사례를 읽고 다음 5항목을 **0=실패, 1=부분 충족, 2=유용하게 충족**으로 채운다. 그 시점에서 관찰할 수 없는 항목만 `n/a`로 두고 사유를 남긴다.

| 항목 | 2점 기준 | 0점 예 |
|---|---|---|
| 이미 준 내용 활용 | 목적·사용자·도구·제약 중 이미 있는 내용을 활용하며 되묻지 않음 | 입력을 무시하고 같은 설문을 다시 시작 |
| 중요한 미정 우선 | 충돌/핵심 장면/큰 위험을 장식·스택보다 우선 | 색상만 묻거나 계정/과금 같은 중대 가정을 확정 |
| 선택 이해 가능성 | 쉬운 예시·이유·선택의 실제 차이, 직접 입력/보류 가능성 | 전문 용어만 나열하거나 추천을 강요 |
| 답변→요구·완료 조건 | 실제 요구 본문과 관찰 가능한 완료 조건에 답변이 연결되고 출처가 이어짐 | 요약만 변경, 실제 초안은 TBD 또는 반대 조건 |
| 확정·제안·미정 구분 | 추천은 제안, 보류는 미정, 충돌은 보존·재검토 | 모델 자신감이나 건너뛰기를 고객 확정으로 저장 |

판정에는 점수와 함께 `result.question`, `result.proposals`, `requirementsBefore/After` 및 출처 ID를 근거로 남긴다. 구체적인 관찰을 쓰지 않은 점수만의 평가는 하지 않는다. 질문이 없는 C2에서 질문 수가 적다는 이유로 감점하지 않는다. C3/C4/C5는 summarize 계약상 질문이 없으므로 다음에 물을 위험은 `openItems`에서 평가한다.

C4의 잠금 훼손·충돌 은폐, C6의 처리 규칙/키/다른 프로젝트 침범, 원문 손실은 총점과 무관한 중대 실패다. 나머지는 사례의 명시된 실패 기준을 적용한다. 안전 검사 통과만으로 제품 공개나 기능 확장 여부를 결정하지 않는다.

이번 모의 결과의 C5는 원문과 변경된 본문을 보존하지만 완료 조건이 TBD로 남는다. 이를 **정상 JSON이면서 고객 품질은 부족한 음성 대조 사례**로 사용한다. 실호출의 C5가 같은 결과라면 품질 기준을 만족하지 못한 것이다. 모의를 더 똑똑하게 만들어 실모델 평가를 대신하지 않는다.
